# 201 — 21.2.2 Feed refresh button (+ 19.5.5 community feed refresh, 19.6.6 UI half)

**Phase 21** (Sample UI expansion) / **Phase 22** (functional-explorer rebuild), the **21.2.2 "Feed
refresh button"** — a **Refresh** button on the Feed and Community feed cards that issues
`?refresh=true` (the page-cache bypass). This one feature closes three ROADMAP items at once:

- **21.2.2** — Feed refresh button (the Feed page's `PagedCollection` gains a Refresh button).
- **19.5.5** — Community feed correctness (UI remainder): the community UI feed screen now issues
  `?refresh=true` on a manual refresh.
- **19.6.6** (UI half) — Cache bypass: the refresh path actually re-fetches (a new activity is visible
  after the bypass).

## The change (UI only, no backend change)

### `PagedCollection.razor` (shared component)

- **`ShowRefreshButton`** parameter (`bool`, default `false`). When `true`, renders a **Refresh** button
  above the items list.
- **`Refreshing`** state + **`_bypassNext`** flag. The Refresh button triggers `RefreshAsync`, which
  sets `_bypassNext = true`, resets the items list, and re-fetches the first page with
  `BypassCache: BypassCache || _bypassNext` (a **one-shot** bypass — it does not change the permanent
  `BypassCache` parameter). The flag is reset in the `finally` block.
- **`EnumerateOnePageAsync`** now honors `_bypassNext`: the `CollectionQuery` is built with
  `BypassCache: BypassCache || _bypassNext`, so the one-shot refresh sends `?refresh=true` on the wire.

### `Feed.razor` (the home timeline page)

- `PagedCollection` gains `ShowRefreshButton="true"`.

### `Community.razor` (the community page)

- The hand-rolled **Feed** card (not a `PagedCollection` — it uses `GetCommunityFeedAsync` directly)
  gains a **Refresh** button + `FeedRefreshing` state + `RefreshFeedAsync` method. The method
  re-fetches the community feed with `new CollectionQuery(BypassCache: true)` (the `?refresh=true`
  path), replacing the current feed items.

No backend change. The `?refresh=true` wire parameter and the server-side cache-bypass handling already
existed (changes 149/154); this change adds the **UI affordance** that triggers it.

## Method

Phase 22 manual-testing discipline (operator directive, rule 5): **no new framework tests** — this is a
manual Playwright-MCP pass of the UI + wire. No backend change was made, so no integration test ships
with it.

## The pass (compose stack, `iris-a`/`iris-b`/`iris-ui`; logged on as `alice@localhost` dialing `http://localhost:8081`)

### Feed page (21.2.2)

- The **Refresh** button is present on the Feed page (the home timeline `PagedCollection`).
- The followed-feed endpoint (`/ap/v1/u/alice/feed`) **500s** in this local compose setup: the server's
  `FeedService.FetchRemoteOutboxAsync` resolves the followed actor's (bob's) outbox via the **advertised**
  FQDN (`iris-dev1.luit.ink`), which does not resolve inside the container (the same documented
  external-FQDN blocker that affects 19.6.1/19.6.2). The UI handles the 500 gracefully (shows the empty
  state). This is a **pre-existing environmental limitation**, not a defect in the Refresh button.
- On the public FQDN route (where `iris-dev1.luit.ink` resolves), the Feed page's Refresh button will
  re-fetch the followed feed with `?refresh=true` — the same mechanism verified on the Community feed
  below.

### Community feed (19.5.5 / 19.6.6 UI half) — full cache-bypass scenario

The Community feed endpoint (`/ap/v1/c/iris/feed`) works in this setup (it does not need to resolve a
remote FQDN — the community is local). The full stale-cache → refresh → fresh scenario was verified:

1. **Load the Community page** → the feed loads (client caches the first page). Shows **1080 items**.
2. **Publish a new note** (from a second browser tab, logged on as alice) → the note lands in the
   community feed on the server.
3. **Without refresh:** the feed still shows **1080 items** (the client's `CollectionPageCache` has the
   stale page; the 60s TTL has not expired).
4. **Click Refresh** (the new button) → the client re-fetches with `?refresh=true` (bypassing its
   cache) → the feed now shows **1200 items** (the new note + others published in the interim are at
   the head).
5. **Network evidence:** every page fetch carried `?refresh=true`
   (`POST /ap/v1/proxy/https://iris-dev1.luit.ink/ap/v1/c/iris/feed?refresh=true` → 200, and the
   subsequent `?page=2&refresh=true` pages).

| Step | Feed item count | `?refresh=true` on wire |
|---|---|---|
| Initial Load | 1080 | no (plain read) |
| After publishing (no refresh) | 1080 (stale) | n/a |
| After Refresh click | **1200** (fresh) | **yes** (every page) |

The bypass is **one-shot**: the `BypassCache` parameter is not changed (subsequent plain reads still
use the cache).

### Console errors (reviewed, all by-design / pre-existing)

- **`404 favicon.ico`** — cosmetic.
- **`500 .../u/alice/feed`** — the followed-feed FQDN resolution issue (documented blocker, pre-existing).
- **`429 Too Many Requests` on `.../c/iris/feed/?page=2`** — the Community feed has 1200+ items at
  5/page (240+ pages); the hand-rolled `LoadAsync`/`RefreshFeedAsync` fetches **all** pages (a
  pre-existing performance characteristic of the hand-rolled community feed, not introduced by this
  change). The rate limiter kicked in on the last page; the UI had already rendered 1200 items from
  the earlier pages. The `PagedCollection`-based Feed page (21.2.2) only fetches **one page** (5
  items) on refresh, so it is not affected.

No 500s from the Refresh path itself, no signature failures, no delivery errors.
