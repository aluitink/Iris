# 186 — Phase 22.2: object page — reply form (US-12)

## Summary

Fourth (and final) 22.2 sub-slice (detail pages on the shared components). The object page
(`ObjectPage`) gains the missing half of **US-12** — a **reply form** — so a user can reply to any
loaded object and see the reply appear in the thread. The page already reviewed the object in full
(US-7), toggled like/boost (US-13), deleted own content (US-14), and listed existing replies; this
adds the *author a reply* path. This completes 22.2.

- **US-12 (reply to an object).** A new "Reply" card between the Raw Inspector and the Replies list:
  a reply text input, an optional comma-separated mentions field, and a **Reply** button. Posting
  calls the session's `IActivityPubClient.PostReplyAsync` (a note whose `inReplyTo` is the loaded
  object, with an `@mention` tag per mention and a public `as:Public` `to` audience). On success the
  form clears and the object is re-loaded so the new reply surfaces under "Replies"; the reply
  chain (the existing replies list, rendered via `ObjectView` and deep-linking to each reply's
  object page) was already present.

This is the object slice of 22.2. Combined with the actor slice (change 183), the instance slice
(change 184), and the community slice (change 185), all four 22.2 detail pages are complete:
object (US-7/12/13/14), actor (US-5/15/16/17), community (US-6/18), and instance (US-10).

## What changed (code)

- **`samples/SampleBlazorClient/Pages/ObjectPage.razor`**
  - New "Reply" card (between the `RawInspector` and the Replies card): a `<textarea>`
    (`ReplyContent`), an optional mentions `<input>` (`ReplyMentions`), a **Reply** button, a busy
    indicator, a success line (`Status: posted reply (status 202)`), and an error line.
  - New state: `ReplyContent`, `ReplyMentions`, `ReplyBusy`, `ReplyResult`, `ReplyError`, and a
    static `AsPublic` (`https://www.w3.org/ns/activitystreams#Public`).
  - New `ReplyAsync()`: trims the content, guards empty, and calls
    `Session.GetClient().PostReplyAsync(actorIri, loadedObjectIri, content, ParseReplyMentions(),
    [AsPublic])` with `Session.ActorIri`. On success → clear the form + re-load the object (so the
    new reply appears under "Replies"); on a non-2xx → `failed (status …)`; an exception → its
    message.
  - New `ParseReplyMentions()`: splits the mentions input on commas into `Iri` tags (null when
    empty) — mirrors the Compose page's mention parsing.
  - **Replies read now bypasses the collection cache:** the `GetRepliesAsync` call in `LoadAsync`
    passes `new CollectionQuery { BypassCache = true }`. The replies collection is public data that
    changes when a reply is posted, so a re-load after a reply (or any write) must reflect the
    current store, not a page cached from a prior load — the same reason the object's like-count and
    like-state reads already bypass the cache. Without this, posting a reply and re-loading showed
    the stale (pre-reply) replies list.

## Decisions

- **The reply carries an explicit public `as:Public` `to` audience.** `PostReplyAsync` accepts an
  optional `to`; passing `[AsPublic]` makes the reply publicly visible (the conventional audience
  for public replies), mirroring the Compose page's `ParseAudience` → `as:Public` idiom. A reply with
  no `to` would be private to the actor, which is not what a public thread participant expects.
- **The replies read bypasses the collection cache after a re-load.** `GetRepliesAsync` reads through
  the client's `CollectionPageCache` by default. The replies collection changes when a reply is
  posted, so a re-load right after a reply must fetch fresh — otherwise the page shows the stale
  (pre-reply) list even though the server has recorded the reply. This matches the existing
  cache-bypass treatment of the object's like-count and like-state reads (which also reflect
  writes). Bypassing on every load is a small extra read for a public collection — acceptable for
  the explorer (it is a debugging/review tool, not a hot-path reader).
- **Reply, then re-load (two-step), not a live append.** Rather than optimistically appending the
  reply to the list (the client does not learn the server-minted reply id from the 202 body in a
  usable form here), the page re-loads the object on success — the same idiom the Delete action uses
  (re-load to surface the tombstone). This keeps the replies list authoritative (server-sourced) and
  reuses the existing load path.
