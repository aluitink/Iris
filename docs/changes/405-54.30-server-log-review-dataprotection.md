# 54.30 — Server Log Review & DataProtection Key Persistence Fix

## Summary

Reviewed the running server's logs for interesting errors/warnings. One actionable defect
found and fixed; the rest are expected federation noise.

## Findings

### 1. DataProtection keys stored on ephemeral path (FIXED)

**Symptom in logs:**

```
warn: Microsoft.AspNetCore.DataProtection.Repositories.FileSystemXmlRepository[60]
      Storing keys in a directory '/app/.aspnet/DataProtection-Keys' that may not be persisted
      outside of the container. ...
fail: Microsoft.AspNetCore.Antiforgery.DefaultAntiforgery[7]
      The antiforgery token could not be decrypted.
      ---> System.Security.Cryptography.CryptographicException: The key {7f191c53-...} was not
      found in the key ring.
```

**Root cause:** The `docker-compose.yml` mounts the `iris-dp-keys` volume at
`/home/iris/.aspnet/DataProtection-Keys` (the iris user's home), but the app process runs via
`setpriv --reuid=1001 --regid=1001 --clear-groups dotnet Iris.Web.dll` which does **not** set the
`HOME` env var. ASP.NET Core's `FileSystemXmlRepository` resolves the key directory from
`Environment.GetFolderPath(SpecialFolder.UserProfile)`, which falls back to the `HOME` env var —
and with `HOME` unset, it defaults to the `WORKDIR` (`/app`). Keys were therefore written to
`/app/.aspnet/DataProtection-Keys` (ephemeral container layer) instead of the mounted volume.

**Consequence:** Every container recreation (deploy) wiped the key ring, invalidating all
auth cookies and antiforgery tokens. Users were logged out and in-flight form POSTs failed with
`AntiforgeryValidationException`.

**Fix:** Added `HOME: /home/iris` to the `iris-web` service environment in
`apps/Iris.Web/docker-compose.yml`. This makes `Environment.GetFolderPath(UserProfile)` resolve
to `/home/iris`, so keys land on the `iris-dp-keys` volume and survive restarts.

**Verification:**
- `docker exec` confirms keys now at `/home/iris/.aspnet/DataProtection-Keys/` (on volume).
- `/app/.aspnet/DataProtection-Keys` no longer exists.
- `FileSystemXmlRepository` warning no longer appears in logs.
- Health check returns 200; container healthy.
- Full test suite green (Web 63/0, Server 952/0).

### 2. HttpSignatureValidator warnings (EXPECTED NOISE — no change)

`warn: Signature rejected: could not resolve public key for keyId ...` and
`warn: Signature rejected: malformed Signature header` on `POST /ap/v1/u/{handle}/inbox`.

These are the federation security boundary working correctly. When a remote instance (e.g.
Mastodon) delivers an activity and Iris cannot resolve the signing key (remote down, key
rotated, network timeout), the signature is rejected and the activity is dropped. The Warning
level is appropriate: each occurrence is a rejected unauthenticated federation request, which is
security-relevant and warrants operator visibility. No code change needed.

The F-21 key-rotation invalidation logic (re-fetch on verification failure) already handles the
"key rotated but same IRI" case correctly.

### 3. `libgssapi_krb5.so.2` not found (BENIGN)

`Error: libgssapi_krb5.so.2: cannot open shared object file: No such file or directory`
at container startup. This is a libcurl/Kerberos probe that fails harmlessly — the container
image doesn't include GSSAPI, and no feature uses it. No action needed.

## Changes

| File | Change |
|------|--------|
| `apps/Iris.Web/docker-compose.yml` | Added `HOME: /home/iris` to iris-web environment (with explanatory comment) |

## Decision Log

- **Did NOT change the HttpSignatureValidator log level.** The warnings are correct and
  informative for a public federated instance. Rate-limiting or downgrading to Information would
  hide genuine federation problems (e.g. a remote instance going down, a misconfigured relay).
  If volume becomes a problem at scale, the right fix is structured logging with per-keyId
  rate-limiting (see 54.32 for the broader logging improvement).

- **Did NOT add a `DataProtection` configuration in code.** The `HOME` env var fix is the
  minimal, idiomatic solution — it aligns the app's runtime environment with the volume mount
  path that was already configured (and documented) in the compose file for this exact purpose
  (slice 48.2).
