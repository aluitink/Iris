# 28.3 — Relay subscription lifecycle (end-to-end lock)

## What was built

A test-only lock (no code change): the full **relay subscription lifecycle** is
now verified end-to-end on a 2-instance `TestServer`.

### Test

**File:** `tests/Iris.Server.Tests/RelayLifecycleIntegrationTests.cs` (1 test,
2-instance `TestServer` topology: author instance B + relay instance R)

Topology: instance B (relay-lifecycle-b.domain.local, `bob`) hosts the local
author `bob`, who authenticates with **Basic auth** (username = handle,
password) via `IActorCredentialValidator`. The relay subscription is an
Iris-specific local decision, recorded from an authenticated local request at
`POST /local/v1/u/{handle}/relays/{target}` (and removed at
`POST ...?unsubscribe=true`). Instance R (relay-lifecycle-r.example.com) hosts
the relay. B's outbound delivery routes to R's `TestServer` (so the fanned-out
`Create` reaches the relay's inbox), signed as bob; B's fetcher resolves the
relay's document from R and bob's document from B.

Flow (the single test `RelayLifecycle_Subscribe_Post_Unsubscribe_Post`):
1. **Subscribe** — bob subscribes to the relay
   (`POST /local/v1/u/bob/relays/{relay}`, Basic auth). B records the F-06 edge
   in its `IRelayStore`.
2. **Post (while subscribed)** — bob publishes a `Create` to his outbox. The
   28.1 fan-out delivers it to the relay; R's `CreateActivityHandler` stores the
   `Create`.
3. **Unsubscribe** — bob unsubscribes
   (`POST /local/v1/u/bob/relays/{relay}?unsubscribe=true`, Basic auth). B
   removes the F-06 edge.
4. **Post (after unsubscribe)** — bob publishes a second `Create` to his
   outbox. The relay store is now empty, so no relay fan-out occurs; R stores
   nothing for the second `Create`.

The under-test invariant: **relay fan-out is driven by the live state of the
F-06 subscription edge in `IRelayStore`** — while subscribed, content reaches
the relay; once de-subscribed, it does not.

## Non-vacuity

Making `LocalRelayHandler`'s unsubscribe branch a no-op (skipping
`IRelayStore.RemoveRelayAsync`) → the test fails at the "B should have removed
the F-06 relay subscription edge for bob" assertion (step 3). This proves the
test exercises the full request → handler → store path, not just a static state.

The "second post not fanned out" assertion (step 4) is non-vacuous by
construction: after a correct unsubscribe, `GetRelaysAsync` returns empty, so
`DeliverToRelaysAsync` (28.1) enqueues no delivery job — R can never store the
second `Create`. If the edge were not removed (or if the fan-out cached relays),
the second `Create` would reach R and the test would fail.

## Key decisions

- **Test-only slice:** the relay subscription lifecycle (subscribe → fan-out →
  unsubscribe → no fan-out) was already implemented across 19.0b.2b (the local
  relay endpoint) and 28.1 (the `DeliverToRelaysAsync` fan-out); this slice
  locks the full lifecycle end-to-end with no new code.
- **Uses the actual local endpoint (not direct store manipulation):** bob
  subscribes/unsubscribes via the real `POST /local/v1/u/{handle}/relays/{target}`
  endpoint with Basic auth (via `IActorCredentialValidator`), so the full
  request → handler → store → fan-out path is exercised rather than seeding the
  `IRelayStore` directly.
- **Closes Phase 28:** with 28.1 (Create/Announce relay fan-out), 28.2 (Update/Delete
  relay fan-out), and 28.3 (relay lifecycle lock) all done, the F-06 relay
  fan-out is complete across all four content-producing activity types on the
  outbox-publish path, and the lifecycle is locked end-to-end.
