# 26.1 — Cross-instance `Accept` (follow-acceptance) propagation

Phase 26, slice 1. **Type:** invariant lock (test-only — the cross-instance auto-`Accept` path was already
fully implemented; it was simply the follow-acceptance flow with no end-to-end 2-instance test of the
B → A `Accept` hop). This is the inverse of 25.2's `Reject` lock and the more common follow flow
(auto-accept, the default when the followed actor does not set `manuallyApprovesFollowers`).

## Problem

`Accept` (follow-acceptance) is the response a follow-target sends when it accepts an inbound
`Follow`. Iris's follow lifecycle is two-sided:

- **On the follower's home instance (A):** publishing `Follow(target)` to the follower's outbox runs
  `RecordFollowLocalAsync`, which records the provisional `follower → target` edge in A's follow store
  (`IFollowStore.RecordFollowAsync`) **at publish time** and returns the target's IRI so the server can
  deliver the `Follow` to the remote side.
- **On the followed side (B):** the inbound `FollowActivityHandler` records the remote edge (the target's
  followers set lists the follower; the `follower → target` edge in B's follow store) **and, when the
  target auto-accepts (the default), constructs an `Accept`** (`FollowIris.BuildAccept`: actor = the local
  actor/community being followed, object = the original follow by its original IRI, id minted under
  `{localActorIri}/accepts/{ulid}`) and schedules it for delivery to the follower's inbox via
  `IDeliveryService.DeliverToActorAsync`. B's `DeliveryWorker` POSTs it, signed as the followed actor.
- **Back on the follower's home instance (A):** the inbound `AcceptActivityHandler` finalizes the follow —
  recording the `follower → target` edge for a person follower, or the community's follows set
  (`ICommunityStore.AddFollowAsync`) for a community follower (the G-3 community-follower override). This
  is **idempotent** on the person path (the edge was already recorded at publish on A), but it is the
  handler that makes the follower side of a community-initiated follow two-sided.

The follow-acceptance coverage was **incomplete**: the single-instance `OutboxFollowDecisionIntegrationTests`
and the community-outbox publish test
(`CommunityOutboxPublishIntegrationTests.CommunityOutbox_FollowOfRemoteCommunity_FederatesAndAcceptFinalizesBothSides`)
collapsed both sides or asserted only the follow edge (which is recorded at publish, so it is not a
cross-instance signal). There was **no** 2-instance test that proved the `Accept` actually built by the
followed side (B) reached the follower's inbox on the follower's home instance (A) and was stored there —
the cross-instance `Accept` hop.

This slice locks that path.

## The cross-instance `Accept` flow (what the test locks)

Topology: instance A (`accept-a.domain.local`) hosts the local person `alice` (A's instance actor, the
person follower) and the community `iris` (the community follower, with its own signing key). Instance B
(`accept-b.domain.local`) hosts the local person `bob` (the person follow target) and the community `lumen`
(the community follow target). A's outbound delivery worker routes to B (the outbound `Follow` hop); A's
fetcher routes by actor-IRI host (alice/iris → A, bob/lumen → B). B's outbound delivery worker routes to A
(the `Accept` hop — B's `FollowActivityHandler` emits the auto-`Accept` and B's delivery worker delivers it
to the follower's inbox on A); B's fetcher routes by actor-IRI host (bob/lumen → B, alice/iris → A) so B
can resolve the follower's inbox when delivering the `Accept` back to A.

1. **The follow (A → B):** the follower publishes `Follow(target)` to its outbox on A. A records the
   provisional edge on publish and server-delivers the signed `Follow` to the target's inbox on B. B's
   `FollowActivityHandler` records the remote edge **and stores the original `Follow` in B's activity
   store** — the copy the auto-`Accept` references by its original IRI.
2. **The `Accept` (B → A, under test):** because the target does not set `manuallyApprovesFollowers`, B's
   `FollowActivityHandler` auto-constructs the `Accept` (actor = the target, object = the minted follow id)
   and B's delivery worker delivers it to the follower's inbox on A. A's inbox stores the inbound
   `Accept` (the inbox processor stores every inbound activity before dispatch) and A's
   `AcceptActivityHandler` finalizes the follower's edge (idempotent).

The non-vacuous signal is the **stored `Accept` on A**: the follower's follow edge is recorded at publish
on A, so it is *not* a usable cross-instance signal here (it would exist even if the `Accept` were never
delivered). Instead the test scans A's activity store (`IActivityStore.GetAllActivitiesAsync`) for an
`Accept` whose `actor` is the followed actor and whose `object` references the follower's minted follow id
— a fact that can only be true if B built the `Accept` **and** B delivered it to A **and** A stored it.

## Where

- `tests/Iris.Server.Tests/CrossInstanceAcceptPropagationIntegrationTests.cs` (new, 2 tests, 2-instance
  `TestServer`), modeled on `CrossInstanceRejectPropagationIntegrationTests` (25.2):
  - `PersonFollowOfRemoteActor_AutoAcceptPropagatesBackToFollowerHomeInstance`: alice on A follows bob on
    B; asserts A records its local edge on publish, B records + stores the `Follow`, and A's activity store
    holds the inbound `Accept` (actor = bob, object = the minted follow id).
  - `CommunityFollowOfRemoteCommunity_AutoAcceptPropagatesBackToFollowerHomeInstance`: community iris on A
    follows community lumen on B; asserts A records iris's follows edge on publish, B records the community
    follow (lumen's follows + followers sets include iris), and A's activity store holds the inbound
    `Accept` (actor = lumen, object = the minted follow id) — additionally locking the
    `AcceptActivityHandler`'s G-3 community-follower override.

The harness follows the existing cross-instance propagation tests: two `TestServer` instances via
`ActivityPubHostFactory.Create`, `SeedPersonWithKey`/`SeedCommunityWithKey`, a host-routed `RoutingFetcher`
for both A and B (so each instance resolves its own actors for inbound signature verification and the
peer's actors for the cross-instance hop), explicit `IdentityKeys` registering both the instance actor's
and the community's key at their correct IRIs (so the `DeliveryWorker` can sign the federated `Follow`/
`Accept` as the community), a `LazyHandler` delivery transport for both directions, a
`CaptureHandler`-based signed-request replay for the outbox writes, and minted-id learning from the 202
body (decision 055).

## Design decision (recorded)

**Auto-accept path, not manual-decision.** The slice could lock either of two `Accept` code paths:
(a) the **auto-accept** path — the followed side does not set `manuallyApprovesFollowers`, so the
`FollowActivityHandler` auto-constructs + delivers the `Accept`; or (b) the **manual-decision** path — the
followed side sets `manuallyApprovesFollowers` and later publishes an explicit `Accept` to its outbox
(server-delivery arm). This slice locks **(a)**, because:

- It is the realistic/common federation flow (most follows are auto-accepted; the default when
  `manuallyApprovesFollowers` is unset).
- It directly exercises the `FollowActivityHandler`'s auto-`Accept` emission **and** the
  `AcceptActivityHandler`'s G-3 community-follower override — the exact code the slice names.
- Its non-vacuous signal (the stored `Accept` in the follower's activity store, found by scanning
  `GetAllActivitiesAsync`) is clean and deterministic — the `Accept`'s id is minted by B and not returned to
  the test, so the store-scan is the right lookup (decision 055's unguessable-id consequence).

The **assertion strategy** relies on the stored `Accept` (not the follow edge) as the cross-instance
signal, precisely because the follow edge is recorded at publish on the follower's home instance and would
otherwise pass vacuously (it exists even if the `Accept` were never delivered).

## Non-vacuity (proven)

Per the loop's "prove it fails" discipline, B's `FollowActivityHandler` auto-`Accept` emission was
temporarily disabled — the `FollowIris.BuildAccept` + `DeliverToActorAsync` block was commented out:

- **Both** tests **fail** (time out waiting for the inbound `Accept` in A's activity store — it never
  arrives, because B no longer builds/delivers it).
- Six pre-existing single- and multi-instance tests that assert the auto-`Accept` behavior
  (`FollowActivityHandlerTests`, `InboxProcessorTests`, `FederationSignatureIntegrationTests`,
  `DuplicateInboundDeliveryIdempotencyIntegrationTests`) also fail, independently confirming the emission
  was genuinely removed.

This confirms the new tests genuinely exercise the B → A `Accept` hop — they are not passing vacuously
(e.g. they would not pass merely because the follow edge was recorded at publish). Restoring the emission
turns all tests green.
