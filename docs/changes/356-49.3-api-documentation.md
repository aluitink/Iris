# 49.3 — API documentation (OpenAPI + Swagger UI)

## Summary

Added OpenAPI 3.1 spec generation and a Swagger UI page for the Iris.Web app's REST
endpoints. The spec covers all 44 minimal-API endpoints across the ActivityPub federation
surface (`/ap/v1/`, `/.well-known/`) and the local app surface (`/local/v1/`, auth).

## New NuGet package

**`Microsoft.AspNetCore.OpenApi` 10.0.11** (added to `apps/Iris.Web/Iris.Web.csproj` +
`Directory.Packages.props`).

Justification: the built-in ASP.NET Core OpenAPI generator. It inspects the minimal-API
endpoint delegates at startup and emits a valid OpenAPI 3.1.1 spec at `/openapi/v1.json`.
No third-party Swagger package (Swashbuckle) is needed — the Swagger UI is a static HTML
page that loads the spec via the CDN-hosted `swagger-ui-dist` JS.

## Access

- **Swagger UI**: `GET /api/` (or `/api`) — interactive browser UI, expandable endpoints, "Try it out"
- **Raw spec**: `GET /openapi/v1.json` — OpenAPI 3.1.1 JSON

## Design decisions

1. **Middleware before `UseRouting`** for the Swagger UI page: the Blazor SPA fallback
   (`MapFallbackToFile("index.html")`) uses a catch-all `{*path:nonfile}` route that
   ambiguously matches `/api`. A minimal-API `MapGet("/api")` also conflicts. Serving the
   HTML via a simple `app.Use(...)` middleware before routing avoids both issues.

2. **Swagger UI via CDN** (`unpkg.com/swagger-ui-dist@5`): no local JS/CSS to maintain.
   The page is a single HTML file. In production behind the nginx reverse proxy (48.1),
   the CSP header allows `unpkg.com` for script/style (the existing CSP already permits
   `https: ` for scripts).

3. **No Swashbuckle**: the built-in `Microsoft.AspNetCore.OpenApi` generates the spec;
   Swagger UI is a separate static page. This keeps the dependency footprint minimal
   (one package, not the Swashbuckle + Swashbuckle.AspNetCore.ApiDocumentation +
   Swashbuckle.AspNetCore.SwaggerUI + Swashbuckle.AspNetCore.Swagger combination).
