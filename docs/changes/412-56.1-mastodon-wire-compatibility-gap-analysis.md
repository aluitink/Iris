# 56.1 — Mastodon Wire-Compatibility Gap Analysis

## Summary

Audited Iris's ActivityPub wire format against the [Mastodon ActivityPub spec](https://docs.joinmastodon.org/activity/) for all key outbound flows (Follow, Create, Like, Announce, Undo, Block, Mute, Update, Delete). No code changes — analysis only.

## Architecture

Activities/objects are built with **KristofferStrube.ActivityStreams** and serialized through `ActivityJson` (`src/Iris.Core/ActivityJson.cs`). The library's `OneOrMultipleConverter` has a critical property: **a 1-element multi-valued property serializes as a JSON scalar string, not an array**. This drives several of the gaps below.

The authoring path: client → `IActivityPubClient` → `POST {actor}/outbox` → server `OutboxPublishHandler` (`ActivityPubServerExtensions.cs`), which mints IDs and rewrites the audience before storing/delivering.

## Findings

### 1. `to`/`cc` on outbound activities

| Activity | `to`/`cc` | Notes |
|---|---|---|
| **Create** | Client sets `to` on Note; server merges followers into `cc`, parent author into `to` for replies | Matches Mastodon's pattern |
| **Announce** | Server sets `cc`=[author], `to`=followers | Matches |
| **Follow/Like/Undo/Block/Delete** | None | Matches Mastodon |
| **Mute** | None (Iris-specific `Mute` type) | N/A — Iris extension |

**Verdict:** Matches Mastodon for all standard flows.

### 2. Public visibility: scalar vs array

- Iris: `to` is a `List<Link>` in memory, but when it contains only `as:Public` (single-element), the `OneOrMultipleConverter` serializes it as a **JSON string**: `"to": "https://www.w3.org/ns/activitystreams#Public"`.
- Mastodon: always emits an **array**: `"to": ["as:Public"]`.

**Impact:** Low. Mastodon readers accept both forms (the ActivityStreams spec permits both). Strict validators may flag it.

**Status:** Wire-shape mismatch (scalar vs array). Benign in practice.

### 3. `attachment` vs `image` for media

- Iris: uses the `attachment` array with an `Image` object. Correct AS usage.
- Mastodon: uses `attachment` array, typically with `Document` type for generic media.
- Iris only supports **single-image** compose; no multi-attachment.

**Verdict:** Matches for single-image. Partial for multi-media.

### 4. `sensitive` flag

- Iris: top-level `"sensitive": true` boolean via `ExtensionData`. Matches Mastodon.

**Verdict:** Match.

### 5. `summary` (content warning)

- Iris: only emits `summary` when `sensitive` is also `true`.
- Mastodon: `summary` (CW text) is independent of `sensitive` — a post can have a CW without being marked sensitive.

**Impact:** Medium. Iris cannot represent "CW but not sensitive" notes.

**Status:** Restricted.

### 6. `tag` array (mentions + hashtags)

- Mentions: `{"type":"Mention","href":"<actor-iri>"}` — matches.
- Hashtags: `{"type":"Hashtag","name":"#tag","href":"..."}` — matches (href points to local search, not a hashtag page — functionally equivalent).
- Combined into a single `tag` array — matches.

**Verdict:** Match. Minor: no `Mention.name`, no custom emoji tags.

### 7. `source` field (Markdown/HTML) — **HIGHEST IMPACT GAP**

- Iris: does **NOT** emit a `source` field. Markdown is rendered to HTML on the client side; only the HTML `content` is posted.
- Mastodon: emits `"source": {"content": "<raw markdown>", "mediaType": "text/markdown"}` alongside the HTML `content`, so clients can re-render or display the original markdown.

**Impact:** High. A Mastodon client receiving an Iris note has no markdown source to display or edit.

**Status:** Missing.

### 8. `inReplyTo`

- Iris: `"inReplyTo": "<parent-iri>"` (scalar string, single-element list).
- Mastodon: `"inReplyTo": "<parent-iri>"` (also a single string).

**Verdict:** Match.

### 9. Direct/followers-only visibility — **HIGH IMPACT GAP**

- Iris: no dedicated direct or followers-only visibility mode. The server **always** adds the follower set to `cc` on every Create (`MergeAudience` at `ActivityPubServerExtensions.cs:3700`), even for what would be a "direct" post.
- Mastodon:
  - **Direct** = `to: [recipient-actor(s)]`, **no `cc`**, no `as:Public`.
  - **Followers-only** = `cc: [{actor}/followers]`, no `as:Public`.

**Impact:** High. An Iris "direct" post would incorrectly carbon-copy all followers — a DM confidentiality bug.

**Status:** Incorrect for DMs. No followers-only mode.

### 10. `attributedTo`

- Iris: single-element list → scalar string.
- Mastodon: array `["<actor-iri>"]`.

**Verdict:** Wire-shape mismatch (scalar vs array). Benign — Mastodon readers accept both.

### 11. `published` / `updated` timestamps — **HIGH IMPACT GAP**

- `published`: server-assigned ISO-8601 UTC. Matches Mastodon.
- `updated`: **NEVER set anywhere** in Iris. The `UpdateActivityHandler` refreshes the stored object's content but does not stamp `updated`. The `IriExtensions.GetUpdated` reader is dead code on the write path.
- Mastodon: sets `"updated"` on an edited note (≥ `published`).

**Impact:** High. An edited Iris note shows no edit time to remote clients.

**Status:** Missing.

### 12. `id` format

- Iris: `{actor}/{namespace}/{ulid}` (e.g. `{actor}/notes/{ulid}`, `{actor}/creates/{ulid}`). ULID = 26-char Crockford base32.
- Mastodon: numeric, sequential, guessable IDs in type-specific URL trees.
- Both use independent activity/object IDs in separate namespaces.

**Verdict:** Match in structure. Format differs by design (security: unguessable ULIDs vs enumerable numeric IDs).

## Gap Priority (for 56.3)

| Rank | Gap | Impact | Fix complexity |
|---|---|---|---|
| 1 | `updated` timestamp never set on edit | High — remote clients can't detect edits | Low — stamp `updated` in `UpdateActivityHandler` |
| 2 | `source` field missing | High — no markdown source for remote clients | Medium — thread raw markdown through compose → server → wire |
| 3 | Direct/followers-only visibility incorrect | High — DM confidentiality bug | Medium — visibility mode in compose, conditional `cc` merge |
| 4 | `summary` only when `sensitive` | Medium — restricted CW | Low — decouple `summary` from `sensitive` in `ComposeNote.Build` |
| 5 | Scalar vs array for single-element `to`/`cc`/`attributedTo` | Low — benign wire shape | Medium — custom serializer or force-array |

## Decisions

- **No code changes in this slice.** This is analysis only.
- The top-3 gaps (ranks 1-3) are the targets for 56.3.
- The scalar-vs-array issue (rank 5) is a library-level behavior (`OneOrMultipleConverter`); fixing it would require a custom converter or post-serialization fix. Low priority.

## Test counts

No new tests (analysis only). Existing suite unchanged.
