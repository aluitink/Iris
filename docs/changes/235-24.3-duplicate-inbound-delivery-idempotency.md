# 24.3 — Idempotent handling of duplicate inbound deliveries

Phase 24, slice 3. **Type:** test-only lock. A real federation peer may redeliver the same signed
activity — on a delivery timeout, a retry, or a network retransmission — so the receiving instance must
treat a repeat as a no-op: the recorded edge appears exactly once, the activity is stored exactly once,
the handler is not re-run (no duplicate side effect), and nothing errors.

## What is locked

The C-07 inbox-Id dedup guard in `InboxProcessor.ProcessAsync`: it stores an inbound activity
add-if-absent by its IRI (`TryAddActivityAsync`), and — when the activity was already stored (a
re-delivery, `firstDelivery == false`) — does **not** re-dispatch it to a handler. This slice extends
that invariant from a content activity (a `Create`, pinned by
`MutualFollowDeliveryLoopIntegrationTests` for the mutual-follow re-fan-out loop) to an
**edge-recording** activity (a `Block` / a `Follow`), where the durable effect is a store edge and a
handler side effect (not merely an outbox entry).

## Why the `Follow` case is the non-vacuous one

The moderation and follow stores are `HashSet`-backed, so `RecordBlockAsync`/`RecordFollowAsync` are
idempotent at the store level: even if the handler ran **twice** on a re-delivery, the edge would still
be recorded exactly once. The "edge appears once" assertion alone therefore cannot prove the guard is
load-bearing.

The load-bearing, observable effect of the guard is that a re-delivered activity is **not re-dispatched
to its handler**. For a `Follow`, the `FollowActivityHandler` mints a **fresh** `Accept` id on every
dispatch (`FollowIris.BuildAccept` → `IdMinter.Mint`, a per-call ULID) and delivers it to the follower's
inbox. So:

- **Guard on:** the handler runs once → exactly **one** `Accept` lands in the follower's inbox.
- **Guard off:** the handler runs twice → **two** distinct `Accept`s (two different minted ids) land in
  the follower's inbox — a real duplicate side effect (the follower would see two accept-notifications).

The "exactly one Accept" assertion is therefore the non-vacuous proof that the guard prevents the
handler from re-running. The `Block` case additionally asserts the second delivery is accepted as a no-op
(HTTP 202), not an error (500) — the inbox endpoint returns 500 if `ProcessAsync` throws, so a
redelivery that errors would be caught here.

## Where (tests)

- `tests/Iris.Server.Tests/DuplicateInboundDeliveryIdempotencyIntegrationTests.cs` (2 integration tests),
  a 2-instance `TestServer` topology (A = `dup-a.domain.local`/`alice`, the blocker/follower; B =
  `dup-b.domain.local`/`bob`, the blocked/followed target), mirroring the 22.13/22.14/24.1 wiring:
  - **`RedeliveredBlock_IsRecordedExactlyOnce_NoError`:** the same signed `Block` is delivered twice to
    bob's inbox on B (the `DeliverDirectly` mechanism from `MutualFollowDeliveryLoopIntegrationTests` —
    sign + deliver through a hosted `DeliveryWorker` routing to B). Asserts: both deliveries accepted
    (202, not 500); B stored the `Block` once; the `alice → bob` block edge recorded exactly once (bob has
    exactly one blocker).
  - **`RedeliveredFollow_IsRecordedExactlyOnce_ExactlyOneAccept`:** the same signed `Follow` delivered
    twice to bob's inbox on B. B's outbound delivery (the `Accept` it emits in response) routes to A's
    inbox, and A has a host-routed cross-instance fetcher so it can validate B's signature on the
    `Accept`. Asserts: the `alice → bob` follow edge recorded exactly once (bob has exactly one
    follower); **alice's inbox contains exactly one `Accept`** for this Follow (the non-vacuous proof the
    handler ran exactly once).

## Non-vacuity (proven)

Per the loop's "prove it fails" discipline, the C-07 early-return in `InboxProcessor.ProcessAsync` was
temporarily disabled (the `if (!firstDelivery) return;` guard short-circuited) and restored:

- **Guard on:** `RedeliveredFollow` observes exactly **one** `Accept` in alice's inbox — the test passes.
- **Guard off:** the `FollowActivityHandler` runs twice on the re-delivery and mints two distinct
  `Accept`s (two different ids, confirmed in diagnostics) — alice's inbox holds **two** `Accept`s, and the
  "exactly one Accept" assertion fails.

Restoring the guard turns the test green, confirming it genuinely exercises the C-07 dedup guard (not a
vacuous pass from the stores' `HashSet` idempotency).
