# 174 — Phase 19.5.3: community UI — "Inbound follows" card on the Community page

## Summary

The Community page now has an **"Inbound follows"** card, mirroring the person `ActorDetail` page's
card (change 151). The card lists the actors/communities that follow the loaded community (read from the
community's outbox — each inbound `Follow` is stored in the followed community's outbox on receipt) and
offers **Accept / Reject** buttons.

Accept/Reject are AP-native: the client authors the deterministic `Accept`/`Reject` and publishes it to
the community's own outbox (the operator IS the followed community); the instance records the edge effect
and server-delivers the activity to the follower's inbox. After a decision, the card refreshes the
inbound-follows list (bypassing the page cache) so the `Accept`/`Reject` activity is visible immediately.

This closes the 19.5.3 "community UI Inbound follows card" gap. The client-level follow-decision endpoint
(`POST /ap/v1/c/{name}/follows/{**followId}`) was already proven in change 152; this slice wires the UI
surface.

## What changed (code)

- **`samples/SampleBlazorClient/Pages/Community.razor`**
  - **Markup:** a new "Inbound follows" card (between the "Followers" and "Follow / unfollow" cards). It
    renders the `PendingFollows` list (each entry shows the follower IRI + Accept / Reject buttons) and
    the decision status/error. When empty it shows "No inbound follows recorded."
  - **State:** `PendingFollows` (`IReadOnlyList<(string FollowerIri, Iri FollowIri)>?`),
    `FollowDecisionBusy`, `FollowDecisionResult` (`DeliveryResult?`), `FollowDecisionError`.
  - **`LoadAsync`:** after loading followers/following, reads the community's outbox
    (`communityIri.OutboxOf()`) for `Follow` activities (each is an inbound follow) and populates
    `PendingFollows` with the (follower IRI, follow IRI) pairs.
  - **`AcceptFollowAsync` / `RejectFollowAsync` / `FollowDecisionAsync` / `RefreshPendingFollowsAsync`:**
    mirror the person page's methods. `FollowDecisionAsync` calls `Session.GetClient().AcceptAsync` /
    `RejectAsync` (the community IRI as the actor — the community signs with the primary actor's key in
    the sample seed), then refreshes the inbound-follows list (bypassing the page cache) so the
    decision's activity is visible immediately.

## Key types / API

- The client's existing `AcceptAsync(Iri actorId, Iri followIri)` / `RejectAsync(Iri actorId, Iri
  followIri)` (change 151/152) — the UI now calls these with the **community IRI** as `actorId`.
- The server's existing follow-decision endpoint (`POST /ap/v1/c/{name}/follows/{**followId}`, change
  152) — the UI's Accept/Reject round-trip through it is the same wire the person path proved.
- The community's outbox (`communityIri.OutboxOf()`) — the inbound follows are read from here (each
  inbound `Follow` is stored in the followed community's outbox on receipt).

## Decision: why the community card mirrors the person card (not a new surface)

The person `ActorDetail` page's "Inbound follows" card (change 151) is the proven pattern: read the
followed actor's outbox for `Follow` activities, list them with Accept/Reject, and on a decision publish
the `Accept`/`Reject` to the same outbox (the operator IS the followed actor). The community is the same
shape (a `Group` actor with an outbox; inbound follows stored in the community's outbox on receipt), so
the card mirrors the person card exactly — same markup structure, same state, same method names, same
client calls (with the community IRI as the actor). No new server endpoint or client method was needed;
the slice is purely the UI wiring.

## Direction note: sample-client UI is manual-tested (not bUnit-tested)

Per the current direction, the sample-client UI is **in flux and subject to a lot of change** once core
stuff is worked out. Rather than invest in bUnit tests for the sample UI (which would need to track every
UI change), the sample UI is **verified manually** (drive the screens through the browser). This change
follows that direction: the "Inbound follows" card is wired and builds clean, but has no bUnit test. The
underlying wire (the follow-decision endpoint + the client's `AcceptAsync`/`RejectAsync`) is proven by
the existing server/client integration tests.

## Scope / limits

- The **live/UI-verification half** of 19.5.3 (drive a gated community's inbound follow through the
  browser — log on, see the "Inbound follows" card, click Accept/Reject, confirm the edge effect) remains
  a live-verification item. The code (the card + the client calls + the server endpoint) is in and
  builds clean.
- The **two-instance wire drive** of a gated community's inbound follow (a remote actor follows a gated
  community; the operator Accepts/Rejects; the remote side finalizes/removes its edge) is a live-interop
  item (needs the external two-instance infra).
