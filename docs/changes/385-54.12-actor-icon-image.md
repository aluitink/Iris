# 54.12 — No way to set actor icon/image via edit profile

Phase 54 slice. The edit-profile form (`EditProfileForm`) only exposed the
display name, bio, and the "require approval for follow requests" gate — there
was no way to set (or remove) the actor's avatar/icon. The slice called for an
avatar control in the edit form so a user can upload a new avatar, see it
previewed, save it to their actor document, and remove it again.

## Change

### Client (WASM)

[EditProfileForm.razor](apps/Iris.Web.Client/Components/EditProfileForm.razor):

- Added an `InitialIconIri` parameter (the actor's current icon IRI, or null).
- Added an avatar section at the top of the form: a circular preview
  (`.edit-profile-avatar-preview`) showing the current/uploaded avatar, a
  "Choose avatar" / "Change avatar" button wrapping a hidden `<InputFile>`, and
  a "Remove avatar" button (shown only when an icon is set).
- Added an `OnIconUpload` callback (`Func<IBrowserFile, Task<MediaUploadResult?>>`)
  — the form uploads the chosen file on selection (not at submit) so the
  preview updates instantly. On success it stores the returned media IRI in
  `_iconIri`; on failure it surfaces the error.
- The "Remove avatar" button sets `_iconIri = null` so the next save clears it.
- `OnSubmit` now takes 4 args (name, summary, approveFollowers, **iconIri**) so
  the parent receives the icon decision alongside the other fields.

[Profile.razor](apps/Iris.Web.Client/Components/Pages/Profile.razor):

- Added `GetIconIri()` — resolves the first icon IRI from `ActorObj.Icon`
  (an `IObject` by `Id`, or an `ILink` by `Href`), passed to the form as
  `InitialIconIri` so the current avatar is shown on entry.
- Added `UploadIconAsync(IBrowserFile)` — reads the file bytes (capped at 10 MiB
  via `ReadAvatarBytesAsync`), calls `Session.UploadMediaAsync`, and returns the
  `MediaUploadResult` (whose `Iri` is the same-origin media URL used as the
  icon).
- `SubmitEditAsync` now accepts `string? iconIri` and sets `updated.Icon` on the
  embedded `Person`: an empty array `[]` when removing, or
  `[new Link { Href = new Uri(iconIri) }]` when setting.

[app.css](apps/Iris.Web.Client/wwwroot/css/app.css) (+ server mirror):

- Added `.edit-profile-avatar-group`, `-preview`, `-img`, `-fallback`,
  `-actions` styles (circular preview, centered layout, button row).

### Server

[UpdateActivityHandler.cs](src/Iris.Server/Inbox/UpdateActivityHandler.cs):

- **Icon-merge semantics** (both the Person `MergeActorFields` and the Group
  branch): a non-empty icon array sets the icon; an **empty** icon array
  (`[]`) clears it (an explicit "remove avatar"); a missing icon field (null)
  leaves the stored icon unchanged (a partial update that does not touch the
  icon). Previously only non-empty arrays were merged, so there was no way to
  clear the icon via an `Update`.
- **Cache invalidation (the key fix):** injected `LocalActorDocumentCache`
  (optional, null in test seams) and call `_actorDocumentCache?.Invalidate(actorIri)`
  after the stored actor/community is persisted. Without this, a profile edit
  persisted to the store but the public `GET /ap/v1/u/{handle}` kept serving a
  **stale cached copy** (60 s fresh / 300 s stale) — the updated name/icon were
  invisible to external readers (federation, other clients, a fresh page load)
  until the cache entry expired or `?refresh=true` was used. This mirrors the
  existing invalidation in the `Add`/`Remove` (manuallyApprovesFollowers) path,
  which already called `actorDocumentCache.Invalidate(actorIri)` — the `Update`
  path was the one place that persisted an actor without invalidating.

## Why the cache fix was required for this slice

The icon-setting UI was functionally complete before the fix, but the served
actor document did not reflect it: `PutActorAsync` wrote the icon to the store,
yet `BuildActorDocument` (via the `LocalActorDocumentCache`) served the pre-edit
document. The icon was a **false positive** in the client (its in-memory cache
showed the new value) and **absent** everywhere else (curl, federation, a fresh
browser load). Because 54.12 is about the avatar being *settable and visible*,
the invalidation was in scope: without it the feature did not actually work for
any consumer other than the editing client's own cache.

## Notes

- This is Phase 45+ (WASM manual-test phase): no new coded tests; verification
  is the live Playwright pass.
- The cache fix is a **pre-existing bug** that affected *all* actor-document
  field edits (name, summary, icon, …), not just the icon. It was masked before
  because (a) profile edits were rare, (b) `?refresh=true` worked, and (c) the
  WASM client's own in-memory cache showed the updated value. It is now closed
  for the `Update` path, consistent with the `Add`/`Remove` path.
- The immutable `_framework` cache gotcha: `dotnet.js` and the hashed `.wasm`
  are served `max-age=31536000, immutable`, so a live re-test after a redeploy
  requires a fresh context with the browser cache disabled (CDP
  `Network.setCacheDisabled`) or the stale bootstrap is loaded.
