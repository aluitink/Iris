# 54.4 — Global error-boundary & circuit-disconnect pass

Phase 54 slice. App-shell-level hardening (continues the 54.2 `ex.Message`
sweep): verify the Blazor global error UI and the circuit-disconnect/reconnect
messages never leak stack traces or raw exception text to users, and give
unhandled render exceptions a friendly, on-brand recovery UI instead of the
bare default.

## Findings

### Default WASM unhandled-exception UI is safe but bland

Out of the box, an unhandled render exception in a Blazor WebAssembly app
shows a bare, unstyled panel: *"An unhandled error has occurred. /
Reload"* (no branding, no guidance). Crucially it is **safe**: the exception
message and stack trace go to the **browser console only** — the visible panel
renders no internal details. So there is no active leak, but the default UI is
jarring and offers no recovery guidance beyond "Reload".

The `<Router>` in this .NET version does **not** accept an `<Error>` child
template (only `NotFound` / `Found` / `Navigating`), so the clean way to
customize the render-exception UI is an `<ErrorBoundary>` around the routed
body, not a Router-level override.

### Circuit disconnect is inherently safe

A WebSocket/HMR circuit drop is a **transport-level** event with no exception
stack to leak. The WASM host shows its built-in *"The connection to the server
was lost"* + Reload banner, which is already friendly and generic. No change
required — documented here so the disconnect path is explicitly covered by this
pass.

## Fix

### Render-exception `<ErrorBoundary>` in `MainLayout` (friendly, no leak)

`MainLayout.razor` now wraps `@Body` in an `<ErrorBoundary>` with a branded
`ErrorContent` template:

- **Friendly copy only** — "Something went wrong" + "An unexpected error
  interrupted this page. Your account and data are safe — please try again."
  The exception (`Context`) is **deliberately not rendered** (no `Context.Message`,
  no stack). A code comment marks this so a future edit doesn't re-introduce a
  leak. The full exception is still logged to the console for diagnosis.
- **`role="alert"`** on the card so a screen reader announces the failure
  (consistent with the 54.3 live-region pass).
- **Two recovery actions**: "Try again" (a hard reload via
  `window.location.reload()` — a plain in-circuit navigation would not clear the
  broken render) and "Go home" (secondary link to `/home`).
- The header (brand + nav) and footer remain mounted, so only the page-content
  area is replaced — the user keeps their wayfinding.

Supporting CSS (`.error-boundary-card`, `.error-boundary-actions`) added to
`app.css` and mirrored to the server copy.

### Background-task exceptions stay out of the global UI

`Program.cs` already subscribes `TaskScheduler.UnobservedTaskException`
(log + `SetObserved()`), so background/`fire-and-forget` task faults are
suppressed and never trip the `<ErrorBoundary>` — only genuine render-path
exceptions reach the friendly UI.

## Live verification

Deployed via Docker; a temporary throw-on-render route (`__TestError.razor`,
deleted before commit) was used to exercise the boundary in the browser:

- Navigating to the throwing route renders the branded card: `alert` →
  `h1 "Something went wrong"` → friendly paragraph → "Try again" / "Go home".
- Header + footer remain; **no raw exception text or stack trace** is visible
  anywhere in the rendered page.
- "Try again" triggers a full reload (reboots the WASM host) — recovery
  confirmed.
- After removing the test route and redeploying, normal pages (landing, home)
  render cleanly with **no spurious error boundary** and 0 client-side console
  errors.
