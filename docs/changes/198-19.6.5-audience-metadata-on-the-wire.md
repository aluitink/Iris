# 198 — 19.6.5 Audience metadata (on-the-wire `to`/`cc` enumeration)

**Phase 19.6** (C2S invariants), the production half that change 158 scoped out.

## The gap

Change 158 implemented the **delivery-recipients** half of 19.6.5 (the server resolves and delivers an
outbound Create/Announce to the right inboxes — the remote, non-blocked follower set) but explicitly
deferred the **audience-metadata** half: rewriting the outbound activity's on-the-wire `to`/`cc` so the
federated document *enumerates* the audience, not just the author's composed address.

Before this change the outbox publish recorded and delivered the activity exactly as the author composed
it — a public post carried `as:Public` in its `to` and nothing else. The **delivery** reached every
remote follower's inbox (verified), but the **wire document** carried no per-follower enumeration. A
conforming receiver that reads `to`/`cc` to determine the distribution list would see only the composed
address, not the actual followers the server chose to deliver to.

## The fix — `src/Iris.Server/ActivityPubServerExtensions.cs`

`OutboxPublishHandler` now rewrites the activity's audience **after the id mint and before the
outbox/activity-store record** (so the stored form and the federated on-the-wire form are the same
canonical activity — no mutation-after-store leak into the in-memory outbox).

New helper `RewriteOutboundAudienceAsync(activity, authorIri, persistence, localActors, ct)`:

- Computes the author's **remote, non-blocked follower set** (`GetRemoteNonBlockedFollowersAsync` — the
  same set the delivery loop already uses, so audience and delivery never diverge).
- Splits the audience per the ActivityStreams convention, mirroring the inbound-federation boost
  convention in `AnnounceIris.BuildAnnounce`:
  - **`Announce` (boost):** addressed `to` each follower, carbon-copied `cc` to the announcer. So
    `to` = the follower set; `cc` = the announcer.
  - **`Create` (post/reply):** a post's followers are the carbon-copy (public/follower) audience, so the
    follower set is **appended to `cc`**; `to` keeps the composed direct recipients (which for a public
    post is the `as:Public` sentinel, preserved). When the embedded object is a **reply**
    (`inReplyTo` set), the reply target — the parent note's author, read from the parent's `attributedTo`
    — is a direct recipient and is **appended to `to`**.
- The embedded **Note is not rewritten** — its own `to`/`cc` are the author's composed address (the
  existing `OutboxAudienceMatchIntegrationTests` pin that the federated Note's `to` carries `as:Public`
  is unaffected).
- No-op for an activity that is neither a Create nor an Announce (Follow/Block/Flag/Like keep their
  single-target addressing).

A `MergeAudience` helper preserves the existing entries (including `as:Public`), appends the follower set
(or a reply target), and de-duplicates case-insensitively via a small `AudienceIriComparer` (first
occurrence wins; an empty result is `null`). The author is never added to the audience (a post is not
addressed to its author).

## Verification

- `dotnet build` clean (0 warnings, `TreatWarningsAsErrors`), full suite green: **1,294 tests** (was
  1,291; +3 new, 0 failures).
- New `OutboxAudienceMetadataIntegrationTests` (three-instance topology: A=alice the author, B=bob a
  remote follower, C=carol a non-follower and the parent-note author) pin the on-the-wire enumeration on
  the **federated** (stored-on-B) activity:
  - **public Create** → the Create's `cc` enumerates bob (the follower); the Create's `to` keeps
    `as:Public`; the embedded Note's own `to` still carries `as:Public` (untouched).
  - **Announce (boost)** → the Announce's `to` enumerates bob; its `cc` is alice (the announcer).
  - **reply Create** → the Create's `to` additionally carries the reply target (the parent note's author,
    carol) in addition to `as:Public`; the `cc` still enumerates bob.

## Design note (Design A — activity-level single object)

The rewrite is at the **activity level** on the single outbound object (the same object the outbox
records and the delivery loop delivers to every recipient). This was chosen over Design B (per-follower
copies, mirroring inbound `AnnounceIris.BuildAnnounce`'s one-object-per-follower shape) because:

- It is the literal reading of the 19.6.5 scope ("the server rewriting an outbound Create/Announce
  `to`/`cc` to enumerate the follower set") — one `to`/`cc` carrying the set, not N copies.
- It preserves the single-activity single-id model (decision 055) already used on the outbox path, so the
  outbox record, the activity store, and every delivery are the same activity — no N-way duplication.
- It keeps audience and delivery trivially in lockstep (both derive from
  `GetRemoteNonBlockedFollowersAsync`).

Design B remains available should a future interop requirement demand per-recipient addressing (a
follow-up would switch the delivery loop to build per-follower copies like the inbound path).
