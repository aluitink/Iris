# 286 — 32.2: EF Core + PostgreSQL persistence provider

> 2026-09-06 · Slice 32.2 · Phase 32 (production social platform app) — step 2 (production persistence)

## What was built

Phase 32's **step 2** adds the production persistence layer: a new `src/Iris.Server.Data` project
that implements **every** store interface behind the `IPersistenceProvider` seam against
**PostgreSQL** via **EF Core**, using the **hybrid schema** recommended by
[production-app-persistence.md §2](../plans/production-app-persistence.md) (relational tables for the
stable, queryable shape — ids, edges, timestamps, a `jsonb` payload column — so adding
ActivityStreams/`iris:` fields over time does **not** require a migration; the `jsonb` document is
the source of truth for content). The `InitialCreate` migration creates the full schema from empty.

The provider is wired into the production host (`apps/Iris.Web`) **config-driven**: when
`Iris:ConnectionString` is set, the app uses the EF Core (PostgreSQL) provider; otherwise it falls
back to the in-memory provider (the slice-32.1 default, and the default for the integration tests).
`Iris.Web` now boots against a real PostgreSQL container and proves the **durability** requirement:
data written by the provider survives a "restart" (a fresh provider over the same database + blob
directory).

Per the rule in the plan, `Iris.Server`'s handlers, endpoints, and options **do not** depend on the
new project or reference EF Core types — DI wiring (`AddEntityFrameworkPersistence`) is the only
place that knows both sides.

## Decisions

- **Hybrid schema (relational index + `jsonb` payload).** The content-bearing tables (`Objects`,
  `Activities`, `Actors`) carry the full canonical AS2.0/`iris:` document in a `jsonb` `Document`
  column (serialized via `ActivityJson`); the relational columns index only the stable, queryable
  shape (ids, `attributedTo`, `type`, tombstone flag, timestamps). Relationship edges (follows,
  likes, announces, replies, relays, moderation, community membership/follows/moderation, media
  source-url + content-hash dedupe) live in a single `Edges` table with an `EdgeKind` discriminator —
  the 17 edge kinds cover every relationship the store interfaces express. This keeps migrations
  small and rare (new AP fields land inside the `jsonb`, zero migration).
- **One shared `Edges` table + a public `EdgeStore`.** The relationship stores are thin delegates over
  a single `EdgeStore` (add / remove / contains / out-targets / in-sources / add-if-new) parameterized
  by `EdgeKind`, so the 8 relationship stores (`Follow`, `Like`, `Announce`, `Reply`, `Relay`,
  `Moderation`, and the community's follows/followers/membership/moderation) share one code path and
  one table.
- **Outbox/inbox as `BoxItemEntity`.** An actor's outbox (direction 0) and inbox (direction 1) are
  rows in `BoxItems` (composite key: direction + actor + item IRI + position). `AddToOutbox`/
  `AddToInbox` insert with `Position = min(existing) - 1` so the newest item is position 0 and
  `GetOutbox`/`GetInbox` order by `Position` ascending (newest first).
- **Synchronous `TryGet*` (and the whole `IKeyStore`).** `async` methods cannot have `out`
  parameters, so the EF stores' `TryGet*` methods (and the synchronous `IKeyStore` contract) are
  implemented non-async — they open a context from the `IDbContextFactory` and run a synchronous
  LINQ read. This matches the in-memory stores' shape (which also return `Task.FromResult`).
- **DI deadlock fix (the important one).** `AddActivityPubServer` registers a **fallback**
  `TryAddSingleton<IPersistenceProvider>(sp => sp.GetRequiredService<IPersistenceProvider>())` (a
  self-referential factory that resolves the concrete provider registered by the persistence
  package). Resolving that fallback inside a **synchronous** host-configure/startup context
  **deadlocks**: the activation path awaits an async startup service on the captured sync context and
  never returns. The fix is to register the concrete provider **as its own binding** (the EF provider
  via `TryAddSingleton<IPersistenceProvider>(factory)` in `AddEntityFrameworkPersistence`; the
  in-memory provider via an instance in `WebAppFactory`), so the fallback is never the *first*
  registration and is never triggered. The test host additionally calls
  `WebAppFactory.InitializePersistence` **after** the `TestServer` has started (not inside the
  synchronous `Configure` delegate) — the same rule that keeps a real host from seeding inside
  startup.
- **Config-driven provider in `Iris.Web`.** `Iris:ConnectionString` set → EF Core (PostgreSQL);
  unset → in-memory (the default for the bare host + the integration tests). `Iris:MediaBlobDir`
  (default `AppContext.BaseDirectory/media-blobs`) is where the EF media store writes raw bytes.
  `EnsureCreatedAsync` (runs `Migrate`) is called at startup for the EF provider only.
