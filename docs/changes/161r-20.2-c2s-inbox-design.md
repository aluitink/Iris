# 161r — Phase 20.2: the C2S inbox (decision 056) — a persisted, owner-only, per-actor inbox collection

## Summary

Phase 20.2 resolves **how a local client user browses their own inbox in a client-to-server (C2S)
scenario** and **how that content is accessible to the browser**. The investigation (this change) found
the inbox was **write-only**: inbound federation is accepted at `POST /{handle}/inbox`, stored in the
activity store, and the per-type handlers record the content into the **recipient's outbox** — but there
was no `GET /inbox`, no inbox query on `IActivityStore`, and no fetch-on-encounter. A local client user
therefore could not read "what was delivered to me" as a distinct surface.

**Decision 056** (`docs/decisions/056-c2s-inbox-model.md`) resolves all five sub-questions and the
foundation is now implemented: the inbox is a **first-class, persisted, per-actor collection** (distinct
from the outbox), recorded on first delivery, and read back via an **owner-only** `GET /ap/v1/u/{handle}/inbox`
(Basic auth; 403 for a non-owner; no-store).

## The five sub-questions, resolved

- **(a) Browser access** — the inbox is **private** (DMs, inbound follows, moderation). It is **not** on
  the public collection GET path. It is read via an **owner-only** `GET /ap/v1/u/{handle}/inbox` requiring
  the **owner's Basic auth** (the same `IActorCredentialValidator.TryValidateAsync` seam the actor-document
  endpoint uses for the owner-only `privateKey`). The browser already holds the logged-on user's Basic
  credentials, so this needs no new auth mechanism. Unauthenticated / wrong owner → **403**; unknown actor
  → **404**. The response is **no-store** (private, owner-scoped data — the same treatment as the
  owner-only actor document).
- **(b) Content + attachments** — the inbound object is **stored locally verbatim** (the object store
  already does this under the **originator's id**, per decision 055). Remote attachments are **served
  verbatim (link-out)** in this slice; **local media storage + URL-rewrite** (storing the bytes locally and
  rewriting the `url` to a same-origin `/media/…` path) is **staged to 20.4 (media)** — a self-contained,
  testable slice orthogonal to the inbox-collection foundation.
- **(c) Id rewrite** — **none**. Inbound objects keep the **originator's id** verbatim (decision 055). The
  inbox yields the received activities/objects **by their originator id**; a request for that id serves the
  **local copy** already stored in the object store. No local-id rewrite (it would break the 055 global-id
  invariant and duplicate the object under two ids; the local copy is served *at* the originator id).
- **(d) Reply + like/boost sync** — **out of scope** for the foundation. The inbox surfaces the delivered
  **activities** (a received note, like, boost). Building the **reply thread tree** and **accumulating
  per-object like/boost counters** are separate, self-contained slices, recorded as follow-up.
- **(e) Pull-on-encounter fidelity** — **store-on-receive** (the current behavior; a durable local copy,
  higher fidelity than a TTL cache). **Fetch-on-encounter** of *referenced-but-not-delivered* remote
  objects (e.g. a note whose `inReplyTo` parent is remote) is a follow-up with its own fetch plumbing.

## What changed (code)

- **`IActivityStore`** — two new members: `GetInboxAsync(actorIri)` (the delivered activities, newest
  first) and `AddToInboxAsync(actorIri, item)` (idempotent by IRI, newest first — mirroring the outbox).
- **`InMemoryActivityStore`** — an `_inboxes` concurrent dict (actor → list) backing both methods.
- **`FileBackedActivityStore`** — a new `inboxes` section (serialize/deserialize + `InboxMap`), backing
  both methods (idempotent by IRI, newest first).
- **`InboxProcessor.ProcessAsync`** — records the delivered activity in the recipient's inbox on
  **first delivery** (gated on the same `firstDelivery` loop-safety guard that prevents re-fan-out, so a
  duplicate delivery does not duplicate the inbox entry).
- **`ActivityPubServerExtensions`** — a new `GET /ap/v1/u/{handle}/inbox` route (`InboxEndpointHandler`):
  404 for an unknown actor, 403 when the requester is not the owner (Basic auth via
  `IActorCredentialValidator`), otherwise a paged `OrderedCollection` (no-store). A bare 403 (not
  `Results.Forbid`, which would require `IAuthenticationService`) so the endpoint works in any host.
- **`IActivityPubClient` / `ActivityPubClient`** — a new `GetInboxItemsAsync(actorId, credentials, …)`
  that reads the owner's inbox (a Basic-authenticated GET on each page, never through the
  `CollectionPageCache` — private, owner-scoped data is no-store).
- **Three test stubs** (`IrisRemoteCollectionFetcherTests.StubCollectionClient`,
  `IrisActorDocumentFetcherTests.StubActivityPubClient`, `FeedServiceTests.StubClient`) implement the new
  interface member (yield nothing).

## New tests (4, all passing)

`tests/Iris.Server.Tests/Inbox/InboxCollectionIntegrationTests.cs` (two instances A/B; a single inbound
`Follow` alice → bob is the cleanest single-recipient case; a `BasicAuthCredentialValidator` is wired for
bob so the owner-only GET is exercisable):

1. **`InboundFollow_IsRecordedInRecipientInbox_DistinctFromOutbox`** — the delivered Follow is recorded in
   bob's **inbox** (by its minted id), independent of the follow edge and the outbox.
2. **`InboxEndpoint_OwnerOnly_200ForOwner_403ForNonOwner_NoStore`** — `GET /inbox` is 200 + no-store for
   the owner (Basic auth), 403 for no/wrong credentials, 404 for an unknown actor.
3. **`Client_GetInboxItemsAsync_YieldsDeliveredActivity_ForOwnerOnly`** — the client reads the owner's
   inbox (yields the delivered Follow) and yields nothing for a non-owner (403).
4. **`Inbox_AddSameActivityIriTwice_IsRecordedOnce`** — the store's idempotent-by-IRI guard (a same-id
   re-delivery is recorded once, mirroring the outbox).

## What is deliberately NOT in this slice (staged plan)

1. **Local media storage + URL-rewrite** for remote attachments → **20.4 (media)**.
2. **Reply thread tree** building → follow-up.
3. **Per-object like/boost counters** (a `likedBy`/`announcedBy` index) → follow-up.
4. **Fetch-on-encounter** of referenced-but-not-delivered remote objects → follow-up.
