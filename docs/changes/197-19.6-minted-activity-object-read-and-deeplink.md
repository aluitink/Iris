# 197 — 19.6 minted-activity object-document read + client deep-link reload

**Phase 19.6** (C2S invariants), the raw-inspector read path (server) + the actor/object deep-link
reload (client).

## The gaps

Two independent gaps blocked the **19.6.1 raw-inspector UI invariant** ("the rendered signed message is
the stored activity document, fetched by its minted id") while driving the write screens through the
browser on the local compose stack:

1. **A minted activity id had no object-document read path.** The outbox publish mints an activity id
   (e.g. `/u/alice/blocks/{ulid}`) and stores the activity in the **Activities** store
   (`PutActivityAsync`). But the object-document catch-all (`GET /ap/v1/{**path}` → `ObjectDocumentHandler`)
   only consulted the **Objects** store (`persistence.Objects.TryGetObjectAsync`). A minted *activity*
   lives in the Activities store, so fetching it by its IRI 404'd — the Object view / raw inspector
   showed "Object not found" for every Follow/Block/Flag/Like/Create the outbox had minted.
2. **The actor/object detail pages did not reload on a deep-link param change.** Both
   `ActorDetail.razor` and `ObjectPage.razor` loaded the entity in `OnInitializedAsync`, which fires only
   once on component creation. Navigating to a *different* `?iri=` on the **already-loaded** page (e.g.
   clicking an "in reply to" link on the Object page, or a different actor link while on `/actor`) is a
   query-param change on the already-initialized component — `OnInitializedAsync` did not re-fire, so the
   new entity never loaded (the stale one stayed on screen).

## The fix

### Server — `src/Iris.Server/ActivityPubServerExtensions.cs`

`ObjectDocumentHandler` now falls back to the Activities store when the Objects store misses:

- The handler first tries `persistence.Objects.TryGetObjectAsync(objectIri, …)` (content objects: Notes,
  Links, embedded objects — unchanged).
- On a miss it tries `persistence.Activities.TryGetActivityAsync(objectIri, …)` (minted activities:
  Follow/Block/Flag/Like/Undo/Create, stored under their minted id by the outbox publish).
- A IRI in **neither** store still 404s (the fallback does not mask a genuine miss).

The served document is the stored activity as-is (the canonical AS representation), so the raw inspector
shows exactly what the outbox recorded. This is what makes the 19.6.1 invariant checkable in the UI.

### Client — `samples/SampleBlazorClient/Pages/ActorDetail.razor`, `ObjectPage.razor`

Both pages move the deep-link load from `OnInitializedAsync` to **`OnParametersSetAsync`** (which fires
on both the initial render *and* subsequent param changes) with a **`_lastLoadedParamKey` guard**:

- The guard key is the deep-link param value (`iri:<value>` / `handle:<value>` for the actor page;
  `iri:<value>` for the object page). Only a *change* to the key re-loads the entity.
- On first render Blazor calls `OnParametersSetAsync` after `OnInitialized`, so the initial deep-link
  load is preserved.
- The guard stops a re-render (a write such as Mute/Block/Like/Reply re-renders the component with the
  param still set) from re-loading when the param is unchanged — no spurious refetch or content flicker.

## Verification

- `dotnet build` clean (0 warnings, `TreatWarningsAsErrors`), full suite green: **1,291 tests** (was
  1,289; +2 new, 0 failures).
- Browser pass on the compose stack (`iris-a` :8081, `iris-ui` :8090, logged in as `alice@localhost`):
  - The minted **Block** activity (`…/alice/blocks/{ulid}`) fetched by its IRI returns **HTTP 200** with
    the full signed AS document (was 404). The Object view's **Raw inspector** renders exactly the stored
    activity — same minted `id`, normalized advertised `object` IRI
    (`https://iris-dev1.luit.ink/ap/v1/u/bob`), correct `type`, and `actor` — matching the outbox
    enumeration 1:1. (The 3 console 404s for `/replies` `/likes` `/shares` are the expected interaction-
    collection probes for a non-Note object, not a regression.)
  - **Object page deep-link:** SPA nav `/object?iri=…/bob/notes/2` → `/object?iri=…/alice/notes/1`
    (via the "in reply to" link, a param change on the loaded page) re-loads to alice's note 1
    ("Welcome to the Iris sample server!", 1 like, "You authored this", 2 replies) — before the fix the
    stale note 2 stayed on screen.
  - **Actor page deep-link:** the same pattern (verified in the 22.6 local manual test pass, change 195)
    now applies identically.
