# 43.2 — Follow-request queue (person actor)

**Status:** COMPLETE
**Commit:** `534db34`
**Tests:** 5 new integration tests (full suite: 1241 passing)

## What

When a person actor enables **manually approve followers** (`manuallyApprovesFollowers`,
toggled on the profile edit form — Phase 42.2), inbound `Follow` activities are no longer
auto-accepted. They land in the actor's **outbox** as pending `Follow` items. This slice adds
the UI to review them.

The `/profile` page gains a **Requests** tab that appears only when the signed-in actor has
`manuallyApprovesFollowers` set. The tab lists every pending `Follow` activity from the actor's
outbox (the same collection the "Your posts" tab reads, filtered to `Type == "Follow"`). Each
row shows the follower's handle and two buttons:

- **Accept** — sends a signed `Accept` activity to the follower via
  `IActivityPubClient.AcceptAsync(me, followIri)`. The server records the follow edge.
- **Reject** — sends a signed `Reject` activity via `IActivityPubClient.RejectAsync(me, followIri)`.

After a successful accept or reject the row's buttons disable (busy state) and the list re-renders.
The pending Follow remains in the outbox (the UI does not delete it); the follow edge state is
what changes server-side.

## Changes

### `apps/Iris.Web/Components/Pages/Profile.razor`

- New `Requests` tab in the tab bar, rendered only when `ApprovesFollowers` is true.
- `ApprovesFollowers` property: reads `ActorObj?.GetManuallyApprovesFollowers() == true`.
- New `RequestsKey` const, `IsFollow` item filter (`Type == "Follow"`), and `FollowRequestTemplate`
  render fragment that renders a `FollowRequestRow` per item.
- The Requests tab reuses the existing `OutboxClient` / `OutboxIri` (the actor's outbox) — no new
  client wiring needed.

### `apps/Iris.Web/Components/FollowRequestRow.razor` (new)

- Renders one pending follow request: the follower's handle (link to `/actor/{handle}`) and
  "wants to follow you".
- Accept / Reject buttons. `AcceptAsync` / `RejectAsync` extract the `Follow` activity's `Id`
  (the follow IRI) and call `client.AcceptAsync` / `client.RejectAsync`.
- `_busy` flag disables both buttons while a request is in flight.
- The row only renders when the item is a `Follow` whose `Actor` is a `Link` (defensive — the
  template is only invoked for `IsFollow` items).

### `apps/Iris.Web/wwwroot/css/app.css`

- `.follow-request-row` (flex, space-between), `.follow-request-info`, `.follow-request-actor`,
  `.follow-request-actions`, and a `.btn-sm` size modifier.

### `tests/Iris.Web.Tests/FollowRequestQueueIntegrationTests.cs` (new)

5 integration tests booting the real app in-process via `WebAppFactory` + `TestServer`:

1. `WithFlag_On_FollowAppearsInOutbox_WithoutAccept` — enable the flag, deliver a signed Follow
   from a seeded remote follower; assert exactly one `Follow` in alice's outbox and zero `Accept`s.
2. `WithoutFlag_FollowAutoAccepts` — deliver a Follow with the flag off; assert the follow edge is
   recorded (auto-accept).
3. `AcceptFollow_SendsAcceptActivity` — flag on, deliver a Follow, then `AcceptAsync` on the
   outbox Follow IRI; assert a successful signed delivery.
4. `RejectFollow_SendsRejectActivity` — same but `RejectAsync`.
5. `MultipleFollows_AllAppearInOutbox` — two distinct followers; both Follows appear in the outbox.

The `DeliverFollowAsync` helper seeds a fresh follower (key pair in **both** the in-memory
persistence key store and the DI `IKeyStore`, registered with the DI `IKeyProvider`), writes the
follower's public document (with `publicKey` PEM) into the actor store, then delivers a signed
`Follow` to alice's inbox. A `LocalActorDocumentFetcher` inner class (reads actors/communities
directly from `IPersistenceProvider`) is registered as `IActorDocumentFetcher` so the server's
`RemoteInboundKeyResolver` can verify the follower's signature without a round-trip HTTP fetch
(the TestServer can't serve itself over a real `HttpClientHandler`).

## Design notes

- The queue is the **outbox**, not the inbox. An inbound Follow is recorded in the *recipient's*
  outbox (the recipient's own activity of "having been followed" / pending relationship), which is
  what `PagedCollection` reads for the actor's own collections. This matches the existing
  posts/replies/likes tabs, which all read the actor's own outbox/inbox.
- Accept/Reject use the **follow activity IRI** (the `Follow`'s `id`), per the ActivityPub
  convention that an Accept/Reject references the activity being responded to.
- The Requests tab is gated on `manuallyApprovesFollowers`; without the flag there are no pending
  requests to review (follows auto-accept), so the tab is hidden.
- Community follow requests (`manuallyApprovesMembers`) use the same outbox-Follow pattern and are
  handled on the community detail page (Phase 41.3); this slice covers the **person actor** only.
