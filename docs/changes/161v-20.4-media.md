# 161v — Phase 20.4 (a): media attachments end-to-end

## Summary

Phase 20.4 (sub-part **a**) makes media attachments work end-to-end: a note's attachment is **uploaded** to
the author's instance (a local, Basic-authenticated multipart POST), stored on that instance, and served
back from the **same origin** when the note is read — so the browser loads the attachment from the same
origin, never a cross-origin media host. This closes Phase 20.4 (media, sensitivity, markdown all done).

It builds on the **20.2 attachment-rewrite decision** (Decision 056 (b)): inbound attachments are rewritten
to the same origin by storing the bytes locally and pointing the attachment's `url` at
`/ap/v1/media/{id}`. (For the *local* authoring path this change implements, the attachment's `url` is set
to the same-origin media IRI **at upload time** — the server returns that IRI and the client puts it on the
note it posts, so there is no cross-origin URL to rewrite on the way out.)

## The design

- **Upload route:** `POST /local/v1/u/{handle}/media` — owner-only (Basic auth via `IActorCredentialValidator`),
  **multipart** POST of the attachment's bytes. Returns `201` + JSON `{ id, type, name }`. This is **not** an
  ActivityStreams activity — it is a local, non-federated write on the non-AP `/local/v1` tree (like the
  local moderation / mute routes), **not** the signing pipeline. 10 MiB cap → 413.
- **Serve route:** `GET /ap/v1/media/{id}` — public, same-origin, long-cacheable
  (`Cache-Control: max-age=31536000, immutable`). Media is immutable (an opaque, unguessable id), so caching
  forever is correct.
- **Media id:** an opaque, unguessable `Guid.ToString("N")` — media is not an ActivityStreams object, so it
  does not use the ULID id-minting scheme (decision 055). It is a storage key, not a federated identity.
- **Store:** `IMediaStore` (`PutAsync` → the media IRI; `TryGetAsync` → bytes + content-type + file name). Two
  implementations: `InMemoryMediaStore` (a `ConcurrentDictionary`) and `FileBackedMediaStore` (metadata JSON
  via `FilePersistence` + the bytes as sibling files, written atomically via temp+move). Wired into both
  persistence providers (`InMemoryPersistenceProvider` + `FileBackedPersistenceProvider`) via
  `IPersistenceProvider.Media`.

    → Task<Iri>` + `TryGetAsync(Iri, out byte[]?, out string?, out string?, ct) → Task<bool>`.
  - `src/Iris.Server.InMemory/Stores/InMemoryMediaStore.cs` (new) — in-memory impl.
  - `src/Iris.Server/Persistance/Stores/FileBackedMediaStore.cs` (new) — file-backed impl (metadata JSON +
    sibling byte files, atomic write).
  - `src/Iris.Server/Stores/IPersistenceProvider.cs` (+ `Media` member); both providers wired.
  - `src/Iris.Server/ActivityPubServerExtensions.cs` — `LocalMediaUploadHandler` (the multipart upload, owner
    guard, 10 MiB cap) + `MediaServeHandler` (the long-cacheable serve). Routes: `localGroup.MapPost(
    "/u/{handle}/media", …)` and `group.MapGet("/media/{id}", …)` under `/ap/v1`.
  - `src/Iris.Client/MediaConstants.cs` (new) — `UploadSegment="media"`, `ServeRoutePrefix="/ap/v1"`,
    `ServeSegment="media"`.
- **Client**
  - `src/Iris.Client/IMediaClient.cs` + `MediaUploadResult.cs` (new) + `MediaClient.cs` (new) —
    `UploadAsync(Iri actorId, byte[], contentType, fileName, [ProxyCredentials,] ct) → Task<MediaUploadResult>`
    (a Basic-auth multipart POST via `LocalAuthHandler`, mirroring `LocalModerationClient`).
  - `IActivityPubClientFactory` / `ActivityPubClientFactory` + `IrisClientFactory` / `IrisClientBundle` —
    `CreateMediaClient` (built from `ActivityPubClientOptions.LocalCredentials`, mirroring
    `CreateLocalModerationClient`).
  - `IActivityPubClient` / `ActivityPubClient` — `PostNoteAsync(Iri actorId, Note note, ct)` overload (posts a
    fully-built `Note`, e.g. one carrying an `Image` attachment); the string overload delegates to it.
- **Core**
  - `src/Iris.Core/Identity/IriExtensions.cs` — `GetMediaAttachments(this IObject?)` (new public): the single
    boundary read of an object's `Image` attachments → `IReadOnlyList<(Iri Iri, string? Name)>`. It resolves
    each attachment's media IRI from the `Image`'s `Url` (first link) and is the only place that reads the
    attachment shape, so the object view (and the rewrite) stay shape-agnostic.
- **Sample (Blazor WASM)**
  - `Compose.razor` — a file `<InputFile>`; on change it reads the bytes (`IBrowserFile.OpenReadStream`, 10 MiB
    cap), uploads via `IMediaClient`, builds the `Note` with an `Image` attachment (`Url` = the returned media
    IRI, plus `Id`/`MediaType`/`Name`), and posts it via `PostNoteAsync(actorIri, note)`.
  - `ObjectView.razor` — renders each media attachment as an `<img>` (via `GetMediaAttachments`).
  - `ClientService` / `ExplorerSession` — `GetMediaClient()` (lazy, from the `IrisClientBundle`).

## What is deliberately NOT in this slice

- **Remote/inbound attachment rewrite** — 20.2's rewrite of *inbound* (fetched) attachments to the same
  origin is the *read* path; this slice is the *local authoring* path (upload → post → serve). The two
  converge on the same `GET /ap/v1/media/{id}` serve + `IMediaStore`.
- **Video / non-image attachments** — the upload accepts any content-type (it stores bytes opaquely), but the
  object view currently renders only `Image` attachments as `<img>`; a `Video`/`Document` attachment would
  need a different presentation.
- **Signed-URL or expiring media** — media is served public + immutable (no auth on the GET), matching the
  "stored on the instance, same-origin" model.
