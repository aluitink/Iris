# 283 — 31.10: remote Likes are recorded on local objects

> 2026-09-06 · Slice 31.10 · Phase 31 (explorer UI & server namespace polish)

## What was built

`LikeActivityHandler` now records the like edge when the **liked object is local**
(stored in this instance's object store), regardless of whether the **liker** is
local or remote. Previously the handler recorded the edge only when the *liker* was
a local actor; a remote actor's `Like` of a local object was accepted and stored in
the inbox but never surfaced (no entry in the object's `/likes` collection, no like
count, no entry in any `liked` collection). This is the 31.10 bug: a Mastodon user
starred alice's post, Iris accepted it (202) and stored it, but the post's like
count stayed at zero.

The fix is surgical — one guard flipped in `LikeActivityHandler.HandleAsync`:

- **Before:** `if (await _localActors.IsLocalActorAsync(likerIri, ...))` → record the
  edge.
- **After:** `if (await _persistence.Objects.TryGetObjectAsync(objectIri, ...))` →
  record the edge.

A `Like` of a *local* object now records the edge no matter who the liker is. A
`Like` of a *remote* object (not stored locally) is **not** recorded here — the edge
is recorded on the object's author's home instance instead, so recording it here
would duplicate the edge. The community-recipient path (a `Like` to a local
community inbox recorded in each member's outbox) is unchanged.

The object's like count is surfaced over the existing per-object `/likes`
collection endpoint (`GET {object}/likes`, decision 056 (d)) — the reverse index
`ILikeStore.GetLikersAsync` already exists and was already wired to that endpoint;
the only thing missing was the *record* for a remote liker of a local object. The
symmetric `Undo(Like)` path already removes the edge unconditionally
(`UndoActivityHandler` calls `RemoveLikeAsync` for the original like's parties), so
no Undo change was needed — the new integration test confirms the edge is removed on
the object's home instance after the Undo federates.

This refines (not contradicts) Decision 052: 052's concern was that the *directed*
`liked` collection lists objects *this* actor liked (not an aggregate), and that a
remote liker should not be *treated as a local actor*. 31.10 records the edge in the
same `ILikeStore` (keyed by liker IRI, with the reverse index), but only when the
object is local — which is exactly the case where the object's own `/likes`
collection and like count live. A remote liker's like of a *remote* object is still
not recorded locally (it is the object's author's home instance's concern), so
Decision 052's "no incorrect local state" consequence still holds.

## Decisions

- **Record on local-object, not local-liker.** The 31.10 Inbox entry's scope
  ("record remote-liker likes on local objects") is the exact inverse of the old
  guard. The object's home instance is the authoritative place for the object's like
  count (the object's `/likes` collection lives there), so the edge is recorded when
  the object is local — independent of the liker's locality. A like of a remote
  object is the object's author's home instance's concern (recording it here would
  duplicate the edge).
- **No new store / endpoint.** The `ILikeStore` reverse index
  (`GetLikersAsync`) and the per-object `/likes` endpoint already existed
  (decision 056 (d)); only the *record* for a remote liker of a local object was
  missing. The fix wires the existing surface to the new record condition.
- **`Undo(Like)` needs no change.** `UndoActivityHandler` removes the edge
  unconditionally for the original like's parties; the new integration test confirms
  the edge is removed on the object's home instance after the Undo federates.
- **Decision 052 refined, not overturned.** 052's directed-`liked` concern (a
  remote liker is not a local actor) still holds — a remote liker's like of a
  *remote* object is not recorded locally. 31.10 records the edge only when the
  object is local, which is where the object's own like count lives.
