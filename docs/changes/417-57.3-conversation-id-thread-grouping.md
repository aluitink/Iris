# 57.3 — `conversationId` support for Pleroma thread grouping

## Summary

Pleroma and Misskey set a stable thread-root IRI (`conversationId`) on every note in a conversation; clients use it for thread grouping. Iris never set it. This change adds server-side `conversationId` resolution on both the local-post and federation inbound paths, a client-side explicit override, and the `GetConversationId`/`SetConversationId` boundary helpers.

## Design decision

**Server-side resolution, not client-side.** Under Decision 055 the server is the object-id authority — it mints the ULID for every embedded note. The client does not know the note's IRI when it composes the reply, so it cannot set `conversationId` to the note's own IRI. The server resolves the thread root after minting the ID:

- **Top-level note** (no `inReplyTo`): `conversationId` = the note's own IRI.
- **Reply** (`inReplyTo` set): look up the parent's `conversationId`. If the parent has one, copy it (thread root preserved across nesting). If the parent has none, use the parent's own IRI (the parent is the thread root).
- **Already set** (e.g. inbound from Pleroma): preserve it (no overwrite).

This is best-effort: if the parent is not found (remote, not yet fetched), `conversationId` is left unset rather than failing the post.

## Changes

### `Iris.Core` — boundary helpers

- **`IriExtensions.GetConversationId(this IObject?)`** — reads `conversationId` from `ExtensionData` (bare, un-namespaced term, like `sensitive`). Returns `Iri?`.
- **`IriExtensions.SetConversationId(this IObject, Iri)`** — writes `conversationId` into `ExtensionData`.

### `Iris.Server` — server-side resolution

- **`ActivityPubServerExtensions.EnsureConversationIdAsync`** (private static) — the local-post path. Called in `RecordCreateLocalAsync` after `MintActivityIds` but before `PutObjectAsync`, so the minted ID is available and the `conversationId` is part of the stored document.
- **`CreateActivityHandler.EnsureConversationIdAsync`** (private instance) — the federation inbound path. Called in `StoreEmbeddedObjectAsync` before `PutObjectAsync`. Same logic as the local-post path.

### `Iris.Client` — explicit override

- **`PostReplyAsync`** gains an optional `Iri? conversationIri = null` parameter. When set, it is written into the note's `conversationId` via `SetConversationId` before the Create is posted. The server's `EnsureConversationIdAsync` sees it is already set and preserves it.

## Tests

Four new integration tests in `ReplyIntegrationTests`:

1. **`Client_PostReplyAsync_ReplyCarriesConversationId`** — a reply to a parent with no pre-set `conversationId` gets `conversationId` = parent's IRI.
2. **`Client_PostReplyAsync_ExplicitConversationId_Preserved`** — a reply posted with an explicit `conversationIri` parameter has that value preserved (not overwritten by the server).
3. **`Client_PostReplyAsync_SecondReply_InheritsConversationId`** — a nested reply (reply to a reply) inherits the thread root from the first reply's `conversationId`.
4. **`Inbound_Note_WithConversationId_Preserved`** — a note with a pre-set `conversationId` (Pleroma-style) is stored and served with the value intact.

## Inbound preservation (no code change needed)

Inbound `conversationId` from remote servers is already preserved: the storage model is serialize → store JSON (`jsonb`) → deserialize, and `Object.ExtensionData` is `[JsonExtensionData]`, so all unknown inbound fields round-trip with no code. The `EnsureConversationIdAsync` check (`if already set, return`) ensures the server does not overwrite a remote server's value.
