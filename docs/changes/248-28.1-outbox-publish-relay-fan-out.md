# 28.1 — Outbox-publish relay fan-out for `Create` / `Announce`

## What was built

A code fix + 3 integration tests to make the **outbox-publish** write surface
(`POST /ap/v1/u/{handle}/outbox`) fan out a local `Create` or `Announce` to the
actor's subscribed **relays** (F-06, ActivityPub §5.1.3), complementing the
existing **inbox** post path that already handled relay fan-out (Phase 12,
Slice 12.19, `RelayFanOutIntegrationTests`).

### Code fix: outbox-publish relay fan-out

**File:** `src/Iris.Server/ActivityPubServerExtensions.cs`

The `OutboxPublishHandler` delivered a local `Create` and `Announce` only to the
actor's remote, non-blocked followers (`GetRemoteNonBlockedFollowersAsync` /
`RecordCreateLocalAsync`), never to their subscribed relays. A relay is a
`star`-subscribed fan-out server: the actor advertises its relays via the `star`
actor property, and its content is delivered to those relays so they can re-fan
the content to the wider federation. The relay subscriptions are persisted in the
`IRelayStore` (the actor's `relays` collection), recorded when the actor
subscribes to a relay.

Added a `DeliverToRelaysAsync` helper (placed next to
`GetRemoteNonBlockedFollowersAsync`) that reads the actor's relay subscriptions
from `IRelayStore.GetRelaysAsync` and enqueues one delivery job per relay via
`IDeliveryService.DeliverToActorAsync` (signed as the acting actor). Each relay
is an independent delivery job — a failure for one does not suppress the others.
The helper is called from the outbox-publish `Create` branch (after the follower
fan-out) and the `Announce` branch (after the follower fan-out).

This mirrors the relay fan-out already present on the **inbox** post path
(`CreateActivityHandler`, Phase 12) — the two paths now behave consistently.

## Tests

**File:** `tests/Iris.Server.Tests/OutboxRelayFanOutIntegrationTests.cs` (3
tests, 2-instance `TestServer` topology: author instance A + relay instance R)

Topology: instance A (outbox-relay-a.domain.local) hosts the local author
`alice`, who has subscribed to a relay (the `relay` actor on instance R,
outbox-relay-r.example.com). A's outbound delivery transport routes to R's
`TestServer` (so the fanned-out activity reaches the relay's inbox), and A's
fetcher resolves the relay's document from R and alice's document from A.

1. **`OutboxPublish_Create_IsFannedOutToRelay`** — alice publishes a `Create` to
   her own outbox (signed as alice). A's outbox-publish handler records the post
   in alice's outbox and fans it out to the relay (F-06), signed as alice. R
   validates the delivery (resolving alice's key from A's actor document) and
   stores the `Create`.

2. **`OutboxPublish_Announce_IsFannedOutToRelay`** — same, but alice publishes an
   `Announce` (boost) to her outbox. R stores the `Announce`.

3. **`OutboxPublish_WithNoSubscribedRelays_IsNotFannedOut`** — a fresh author
   (bob) with **no** subscribed relays publishes a `Create` to his outbox. The
   relay store is empty, so no relay fan-out occurs; R stores nothing. (Negative
   control — confirms the fan-out is driven by the relay subscription, not by
   any blanket delivery.)

## Non-vacuity

- **`Create` branch:** Removing the `DeliverToRelaysAsync` call from the
  outbox-publish `Create` branch → test 1 fails (R never stores the `Create`;
  the assertion "R should have stored the Create fanned out by A's
  outbox-publish handler" fails after the 10s wait).
- **`Announce` branch:** Removing the call from the `Announce` branch → test 2
  fails (R never stores the `Announce`).
- **Negative control:** test 3 passes regardless (no relays → no fan-out),
  confirming the behavior is subscription-driven.

## Key decisions

- The fix is scoped to `Create` and `Announce` (the two content-producing
  activity types that the outbox-publish path fans out to followers). `Update`
  and `Delete` relay fan-out is tracked as a follow-up slice (28.2).
- `DeliverToRelaysAsync` reads relays from the `IRelayStore` (the actor's
  `relays` collection), the same source the inbox post path uses — keeping the
  two paths consistent and avoiding a second relay registry.
- Delivery is enqueued (asynchronous), so the test waits on the *effect* (R
  storing the activity) rather than asserting on A's storage — matching the
  existing `RelayFanOutIntegrationTests` pattern.
