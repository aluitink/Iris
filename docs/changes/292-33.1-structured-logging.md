# 33.1 — structured logging + diagnostics

**Slice:** Phase 33 step 1 (was 30.3). **Branch:** `phase-32-production-app`. **Commit:** `b03fd43`.

## What was built

The server now emits **actionable structured logs** through `ILogger<T>` without adding a logging
package — so a production deployment can answer "what did this instance do with that activity?" and
"why did that signature get rejected?" from its logs. Three production components were wired:

- **`HttpSignatureValidator`** (`src/Iris.Server/Security/HttpSignatureValidator.cs`) — gains an
  `ILogger<HttpSignatureValidator>` (primary-constructor parameter, defaults to `NullLogger`). Each of
  the four rejection branches now logs the **specific reason** at `Warning`:
  - `Signature rejected: malformed Signature header on {Method} {Path}` (the `Signature` header does not
    parse);
  - `Signature rejected: unparseable keyId '{KeyId}' on {Method} {Path}` (the keyId is not a valid IRI);
  - `Signature rejected: could not resolve public key for keyId {KeyId} on {Method} {Path}` (unknown
    actor / missing `publicKey` / fetch failure);
  - `Signature rejected: cryptographic verification failed for keyId {KeyId} on {Method} {Path}` (the
    resolved key did not verify — including after the F-21 key-rotation re-resolve).

  Previously these branches collapsed to a bare `false` in `SignatureValidationResult` with no diagnostic.

- **`InboxProcessor`** (`src/Iris.Server/Inbox/InboxProcessor.cs`) — gains an
  `ILogger<InboxProcessor>` (defaults to `NullLogger`). `ProcessAsync` logs, with the activity's type,
  id, actor IRI, and recipient:
  - `Inbox received {ActivityType} {ActivityId} from {Actor} to {Recipient}` (every inbound activity);
  - `Inbox re-delivery of {ActivityType} {ActivityId} (already stored); skipping dispatch to {Recipient}`
    (the C-07 loop-safety guard — a duplicate IRI is stored as a no-op and **not** re-dispatched);
  - `Inbox stored {ActivityType} {ActivityId} but no handler is registered; nothing dispatched to {Recipient}`;
  - `Inbox handler {Handler} failed for {ActivityType} {ActivityId} to {Recipient}` (`Error` + rethrow)
    when the handler throws;
  - `Inbox dispatched {ActivityType} {ActivityId} to {Handler} (actor {Actor}, recipient {Recipient}) — ok`
    on success.

- **`ActivityHandlerBase<TActivity>.DispatchAsync`** (`src/Iris.Server/Inbox/ActivityHandlerBaseT.cs`) —
  the base gains a `protected ActivityHandlerBase(ILogger? logger = null)` ctor and `DispatchAsync`
  becomes `async` with a try/catch: `Handler {Handler} processed {ActivityType} {ActivityId} (actor {Actor},
  recipient {Recipient}) — ok` at `Info` on success, `Handler {Handler} failed for …` at `Error` +
  rethrow on failure. So the **per-handler** effect (the thing that actually mutates state) is observable,
  distinct from the processor's receive/dispatch framing.

- **All 15 concrete activity handlers** (Block, Like, Add, Remove, Mute, Flag, Undo, Follow, Create,
  Delete, Update, Move, Announce, CommunityInbox, and the `FollowResponseActivityHandler<T>` base for
  Accept/Reject) accept an `ILogger<T>?` and forward it to the base. The **`DeliveryWorker` was already
  fully logged** (per-attempt success/failure, per-dead-letter) — no change.

### DI wiring

`ActivityPubServerExtensions` now passes the loggers: the `ISignatureValidator` registration adds
`sp.GetRequiredService<ILogger<HttpSignatureValidator>>()`, and the `IInboxProcessor` registration is
replaced by a factory that passes `sp.GetRequiredService<ILogger<InboxProcessor>>()`. The handlers are
constructed by their existing DI registrations (their new `logger` parameter is optional, defaulting to
`NullLogger`); the processor's `DispatchAsync` supplies the per-handler logger through the base.

## Test approach: construct the production components with a capturing logger

The host factory (`ActivityPubHostFactory.Create`) clears all log providers
(`ConfigureLogging(l => l.ClearProviders()); l.SetMinimumLevel(LogLevel.None)`), so a test **cannot**
inject a capturing `ILoggerProvider` through the `ExtraServices` seam — the host-level `ClearProviders`
overrides any service-level provider added in `ConfigureServices` (verified empirically: a probe logger
registered via `ExtraServices` captured zero entries). The full signature-validated inbound path (a valid
signed activity accepted end-to-end) is already covered by the existing integration tests.

So `tests/Iris.Server.Tests/Observability/StructuredLoggingIntegrationTests.cs` pins the **log output**
by constructing the real production components directly with a thread-safe `CapturingLogProvider`
(`ILogger<T>` + `ILogger`):

1. **`InboxProcessor_LogsReceivedActivity_AndDispatchOutcome`** — an `InboxProcessor` wired with the real
   `LikeActivityHandler` (real `DefaultLocalActorResolver` + a seeded `InMemoryPersistenceProvider`)
   dispatches a Like and the test asserts the three expected `Information` entries: `Inbox received Like`,
   `Inbox dispatched Like … LikeActivityHandler`, and `Handler LikeActivityHandler processed … — ok`.
2. **`Validator_LogsRejectionReason_WhenSignatureHeaderIsMalformed`** — an `HttpSignatureValidator`
   (real `HttpSignatureVerifier` + a no-op key resolver) given a `DefaultHttpContext` POST with a
   `Signature` header that does not parse returns `IsValid == false` and the test asserts the `Warning`
   entry `Signature rejected: malformed Signature header`.
