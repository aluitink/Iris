# 282 — 31.9: followed feed (`/feed`) returns the followed actors' data — verification (no server change)

> 2026-09-05 · Slice 31.9 · Phase 31 (explorer UI & server namespace polish)

## What was built

A focused verification of the followed-feed (`/feed`) contract: that the feed
**returns data** — the followed actors' outbox items, every activity type
(Create, Announce, Like, Accept, Note) — for both local and remote follows, under
both the in-memory and the file-backed persistence provider (the live sample's
configuration). **No server, client, or UI code changed**: the 31.9 report
hypothesized a server `FollowFeedHandler` union bug (dropping Create + Accept
items), but the in-process repro could not reproduce that drop. Per the user's
direction ("What Mastodon shows is what they show — we shouldn't worry to
rationalize it too much — we just need to confirm that it does return data and
that we can see that data in the sample"), this slice stops at the verification:
the followed feed demonstrably returns the followed actors' data in-process, and
the live display is the UI faithfully rendering what the server returns (which
this test confirms the server produces, given the followed actors' outbox
contents).

The 31.9 Inbox entry's own proposed fix ("ensure the followed-feed union includes
all activity types … de-duplicated, newest-first") is **already the implemented
behavior** — `FeedService.BuildFeedAsync` merges every followed actor's outbox
items with no per-type filter, de-duplicates by IRI, and caps by
`FeedOptions.MaxItems`. This change documents and locks that in with integration
tests, rather than changing it.

## Key types & files

- `tests/Iris.Server.Tests/Services/FollowFeedTypeProbeTests.cs` — **new**, 6
  integration tests (see Tests). Seeds a followed actor's outbox with one item of
  every feed-relevant activity type and asserts the follower's `/feed` (and the
  client's `GetFollowFeedAsync`) returns them all.
  - `ProbeHost` — a `TestServer` (via `ActivityPubHostFactory`) with a local
    alice following a local carol whose outbox holds one Create + Announce + Like
    + Accept + Note. Used by the four local-follow probes (in-memory + file-backed,
    endpoint + client enumeration).
  - Remote-follow probe — a **second** in-process host (B) hosts rayven; alice on
    A follows rayven on B. A's outbound feed client + actor-document fetcher are
    overlaid onto B's in-process `TestServer` transport (the production
    registration hardcodes a real `HttpClientHandler`, which cannot reach an
    in-process `TestServer`); alice signs as herself so the outbound requests carry
    a valid signature. B is held as a test-class field and disposed in
    `Dispose()` (the same multi-host pattern as the federation suites) so its
    transport target outlives the feed request.
- No changes to `src/` — the `FeedService` / `FollowFeedHandler` behavior is
  verified as-is.

## Tests

6 new integration tests (full fast suite grew 1451 → **1459**; the other +2 are the
prior-turn sample `Program` configuration-source tests). All 6 pass:

- `Probe_InMemory_Endpoint_ReturnsAllActivityTypes` — `GET /feed` returns all five
  of carol's outbox items (in-memory).
- `Probe_InMemory_Client_ReturnsAllActivityTypes` — `GetFollowFeedAsync` enumerates
  all five (in-memory).
- `Probe_FileBacked_Endpoint_ReturnsAllActivityTypes` — `GET /feed` returns all
  five (file-backed — the live sample's persistence).
- `Probe_FileBacked_Client_ReturnsAllActivityTypes` — `GetFollowFeedAsync`
  enumerates all five (file-backed).
- `Probe_UiPath_CollectionIriWithQuery_ReturnsAllActivityTypes` — the exact
  `Feed.razor` enumeration (`GetCollectionAsync` on `{actor}/feed`, page-by-page,
  following `NextPage`) returns all five — the path the UI actually walks.
- `Probe_RemoteFollow_ReturnsAllActivityTypes` — a **remote** follow (alice on A →
  rayven on B): A's `FeedService` fetches B's outbox over the in-process wire and
  the feed returns all five of rayven's items. This isolates the remote-walk path
  (`FetchRemoteOutboxAsync`) — the one path the live sample exercises for a
  cross-instance follow.

## Decisions

- **Verify, don't refactor (per user direction).** The 31.9 symptom was a
  *live*-only observation (the in-process repro returns all five types for both
  local and remote follows). Rather than change a server path that the in-process
  tests show to be correct, this slice locks the contract with tests. If the live
  feed still shows fewer items than the followed actors' outboxes contain, the
  residual cause is in what the followed actors' outboxes actually hold live (an
  upstream data / delivery concern), not the feed-merge — which this test
  confirms is correct.
- **The remote probe overlays the feed client onto B's in-process transport.**
  The production `IFollowFeedService` registration hardcodes a real
  `HttpClientHandler` (it dials the remote instance's public URL), which cannot
  reach an in-process `TestServer`. The test therefore builds A's feed client +
  document fetcher against B's `TestServer` handler (signed as alice) — the same
  overlay the existing follow-feed integration tests use. This exercises the real
  `FeedService` remote-walk code path (the only part the live sample uses for a
  cross-instance follow) against a real in-process remote.
- **B is a field, disposed in `Dispose()`.** A remote-follow probe needs the peer
  host (B) alive for the whole feed request. The federation multi-host suites hold
  both servers as fields and dispose them in the test class's `Dispose()`; this
  probe does the same for B (A is created per-test and disposed with `using`).
- No new NuGet packages; no `src/` changes; no UI/CSS changes.
