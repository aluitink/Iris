# 199 — 19.6.2 Outbox page-cache invalidation on a local outbox write

**Phase 19.6** (C2S invariants), the **19.6.2 "all activities flow through the outbox" UI half** — the
server-side defect that was keeping the UI's outbox card from enumerating the outbox 1:1 with the writes
taken.

## The defect

The outbox collection page (page 1) is served through the `LocalCollectionPageCache` — a server→client
response cache with a 60s TTL, keyed by the page IRI (`{owner}/outbox`). A local outbox **write**
prepends the new activity to the collection (newest-first, `Insert(0)`), but nothing invalidated the
cached page-1 entry on that write. So a plain, non-`?refresh=true` read of the outbox within the TTL
returned the **stale** page — the actor's outbox card did not surface the activity it had just published
until the 60s TTL lapsed or a manual refresh bypass was issued.

This was observed in the live manual test: after publishing a Block (202, minted) the UI outbox card
still showed the pre-write count, while the wire (a `?refresh=true` / bypass read) showed the new
activity at the head. The outbox enumeration — the 19.6.2 "match entries 1:1 with the actions taken"
invariant — was being broken not by a recording bug (the activity *was* in the outbox) but by a stale
response cache in front of it.

## The fix — `src/Iris.Server/ActivityPubServerExtensions.cs`

A local outbox write is made to **invalidate the cached page-1 entry** for the owner's outbox, so the
next plain read re-renders from the live store.

- New helper `InvalidateLocalOutboxPage(collectionCache, ownerIri)` → drops the page-1 key
  (`{ownerIri}/outbox`) from the `LocalCollectionPageCache`. A newest-first insert always lands the new
  item at the **head** of the collection (page 1), so invalidating page 1 is sufficient for the primary
  read; deeper pages shift when page 1 is full, but their staleness self-heals within the short TTL and
  the new item is never on a deeper page.
- `OutboxPublishHandler` (the actor outbox write — Create/Announce/Follow/Block/Flag/Like/Accept/Reject/
  Undo) now receives the `LocalCollectionPageCache` (resolved by DI; the endpoint uses the method-group
  form) and calls `InvalidateLocalOutboxPage` immediately after `AddToOutboxAsync`.
- `CommunityOutboxPublishHandler` / `FinishCommunityOutboxPublishAsync` (the community / Group outbox
  write) thread the cache through and invalidate the community's outbox page-1 the same way.

## Why only the handler path (and not every store write)

The adjacent `OutboxCacheBypassIntegrationTests` (19.6.6) pins the **store-write** boundary from the
other side: a write that bypasses the handler (a direct store `AddToOutboxAsync`) leaves the cached page
stale and relies on the `?refresh=true` escape hatch. That is still correct and unchanged — this fix
does **not** invalidate on a raw store write. The two are complementary, not contradictory:

- A **real user** publishes through the outbox HTTP endpoint → the handler records the activity **and**
  invalidates the cached page → the primary (plain) read is fresh.
- A **direct store write** (an internal/system write, or a test's artificial injection) does not touch
  the handler → the cache is left alone → `?refresh=true` remains the escape hatch (the 19.6.6 pin).

Invalidating at the handler is the right seam: the handlers are the only *local* outbox writers a user
exercises, they already hold the owner IRI, and putting the invalidation in the persistence layer would
create a persistence→cache layering inversion.

## 19.6.2 status

This removes the **blocker** to the 19.6.2 UI half (the outbox no longer lags the writes it records).
The Create and Block write screens are now verified 1:1 (outbox count and head item track the actions
taken). The remaining 19.6.2 surface — enumerating the *every* write screen (Follow, Like, Flag, Mute,
Accept/Reject, Undo) 1:1 through the UI — is the broader raw-inspector pass folded into the Phase 22
manual test (22.6); the server-side precondition for that pass (a fresh outbox read after a write) is now
in place.
