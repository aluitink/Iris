# 59.4 — `ld+json` production (F-31)

## Summary

Completes F-31 (the last remaining open F-item). Iris now performs content-type negotiation on its
ActivityPub responses: when a client sends `Accept: application/ld+json` (or includes it in an
`Accept` list), the server responds with `Content-Type: application/ld+json`. When the client does
not accept `ld+json` (or sends no `Accept` header), the server responds with the default
`application/activity+json` (unchanged from before).

Both media types are spec-valid per ActivityPub §4.4 (draft-cavage-03) and AS2.0. The `application/activity+json`
media type is a subtype of `application/ld+json` with a fixed `@context`, so the JSON body is
identical in both cases — only the `Content-Type` header differs.

## Changes

### `NegotiateContentType(HttpContext)` (Iris.Server)

New private static helper in `ActivityPubServerExtensions`. Checks the request's `Accept` header:
if any value contains `ld+json` (case-insensitive), returns `ActivityJson.JsonLdContentType`
(`application/ld+json`); otherwise returns `ActivityJson.ActivityJsonContentType`
(`application/activity+json`).

### Response sites updated (Iris.Server)

18 response sites in `ActivityPubServerExtensions.cs` now call `NegotiateContentType(context)`
instead of the hardcoded `ActivityJson.ActivityJsonContentType`:

- Actor document (owner-only + public cached)
- Object document (`GET /ap/v1/{**path}`)
- Replies collection
- Per-object `likes`/`shares` interaction collections
- Inbox collection
- Actor paged collections (`outbox`/`followers`/`following`/`liked`/`blocks`/`flags`/`mutes`/`relays`)
- Actor feed
- Public feed
- Community (Group) document
- Community collections (`members`/`feed`/`following`/`followers`/moderation)
- Community outbox
- Community search
- Global search / directory
- Outbox publish 202 bodies (person + community, including `Add`/`Remove` person settings)

`FinishCommunityOutboxPublishAsync` gained an `HttpContext` parameter (it didn't have one before)
so it can call `NegotiateContentType`. All 4 call sites updated.

### NOT changed (intentionally)

- **Outbound delivery** (`DeliveryWorker`): still sends `application/activity+json` to remote inboxes
  (the remote's `Accept` is not known at delivery time; `activity+json` is universally accepted).
- **Proxy-fallback relay**: still relays the remote's own response content type (it's not Iris's
  content).
- **WebFinger**: still returns `application/jrd+json` (JRD, not ActivityPub).
- **NodeInfo**: still returns `application/json` (NodeInfo 2.0 spec).
- **Namespace document**: still returns `application/ld+json` (it's a vocabulary document).

## Design notes

- The negotiation is deliberately simple: a substring match on `ld+json` in any `Accept` value.
  This handles the common cases (`Accept: application/ld+json`,
  `Accept: application/activity+json, application/ld+json`, `Accept: */*` → no match, default).
  It does not implement full RFC 7231 quality-value (q) parsing — for this use case (two known
  media types, one of which is a supertype of the other), the simple check is sufficient and
  matches what the ActivityPub spec requires.
- The JSON body is identical in both cases (same `@context`, same serialization). The only
  difference is the `Content-Type` header. This means no changes to the serialization pipeline
  are needed.
