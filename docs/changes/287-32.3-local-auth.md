# 287 — 32.3: local auth (registration, login, logout)

> 2026-09-06 · Slice 32.3 · Phase 32 (production social platform app) — step 3 (local accounts)

## What was built

Phase 32's **step 3** adds **local-account authentication** to `apps/Iris.Web`: a user registers
with a handle + password, is provisioned a **local actor** (a real ActivityPub `Person` with a
signing key), and signs in/out via a browser cookie session. This is the "bootstrap mechanism"
[production-app-authentication.md](../plans/production-app-authentication.md) describes — the
platform's own users get first-class local actors so they can post, follow, and be federated from
day one.

The auth surface is deliberately **plain HTTP**, not the Blazor interactive circuit: an interactive
(WebSocket/SSE) circuit **cannot set or clear cookies** (the circuit's response headers are read-only
once the signal stream starts — confirmed live: a `SignInAsync` from the circuit throws
`Headers are read-only, response has already started`). So `/register`, `/login` are `POST`
endpoints (a writable response) that validate, sign in via the cookie scheme, and 302-redirect to
`/`; `/logout` is a `GET` endpoint that signs out and redirects to `/login`. The Razor pages at
those routes are simple HTML `<form>`s that post to the endpoints (with an `<AntiforgeryToken />`),
reading `?error=…` from the redirect to surface validation errors.

Account state lives in `Iris.Server.Data` (a `UserAccount` + `IUserAccountStore` with in-memory and
EF Core implementations), so the account store follows the same persistence seam as everything else
in Phase 32: in-memory by default (and for the tests), PostgreSQL when `Iris:ConnectionString` is
set. The `InitialCreate` migration was **squashed** to a single migration (per the
[pre-launch migration policy](../plans/production-app-persistence-schema.md) §4.1) now that it
includes the `UserAccounts` table.

## Key types & files

### Account model — `src/Iris.Server.Data`
- `Accounts/UserAccount.cs` — `Id`, `Username` (the handle), `DisplayName?`, `PasswordHash`,
  `ActorId` (`Iri`), `Role` (`UserRole`), `CreatedAt`.
- `Accounts/UserRole.cs` — `User`, `Admin`.
- `Accounts/IUserAccountStore.cs` — `CreateAsync`, `FindByUsernameAsync`,
  `FindByActorIdAsync`, `UpdatePasswordHashAsync`, `AnyAdminExistsAsync`, `ListAsync` (paged).
- `Accounts/InMemoryUserAccountStore.cs` + `Accounts/EfUserAccountStore.cs` — the two store
  implementations (the EF one maps to the `UserAccounts` table).
- `Entities/UserAccountEntity.cs` + `IrisDbContext.ConfigureUserAccount` — the EF entity + table
  mapping (`Username` unique).
- `Migrations/20260906102841_InitialCreate.*` — the **squashed** single migration (replaces the
  layered 32.2 `InitialCreate`; now includes `UserAccounts`). `has-pending-model-changes` = none.

### Auth stack — `apps/Iris.Web`
- `HandleRules.cs` — `Validate(string?)`: 2–32 chars, `[A-Za-z0-9-]`, no leading/trailing hyphen,
  a reserved set (`ap, ns, nodeinfo, admin, apiv1, wellknown`, …). Returns an error string or null.
- `Accounts/PasswordHasher.cs` — wraps ASP.NET Core Identity's `PasswordHasher<UserAccount>`
  (pulled by the Web SDK; no new NuGet package). `Hash` + `Verify` → `PasswordVerificationResult`
  (`Success` / `SuccessRehashNeeded` / `Failed`).
- `Accounts/ActorProvisioner.cs` — `ProvisionAsync(handle, displayName?)`: generates an RSA key
  (`KeyPairGenerator.GenerateRsa`), stores it (`IKeyStore.PutKey`), builds a `Person` (id
  `{base}/ap/v1/u/{handle}`, the `iris:` public-key extension), `PutActorAsync`, and
  `IKeyProvider.RegisterKey`. Returns the account's `ActorId`.
- `Accounts/RegistrationService.cs` — `RegisterAsync(handle, password, displayName?)`:
  `HandleRules` validation, `MinPasswordLength` (8), duplicate check, `PasswordHasher.Hash`,
  provision the actor, persist the `UserAccount` (role `User`). → `RegistrationResult`.
- `Accounts/LoginService.cs` — `LoginAsync(handle, password, remoteIp)`: rate-limit check,
  `FindByUsernameAsync`, `Verify`, **re-hash on `SuccessRehashNeeded`** (algorithm upgrade),
  `Clear` the failure window on success. Generic `InvalidCredentials` / `RateLimited` messages
  (no user enumeration). → `LoginResult`.
- `Accounts/LoginRateLimiter.cs` — `ILoginRateLimiter` + `SlidingWindowLoginRateLimiter`
  (5 failures / 15 min, keyed by `handle + remoteIp`). `IsBlocked` returns `count >= max` so
  "N attempts" blocks the (N+1)th.
- `Accounts/AdminBootstrapper.cs` — a plain class (not an `IHostedService`) invoked directly at the
  end of `WebAppFactory.InitializePersistence` (after migration + seed, so persistence is ready).
  Idempotent via `AnyAdminExistsAsync`; reads `App:Admin:Username` / `App:Admin:Password`.
- `Accounts/ClaimsFactory.cs` + `Accounts/ActorClaims.cs` — builds a `ClaimsIdentity` for
  sign-in: `sub` (account id), name, the custom `actor_iri` claim, and the role.
- `Accounts/IActorSessionAccessor.cs` — scoped accessor that reads the `AuthenticationState` and
  lazily builds a cached `IActivityPubClient` (via `IActivityPubClientFactory.Create`) for the
  signed-in actor — the seam later slices use to act "as the current user."

### Wiring — `apps/Iris.Web/WebAppFactory.cs`
- Cookie authentication (`iris.auth` cookie, 14-day sliding) + `AddAuthorization` +
  `AddHttpContextAccessor`.
- DI: `PasswordHasher` (singleton), `ILoginRateLimiter` (singleton, 5/15min), `ActorProvisioner`
  (singleton), `IUserAccountStore` (`TryAddSingleton` — the EF provider, registered earlier in
  `AddEntityFrameworkPersistence`, wins; the in-memory one is the fallback), `RegistrationService`,
  `LoginService` (singletons), `IActorSessionAccessor` (scoped).
- `MapAuthEndpoints(IEndpointRouteBuilder)` (now **public**): `POST /register`, `POST /login`,
  `GET /logout`. `ConfigurePipeline(WebApplication, base)` (now **public**) is the single
  middleware+endpoint pipeline `BuildApp` calls and the tests reproduce on a `TestServer`.
- `InitializePersistence` now calls the `AdminBootstrapper` directly (after the EF migration +
  seed) instead of as an `IHostedService` (which would run before the tables exist).

### Pages — `apps/Iris.Web/Components/Pages/`
- `Register.razor`, `Login.razor` — plain HTML `<form method="post">` with an
  `<AntiforgeryToken />`, posting to the endpoints; `?error=…` (via `QueryHelpers`) is rendered in
  an `<p role="alert">`. No circuit handlers (the circuit cannot sign in).

## Tests

`tests/Iris.Web.Tests/LocalAuthIntegrationTests.cs` — 36 tests (23 service-level + 7 endpoint-level
+ 6 pre-existing HTTP-surface):
- **Handle rules**: valid handles accepted; too short / too long / bad chars / edge hyphen /
  reserved names rejected.
- **Registration**: creates account + provisions actor (deterministic IRI
  `https://web.test.local/ap/v1/u/{handle}`); duplicate handle → error; case-insensitive duplicate;
  short password → error.
- **Login**: correct password succeeds; wrong password fails; unknown handle fails; rate limiter
  blocks after 5 failures (and is keyed by `handle + IP`, so a different IP is not blocked).
- **Password hasher**: round-trips; rejects a wrong password; `SuccessRehashNeeded` path.
- **Admin bootstrap**: idempotent (no admin when config unset; one admin when set; a second run
  does not create a duplicate).
- **Claims factory**: `sub` / name / `actor_iri` / role claims are set correctly.
- **Endpoint surface (new)**: `POST /register` (create + 302 to `/` + account/actor persisted;
  duplicate → 302 back with `?error=`; short password → 302 back), `POST /login` (valid → 302 to
  `/`; wrong password / unknown → 302 back with `?error=`), `GET /logout` (302 to `/login`). The
  endpoint tests run the **real** production pipeline (`ConfigurePipeline`/`MapAuthEndpoints`) on a
  `TestServer` and send the antiforgery cookie + token manually (captured from the rendered form's
  `Set-Cookie` + `<input>`), since `TestServer.CreateClient()` does not persist cookies.

`dotnet build Iris.slnx` clean (0 warnings, `TreatWarningsAsErrors` on); full `dotnet test`
green (all 11 test projects; Iris.Web.Tests 36/36, Iris.Server.Data.Tests 8/8, Iris.Server.Tests
926/943 with 17 pre-existing skips). Live Playwright E2E against the **published** app confirmed
register → sign in → `/`, logout → `/login`, re-login → `/` with no console errors.

## Decisions

- **Auth is plain HTTP, not the Blazor circuit.** The interactive circuit cannot set/clear cookies
  (read-only response headers). This is the documented Blazor Web App pattern for auth. Consequence:
  the login/register pages are plain HTML forms, not interactive components — acceptable here since
  the auth screens are static; later product screens (timeline, etc.) use the interactive circuit.
- **Account store lives in `Iris.Server.Data`, not `Iris.Web`.** Accounts are a persistence concern
  (they must survive restarts in the EF path); `Iris.Web` consumes the store only via DI. The
  in-memory store is the default + test path; the EF store wins when the EF provider is registered.
- **The `InitialCreate` migration was squashed to a single migration** (pre-launch, per the plan's
  migration policy): the layered 32.2 migration + a 32.3 delta collapse into one `InitialCreate`
  reflecting the current model. `dotnet ef migrations has-pending-model-changes` reports no pending
  changes.
- **`PasswordHasher` uses ASP.NET Core Identity's built-in hasher** (`Microsoft.AspNetCore.Identity`,
  already present via the Web SDK) rather than a third-party package — no new dependency.
- **Admin bootstrap is a direct call in `InitializePersistence`**, not an `IHostedService`:
  hosted services run at `Build()` (before the EF migration creates the tables), so the bootstrap
  must run after `EnsureCreatedAsync`. It is idempotent, so re-running on every boot is safe.
- **Login rate limiting is keyed by `handle + remoteIp`** (5 failures / 15 min) to bound
  brute-force per credential without a global lockout; the error messages are deliberately generic
  (no user enumeration).
