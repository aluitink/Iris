# 33.2 — server production-readiness: signing-identity persistence across restarts

**Slice:** Phase 33 step 2. **Branch:** `phase-32-production-app`. **Commit:** `149e4f0`.

## Problem

A local actor's **signing identity did not survive a server restart** under EF Core + PostgreSQL. The
app (`apps/Iris.Web/WebAppFactory.cs`) unconditionally bound an **in-memory** `IKeyStore` even when the
EF persistence provider was configured, so:

- the seeded instance actor **minted a fresh RSA key on every boot** (a new public key in the actor
  document each restart — breaking the "stable key" property federation relies on); and
- a **registered user's** actor key (created by `ActorProvisioner` at signup) was lost entirely on
  restart — it was never in the durable store, so the actor could no longer sign outbound federation
  (the `SigningHandler` threw `No signing identity registered for actor '<actor>'`).

The durable `EfKeyStore` (which already persisted private-key PEM to Postgres) existed but was only
wired into the file-backed persistence variant, not the app's EF path. And the in-process `IKeyProvider`
(the actor→key-IRI map, an `InMemoryKeyProvider`) is, by design, not durable — so even when a key *is*
in the durable store, the actor→key registration is gone after a restart.

## What was built

- **`WebAppFactory.ConfigureServices` — conditional `IKeyStore` / `ISignatureSigner` binding.**
  - *In-memory* (no `Iris:ConnectionString`): `InMemoryPersistenceProvider` + a fresh `InMemoryKeyStore`
    + `HttpSignatureSigner(keyStore)` — the slice 32.1 default, ephemeral by design.
  - *EF Core* (connection string set): `AddEntityFrameworkPersistence` + `ISignatureSigner` bound to a
    factory that resolves `IKeyStore` + **`IKeyStore` bound to the durable `EfKeyStore`** (the same
    object the EF persistence provider's `Keys` uses). So a `PutKey` persists the private key to
    Postgres and a restart reads it back. The signer and the seed/provisioning path all share that one
    `IKeyStore` instance.

- **`WebAppFactory.SeedActor` — idempotent by key.** It now checks
  `keyStore.TryGetKey({actor}#key-1, out existing)` and **reuses the persisted key** when present
  (restart → same public key), minting a fresh RSA key only on a first boot. The actor document is still
  re-stored each boot.

- **`WebAppFactory.RestoreLocalSigningKeys(IServiceProvider)` — new startup pass.** After the migration,
  seed, and admin bootstrap, it enumerates every local account (`IUserAccountStore.GetAllAsync`) and,
  for each account whose key is present in the durable store, re-registers `{actor}#key-1` with the
  in-process `IKeyProvider`. This rebuilds the actor→key map that a restart wipes, so **every** local
  actor (the seeded instance actor *and* every registered user, including the bootstrapped admin) can
  sign outbound federation again. No-op for accounts whose key is absent (defensive).

- **`IUserAccountStore.GetAllAsync(CancellationToken ct = default)` — new enumeration method**,
  implemented by `EfUserAccountStore` (`AsNoTracking().ToListAsync(ct)`) and `InMemoryUserAccountStore`
  (snapshot under the store's gate). Needed to rebuild the key-provider map from the persisted accounts.

## Design decisions

- **`IKeyStore` is bound to the durable store in the app, not the library.** The library
  (`AddActivityPubServer`) deliberately does not register an `IKeyStore` (the in-memory key store is
  ephemeral by design and the file-backed variant has its own). The app is the composition root that
  knows whether it is running under EF, so it owns the `IKeyStore`/`ISignatureSigner` binding. This keeps
  `Iris.Core`/`Iris.Server` free of any EF dependency.
- **Key IRI convention is `{actorIri}#key-1`** — the same convention `SeedActor` and `ActorProvisioner`
  already use, so the restore pass finds exactly the keys those paths created.
- **A "restart" is the same advertised base.** Production fixes `Iris:AdvertiseBase`, so the actor IRI
  (and therefore the key IRI, which encodes the base) is identical across boots; what must survive is the
  *key material*, which the durable store addresses by its `KeyId`.
- **The test avoids the UI entirely.** It builds the service container through the real
  `WebAppFactory.ConfigureServices` + `WebAppFactory.InitializePersistence` (the same startup code the
  production host runs) and builds the provider — no Blazor host, no pipeline, no `TestServer`. A
  "restart" is a brand-new container over the same Testcontainers Postgres with the same advertised base.

## Test approach

`tests/Iris.Server.Data.Tests/SigningIdentityRestartTests.cs` (`IClassFixture<PostgresFixture>`, the
shared `postgres:16-alpine` Testcontainers) — 2 `[Fact]`s:

1. **`InstanceActorSigningIdentity_SurvivesRestart`** — boots the real app's service graph twice over the
   same Postgres (same base). Asserts the seed key is read back into the durable store and can
   sign/verify, the **same** public key is unchanged across the restart, the instance actor is
   re-registered in the fresh key provider, and an outbound `HttpSignatureSigner.Sign` produces a header
   carrying the keyId.
2. **`UserActorSigningIdentity_SurvivesRestart`** — provisions a user (`ActorProvisioner`) + creates a
   `UserAccount`, restarts, and asserts the user key is read back (same public key) **and** re-registered
   in the fresh key provider (the exact 33.2 gap: a registered user's key was previously lost on restart).

Both boot via `WebApplication.CreateBuilder()` + `ConfigureServices` + `BuildServiceProvider` +
`InitializePersistence` — no web pipeline.
