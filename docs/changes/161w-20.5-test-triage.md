# 161w — Phase 20.5: test-suite triage

## Summary

Phase 20.5 audits the test suite and **removes the tests that add no coverage**, per the ROADMAP: "target a
smaller or stable count with higher per-test value, not growth." The audit found **34 over-fine unit tests of
trivial glue** (null-guard tests) and removed them. It found **no duplicates** and **no pre-055 id pins**
(the suite is already Decision-055 compliant), so those two categories contributed zero removals. The net
effect: **1,371 → 1,337 tests (−34), 0 failed**, with no loss of meaningful coverage.

## What was audited

Every test project except `Iris.LiveInterop.Tests` (gated live interop — out of scope): `Iris.Core.Tests`,
`Iris.Client.Tests`, `Iris.Client.Extensions.Tests`, `Iris.Server.Tests`, `SampleBlazorClient.Tests`,
`SampleServer.Tests`. Each candidate test method was read in full (arrange/act/assert) before classifying —
not from its name alone.

## What was removed (34 — all category B: over-fine glue)

All 34 are in `Iris.Server.Tests`, in the per-activity **inbox handler** test files + the delivery service
test. Each is a single `Assert.Throws<ArgumentNullException>` / `Assert.ThrowsAsync<ArgumentNullException>`
asserting that a constructor or `DispatchAsync`/`DeliverAsync` rejects a `null!` argument. That is the BCL's
`ArgumentNullException.ThrowIfNull` guard — one line, no Iris-specific logic — so it adds no coverage of
Iris behavior (per CODING_STYLE "Testing Conventions": unit tests only for pure logic; integration-first).

## What was kept (explicitly, with reasoning)

- **Every integration test** — outbox write→delivery→peer record, collection→paged items, proxy fallback,
  inbox attachment rewrite, digest auth, federation sign/verify, delivery queue/retry, OAuth flows, media
  upload/serve/round-trip, sensitivity, markdown, replies/threading, community membership/feed/moderation,
  relays, search, key rotation.
- **Pure-logic unit tests** — crypto (Ed25519, signatures, KeyPair), IRI derivation, cache, rate limiter,
  circuit breaker, collection paging.
- **Every "throws" test that asserts a real Iris invariant** — e.g. `InMemoryCommunityStoreTests` (blank
  Id → `ArgumentException`), `InboundRateLimiterUnitTests` (negative max / zero window → `ArgumentException`),
  `IrisClientFactoryTests` (proxy fallback without credentials → `InvalidOperationException`),
  `WebFingerClientTests.NormalizeSubject_NoAtSign_Throws`, `ActivityPubClientFactoryTests.Create_MissingActorId_Throws`,
  `LocalModerationClientTests`/`MediaClientTests` (`NoCredentials_..._Throws`), and the wrong-activity-type
  rejections (`Dispatch_NonAddActivity_Throws`, `Dispatch_NonRemoveActivity_Throws`,
  `Dispatch_NonIntransitiveActivity_ForwardsToMembershipHandler`).
- **The Decision-055 id-authority tests** — the client suite already asserts the *correct* post-055 contract
  (the client does **not** set ids; it uses the learned `MintedId`). These are the 055 tests, not pins of the
  old model, so they stay.

## The two categories that came up empty

- **Duplicates (category A):** none. Each handler test class covers a distinct activity type; the guard tests
  were repetitive in *shape* but asserted a different ctor signature per class, and each was already covered
  by category B. No two tests asserted the same behavior.
- **Pre-055 id pins (category C):** none clean. Two ambiguous cases were reviewed and **kept**:
  1. `SampleBlazorClient.Tests/S10RawDeliveryTests.cs` — `BuildFollow` sets a client-computed deterministic
     Follow IRI, but the test's primary assertions are that signed `DeliverAsync` is accepted (202) and the
     follow edge is recorded (real federation behavior); the id is part of the raw-payload fixture.
  2. `SampleServer.Tests/*` — uses `{actor}/notes/1` IRIs, but those are **seed/fixture** objects the sample
     server creates via `SeedSampleData` (a demo dataset, not a client choosing ids through the 055 pipeline);
     the tests assert seeding idempotency / federation edges / persistence round-trip.
