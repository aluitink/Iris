# 24.2 — Cross-instance mute / un-mute propagation

Phase 24, slice 2. **Type:** feature + test. `Mute` is an Iris-specific activity (there is **no**
ActivityStreams `Mute` type — the library has `Block`, `Flag`, `Dislike`, `Ignore`, `Invite`, but no
`Mute`), so a local actor's `Mute` of a remote actor previously could not federate at all.

## Problem

Unlike `Block`/`Flag` (real ActivityStreams types with library classes), an inbound `"type": "Mute"`
deserializes, through the library's `ObjectOrLinkConverter`, to a **plain `Object`** (not an
`Activity`) — the converter only maps known `ObjectTypes.Types` keys to concrete classes, and `Mute` is
not one. Two consequences:

1. **Inbound:** the inbox endpoint deserialized the delivery to a non-`Activity` and 400'd it, so B never
   received the mute (its `MuteActivityHandler` was never dispatched).
2. **Wire round-trip:** even a server-built `MuteActivity` serialized as a **generic object** — the
   library's `ObjectConverter.Write` looks the value up in `ObjectTypes.Types`; an unknown type is written
   via `typeof(object)`, which drops the `@context` (the `@context` property lives on the
   `ObjectOrLink` class, not the `Object` base) and the `type`. A `@context`-less payload cannot be
   re-deserialized, so the 202 body, the A → B federated delivery, and the re-read on an `Undo` all broke.

In short: `Mute` could neither be sent nor received across instances.

## Fix

Make the library model `Mute` as the Iris-specific `MuteActivity`, so the standard serialization +
dispatch pipeline handles it end-to-end:

- `src/Iris.Server/Inbox/MuteActivity.cs` (**new**): a thin `Activity` subclass pinning `Type` to
  `["Mute"]` (per the coding-style rule against re-declaring library types, this is an Iris-specific
  wrapper, Rule 6). It carries the `actor` (muter) and `object` (muted actor) through the inherited
  `Activity` properties and adds no properties of its own.
- `src/Iris.Server/ActivityPubServerExtensions.cs`:
  - In `AddActivityPubServer`, register the wrapper in the library's type registry —
    `ObjectTypes.Types["Mute"] = typeof(MuteActivity)` (idempotent guard). This is the load-bearing
    change: it makes the library (a) serialize a `MuteActivity` **with** its `@context`/`type` (so the
    202 body, the A → B federated delivery, and the re-read on an `Undo` all round-trip) and (b)
    deserialize an inbound `"type": "Mute"` back into a `MuteActivity`.
  - `MuteActivityHandler` is registered as an inbound `IActivityHandler` (exact-type, distance 0 — it does
    not contend with any other handler).
  - Inbox **and** outbox-publish endpoints: a defensive `Mute` wrap. Because the registration makes the
    library deserialize `type:"Mute"` straight into a `MuteActivity` (an `Activity`), the normal
    `payload is Activity` branch already matches; the `WrapAsMuteActivity`/`IsMuteType` path is a
    fallback for a `Mute` that arrives as a generic `Object` (e.g. id-less, or from a peer that does not
    model `Mute`). `WrapAsMuteActivity` reads the `actor`/`object` references from the `Object`'s
    `ExtensionData` (where the converter parks references for an activity type it does not model) and
    builds the `MuteActivity`.
  - Outbox-publish mute arm: `MuteActivity => RecordMuteLocalAsync` records the local `muter → muted`
    edge and returns the muted actor as the delivery recipient (the server delivers it, signed as the
    muter, to the muted actor's inbox on the remote instance).
  - Outbox-publish `Undo` arm: `RemoveMuteLocalAsync` removes the local edge (the inverse).
  - `"mutes"` collection-page invalidation on a `Mute` and on an `Undo` of a `Mute` (the 22.11 C2S
    invariant: the owner's `mutes` card must not stay stale).
- `src/Iris.Server/Inbox/MuteActivityHandler.cs` (**new**): the inbound handler — records the
  `muter → muted` edge in the `IModerationStore` when the **muted** actor is local (the mute arrived in
  the muted actor's inbox, so the muted actor's home instance knows it was muted). Idempotent.
- `src/Iris.Server/Inbox/UndoActivityHandler.cs`: an `Undo(Mute)` branch — `ResolveMuteEdgeAsync` reads
  the stored original `MuteActivity` (by IRI) and `UndoActivityHandler` removes the recorded edge (the
  inverse of `MuteActivityHandler`). A missing/malformed mute is a no-op.

## Where (tests)

- `tests/Iris.Server.Tests/MuteUndoPropagationIntegrationTests.cs` (1 integration test), a 2-instance
  `TestServer` topology (A = `mute-a.domain.local`/`alice`, the muter; B = `mute-b.domain.local`/`bob`,
  the muted actor), mirroring the 22.13/22.14/24.1 wiring. A's outbound delivery routes to B; A's fetcher
  routes by actor-IRI host (alice → A, bob → B); B's fetcher routes to A (to validate the signature of the
  federated Mute/Undo). `Mute_AndUndo_ServerDeliverToRemote_RecordAndRemoveEdge` asserts:
  1. A records its local `alice → bob` mute edge on publish;
  2. B records the edge after A delivers the signed Mute (the cross-instance federation — and B stores the
     `MuteActivity` in its activity store, which the Undo resolution depends on);
  3. A's `Undo(Mute)` removes A's edge;
  4. B's `UndoActivityHandler` resolves the stored `MuteActivity` and removes B's edge (the cross-instance
     half); the forward `mutes` collection agrees on both sides.

## Non-vacuity (proven)

Per the loop's "prove it fails" discipline, the two load-bearing production pieces were each disabled and
restored:

- **The `ObjectTypes.Types["Mute"]` registration** (the wire round-trip): with it disabled, the serialized
  Mute lost its `@context`, so the client could not learn the minted id from the 202 body — the test fails
  at the "A should have returned the minted Mute id" step.
- **The `MuteActivityHandler` registration** (the inbound record on B): with it disabled, B never records
  the edge — the test fails at "B should have recorded the alice → bob mute edge" (the exact cross-instance
  path under test).

Restoring each turns the test green, confirming it genuinely exercises the 24.2 mute/un-mute propagation.
