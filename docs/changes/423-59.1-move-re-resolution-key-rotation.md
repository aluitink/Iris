# 59.1 — `Move` re-resolution + key rotation (F-25)

## Summary

Completes the read-side of F-08 (`Move` handling): after a `Move` activity is processed, Iris now
resolves the old actor's actual key IRI (from the cached actor document) instead of assuming the
`#key-1` fragment convention. It also warms the new actor's document into the `RemoteActorCache`
so subsequent reads of the new IRI are cache hits. Separately, `RemoteInboundKeyResolver` now honors
the `replaces` property on a remote actor's `publicKey`: when a fetched document declares
`publicKey.replaces`, the old key's cache entry is invalidated, ensuring a key rotation on a remote
instance is picked up on the next signature verification.

## Changes

### `IriExtensions.GetPublicKeyIri` (Iris.Core)

New extension method `GetPublicKeyIri(this IObject? actor)` extracts the `publicKey.id` from an
actor's `ExtensionData`. Returns `null` when the actor is null, has no `publicKey`, or the `id` is
missing/empty. This replaces the hard-coded `#key-1` fragment assumption that was used everywhere
the old actor's key IRI was needed.

### `MoveActivityHandler` (Iris.Server)

- New optional 5th constructor parameter: `IActorDocumentFetcher? actorDocuments`. When provided,
  the handler warms the new actor's document into the `RemoteActorCache` after processing the `Move`
  (non-fatal on fetch failure).
- `ResolveOldKeyIri(Iri oldActorIri)`: reads the cached actor document and calls
  `GetPublicKeyIri()` to obtain the actual key IRI. Falls back to `oldActorIri + "#key-1"` when the
  cached document is absent or carries no `publicKey.id`.
- The cache-invalidation block now invalidates the resolved key IRI (not the hard-coded `#key-1`).

### DI registration (`ActivityPubServerExtensions`)

The `MoveActivityHandler` factory now resolves `IActorDocumentFetcher` from DI and passes it as the
5th argument.

### `RemoteInboundKeyResolver` (Iris.Server.Security)

`FetchJwkAsync` now checks the fetched document's `publicKey` for a `replaces` property. When
present and parseable as an IRI, the old key's entry in `RemoteKeyCache` is invalidated. This is the
key-rotation read-side: Iris does not store the old→new mapping, it just ensures the stale entry
doesn't outlive the rotation.
