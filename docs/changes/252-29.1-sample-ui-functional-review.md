# 29.1 — Functional review of every SampleBlazorClient page (proxy query-string fix)

> 2026-09-05 · Slice 29.1 · Phase 29 (sample-UI functional + visual review)

## What was built

Walked every `SampleBlazorClient` page against the running two-instance `docker compose`
stack (`iris-a` on `:8081`, `iris-b` on `:8082`, `iris-ui` on `:8090`), logged on as
`alice@iris-a` (endpoint override `http://localhost:8081`), and verified each page's
actions end-to-end. Found and fixed **one real bug** (the proxy dropped the target IRI's
query string, causing an infinite `next`-link loop on any paginated cross-instance read);
catalogued several UX limitations.

### The bug: proxy dropped the target's query string (infinite feed loop)

**Symptom:** the Community page's feed showed **1080+ items** (only ~31 unique objects,
each repeated dozens of times) and fired a burst of `429` console errors on Load.

**Root cause:** the cross-instance read proxy (`POST /ap/v1/proxy/{target}`) reconstructs the
forwarded request from the `{**target}` catch-all **route value**. ASP.NET Core route values
capture only the **path** of the matched URL — the target's **query string** (e.g.
`?page=2` on a paginated collection) is carried in the proxy request's *own* query string
(`context.Request.QueryString`), which the route value excludes. So the proxy always relayed
**page 1** regardless of the requested page. The client's `GetCollectionAsync` walks `next`
links indefinitely (no page cap); page 1's `next` is `?page=2`, which the proxy dropped and
re-answered as page 1 again → `next` = `?page=2` again → **infinite loop** (1080+ items,
rate-limited by the target policy's 429s).

The **direct** (non-proxied) endpoint was always correct — it reads `?page=N` from its own
request. Only the proxied path (used when the browser dials a different host than the
advertised IRI, i.e. the local Docker setup) was broken.

**Fix:** in `ProxyHandler` (`src/Iris.Server/ActivityPubServerExtensions.cs`), reconstruct the
full target IRI by appending `context.Request.QueryString` to the route value before
`Iri.TryParse`:

```csharp
var fullTarget = context.Request.QueryString.HasValue
    ? targetValue + context.Request.QueryString.Value
    : targetValue;
if (!Iri.TryParse(fullTarget, out var target)) { ... }
```

The fragment is never sent by a client (browsers strip it), so only the query string needs
re-attaching. After the fix, the proxy relays `?page=2` correctly: page 1 = 20 items
(`next=?page=2`), page 2 = 11 items (`next=null`) — the loop terminates. Verified live: the
Community feed now shows the correct count (~31 items) with **zero** console errors.

The other three `{**target}` handlers (person mute, relay, community mute) were inspected and
need no change: their query params (`?unmute=true`, `?unsubscribe=true`) are control flags read
directly from `context.Request.Query`, and their target IRIs (actor/relay IRIs) carry no query.

### Known UX limitations (catalogued, not fixed this slice)

1. **Session persistence gap:** `ExplorerSession` is purely in-memory — a full page reload /
   direct URL entry / F5 wipes the login (must re-login). In-app nav (Blazor router links)
   preserves it. The only `localStorage` mention is a doc comment about a future follow-up
   (`OAuth2BrowserFlow.cs:27`).
2. **Pre-filled public handle:** the login form pre-fills `alice@iris.luit.ink` (the public
   handle), which does NOT work locally (requires the Advanced endpoint override to dial
   `localhost:8081`). A local operator must change both fields.
3. **Missing favicon:** `wwwroot/` has no `favicon.ico` → 404 console error on every load.
4. **Transient empty-state flash:** the Feed shows "No followed items yet" before the first
   fetch resolves (no loading indicator).
5. **Unlike learned-id limitation** (Decision 055): the UI can only undo a write this session
   made; pre-existing likes cannot be un-liked from the UI.
6. **Advertised-IRI vs dial-base mismatch:** WebFinger resolves actors to the advertised host
   (`iris-dev1.luit.ink`), while the browser dials `localhost:8081`. Cross-instance reads
   route through the proxy (now fixed for pagination); cross-instance *writes* to a remote
   host use the advertised IRI (the proxy re-signs and forwards).

## Tests

**New regression test** `ProxyFallbackIntegrationTests.Proxy_PaginatedGet_ForwardsTargetQueryString_RelaysRequestedPage`
(1 test, 2-instance `TestServer`): seeds 21 activities on bob's outbox (default page size 20 →
2 pages), proxies a `GET` to **page 2** of bob's outbox, and asserts the relaid document is
page 2 (an `OrderedCollectionPage` with `startIndex` 21, holding the single oldest activity)
rather than page 1 (an `OrderedCollection`, the newest 20). A proxy that drops the query string
relays page 1 and the test fails. The `ProxyGetAsync` helper gained an optional `query` parameter
so the target's query string can ride on the proxy request's own query string (the exact shape the
bug depended on). Non-vacuous: reverting the `ProxyHandler` fix makes the test fail
(`OrderedCollection` / page 1 instead of `OrderedCollectionPage` / page 2).

This closes the gap the change doc originally noted ("No new test file"): the existing proxy tests
only drove targets **without** a query string, so they could not catch the query-drop. The live
browser test was what surfaced the bug; the new test now locks it.

Build clean (`dotnet build`, 0 warnings 0 errors); full `Iris.Server` test run green (899 of 899
in the fast run, the new test included).

## Decisions

- **Fix in `ProxyHandler` (server), not the client:** the client correctly sends the full
  target IRI (path + query) as the proxy URL; the server's route-value read was the defect.
  Fixing the server means every client (current + future) benefits, and the direct path was
  already correct.
- **Append the query string, don't re-encode the whole IRI:** the route value is the URL-
  decoded path; appending the raw query string (which starts with `?`) yields the correct
  absolute IRI. Re-encoding would risk double-escaping.
- **No page cap added to the client's `GetCollectionAsync`:** the loop was a *server* defect
  (a malformed `next`), not a client defect. A cap would mask a real server bug. (A defensive
  cap could still be added later, but is not required for correctness once the server is
  fixed.)
