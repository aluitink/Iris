# 189 — Phase 22.4: cross-server manual verification (US-2, US-24) + local compose instance map

## Summary

Closes **Phase 22.4 (cross-server polish)** on the **multi-server identity/switching (US-2, US-24)**
half by **manually verifying** the existing surfaces on a real two-instance compose stack, per the
Phase 22 method (UI work is verified with Playwright MCP, not bUnit). No UI-feature code changed — the
recent-instances one-click switch, the current-instance marker, the identity bar, and the "Continue
where you left off" cross-instance navigable all already exist and worked. The **one code change** is a
sample-config addition: the `InstanceBaseUrls` map now maps the local compose stack's advertised hosts
(`iris-dev1.luit.ink` → `http://localhost:8081`, `iris-dev2.luit.ink` → `http://localhost:8082`) so a
logon by the advertised handle dials the right host-published port. This makes the local two-instance
stack log-on-able in the browser (the `InstanceBaseUrls` surface, when it knows a host, **overrides**
the entered base URL — so the map must contain each advertised host).

## What changed (code)

- **`samples/SampleBlazorClient/Program.cs`** — the `InstanceBaseUrls` map gained two entries:
  `iris-dev1.luit.ink` → `http://localhost:8081` and `iris-dev2.luit.ink` → `http://localhost:8082`
  (the local compose stack advertises iris-a as iris-dev1 and iris-b as iris-dev2 per `.env`). A logon
  by the advertised handle (e.g. `alice@iris-dev2.luit.ink`) now dials `localhost:8082`. No
  client/server seam changed; no new package.

## Manual verification (Playwright MCP, local compose stack)

The local two-instance compose stack was booted (`docker compose up -d`; iris-a on 8081, iris-b on
8082, iris-ui on 8090; internal service names, FQDN IRIs per `.env`). The browser (on the host) dials
the host-published ports; both servers are same-origin (`localhost`), so a cross-instance read routes
through the home proxy (change 188).

- **US-8 (cross-instance reads via the proxy):** logged on to **iris-b** (dial base 8082), then loaded
  an **iris-a** note (`https://iris-dev1.luit.ink/ap/v1/u/bob/notes/2`) on the Object page. It **loaded
  and rendered** (content, reply context, Like/Boost, raw inspector) **without a CORS block** — the
  cross-host GET was relayed through iris-b's home proxy. The "View on originating instance" external
  link (US-7) was present.
- **US-2 (multi-server identity/switching):**
  - **Recent-instances list + one-click switch.** Both instances appeared in the "Recent instances"
    card. Selecting iris-a ("Use") revealed a password field + "Switch"; clicking Switch **logged out of
    iris-b and logged on to iris-a** in one action (the identity bar updated to
    `https://iris-dev1.luit.ink/ap/v1/u/alice`, dialing 8081; the recents reordered with iris-a first
    and marked current; the community feed reloaded to iris-a's items).
  - **Current-instance marker.** The Instance page's recent-instances list marked the active instance
    with "(current)" instead of a switch button.
  - **"Continue where you left off" (cross-instance navigable, 19.8.5).** After viewing an iris-a note
    while on iris-b, the Home page's "Continue where you left off" card surfaced the iris-a note;
    clicking it deep-linked to it on the current instance and it loaded (via the proxy). The navigable
    **survived an instance switch** (it was still present after switching iris-b → iris-a).
- **US-3 (identity bar):** the MainLayout bar showed the resolved actor IRI + dial base and updated on
  switch.

**Result:** US-2, US-3, US-7, US-8 all confirmed on the wire and in the UI. Build clean, format clean,
full solution green.

## Decision

**Verify the multi-server surfaces on the local compose stack (host-published ports) rather than the
external FQDN reverse proxy.** The external `iris-dev1/2.luit.ink` reverse proxy is unreachable in this
environment, but the local compose stack exercises the **same** cross-instance read path (a different
host's IRI routed through the home proxy) and the same switching/navigation surfaces, so the US-2/US-24
behavior is fully proven. The external-FQDN (reverse-proxy) pass is folded into the Phase 22.6 manual
test pass. The `InstanceBaseUrls` addition is sample config (the map is the documented "advertised host
→ browser base URL" surface, SAMPLE_PLAN §4.4), not a behavior change.
