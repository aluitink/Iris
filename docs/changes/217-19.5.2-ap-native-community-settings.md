# Change 217 — AP-native community settings (manuallyApprovesMembers)

**Phase:** 19.5.2 (membership management)
**Commit:** 012578b

## Summary

The community's `manuallyApprovesMembers` flag can now be set or cleared by the community
publishing an `Add` (enable) or `Remove` (disable) of its own document to its outbox, rather
than being seeded only programmatically in tests. This is the AP-native settings change: the
flag becomes state derived from the community's outbox, just like follow edges and membership.

## Design decision

**Option chosen: `Add`/`Remove` of the community document (Option A).**

The community publishes an `Add` (enable) or `Remove` (disable) whose `object` is the
community's own document carrying the `manuallyApprovesMembers` extension in `ExtensionData`.
This is consistent with the existing `Add`/`Remove` membership pattern (where `object` is the
member being added to/removed from the community) — but here the "collection" is the
community's own settings.

**Why not Option B (`Update` activity)?** `Update` is the AS2 activity for "this object
changed," but the codebase already has `Add`/`Remove` handlers for community outbox activities.
Reusing them means the settings change flows through the exact same code path as membership
self-management — no new activity type handler needed.

**Why not a `/settings` endpoint?** A local-only write for a community setting would break the
AP-native protocol surface. The community's outbox is the source of truth for community state;
a `/settings` endpoint would create a second, non-federated write path for the same state.

## Server changes

- `RecordCommunityAddAsync` / `RecordCommunityRemoveAsync` in
  `ActivityPubServerExtensions.cs` now detect when the `object` is the community's own document
  (object IRI == community IRI) and the `ExtensionData` carries the
  `manuallyApprovesMembers` key. In that case, they call `SetManuallyApprovesMembersAsync`
  instead of adding/removing a member.
- New `SetManuallyApprovesMembersAsync` helper performs the read-modify-write on the
  community's `ExtensionData` (set/clear the flag, then `PutCommunityAsync`).

## Client changes

- New `IActivityPubClient.SetManuallyApprovesMembersAsync(communityIri, enabled, ct)` method.
  Builds an `Add` (enable) or `Remove` (disable) with the community's own document as the
  `object` (carrying the flag in `ExtensionData`) and publishes to the community's outbox.

## UI changes (Community.razor)

- New "Settings" card showing the current gating state ("Yes (gated)" / "No (open)") with
  "Require approval" and "Open (auto-approve)" buttons.
- `IsGated` computed property reads the flag from the community document's `ExtensionData`.
- After a successful toggle, the community document is re-fetched so the indicator updates.

## Tests (4 new integration tests)

| Test | Verifies |
|---|---|
| `Add_CommunityDocument_WithManuallyApprovesMembers_SetsFlag` | An `Add` of the community document sets the flag on the stored community; the `Add` is in the outbox |
| `Remove_CommunityDocument_WithManuallyApprovesMembers_ClearsFlag` | A `Remove` of the community document clears the flag; the `Remove` is in the outbox |
| `Settings_ClearFlag_ThenJoin_AutoGrantsMembership` | After clearing the flag, a `Join` auto-grants membership (no pending request) |
| `Settings_SetFlag_ThenJoin_RecordsPendingRequest` | After setting the flag, a `Join` records a pending request (no membership) |

**Test count:** 1,310 → 1,314 (Server: 819 → 823).

`Iris.Server.Tests` now implement the new `SetManuallyApprovesMembersAsync` method (returning a
202 `DeliveryResult`).
