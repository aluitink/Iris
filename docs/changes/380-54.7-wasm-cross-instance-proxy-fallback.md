# 54.7 — WASM cross-instance GET proxy fallback wired up

Phase 54 slice. The client-side cross-instance-read proxy fallback (added in
Phase 6 for the federation path, `RouteCrossInstanceReadsViaProxy` +
`DialBaseUri` + `ProxyFallbackHandler`) existed in the `Iris.Client` library
but was **never wired up in the Blazor WebAssembly app** — and the server's
proxy endpoint only accepted **Basic auth**, which a browser cannot provide
(it has no credentials; it authenticates by the site cookie). Result: the WASM
app could not load **any** remote actor/object — a direct cross-origin `GET`
is CORS-blocked (a network failure with no status code, so the 401/403
fallback never engages), and the proxy path was unreachable (no Basic
credentials to send).

## The problem

A browser cannot make a signed, cross-origin ActivityPub `GET` to a remote
instance. Two blockers made the existing proxy fallback useless for the WASM
app:

1. **No credentials to send.** The `ProxyFallbackHandler` built a `POST` to the
   home proxy carrying an `Authorization: Basic …` header. A browser has no
   Basic credentials — the user's password is not (and must not be) handed to
   the WASM app. The only credential the browser *does* have for its own
   origin is the **site cookie** (set at login, `SameSite=Strict`, carrying the
   `actor_iri` claim).
2. **The proxy endpoint rejected cookie auth.** `POST /ap/v1/proxy/{target}`
   identified the actor **only** via Basic auth (`IActorCredentialValidator`).
   A request with no `Authorization` header (the WASM case) → 401.
3. **The WASM client never set the proxy options.** `IActorSessionAccessor`
   built `ActivityPubClientOptions` with only `ActorId` set — no
   `ProxyBaseUrl`, no `DialBaseUri`, no `RouteCrossInstanceReadsViaProxy`. So
   the `ProxyFallbackHandler` was never even in the WASM pipeline.
4. **Target-IRI encoding mismatch.** The `ProxyFallbackHandler` sends the
   target percent-encoded in the path (`Uri.EscapeDataString(target)`, e.g.
   `https%3A%2F%2Fremote%2F%40alice`). Kestrel does **not** decode `%2F` in a
   path (a `/` is a path separator), so the `{**target}` catch-all route value
   stayed encoded, `Iri.TryParse` produced a *relative* IRI, and the target
   policy rejected it (403 "must be absolute http(s) IRIs"). The integration
   tests sent the target **unencoded** (literal slashes), so they never hit
   this.

## Fix

### 1. Proxy endpoint: cookie-auth fallback (`ActivityPubServerExtensions`)

`ProxyHandler` now identifies the actor by **Basic auth OR the site cookie**,
mirroring the owner-only mute/media pattern: after `AuthenticateAsync`, if the
Basic path found no handle but the request is cookie-authenticated, it reads
the `actor_iri` claim, validates it is a **local** actor (`{base}/ap/v1/u/…`),
and uses that handle. A cookie from a non-local actor IRI is rejected (401) —
the proxy may only act as a local actor. Basic auth still takes precedence and
is unchanged for the federation path.

### 2. `ProxyFallbackHandler`: optional credentials (cookie-auth mode)

`ProxyCredentials` is now **nullable** on all three constructors. When
`null`, `SendViaProxyAsync` sends **no** `Authorization` header — the
same-origin proxy request carries the site cookie automatically (the browser
attaches it to its own origin). When set (the Basic-auth federation path), the
header is sent as before. The XML docs document both modes.

### 3. `ActivityPubClientFactory`: wire the handler for cookie-auth reads

The handler is wired when **either**:
- `ProxyBaseUrl` + `ProxyCredentials` are set (Basic auth: a 401/403 fallback
  or always-proxy writes), **or**
- `ProxyBaseUrl` is set, `ProxyCredentials` is `null`, and
  `RouteCrossInstanceReadsViaProxy` is `true` (cookie-auth cross-instance
  reads — the WASM path).

### 4. `IActorSessionAccessor`: enable the fallback on the WASM client

`BuildClientOptions` sets, on the signed ActivityPub client's options:
- `ProxyBaseUrl` = the home instance's canonical base — the advertised FQDN
  when set, else the browser origin.
- `DialBaseUri` = the same base (the host a `GET` must differ from to be a
  cross-instance read). Local actor IRIs use this host, so a local read dials
  directly; a remote read's host differs → it goes straight through the proxy.
- `RouteCrossInstanceReadsViaProxy = true`.
- `ProxyCredentials = null` (cookie-auth — the browser has no credentials).

### 5. Proxy target decoding (`ActivityPubServerExtensions`)

`ProxyHandler` now `Uri.UnescapeDataString`s the `{**target}` route value
before parsing. This decodes the percent-encoded form the WASM client sends
and is a **no-op** on the already-decoded form the integration tests send (no
`%` sequences) — so both encodings work. Without it, the encoded target
parses as a relative IRI and is rejected 403.

## Verification

- **Build clean** (0 warnings, `TreatWarningsAsErrors` on), full `dotnet test`
  green (968 `Iris.Server.Tests` + all other suites; the 2 known
  parallel-load integration flakes pass in isolation).
- **Proxy back-compat:** all 15 `ProxyFallbackIntegrationTests` pass — the
  decode fix and the cookie-auth branch do not change the Basic-auth path.
- **Live (Playwright, real remote instance):** signed in as `alice`, navigated
  to `/actor?iri=https://mastodon.social/@admin`. The WASM client routed
  **every** cross-instance read through the same-origin proxy — no direct
  cross-origin `GET` was ever made (which would CORS-fail):
  - `POST /ap/v1/proxy/https://mastodon.social/@admin` → **200** (actor doc)
  - `POST /ap/v1/proxy/https://mastodon.social/@admin/followers` → **200**
  - `POST /ap/v1/proxy/https://mastodon.social/users/admin/followers?page=1`
    → **200** (paginated — the target's query string rides on the proxy
    request's own query string, exactly as designed)
  - `POST /ap/v1/proxy/https://mastodon.social/@admin/following` → **200**
  - `POST /ap/v1/proxy/https://mastodon.social/users/admin/following?page=1`
    → **200**
  - `POST /ap/v1/proxy/https://mastodon.social/@admin/outbox` → **404**
    (faithful relay — mastodon's admin outbox genuinely 404s; the page renders
    "No posts yet")
  - The profile rendered fully: the remote actor's name, Follow/Block/Mute/
    Report actions, and **real follower/following counts (59 / 21)** fetched
    through the proxy.
- **Cookie-auth proof (curl):** the proxy endpoint returns **401** with no
  cookie, **200/relay** with the login cookie (both the encoded WASM-client
  form and the unencoded test form). The session endpoint returns the signed-in
  actor for the same cookie.

## Notes

- The proxy **re-signs** the forwarded request as the acting local actor (the
  existing `X-Iris-Actor` override); the proxy request's own path encoding is
  irrelevant to the remote's signature validation (the remote validates the
  re-signed `request-target` of the actual GET, not the proxy path).
- This is Phase 45+ (WASM manual-test phase): no new coded tests; verification
  is the live Playwright pass above against the running instance.
- The proxy target policy (allowlist + rate limit) is unchanged — an empty
  allowlist allows all hosts; the default rate limit (60/min) still applies.
