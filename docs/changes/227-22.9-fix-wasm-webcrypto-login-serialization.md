# 22.9 — Fix the WASM browser login `Task`-serialization regression

**Slice:** Phase 22 closeout item #1 (Up Next) — fix finding **A** from the final manual UI
verification pass (change 226).
**Status:** done. Build clean (0 warnings / 0 errors); **1,360 tests pass** (up from 1,357 — 3 new
`Iris.WebCrypto.Tests`).

## The bug

Logging on to an ActivityPub instance from the Blazor WebAssembly explorer threw:

```
SerializeTypeInstanceNotSupported, System.IntPtr  Path: $.WaitHandle.Handle.
```

WebFinger resolution and the Basic-auth owner-only actor document both fetched fine (both returned
200); the crash happened **after** the actor document was fetched, while the browser WebCrypto path
imported the private key.

### Root cause

`WebCryptoBridgeBootstrap.InjectCoreAsync` (in `src/Iris.WebCrypto/WebCryptoSigningKey.cs`) called:

```csharp
await js.InvokeAsync<bool>("webcryptoSignBootstrap.install", source, ct);
```

`IJSRuntime.InvokeAsync<T>` has exactly two overloads:

1. `ValueTask<T> InvokeAsync<T>(string identifier, object?[]? args)`
2. `ValueTask<T> InvokeAsync<T>(string identifier, CancellationToken ct, object?[]? args)`

Because `source` is a `string` (not a `CancellationToken`), the call bound to **overload 1**, boxing
both `source` **and** `ct` into the `object?[]` argument array. Blazor's JS-interop layer marshals every
element of that array to JS by running it through `System.Text.Json`. `System.Text.Json` then walked
`CancellationToken`:

```
CancellationToken
  └─ .WaitHandle : System.Threading.WaitHandle
       └─ .Handle : System.IntPtr   →  SerializeTypeInstanceNotSupported, Path: $.WaitHandle.Handle
```

`CancellationToken` is *not* JSON-serializable (its `WaitHandle.Handle` is an `IntPtr`). The error
path is identical to what a `Task` would produce (`Task` also exposes `WaitHandle.Handle`), which is why
change 226 initially guessed "a `Task` is being serialized" — the real root type is
`CancellationToken`.

**Why it was missed:** the in-process explorer / client tests use the **BCL / BouncyCastle** key loader
(no `IJSRuntime` in a test host), so they never exercise the browser-only `Iris.WebCrypto` key-import
path. That path had **zero** test coverage.

## The fix

Reorder the call so `ct` binds to the dedicated `CancellationToken` overload — never into the JSON
args:

```csharp
await js.InvokeAsync<bool>("webcryptoSignBootstrap.install", ct, [source]);
```

This is the only `IJSRuntime.InvokeAsync` call in the whole `src` tree that passed a
`CancellationToken` as a JSON argument; the other WebCrypto interop calls (`importPrivateKey`,
`sign`, `verify`, `free`) pass only `int`/`string` args and are unaffected.

## Tests (first coverage of the browser-only path)

A new test project, **`tests/Iris.WebCrypto.Tests`**, now exists — it is the first to reference
`Iris.WebCrypto` and the first to exercise the browser key-import path in-process.

- **`FakeJsRuntime`** — an in-process `IJSRuntime` that records every interop call and, critically,
  **JSON-serializes each non-null argument** (via `JsonSerializer.SerializeToElement`) exactly the way
  Blazor's JS-interop layer does. So any non-serializable element (e.g. a `CancellationToken`) throws
  `JsonException` / `SerializeTypeInstanceNotSupported` here — reproducing in-process the exact failure
  the browser path used to throw.
- **`WebCryptoSigningKeyJsInteropTests.CreateAsync_InstallBootstrap_DoesNotPassCancellationTokenAsJsonArgument`**
  — the core regression test. Asserts the `webcryptoSignBootstrap.install` call carries **only** the
  bridge source string (no `CancellationToken`) and that `importPrivateKey` received the PEM. **Verified
  to fail with the `SerializeTypeInstanceNotSupported` signature when the fix is reverted**, so it
  genuinely guards the regression.
- **`..._CreateAsync_SignsUsingWebCrypto_DoesNotPassCancellationTokenAsJsonArgument`** — asserts the
  sign path leaks no `CancellationToken` into any interop arg.
- **`..._CreateAsync_BridgeNotLoaded_ThrowsClearSetupError`** — with a `MissingBridgeJsRuntime`
  (a fake that throws `JSException` "not a function"), asserts the bootstrap surfaces the clear
  "add `<script src=\"js/WebCrypto.js\">`" setup error.

### Testability seam

`WebCryptoBridgeBootstrap._injected` is a process-global static that caches the injection. To let each
test start from a clean state, `src/Iris.WebCrypto` now:

- declares `[assembly: InternalsVisibleTo("Iris.WebCrypto.Tests")]` (new `AssemblyInfo.cs`), and
- exposes an `internal static void WebCryptoBridgeBootstrap.ResetForTesting()` that clears the cache.

This is the first `InternalsVisibleTo` in the repo (no other project needed it); it's a standard,
minimal testability seam, kept internal so the public API is unchanged.

## Decision

- **No new NuGet packages.** `Microsoft.JSInterop` is already a dependency of `Iris.WebCrypto` and
  comes transitively to the test project via the `ProjectReference`. The new test project uses only the
  standard xUnit stack (`xunit`, `xunit.runner.visualstudio`, `Microsoft.NET.Test.Sdk`,
  `coverlet.collector`) at the centrally-managed versions.
- **Fake `IJSRuntime` over a live browser.** A headless-browser test would be higher fidelity but is far
  heavier to maintain and to run in CI; the fake reproduces the *exact* failure mode (JSON
  serialization of the arg array) at the precise boundary where the bug lived, which is the unit
  boundary the regression lives on. The browser path is additionally covered end-to-end by the manual UI
  verification pass (change 226). This matches the repo's integration-first principle while keeping the
  test fast and deterministic.
