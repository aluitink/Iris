# 175 — Phase 19.5.4: community UI — Moderation card on the Community page

## Summary

The Community page now has a **"Moderation"** card, mirroring the person `ActorDetail` page's Moderation
card. It offers **Mute/Unmute**, **Block/Unblock**, and **Flag/Unflag** buttons that act as the community
(the community signs with the primary actor's key in the sample deployment).

- **Mute/Unmute:** local, Basic-authenticated decisions (no federation) via
  `Session.GetLocalModerationClient().MuteAsync(communityIri, target)` — the client's
  `BuildLocalRequestUri` already handles the `/c/` segment (the community mute endpoint is
  `POST /local/v1/c/{name}/mutes/{target}`).
- **Block/Unblock, Flag/Unflag:** signed writes to the community's own outbox via
  `Session.GetClient().BlockAsync`/`FlagAsync` (the instance records the edge and federates to the
  target's inbox). Decision 055: the learned id of a created block/flag is captured for a later undo.

This closes the 19.5.4 "community UI moderation screen" gap. The underlying server endpoint
(`POST /ap/v1/c/{name}/mutes/{target}`) + the client methods (`MuteAsync`/`BlockAsync`/`FlagAsync`) were
already proven in change 153; this slice wires the UI surface.

## What changed (code)

- **`samples/SampleBlazorClient/Pages/Community.razor`**
  - **Markup:** a new "Moderation" card (between the "Inbound follows" and "Follow / unfollow" cards).
    It has a target-IRI input and six buttons (Mute/Unmute/Block/Unblock/Flag/Unflag) plus a status/error
    display.
  - **State:** `ModTargetInput`, `ModBusy`, `ModResult` (`string?`), `ModError`, `ModBlockLearnedId`,
    `ModFlagLearnedId`.
  - **`ModDecisionAsync(bool isAdd, ModKind kind)`:** the single method that dispatches on the kind
    (Mute/Block/Flag) and the direction (add/remove). Mute uses the local moderation client; Block/Flag
    use the signed client. Decision 055: the learned id of a created block/flag is captured for a later
    undo; on a successful undo the learned id is cleared.

## Key types / API

- `Session.GetLocalModerationClient().MuteAsync(communityIri, target)` / `UnmuteAsync` — the local,
  Basic-authenticated community mute (the client's `BuildLocalRequestUri` handles the `/c/` segment).
- `Session.GetClient().BlockAsync(communityIri, target)` / `UnblockAsync(communityIri, learnedId)` —
  the federated community block (signed write to the community's outbox).
- `Session.GetClient().FlagAsync(communityIri, target)` / `UnflagAsync(communityIri, learnedId)` —
  the federated community flag (signed write to the community's outbox).

## Decision: why the community moderation card mirrors the person card

The person `ActorDetail` page's Moderation card is the proven pattern: a target input + six buttons
(Mute/Unmute/Block/Unblock/Flag/Unflag) + a status/error display. The community is the same shape (a
`Group` actor that can mute/block/flag a target actor), so the card mirrors the person card exactly. The
only difference is the actor: the person card acts as the logged-on actor; the community card acts as the
community (the community's IRI as the actor). No new server endpoint or client method was needed; the
slice is purely the UI wiring.

## Direction note: sample-client UI is manual-tested (not bUnit-tested)

Per the current direction, the sample-client UI is **in flux and subject to a lot of change** once core
stuff is worked out. Rather than invest in bUnit tests for the sample UI (which would need to track every
UI change), the sample UI is **verified manually** (drive the screens through the browser). This change
follows that direction: the "Moderation" card is wired and builds clean, but has no bUnit test. The
underlying wire (the community mute endpoint + the client's moderation methods) is proven by the existing
server/client integration tests.

## Scope / limits

- The **live/UI-verification half** of 19.5.4 (drive the community moderation through the browser — log
  on, mute/block/flag a target, confirm the edge effect) remains a live-verification item. The code (the
  card + the client calls + the server endpoint) is in and builds clean.
- The **two-instance wire drive** of a signed `Block`/`Flag` addressed to a community (the federated
  half reuses the existing `Block`/`Flag` inbox-handler path, proven for the person level) is a
  live-interop item (needs the external two-instance infra).
