# 281 — 31.8: derive the `iris:` extension namespace from the public base URI + host the namespace document

> 2026-09-05 · Slice 31.8 · Phase 31 (explorer UI & server namespace polish)

## What was built

Every public actor/community document the server emits declares the `iris:`
extension terms (the `feed` / `blocks` / `flags` / `mutes` / `search` / `star`
collection endpoints and the `capabilities` / `settings` / `searchQuery`
extensions) under a JSON-LD namespace. Until now that namespace was a **fixed,
unresolvable IRI** — `https://iris.example/ns#` — regardless of the deployment's
public base URI. A JSON-LD processor resolving the `@vocab` it was given found
nothing at `https://iris.example/ns` (the document was never hosted), so the
`iris:` vocabulary was a dangling IRI.

The 31.8 report asked for two things:

1. **Derive the `iris:` extension namespace from the server's public (advertised)
   base URI** — so a deployment at `https://foo.example` advertises
   `https://foo.example/ns#`, not a foreign `iris.example` IRI.
2. **Actually host the namespace document** (the JSON-LD context at that IRI) so
   the advertised `@vocab` is resolvable.

Both are now in place.

## Key types & files

- `src/Iris.Server/ActivityPubServerConstants.cs`
  - New `public const string NamespaceRouteSegment = "ns"` — the single source of
    truth for the namespace-document route (the route, the derived namespace base,
    and the tests all use it).
- `src/Iris.Server/ActivityPubServerExtensions.cs`
  - `IrisExtensionNamespace(ActivityPubServerOptions)` — rewritten. When
    `NamespaceIri` is **set** it is used verbatim (an operator can pin a shared
    cross-instance vocabulary). When it is **unset**, the namespace is **derived**
    from `BaseUri` as `{BaseUri}/ns#`. When `BaseUri` is *also* unset it falls
    back to the canonical `https://iris.example/ns#` (the out-of-the-box default).
  - `BuildNamespaceDocument(ActivityPubServerOptions)` — **new**. Builds the JSON-LD
    `@context` document: the core ActivityStreams `@vocab` plus the `iris:`
    namespace object (keyed by its base, `#` stripped) mapping every extension
    term to its range (the collection endpoints and IRI extensions → `@id`, the
    search query → `string`). The top level is a `Dictionary<string, object>`
    because a C# anonymous member named `@context` would serialize as `context`
    (the `@` escape is stripped), not the literal `@context` a JSON-LD processor
    expects.
  - `NamespaceDocumentHandler(...)` — **new**. Serves the document at the
    namespace base with a long `Cache-Control` (`max-age=86400,
    stale-while-revalidate=604800`) and `application/ld+json`.
  - The route is registered on the **root** `IEndpointRouteBuilder` (not the
    `/ap/v1` versioned group) as `GET /ns`: the namespace base is
    `{BaseUri}/ns#`, so the document is served at `{BaseUri}/ns` (the host root,
    not under `/ap/v1`). The fragment is dropped when served.
- `samples/SampleServer/Program.cs`
  - `NamespaceIri` is no longer a hardcoded `readonly Iri("https://iris.example/ns#")`.
    A new `internal static string ResolveBaseString()` reads the same `Iris:*`
    environment values the host already uses (`Iris:HostName` / `Iris:Port` /
    `Iris:Https`, with `Iris:Advertise*` fallbacks) and returns the slash-free
    `scheme://host:port` base. `NamespaceIri` is computed as
    `{ResolveBaseString()}/ns#`, and the advertised `InstanceName` hostname is
    derived from the same base string — so the namespace, the public base URI, and
    the advertised hostname all agree for a single deployment.
- `tests/Iris.Testing/ActivityPubHostFactory.cs` + `ActivityPubHostOptions`
  - New `bool PinDefaultNamespace` option (default `true`). When true the test
    host pins the canonical out-of-the-box namespace
    (`https://iris.example/ns#`) so the many existing integration tests that assert
    against a **known** namespace stay stable. When false the host leaves
    `NamespaceIri` unset, exercising the production **derived** path.
- `tests/Iris.Server.Tests/NamespaceDocumentIntegrationTests.cs` — **new**, 5 tests
  (see Tests).
- `tests/Iris.Server.Tests/IrisSettingsExtensionIntegrationTests.cs` — its
  hand-built `WebHostBuilder` now pins the default namespace (it asserts against
  `https://iris.example/ns#` directly).
- `tests/SampleServer.Tests/SampleServerTests.cs` — the community feed-key
  assertion now expects the **derived** namespace
  (`{BaseUri}/ns#{feed}`), since the sample derives rather than pins.

## Tests

5 new integration tests in `NamespaceDocumentIntegrationTests` (run with
`PinDefaultNamespace = false` so they exercise the derived path):

- `NamespaceIsDerivedFromPublicBaseUri_WhenNotConfigured` — with `NamespaceIri`
  unset, a public actor document's `@context[1].@vocab` is `https://{host}/ns#`
  (derived from the base URI), **not** `iris.example`.
- `NamespaceDocument_IsServedAtNamespaceBase` — `GET /ns` returns 200 and the body
  is a JSON-LD `@context` with the core AS `@vocab`, the `iris:` namespace object
  (keyed by the base, `#` stripped, `@id` = base + `#`), and the extension terms
  mapped to their ranges (`feed`/`settings` → `@id`, `searchQuery` → `string`).
- `NamespaceDocument_HasJsonLdContentTypeAndCacheHeaders` — the response is
  `application/ld+json` with the long `Cache-Control`.
- `ActorDocVocab_ResolvesToHostedNamespaceDocument` — the `@vocab` declared in a
  public actor document fetches 200 at the namespace base (the advertised `@vocab`
  is resolvable, not dangling).
- `ExplicitlyConfiguredNamespaceIri_IsUsedVerbatim` — a deployment that pins an
  explicit `NamespaceIri` keeps it (the derivation does not override it).

The full fast suite is green and grew by 5 (**1451/1451**): the 27 existing
`iris:`-namespace integration tests (which assert against a known namespace) stay
green via the test factory's `PinDefaultNamespace = true` default; the sample's
33 tests pass with the derived namespace end-to-end.

## Design notes

- **Derivation is the default; pinning is the escape hatch.** A single
  deployment's public base URI is the natural home for its extension vocabulary,
  so the derived `{BaseUri}/ns#` is the out-of-the-box behavior. An operator who
  wants a shared, cross-instance vocabulary (e.g. a canonical `iris:` namespace
  shared by many instances) sets `NamespaceIri` explicitly, which is honored
  verbatim and never overridden by the derivation.
- **The route is at the host root, not under `/ap/v1`.** The namespace base is
  `{BaseUri}/ns#` — the host root, not the versioned API prefix. The JSON-LD
  document is therefore served at `{BaseUri}/ns`, registered on the root
  `IEndpointRouteBuilder` (the same root level the pre-existing
  `/.well-known/webfinger` route lives at), not on the `/ap/v1` versioned group.
  (Registering it on the group would serve it at `/ap/v1/ns`, the wrong base.)
- **The top-level `@context` key is built with a `Dictionary`, not an anonymous
  type.** A C# anonymous member written `@context` serializes as the JSON key
  `context` (the `@` is just an identifier escape and is stripped), which a
  JSON-LD processor does not recognize. The document is therefore assembled as a
  `Dictionary<string, object>` whose key is the literal `@context`.
- **The test host pins the canonical namespace by default.** Rather than
  rewriting the ~27 existing integration tests (across 14 files) to assert a
  per-host derived namespace, the shared test host pins
  `https://iris.example/ns#` (the known, stable value those tests already
  assert). The **derived** path — the actual 31.8 contract — is covered by
  `NamespaceDocumentIntegrationTests` (`PinDefaultNamespace = false`) and by the
  `SampleServer` (which derives end-to-end). This keeps the existing suite stable
  while the new behavior is still fully exercised.
- No new NuGet packages; no client-library changes; no CSS changes.
