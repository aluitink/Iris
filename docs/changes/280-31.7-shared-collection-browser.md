# 280 — 31.7: shared collection browser

> 2026-09-05 · Slice 31.7 · Phase 31 (explorer UI & server namespace polish)

## What was built

The explorer rendered ordered collections in three ad-hoc ways at once: the
`PagedCollection` component (page-walking + an optional item template, defaulting
to a bare `<ObjectView>`), a **hand-rolled paged follower/following list** in
`ActorDetail` (~200 lines of duplicated state + `LoadInitial`/`LoadMore`/
`Enumerate` methods), and a handful of one-shot `<ul class="object-list">`
enumerations. The 31.7 report asked for **a single shared component that walks
the pages of an ordered collection and renders each item extensibly** — a
per-collection-type "template", falling back to basic object rendering when none
is registered — and to reuse it for inbox / outbox / feed / liked / followers /
following (and the moderation collections) instead of the ad-hoc paths.

The new shared component is `Components/CollectionBrowser.razor`. It is
`PagedCollection`'s page-walking engine plus the extensibility the report asked
for:

- **`ItemTemplate`** (`RenderFragment<IObjectOrLink>?`) — a registered
  per-collection-type renderer (e.g. the actor-link template for followers /
  mutes / blocks / flags, the inbox-activity template, the outbox/liked
  `<ObjectView>` template).
- **Built-in basic fallback** — when no template is registered, each item renders
  via the built-in `BasicItemTemplate`: an actor becomes a link to its detail
  page (the short handle) plus a muted type label, a non-actor object a navigable
  `/object` link, and a bare link its IRI as `<code>`. A collection therefore
  renders navigably even when the page does not register a template for its type.
- **`ItemActions`** (`RenderFragment<IObjectOrLink>?`) — optional per-item
  controls rendered after the item's content (the owner-only follower **Block**
  button, a member **Remove** button). This is how per-row management is supplied
  to the shared browser instead of a hand-rolled list.
- All of `PagedCollection`'s behavior is preserved: next-link page walking, the
  31.2 initial-load re-render (no manual Refresh), the empty / error states, the
  one-shot cache-bypass Refresh, and a fresh first-page load when the
  `CollectionIri` changes (`@key`).

## Tests

7 new bUnit tests in `CollectionBrowserTests` pin the shared browser's contract:

- `ItemTemplate_WhenProvided_RendersCustomMarkup_NotBasicFallback` — a registered
  template wins; the basic fallback (`/object` link) is absent.
- `NoItemTemplate_RendersBasicFallback_ForActor` — an actor renders as a
  `/actor?iri=` link (the short handle) + a muted type label.
- `NoItemTemplate_RendersBasicFallback_ForBareLink` — a bare link renders its IRI
  as `<code>`.
- `ItemActions_RendersPerItemControls` — the per-item actions fragment renders a
  "Block" button that coexists with the item link in the same `<li>`.
- `InitialLoad_RendersItems_WithoutManualRefresh`,
  `InitialLoad_EmptyCollection_RendersEmptyState_WithoutManualRefresh`,
  `InitialLoad_Failure_RendersError_WithoutManualRefresh` — the 31.2 invariants
  (the first-page load re-renders; the empty/error states settle without a manual
  Refresh).

The full fast suite is green and grew by 7 (**1446/1446**): the existing
`PagedCollectionTests` (4) and `ActorProfileTests` (6) are unchanged; the community
/ actor-detail integration tests exercise the unchanged data path.

## Design notes

- **The "basic object rendering" fallback is deliberately a navigable link, not a
  full `<ObjectView>`.** A follower/mute/flag is an actor — its natural rendering
  is a link to its detail page, not a full object card. The fallback therefore
  renders an actor as a detail link (handle + type), a non-actor object as a
  navigable `/object` link, and a bare link as `<code>`. The *rich* `<ObjectView>`
  rendering is still available to any collection that registers a template for it
  (the outbox/liked `ObjectItemTemplate`), so "fall back to basic object
  rendering" means "a minimal navigable rendering" rather than a heavy card.
- **`PagedCollection` is retained, not deleted.** The report's "feed" target is
  ambiguous between two things: (a) the **followed feed** (`/feed` page), and (b)
  the **community feed** (`{community}/feed`). The followed feed is a true
  `GetCollectionAsync` walk and *could* use the browser, but it is the one
  `PagedCollection` site with non-trivial behavior — a `?q=`-keyed `@key`, a
  `PageSize=5`, and a `ShowRefreshButton` — so converting it risks the 31.2
  initial-load re-render and the 21.4.2 query-filter re-render for a pure
  rename. The community feed, members, replies, and search results are
  **one-shot enumerations** (full `GetCollectionItemsAsync` /
  `GetCommunityFeedAsync` / `SearchAsync` reads, no `next`-link walking) — they
  are not ordered-collection walks at all, so the shared *browser* (a paging
  component) is the wrong tool for them. The slice therefore converts every
  *paged* ordered-collection surface (followers/following, outbox/liked, the
  moderation collections, inbox) and leaves the non-paged and the
  behavior-sensitive followed feed on `PagedCollection`. This is a deliberate
  boundary, not an omission: the hand-rolled duplication — the actual target of
  "instead of the ad-hoc … hand-rolled follower/following lists" — is eliminated.
- **Per-item management is a first-class slot, not a markup hack.** The follower
  Block button (and, symmetrically, a member Remove button) is supplied via
  `ItemActions`, which receives the item and resolves its IRI — the same pattern
  the hand-rolled list used, but as data to the shared browser rather than
  duplicated `<li>` markup. The management error/result line (which must stay
  visible under the list) is `HeaderContent`.
- No new NuGet packages; no server or client-library changes; no CSS changes (the
  browser reuses `PagedCollection`'s `paged-collection` / `object-list` classes).
