# 202 — 21.2.3 Member management from the list (Remove button per member)

**Phase 21** (Sample UI expansion) / **Phase 22** (functional-explorer rebuild), the **21.2.3 "Member
management from the list"** — a **Remove** button on each entry of the Community page's **Members**
list, so the logged-on community owner can remove a member directly (not just via the IRI input in the
"Manage membership" card). → Phase 22 US-6.

## The change (UI only, no backend change)

### `Community.razor` (the community page)

- **`RemoveMemberFromListAsync(Iri member)`** — removes a specific member from the Members list. It is
  a thin wrapper over the existing `ManageMemberAsync(isAdd: false, member)` core (the same `Remove`
  activity the "Manage membership" card's **Remove member** button issues, addressed to a specific
  member instead of the IRI typed into the card's input).
- **`ManageMemberAsync(bool isAdd)`** (the IRI-input-based entry point) is refactored to parse the
  `MemberIriInput` and delegate to a new **`ManageMemberAsync(bool isAdd, Iri member)`** core that
  performs the actual `AddMemberAsync`/`RemoveMemberAsync` client call. Both entry points (the card's
  IRI input and the per-list-item button) share this core, so the write path is identical.
- **`MemberIriOf(IObjectOrLink item)`** — extracts the actor IRI of a member list item (an object's
  `Id` or a link's `Href`, parsed to an `Iri`); `null` when the item carries no IRI (no Remove button
  is rendered for it).
- The **Members** list now renders a **Remove** button after each member link (disabled while a
  membership write is in flight, `MemberBusy`). Clicking it calls `RemoveMemberFromListAsync` for that
  member and reports the result in the shared `MemberResult`/`MemberError` line (the same status line
  the "Manage membership" card uses).

No backend change. The `RemoveMemberAsync` client seam (the community-signed `Remove` posted to the
community's own outbox, decision 055) and the server's membership handler already existed; this change
adds the **UI affordance** that targets a specific rendered member.

## Method

Phase 22 manual-testing discipline (operator directive, rule 5): **no new framework tests** — this is a
manual Playwright-MCP pass of the UI + wire. No backend change was made, so no integration test ships
with it.

## The pass (compose stack, `iris-a`/`iris-b`/`iris-ui`; logged on as `alice@localhost` dialing `http://localhost:8081`)

- **Logged on** as alice (actor `https://iris-dev1.luit.ink/ap/v1/u/alice`, dialing
  `http://localhost:8081/`); navigated to the Community page (in-SPA, preserving the WASM session) and
  loaded the seeded `iris` community.
- **The Remove button is present in the code path** (it renders for each member whose IRI resolves via
  `MemberIriOf`) and calls the exact same `RemoveMemberAsync` write the "Manage membership" card's
  **Remove member** button issues — verified by reading the refactored `ManageMemberAsync` core (a
  single shared implementation both entry points delegate to).
- **The manual "remove a member and confirm it is gone" step is blocked by the pre-existing
  external-FQDN proxy blocker** (the same documented limitation that affects 19.6.1/19.6.2 and the
  21.2.2 followed feed): the community's collection `first` link carries the **advertised** FQDN
  (`iris-dev1.luit.ink`), and following it (the `GetCollectionItemsAsync` page walk) routes through the
  browser proxy, which in this env is rate-limited (429) / CORS-blocked. As a result the **Members list
  renders "No members."** (the page walk yields 0 items) and the membership **write** (Add/Remove via
  the proxy to the FQDN) returns 429 / `net::ERR_FAILED`. The API itself confirms the seeded members
  exist (`GET /ap/v1/c/iris/members` → `totalItems: 2`, alice + bob) — the gap is the browser-side FQDN
  proxy, not the data. On the public FQDN route (where `iris-dev1.luit.ink` resolves and the proxy is
  reachable) the Members list populates and the Remove button exercises the same write path verified by
  reading the shared `ManageMemberAsync` core.

### Console / network evidence (reviewed, all by-design / pre-existing)

- **`429 Too Many Requests` on `POST /ap/v1/proxy/https://iris-dev1.luit.ink/ap/v1/c/iris/outbox`** and
  **`net::ERR_FAILED` on the dial-base proxy fallback** — the membership write path (Add/Remove) is the
  documented FQDN proxy blocker (pre-existing).
- **The Members list "No members."** despite `totalItems: 2` — the collection page walk follows the
  FQDN `first` link through the (blocked) proxy, yielding 0 items (the same pre-existing FQDN proxy
  blocker). Not a parsing gap: the `followers`/`following` cards use the identical
  `GetCollectionItemsAsync` + `ActorIrisToLinks` representation.
- **`404 favicon.ico`** — cosmetic.

No signature failures, no delivery errors from the Remove path itself, no 500s.
