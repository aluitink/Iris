# 24.1 — Cross-instance like / announce undo propagation (delivery-target fix)

Phase 24, slice 1. **Type:** fix + test (a real delivery-target bug found while scoping the slice, plus
the integration tests that lock it).

## Problem

The "cross-instance undo propagation" theme (22.13 moderation, 22.14 community un-follow) has a residual
gap for `Like` / `Announce`. When a local actor on A likes / announces a **remote** actor's object on B,
and then reverses it by publishing an `Undo`, the `Undo` must reach the object's author's instance (B) so
B can act on it. Tracing the outbox-publish handler (`OutboxPublishHandler`), the delivery recipient for
a `Like` / `Announce` (and an `Undo` of one) was resolved by `RecordLikeLocalAsync` /
`RecordAnnounceLocalAsync` / `RemoveLikeLocalAsync` / `RemoveAnnounceLocalAsync`, which — when the object
is **not** in the local object store (i.e. it is remote) — returned the **object IRI** as the delivery
recipient. `DeliveryService.DeliverToActorAsync` then appends `/inbox` to that IRI, producing a
non-existent `{objectIri}/inbox` URL (a Note has no inbox). The delivery 404s, so **B never receives the
activity or its `Undo`** — B's edge is never recorded (for an `Announce`) nor removed (for either).

In short: the cross-instance like/announce (and their undos) silently failed to deliver to the object's
author's instance.

## Fix

The delivery recipient for a `Like` / `Announce` (or an `Undo` of one) of a remote object is now the
object's **author** (its `attributedTo`), resolved by **fetching the object's document over the wire**:

- `src/Iris.Server/ActivityPubServerExtensions.cs`:
  - Registered the outbound `IActivityPubClient` as a singleton (only when an `InstanceActorId` is
    configured — the only case the server can sign an outbound object fetch; otherwise left unregistered
    so the outbox handler's nullable `IActivityPubClient?` param resolves to null via `GetService`).
  - `OutboxPublishHandler` now receives `IActivityPubClient? objectFetch` and passes it to the four
    `Record*` / `Remove*` like/announce helpers.
  - New shared helper `ResolveObjectOwnerForDeliveryAsync`: a local object's owner is read from the
    object store (no wire hop); a remote object's owner is resolved by `IActivityPubClient.GetObjectAsync`
    + reading `AttributedTo`. A fetch failure (network, not-found, no `attributedTo`) **degrades to the
    object IRI fallback** (the prior behavior) — the remote fetch is best-effort and must never fail the
    local publish (the activity is still recorded locally).
- All four helpers now return the author IRI (resolved) instead of the object IRI for a remote object, so
  both the outbound `Like`/`Announce` **and** their `Undo` deliver to the object's author's inbox on the
  remote instance.

## Where (tests)

- `tests/Iris.Server.Tests/LikeAnnounceUndoPropagationIntegrationTests.cs` (2 new integration tests), a
  2-instance `TestServer` topology (A = `like-undo-a.domain.local`/`alice`, B = `like-undo-b.domain.local`/
  `bob`), mirroring the 22.13/22.14 wiring. B stores bob's `Note` in its object store (`attributedTo` bob)
  so A can fetch it and resolve the author; A's outbound object fetcher (`ActivityPubHostOptions.Client`)
  routes to B. The follow edge (bob → alice) is recorded in **A's** persistence so A's
  `GetRemoteNonBlockedFollowersAsync` finds bob (the Announce variant federates to followers).
  1. `UndoLike_ServerDeliversToRemote_StoredOnRemoteInstance` — a like edge is **home-instance-local**
     (`LikeActivityHandler` records only when the liker is local, so B records **no** like edge for a
     remote liker; the edge lives on A). The cross-instance invariant is therefore **activity delivery**:
     A delivers the `Like` — and its `Undo` — to bob's inbox on B (resolved by A fetching bob's Note, the
     24.1 fix). B's `InboxProcessor` stores every inbound activity, so the test asserts B **stored the
     Like** (step 1) and **stored the Undo** (step 2), while A records then removes its own like edge.
  2. `UndoAnnounce_ServerDeliversToRemote_RemovesRecordedEdge` — an `Announce` **does** record an edge on
     B (`AnnounceActivityHandler` records when the **recipient** is local — bob is). bob follows alice, so
     the outbound `Announce` federates to bob (a follower); B records the announce edge + stores the
     activity. A's `Undo(Announce)` is delivered to the object's author (bob, the 24.1 resolution); B's
     `UndoActivityHandler` resolves the original and **removes** the edge. The test asserts B recorded the
     edge (step 1) then removed it (step 2), and the inverse index agrees.

## Non-vacuity (proven)

Per the loop's "prove it fails" discipline, the remote-object owner resolution was temporarily disabled
(the `objectFetch` branch in `ResolveObjectOwnerForDeliveryAsync` skipped, then restored via
`git checkout`):

- With the fetch disabled, **both tests fail**: the Like test times out waiting for B to store the Like
  (the delivery fell back to the object IRI's non-existent `/inbox`); the Announce test times out at step
  2 (B recorded the edge in step 1 via the follower delivery, but the `Undo(Announce)` delivered to the
  object IRI's non-existent `/inbox`, so B never removed the edge).
- Restoring the resolution turns them green.

This confirms the tests genuinely exercise the 24.1 delivery-target fix (not passing vacuously).
