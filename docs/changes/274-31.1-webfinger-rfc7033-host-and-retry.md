# 274 — 31.1: WebFinger RFC 7033 host handling + client base-URI retry

> 2026-09-05 · Slice 31.1 · Phase 31 (explorer UI & server namespace polish)

## What was built

Two changes making WebFinger (RFC 8410) discovery behave correctly when a query
reaches an instance that is not the account's home:

1. **Server — explicit 404 for a non-matching `host` (RFC 7033).** The
   `WebFingerHandler` now compares the `acct:` resource's host against the
   instance's advertised host (the host of `ActivityPubServerOptions.BaseUri`,
   falling back to the request's `Scheme://Host`). On mismatch it returns 404
   *before* the actor lookup — even for a handle that exists on this instance.
   Previously the handler resolved by handle alone, so a query for
   `acct:alice@elsewhere.example.com` answered 200 with a self link pointing at
   *this* instance — telling the wrong instance's WebFinger client that the
   account lives here.
2. **Client — retry to the account's advertised host.** `WebFingerClient`, when
   given an explicit `dialBaseUri` (the browser-reachability hint for a local
   instance on a host-published port), now treats a failed dial-base
   resolution as a signal to retry the well-known query against the **account's
   own host** (the RFC 8410 norm: a resource lives on its own host), dialed
   over the default scheme (`https`, or the `dialScheme` overload's scheme).
   The retry is skipped when the dial base's host *is* the account's host
   (port ignored — a port-published local instance and the account's bare host
   are the same machine), so the existing S1 localhost scenario is unaffected.

## Key types & files

- `src/Iris.Server/ActivityPubServerExtensions.cs` — `WebFingerHandler`: host
  mismatch → 404 (new ~10 lines before the actor lookup).
- `src/Iris.Client/Discovery/WebFingerClient.cs` — `ResolveActorFromNetworkAsync`
  now runs the first query via a new `QueryWellKnownAsync(authority, subject,
  ct)` helper, then retries against the account host when the dial base failed
  and its host differs. New static helpers `GetAccountHost` (parse the host
  from the normalized `acct:` subject) and `SameAuthorityHost` (compare the
  dialed authority's host to the account host, ignoring the explicit port).
- `tests/Iris.Client.Tests/FakeHttpHandler.cs` — new `RequestCount` property
  (asserts how many requests the client made).

## Design notes

- **Why 404 (not 200 with a foreign self link)?** RFC 7033 says the query
  resource identifies an account *on the dialed host*; when that account does
  not exist there, 404 is the specified response. Answering 200 with a self
  link to *this* instance would mislead any client (including ours) that
  follows the self link to the actor document. The 404 is also the signal the
  client's retry logic keys on.
- **Why retry only when the dial base's host differs?** The dial base exists
  for one reason: browser reachability (a local instance published on
  `localhost:8081`). When its host equals the account's host, a 404 means the
  account genuinely doesn't exist — retrying the same machine over `https`
  (where the test/local instance isn't listening) can only add latency, never
  a resolution.
- **Port is ignored in the host comparison** (`SameAuthorityHost` uses
  `Uri.IdnHost`, which drops the port) because `localhost:8081` and
  `localhost` denote the same machine.
- No new NuGet packages; no public API signature changes (the retry is
  internal to `ResolveActorFromNetworkAsync`).
