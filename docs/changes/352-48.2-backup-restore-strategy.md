# 48.2 — Backup & restore strategy

## Summary

Created the backup/restore tooling and configuration for production Iris.Web deployments:

- `scripts/backup-iris.sh` — creates a timestamped tar.gz containing:
  1. PostgreSQL dump (`pg_dump --format=custom`, allows selective table restore)
  2. ASP.NET Core Data Protection keys (auth cookie encryption, antiforgery tokens)
  3. Media volume (uploaded images; skipped if empty)
  4. MANIFEST.txt with metadata + restore instructions
  - Retention: prunes backups older than `BACKUP_RETENTION_DAYS` (default 14).
- `scripts/restore-iris.sh` — restores from a backup archive:
  - Full restore (DB + keys + media) or selective (`--db-only`, `--media-only`, `--keys-only`).
  - Stops the app, drops + recreates the DB, `pg_restore`, copies keys, extracts media, restarts.
  - `--yes` flag for non-interactive disaster recovery.
- `apps/Iris.Web/deploy/BACKUP.md` — operational documentation:
  - What to back up and why (table).
  - Script usage examples.
  - systemd timer + cron examples for daily 03:00 backups.
  - Off-site backup (rsync/S3) recommendations.
  - RPO/RTO targets (24h / 15min).
  - Verification procedure (test restore on staging).
- `apps/Iris.Web/docker-compose.yml` — added `iris-dp-keys` named volume mounted at
  `/root/.aspnet/DataProtection-Keys` so Data Protection keys survive container recreation
  (`docker compose down` + `up`). Without this, every restart invalidates all user sessions.
- `.gitignore` — added `backups/` (local backup archives are never committed).

## Design decisions

- **`pg_dump --format=custom`**: allows selective restore (`pg_restore --table=...`) if only
  specific tables are corrupted. The plain text format would not support this.
- **Data Protection keys as a named volume**: the keys are in the container filesystem by
  default, so `docker compose down` + `up` (which recreates the container) loses them. The
  named volume persists them. The backup script still copies them (defense in depth — the
  volume protects against container loss, the backup against volume loss).
- **Backup runs on the host** (not inside a container): the script uses `docker compose exec`
  to talk to the containers. This is simpler than a sidecar backup container and matches the
  operator workflow (run the script, check the output, copy off-site).
- **Media tarball is separate from the main archive**: media can be large (hundreds of MB);
  keeping it separate means a DB-only restore doesn't need to transfer the media archive.
- **Retention via `find -mtime`**: simple, no external dependencies. For production, the
  operator should also configure off-site replication (rsync/S3) for disaster recovery.
