# 61.1 — WASM performance audit

**Priority:** MEDIUM
**Status:** COMPLETE

## Problem

The Blazor WebAssembly client downloaded **29.92 MB** (208 WASM files, 219 total resources)
on initial page load. The top 3 WASM files accounted for ~45% of the payload:

| File | Size | Gzipped |
|---|---|---|
| `BouncyCastle.Cryptography` | 5.14 MB | 2.53 MB |
| `System.Private.CoreLib` | 4.87 MB | 1.59 MB |
| `System.Private.Xml` | 3.10 MB | 1.07 MB |

The total gzipped WASM payload was **38.6 MB** — far too large for a social platform UI.

## Root cause

The Blazor WASM build shipped the full BCL (Base Class Library) without trimming. Unused
assemblies (XML, DataContractSerialization, Data.Common, Encoding.CodePages, etc.) were
downloaded and loaded even though the client never uses them. The client uses
`crypto.subtle` (via `Iris.WebCrypto`) for signing, not the BCL crypto stack.

## Fix

Enabled **aggressive WASM trimming** + **invariant globalization** in
`Iris.Web.Client.csproj`:

- `<PublishTrimmed>true</PublishTrimmed>` — the ILLink trimmer removes unreachable
  assemblies and IL code.
- `<InvariantGlobalization>true</InvariantGlobalization>` — eliminates the ICU data
  dependency (the client doesn't need locale-specific formatting).
- Build pipeline (`Iris.Web.csproj`): `BuildAndCopyClient` now runs `Publish` (not `Build`)
  on the WASM client with `PublishTrimmed=true`, clears stale publish output before
  re-publishing, and clears the destination `wwwroot/_framework` before copying (so
  untrimmed files from a previous build don't persist).

### BouncyCastle (5.14 MB) — retained, future work

BouncyCastle is referenced by `Iris.Core` for Ed25519 key support (`Ed25519Key.cs`). The
trimmer cannot remove it because `Iris.Core.dll` (which the client needs for `Iri`,
`ISigningKey`, etc.) has a hard reference to BouncyCastle. Removing it requires a
conditional-reference change to `Iris.Core` (e.g., a `#if !BROWSER` compile guard around
the Ed25519 code, or moving Ed25519 to a separate assembly that the server references but
the client does not). This is deferred to a future slice.

## Verification

- `dotnet build -c Release` — 0 errors, 0 warnings
- `dotnet test --no-build -c Release` — **1651 passed, 0 failed, 17 skipped** (1 known
  flaky `FollowEdgeConvergence` test failed on first run, passed on re-run)
- **Playwright live test** (`https://iris.luit.ink`):
  - WASM app loads correctly (0 console errors, 0 warnings)
  - Page renders (nav, hero, footer all present)

### Performance improvement

| Metric | Before | After | Change |
|---|---|---|---|
| Total transfer | 29.92 MB | **13.13 MB** | **-56%** |
| WASM files | 208 | **65** | **-69%** |
| WASM transfer | 29.40 MB | **12.63 MB** | **-57%** |
| Total resources | 219 | **76** | **-65%** |
| Gzipped WASM | 38.6 MB | **5.0 MB** | **-87%** |
| DOM Content Loaded | 56 ms | **27 ms** | **-52%** |
| Load event | 56 ms | **28 ms** | **-50%** |

## Notes

- The 56% reduction in total transfer (29.92 → 13.13 MB) is the primary win. The
  gzipped WASM payload dropped from 38.6 MB to 5.0 MB (87% reduction).
- BouncyCastle (5.14 MB) is still the largest single file. Removing it requires a
  `Iris.Core` change (conditional Ed25519 reference) — deferred.
- Invariant globalization means the client uses `InvariantCulture` for all
  date/number formatting. This is acceptable for a social platform (timestamps are
  relative, e.g. "2h ago", not locale-specific).
