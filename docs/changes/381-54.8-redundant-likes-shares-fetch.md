# 54.8 — Redundant per-object likes/shares collection fetch

Phase 54 slice. `EngagementBar.razor` (`OnParametersSetAsync`) issued a full
`GetLikesAsync` + `GetSharesAsync` collection walk **per rendered object** to
seed `_likeCount`/`_boostCount`/`_liked`/`_boosted` — even inside timeline and
collection views where many objects render at once. A home feed of 30 posts
therefore fired **60** extra `GET /likes` + `GET /shares` requests on every
render, each a full paginated collection walk, purely to re-derive numbers the
server already knew.

## The problem

Two independent costs, both wasteful:

1. **N+1 collection walks.** `EngagementBar` had no way to know an object's
   engagement without fetching its `likes` and `shares` collections. In a
   timeline every `ObjectView` rendered its own `EngagementBar`, so a feed of N
   posts did 2N collection fetches before the page was even interactive.
2. **The server already computes the counts.** The feed/outbox collection
   handlers load each embedded note and could (and now do) attach the
   engagement counts to the note itself — but the client ignored any such
   fields and always re-fetched.

## Fix

The server now stamps engagement data onto the objects it serves, and the
client uses it as a **fast path**, falling back to the live collection walk
only when the data isn't present (non-Iris objects, cached/stale outbox pages,
standalone reads where the object wasn't enriched).

### 1. Server stamps `iris:likedCount` / `iris:sharedCount` / `iris:repliedCount`

`ActivityPubServerExtensions` enriches each embedded object it serializes in
the **feed** and **outbox** collection pages with the three cacheable counts,
plus the per-requester booleans `iris:isLiked` / `iris:isShared` (only when
`true`) so the client knows the current actor's own engagement without a
fetch. The same counts are also emitted on the **standalone object document**
(`ServeObjectDocument`), so the `ObjectDetail` page gets them too.

The enrichment is done in `EnrichCollectionItemsAsync`, which deep-copies each
item, sets the `ExtensionData` terms on the embedded object, and serializes.

### 2. Library bug: `OneOrMultipleConverter` clones + drops `ExtensionData`

A standalone repro (`/tmp/iobjcheck4`) exposed a **library bug** in
`KristofferStrube.ActivityStreams`:

- The `OneOrMultipleConverter` (bound to `Activity.Object`) **re-materializes
  (clones) the embedded object on every enumeration** of `Activity.Object`.
- Worse, when the enclosing `Activity` is serialized, that converter **drops
  the embedded object's `ExtensionData`** — so any `iris:*` terms set on the
  embedded note were silently lost on the wire.

A standalone `IObject` preserves `ExtensionData` through a round-trip, but a
**nested** object inside an `Activity.Object` collection does not.

**Fix:** after setting `ExtensionData` on the copied embedded object, replace
`activityCopy.Object` with a **single-element array**
(`new IObjectOrLink[] { copyObj }`). This makes every enumeration return the
*same* stable instance, so the serializer uses the enriched object and the
`iris:*` terms survive to the wire. Verified end-to-end in the repro and live
on the deployed feed.

### 3. Client fast path (`EngagementBar`)

`EngagementBar` takes a new `[Parameter] IObject? Object` (the embedded object
the parent `ObjectView` already deserialized). In `OnParametersSetAsync`:

- **Fast path** — when `Object` carries **both** `likedCount` and `sharedCount`
  (read via the new `IObject` extension readers, namespaced against
  `Session.IrisNamespaceBase`): seed `_likeCount`/`_boostCount` from them, seed
  `_liked`/`_boosted` from `isLiked`/`isShared`, and **skip both walks**. At most
  ONE walk still runs (only the collection the actor is engaged with) to recover
  the minted Like/Announce id needed for the Undo.
- **Fallback** — when the counters are absent (non-Iris object, cached/stale
  outbox page, unsigned read), fall back to the original full 2-collection walk.

`ObjectView` passes `Object=` to all four `EngagementBar` usages. `ObjectDetail`
applies the same fast path to its `ObjectDoc`.

### 4. Namespace base (`IActorSessionAccessor`)

Added `Iri? IrisNamespaceBase` = `{instanceBase}/ns#` (instanceBase = advertised
base ?? browser origin), matching the server's `ActivityPubServerOptions.
NamespaceIri`. The client readers default to a placeholder
(`https://iris.example/ns#`) that matches no deployed instance, so the caller
must pass the deployment's base — which `EngagementBar` now reads from
`Session.IrisNamespaceBase`.

### 5. `IObject` receivers (`IrisDocumentExtensions`)

All five readers (`GetLikedCount`/`GetSharedCount`/`GetRepliedCount`/
`GetIsLiked`/`GetIsShared`) and their `GetInt`/`GetBool` helpers changed
receiver from the concrete `Object` to `IObject` (the interface exposes
`ExtensionData`), so they work on the deserialized embedded object regardless of
its runtime type.

## Notes

- **Deployment gotcha (browser cache):** `_framework/dotnet.js` and the
  hashed `.wasm` are served with `Cache-Control: public, max-age=31536000,
  immutable`. During development this pins a browser to the *first* WASM it
  cached — a new build is invisible until the browser's HTTP cache is cleared or
  a fresh profile/context is used. Verified by loading the new
  `Iris.Web.Client.99tpey5kty.wasm` in a fresh context (the stale
  `s276j6gjia` WASM, still cached in the main tab, kept doing the old 2-walk
  behavior). Not a product bug — the immutable cache is correct for production
  (content-hashed assets); it just makes dev iteration require a cache clear.
- This is Phase 45+ (WASM manual-test phase): no new coded tests; verification
  is the live Playwright pass above.
- The fallback walk is preserved for non-Iris / unenriched objects, so
  cross-instance reads (which the 54.7 proxy now supports) still render
  engagement correctly when the remote doesn't emit `iris:*` counts.
