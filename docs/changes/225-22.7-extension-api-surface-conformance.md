# Change 225: Extension API-surface conformance — namespacing + centralized term constants (22.7)

## Summary

Every property the server emits on a public actor/community document is now classified as either a
**core ActivityStreams/ActivityPub** term (emitted **bare**) or an **Iris-invented extension** (emitted
**under the `iris:` namespace**, the full IRI key `{NamespaceIri}{term}`). The classification is pinned
on the actual wire by new integration tests, and every wire term string now lives in a single
`Iris.Core` source of truth so the client (which reads the terms) and the server (which renders them)
can never drift apart.

This is the **extension API-surface audit and namespacing review** (Phase 22 closeout,
[phase-22-closeout.md §4](../plans/phase-22-closeout.md#4-extension-api-surface-audit-and-namespacing-review)):
the audit classified each custom field, the namespacing decision was made (below), and the centralizing
of term names that the audit's "no magic strings" goal implies.

## The classification

| Property | Person | Community | Classification | Wire form |
|----------|--------|-----------|----------------|-----------|
| `id`/`type`/`inbox`/`outbox`/`followers`/`following` | ✓ | ✓ | core AP | bare |
| `liked` | ✓ | — | core AP (AS `Liked`; library-typed) | bare (typed) |
| `members` | — | ✓ | core AS `Group` term | bare |
| `publicKey` | ✓ | ✓ | ecosystem convention (community-profile/Mastodon shape) | **bare** |
| `privateKey`/`keyAlgorithm` | ✓ (owner-only) | — | ecosystem convention (owner-only) | bare |
| `manuallyApprovesFollowers` | ✓ | — | ecosystem convention (Mastodon) | bare |
| `manuallyApprovesMembers` | — | ✓ | ecosystem convention (Mastodon) | bare |
| `iris:capabilities` | ✓ | ✓ | Iris extension | namespaced |
| `iris:settings` | ✓ | ✓ | Iris extension | namespaced |
| `iris:feed` | ✓ | ✓ | Iris extension | namespaced |
| `iris:blocks` | ✓ | ✓ | Iris extension | namespaced |
| `iris:flags` | ✓ | ✓ | Iris extension | namespaced |
| `iris:mutes` | ✓ | ✓ | Iris extension | namespaced |
| `iris:star` (relays) | ✓ | — | Iris extension | namespaced |
| `iris:search` | — | ✓ | Iris extension | namespaced |
| `iris:searchQuery` (on a search page) | — | ✓ | Iris extension | namespaced |

**The exception set** (ecosystem de-facto conventions, kept bare per the closeout scope's explicit
`likes`/`shares`-style exception): `publicKey`, `privateKey`, `keyAlgorithm`, and the
`manuallyApproves*` settings gates. Renaming any of these into the `iris:` namespace would break
cross-ecosystem interop — Mastodon and other ActivityPub implementations expect exactly the bare
community-profile shape (this is why the F-1912-1 Mastodon 401 was fixed by adding JWK to `publicKey`,
not by namespacing it).

## Solution

### 1. The server now declares a JSON-LD `@context` (the wire-level marker)

`BuildActorDocument` and `BuildCommunityDocument` set
`doc.JsonLDContext = [ReferenceTermDefinition(https://www.w3.org/ns/activitystreams),
ExpandedTermDefinition { Vocab = {NamespaceIri} }]`. The core AS context is declared first (so the
bare core-AP terms resolve), and the `iris:` namespace base is declared as `@vocab`. The Iris-invented
extension terms are written under the **full IRI key** `{NamespaceIri}{term}` — so they are
unambiguous and cannot collide with a core-AP or vendor term, and a JSON-LD processor resolves them
via the `@vocab`. This is the wire-level marker that distinguishes an Iris extension from a core-AP
property (which stays bare). The namespace base is deployment-configurable
(`ActivityPubServerOptions.NamespaceIri`); the canonical default applies when unset.

### 2. Centralized term constants in `Iris.Core`

All wire-term strings now live in `Iris.Core` (the lowest shared dependency), so the client and server
reference the same source of truth (a rename is a compile error, not a silent wire drift):

- **`Iris.Core.IrisExtensionTerms`** (new) — the local terms of the `iris:`-namespaced extensions:
  `Capabilities` (`"capabilities"`), `Settings` (`"settings"`), `SearchQuery` (`"searchQuery"`).
  These cannot live in the server's `ActivityPubServerConstants` because `Iris.Client` may not depend
  on `Iris.Server`.
- **`Iris.Core.CollectionExtensionNames`** (new) — the Iris-invented collection-endpoint terms
  (`Feed`/`Blocks`/`Flags`/`Mutes`/`Search`/`Star` — namespaced) plus the core-AS terms emitted bare
  (`Members`) / library-managed (`Liked`), so the full advertised collection surface is documented in
  one place and the client's readers share the canonical terms.
- **`Iris.Core.ActivityPubExtensionNames`** — gains the bare ecosystem-convention key terms:
  `PublicKey` (`"publicKey"`), `PrivateKey` (`"privateKey"`), `KeyAlgorithm` (`"keyAlgorithm"`).

`Iris.Server.ActivityPubServerConstants` **aliases** these for compatibility (`CapabilitiesTerm`,
`SettingsTerm`, `ManuallyApproves*ExtensionName`, `PrivateKeyExtensionName`,
`KeyAlgorithmExtensionName` now flow from Core; their values are unchanged). The server's render path
(`BuildActorDocument`/`BuildCommunityDocument`/`BuildSearchPageDocument`) and the client's readers
(`IrisDocumentExtensions`) both reference the Core constants — the only remaining `namespaceIri +`
literals in the server are gone, replaced by a single `IrisExtensionNamespace(options)` helper.

### 3. Client readers are namespace-aware

`IrisDocumentExtensions.Get{Feed,Blocks,Flags,Mutes,Relays}Iri()` now take
`string namespaceIri = DefaultNamespaceIri` (matching `GetSettingsIri()`/`GetCapabilities()`), so a
client reading a deployment that overrides the namespace passes the same base. `GetMembersIri()`
stays namespace-free (`members` is core-AS, bare). `GetSettingsIri()`/`GetCapabilities()`/
`GetMembersIri()` now build their term from the Core constants instead of literals.

## Decisions (recorded per the autonomous default)

- **`publicKey`/`privateKey`/`keyAlgorithm` stay BARE.** They are ecosystem conventions with no spec
  compact term; the JSON-LD community-profile and ActivityPub implementations (incl. Mastodon) emit
  `publicKey` bare and expect that exact shape. Namespacing them would break signature resolution on
  remote instances. `privateKey`/`keyAlgorithm` are owner-only (never on the public document) and
  follow the same convention. → kept bare, classified as the ecosystem-convention exception set.
- **`members` stays BARE.** It is a core ActivityStreams `Group` term (unlike the Iris-invented
  collection endpoints), so it is not namespaced.
- **`search` has no dedicated client reader** (unchanged from change 222): discovery goes through
  `iris:capabilities` (which advertises the `search` capability). The `Search` constant exists so the
  server's render and search-page paths share one source of truth.
- **The default namespace stays `https://iris.example/ns#`** (unchanged). It is a placeholder IRI
  (the `example` domain is reserved for documentation); a deployment overrides it via
  `ActivityPubServerOptions.NamespaceIri`. Both the server default and the client's
  `IrisDocumentExtensions.DefaultNamespaceIri` carry the same value; a future change may alias one to
  the other in Core if a third consumer appears.

## What is NOT changed

- No endpoint, route, or behavior change. The **route segments** (the `/u/{handle}/blocks`,
  `/c/{name}/members`, … URL paths) are unchanged — only the **JSON-LD property keys** on the document
  moved under the namespace. A client that discovered the collection IRIs from the document (via
  `GetFeedIri()` etc.) is unaffected; only a client that hardcoded the bare `feed`/`blocks`/… keys
  would need to pass the namespace (or use the reader, which defaults to the canonical namespace).
- The `iris:capabilities`/`iris:settings` discovery seam (change 220) and the settings-gate terms
  (change 224) are unchanged in value.
- No new NuGet packages.

## Tests

- **`Iris.Server.Tests.ApiSurfaceConformanceTests`** (new, 6 tests) — pin the classification on the
  actual wire against a live `TestServer`: the `@context` declares the core AS context **and** the
  `iris:` namespace (`@vocab`); the core-AP terms (`id`/`type`/`inbox`/`outbox`/`followers`/
  `following`, + `members` on a community) are present bare; the Iris-invented collection endpoints
  (`feed`/`blocks`/`flags`/`mutes`/`star` on a person, `feed`/`search`/`blocks`/`flags`/`mutes` on a
  community) are present namespaced **and their bare forms are absent**; `iris:capabilities` is
  namespaced; `publicKey` is present bare (the ecosystem-convention exception); and the search page
  records `iris:searchQuery` namespaced (bare form absent).
- **`Iris.Core.Tests.IrisExtensionTermsTests`** (new, 5 tests) — pin the exact wire strings of
  `IrisExtensionTerms`, `CollectionExtensionNames`, and the bare `ActivityPubExtensionNames` key terms
  (a typo would silently break extension discovery).
- **Updated existing integration tests** (Blocks/Flags/Mutes/Relays/CommunityEndpoint/
  CommunityModeration/CommunitySearch/FollowFeed/SampleServer) — their `GetProperty("feed")`/
  `GetProperty("blocks")`/… assertions now read the namespaced key
  (`IrisDocumentExtensions.DefaultNamespaceIri + CollectionExtensionNames.X`), matching the new wire.
- **`IrisDocumentExtensionReaderTests`** (unchanged) — the reader round-trips still pass because the
  readers and the render now share the Core constants.

Suite total: **1,457 → 1,467** (+10 new tests: 6 conformance + 5 Core term pins; 1 existing test's
assertion updated, not a net count change).
