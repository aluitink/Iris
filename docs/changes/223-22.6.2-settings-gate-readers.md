# Change 223: Typed readers for the settings-gate state (22.6.2)

## Summary

`IrisDocumentExtensions` (the client-side reader for JSON-LD extensions on actor/community documents)
now has typed readers for the **settings-gate state** — `manuallyApprovesFollowers` (person) and
`manuallyApprovesMembers` (community). This is the **read half** of the AP-native settings write path
introduced in changes 217 (community `SetManuallyApprovesMembersAsync`) and 221 (person
`SetManuallyApprovesFollowersAsync`): a client can now read an actor's follow-approval policy, or a
community's membership-approval policy, from the fetched public document alone — no persistence access.

## Problem

Changes 217/221 gave the client a **write** seam for the two settings gates, and change 220 gave a
**discovery** seam (`GetSettingsIri()` / `GetCapabilities()` tell a client *that* a settings surface
exists and *where* to publish changes). But there was no **read** seam for the gate *state itself*. A
client that wanted to know "is this actor gating its follows?" / "is this community gating its
members?" had to hand-parse the `ExtensionData` dictionary with the raw term string.

The server already advertises the gate verbatim on the public document (it is stored in
`ExtensionData` and rendered through as-is when set), so the information is on the wire — it just had
no typed reader, the same gap change 222 closed for the collection-endpoint extensions.

## Solution

### Client (Iris.Client)

`IrisDocumentExtensions` gains two readers, both returning `bool?`, over a shared private
`GetManuallyApprovesGate(Object, string term)` helper:

- `GetManuallyApprovesFollowers()` — the `manuallyApprovesFollowers` gate (person documents).
- `GetManuallyApprovesMembers()` — the `manuallyApprovesMembers` gate (community documents).

Tristate semantics (the gate is a *policy*, not a flag that is always present):

| Wire value | Reader returns | Meaning |
|---|---|---|
| term absent | `null` | no settings gate (open) |
| JSON `true` | `true` | gate set (manual approval required) |
| present, not `true` (e.g. JSON `false`) | `false` | present-but-disabled |

These mirror the existing `GetSettingsIri()` / `GetCapabilities()` style and the change-222
collection readers. The terms are **un-prefixed** (no `iris:` namespace), matching how the server
stores/advertises them — so the readers take no namespace argument.

### Tests

**5 new integration tests** (`SettingsGateReaderTests`), against a live `TestServer` host with real
signing keys (the settings write path is exercised through the signed client pipeline, not a raw
store write):

- `PersonDoc_GetManuallyApprovesFollowers_ReflectsClientWrite` — open → `null`; client
  `SetManuallyApprovesFollowersAsync(true)` → `true`; client `(..., false)` → `null` again (full
  write→read→write→read round-trip on the person document).
- `CommunityDoc_GetManuallyApprovesMembers_ReflectsClientWrite` — the same round-trip on the community
  document via `SetManuallyApprovesMembersAsync`.
- `Gate_Readers_ReadOnlyTheirOwnTerm` — with **both** gates enabled, the person document reads
  `manuallyApprovesFollowers=true` and `manuallyApprovesMembers=null` (community-only), and the
  community document reads `manuallyApprovesMembers=true` and `manuallyApprovesFollowers=null`
  (person-only) — the readers do not cross-read.
- `Gate_Readers_BareObject_ReturnNull` — a bare `Object` with no `ExtensionData` returns `null` for
  both readers (no throw).
- `Gate_Readers_PresentButDisabled_ReturnFalse` — a gate stored as JSON `false` reads `false`
  (distinct from the absent `null`), pinning the tristate contract.

## Note

The readers read the gate as **advertised on the public document** (which the server renders from the
stored `ExtensionData` verbatim when set). A cleared gate is stored by *removing* the term (not by
storing `false`), so in practice the wire is `true` or absent; the `false` arm of the tristate is
exercised directly to pin the contract.
