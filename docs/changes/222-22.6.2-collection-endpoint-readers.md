# Change 222: Typed readers for advertised collection-endpoint extensions (22.6.2)

## Summary

`IrisDocumentExtensions` (the client-side reader for JSON-LD extensions on actor/community documents,
introduced in change 220) now has typed readers for the un-prefixed collection-endpoint extensions the
server advertises on the public document. A client fetching a document can read each collection IRI
directly — no hardcoded endpoint paths.

## Problem

Change 220 added `GetSettingsIri()` and `GetCapabilities()`, but the server advertises several more
un-prefixed collection-endpoint extensions in `ExtensionData` that the client had no reader for:

| Extension | Person doc | Community doc | Served at |
|-----------|-----------|---------------|-----------|
| `feed`    | yes       | yes           | `/u/{h}/feed`, `/c/{n}/feed` |
| `blocks`  | yes       | yes           | `/u/{h}/blocks`, `/c/{n}/blocks` |
| `flags`   | yes       | yes           | `/u/{h}/flags`, `/c/{n}/flags` |
| `mutes`   | yes       | yes           | `/u/{h}/mutes`, `/c/{n}/mutes` |
| `star` (relays) | yes | no        | `/u/{h}/relays` |
| `members` | no        | yes           | `/c/{n}/members` |
| `search`  | no        | yes           | `/c/{n}/search` |

A remote client had to parse `ExtensionData` by hand (string keys) to discover these surfaces.

## Solution

### Client (Iris.Client)

`IrisDocumentExtensions` gains six typed readers, all returning `Iri?` (null when the term is absent or
not a valid IRI), over a shared private `GetCollectionIri(Object, string term)` helper:

- `GetFeedIri()` — the `feed` extension (home timeline / community feed).
- `GetMembersIri()` — the `members` extension (community-only).
- `GetBlocksIri()` — the `blocks` extension (moderation).
- `GetFlagsIri()` — the `flags` extension (moderation).
- `GetMutesIri()` — the `mutes` extension (moderation).
- `GetRelaysIri()` — the `star` extension (the relays/fan-out collection, the ActivityPub `star` set).

These mirror the existing `GetSettingsIri()` / `GetCapabilities()` style (namespace-aware where
applicable; these are un-prefixed so they take no namespace argument).

### Tests

**3 new integration tests** (`IrisDocumentExtensionReaderTests`), against a live `TestServer` host:

- `PersonDoc_Readers_ReadCollectionEndpoints` — a person document exposes `feed`/`blocks`/`flags`/`mutes`/
  `star`; `members` is absent (community-only).
- `CommunityDoc_Readers_ReadMembersAndFeed` — a community document exposes `members` (the community-only
  term) + `feed` + the moderation collections (`blocks`/`flags`/`mutes`).
- `Readers_BareObject_ReturnNulls` — a bare `Object` with no `ExtensionData` returns nulls for all
  readers (no throw).

## Note

`search` is community-only and is not given a dedicated reader here (it is covered by the community
document's `iris:capabilities` list, which already advertises the `search` capability for discovery).
It can be added via the same `GetCollectionIri(document, "search")` pattern if a typed reader is wanted.
