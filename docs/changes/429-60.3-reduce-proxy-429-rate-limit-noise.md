# 60.3 — Reduce proxy 429 rate-limit console noise on Notifications

**Priority:** LOW
**Status:** COMPLETE

## Problem

The Notifications page emits ~20 browser console errors per page load after the first
load:

```
[ERROR] Failed to load resource: the server responded with a status of 429
  () @ https://iris.luit.ink/ap/v1/proxy/https://remote.example/users/someactor:0
```

The Blazor WASM client fetches avatar/icon IRIs for remote actors in parallel. With the
default proxy rate limit of 60 requests/minute, a Notifications page with ~28 dead remote
actors + other remote actor avatars easily exceeds the limit, triggering 429 responses.
Each 429 is logged as a browser console error.

This was a **separate** issue from the 410 Gone noise (fixed in 60.2): the 429s come
from the `RateLimitingProxyPolicy`, not from dead remote actors.

## Root cause

`ActivityPubServerConstants.DefaultProxyMaxRequestsPerMinute` was set to 60, which is
too low for a normal page load that fetches many remote actor avatars in parallel. The
rate limiter is a safety valve against abuse, not a performance constraint — 60 req/min
is too restrictive for legitimate use.

## Fix

Raised `DefaultProxyMaxRequestsPerMinute` from **60** to **300**.

Rationale:

- **300 req/min is still a safety valve:** an attacker would need to sustain 5 req/sec
  for a full minute per actor to hit the limit. Legitimate page loads (even with many
  remote actors) stay well under this.
- **No client-side changes needed:** the Blazor WASM client's parallel avatar fetches
  are the correct behavior for a rich social timeline; the server-side limit should
  accommodate them.
- **Per-actor isolation:** the rate limit is per `actorIri`, so one user's traffic does
  not exhaust another user's budget.

## Files changed

| File | Change |
|---|---|
| `src/Iris.Server/ActivityPubServerConstants.cs` | `DefaultProxyMaxRequestsPerMinute`: 60 → 300 |

- `dotnet build -c Release` — 0 errors, 0 warnings

- **Playwright live test** (`https://iris.luit.ink/notifications`):

    once, cached by `ProxyGoneCache`), **0 429s**
  - **Second load** (warm cache): **0 errors** — no 410s (cached-gone → 204), no 429s
    (rate limit not hit)
  - **Third load** (warm cache): **0 errors** — consistent
