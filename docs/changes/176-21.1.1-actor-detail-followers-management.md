# 176 — Phase 21.1.1: actor detail — followers-list management (block a follower, owner only)

## Summary

The actor detail page's **followers list** now offers a **"Block" button per item** when the logged-on
actor owns the actor being viewed (i.e. `ActorIri` == `Session.ActorIri`). Blocking a follower severs
the relationship (the blocked follower's activities no longer reach the owner) via the signed
`BlockAsync` write to the owner's outbox.

This is a **practical management action** for the followers list: the owner can't "unfollow" a follower
in AP (the follower owns the follow edge), but can **block** them.

The **following list remains read-only** (no per-item Unfollow button) because the Decision 055
learned-id model requires the id of the original Follow activity to undo it, which the following
collection does not carry (it carries actor IRIs, not activity ids). The Unfollow capability is provided
by the existing "Follow / unfollow" card (which captures the learned id when the owner follows via this
UI).

## What changed (code)

- **`samples/SampleBlazorClient/Pages/ActorDetail.razor`**
  - **Markup:** the followers list items now include a "Block" button (when `IsOwnActor` is true). The
    button calls `BlockFollowerAsync(blockTarget)` with the follower's IRI.
  - **State:** `FollowersManagementBusy`, `FollowersManagementError`, `FollowersManagementResult`,
    `IsOwnActor` (a computed property: true when `Session.ActorIri.Value == ActorIri.Value`).
  - **`BlockFollowerAsync(Iri target)`:** the method that blocks the target follower. It calls
    `Session.GetClient().BlockAsync(actorIri, target)` (the signed write to the owner's outbox) and
    refreshes the owner's moderation counts (bypassing the page cache) so the new block is visible
    immediately.

## Key types / API

- `Session.GetClient().BlockAsync(actorIri, target)` — the signed Block write to the owner's outbox
  (the instance records the edge and federates to the target's inbox).
- `RefreshMyModerationAsync(bypassCache: true)` — re-reads the owner's mutes/blocks/flags counts
  (bypassing the page cache) so the new block is visible immediately.

## Decision: why the followers list gets a Block button (not an Unfollow button)

In AP, a **follower** is an actor that follows the owner. The follow edge is owned by the **follower**
(they sent the Follow activity). The owner can't "unfollow" a follower (there's no follow edge for the
owner to undo). But the owner **can** block the follower, which severs the relationship (the blocked
follower's activities no longer reach the owner). So the Block button is the practical management
action for the followers list.

The **following list** shows actors the owner follows. The owner **can** unfollow them (undo the follow
edge), but only if they have the **learned id** of the original Follow activity (Decision 055). The
following collection (`/following`) carries **actor IRIs**, not activity ids, so the page doesn't have
the learned ids for each follow. The Unfollow capability is provided by the existing "Follow / unfollow"
card (which captures the learned id when the owner follows via this UI).

## Direction note: sample-client UI is manual-tested (not bUnit-tested)

Per the current direction, the sample-client UI is **in flux and subject to a lot of change** once core
stuff is worked out. Rather than invest in bUnit tests for the sample UI (which would need to track every
UI change), the sample UI is **verified manually** (drive the screens through the browser). This change
follows that direction: the followers-list Block button is wired and builds clean, but has no bUnit
test. The underlying wire (the signed Block write) is proven by the existing server/client integration
tests.
