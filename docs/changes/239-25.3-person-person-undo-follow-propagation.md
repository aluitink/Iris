# 25.3 — Cross-instance person→person `Undo(Follow)` (un-follow) propagation

Phase 25, slice 3. **Type:** invariant lock (test-only — the person→person un-follow path was already
fully implemented; it was simply the one follow-flavored undo path with no end-to-end 2-instance test).

## Problem

`Undo(Follow)` (an un-follow) is the inverse of a follow, and Iris records/removes the directed
`follower → target` edge on **both** sides of the federation:

- **On the follower's home instance (A):** publishing `Undo(Follow)` to the follower's outbox runs
  `RecordUndoLocalAsync` → `RemoveFollowLocalAsync`, which removes the follower's local follow edge
  (`IFollowStore.RemoveFollowAsync`) and returns the *target's* IRI so the server can deliver the `Undo`
  to the remote side.
- **On the target's home instance (B):** the inbound `UndoActivityHandler` (recipient == target) resolves
  the original `Follow` from B's activity store (B stored it when the follow federated in) and removes the
  edge from the target's followers set (`IFollowStore.RemoveFollowAsync(follower, target)`) — the
  `recipientIri == targetIri` branch (the community-target and community-follower arms handle the G-24
  community edges).

The follow-flavored undo coverage was **incomplete**: the two community-initiated un-follows were already
locked end-to-end —

- `CommunityFollowsPersonUnfollowPropagationIntegrationTests` (community on A → person bob on B), and
- `CommunityFollowsCommunityUnfollowPropagationIntegrationTests` (community C on A → community D on B),

but a plain **person → person** un-follow — the *most common* real-federation flow — had **no** 2-instance
test. The single-instance `OutboxFollowDecisionIntegrationTests` collapses both sides into one store, so it
never exercises the B-side removal that depends on B having stored the original `Follow` (the cross-instance
dependency).

This slice locks that path.

## The cross-instance `Undo(Follow)` flow (what the test locks)

Topology: instance A hosts the local person `alice` (A's instance actor, the follower). Instance B hosts
the local person `bob` (B's instance actor, the follow target, so B's document fetcher is routable and bob
exists as a real local actor). A's outbound delivery worker routes to B; A's fetcher routes by actor-IRI
host (alice → A, bob → B); B's fetcher routes to A (to fetch alice's document and validate the signature
of the federated `Follow`/`Undo`). The client's writes are signed POSTs to alice's outbox on A; the
cross-instance hop (A → B) is made by A's server, signed as alice.

1. **The follow (A → B):** alice publishes `Follow(bob)` to her outbox on A. A records alice's local follow
   edge (`alice → bob` in A's follow store) and server-delivers the signed `Follow` to bob's inbox on B. B's
   `FollowActivityHandler` records the remote edge (bob's followers set lists alice; the `alice → bob` edge
   in B's follow store) **and stores the original `Follow` in B's activity store** — the copy the `Undo`
   later resolves against.
2. **The `Undo` (A → B, under test):** alice publishes `Undo(follow)` to her outbox on A. A's
   `RecordUndoLocalAsync` → `RemoveFollowLocalAsync` removes **A's** local edge and returns bob's IRI.
   Because bob is remote, A's outbox-publish handler **server-delivers the signed `Undo` to bob's inbox on
   B**. B's `UndoActivityHandler` (recipient == bob == target) resolves the original `Follow` from **B's**
   activity store and removes **B's** edge (alice from bob's followers set).

The edge is gone on B only if the `Undo` federated A → B **and** B had stored the original `Follow` (the
cross-instance dependency the single-instance test does not exercise).

## Where

- `tests/Iris.Server.Tests/PersonFollowsPersonUnfollowPropagationIntegrationTests.cs` (new, 2 tests,
  2-instance `TestServer`):
  - `PersonFollowOfRemotePerson_FederatesAndRecordsInRemoteFollowStore`: alice on A follows bob on B;
    asserts A records its local edge, B records the `alice → bob` edge, bob's followers list alice, and B
    stored the original `Follow` in its activity store.
  - `PersonUnfollowOfRemotePerson_FederatesAndRemovesFromRemoteFollowers`: alice on A follows bob on B
    (B records + stores the follow), then alice publishes `Undo(Follow)`; asserts A removes its local edge
    **and** B removes its edge (alice no longer in bob's followers set).

The test harness follows the existing cross-instance propagation tests (`LikeAnnounceUndoPropagation…` /
`CommunityFollowsPersonUnfollow…`): two `TestServer` instances, `SeedPersonWithKey`, a host-routed
`RoutingFetcher` for A + `BuildFetcherFor` for B, a `CaptureHandler`-based signed-request replay for the
outbox writes, and minted-id learning from the 202 body (decision 055).

## Design decision (recorded)

The 25.3 item named two candidate gaps: (a) a plain person→person `Undo(Follow)`, and (b) a community's
`Undo` of a join/membership decision. **This slice locks (a); (b) `Undo(Join)` is investigated and
deferred.** Rationale:

- **(a) is canonical and unambiguous.** A person unfollowing a remote person is a core, real federation
  flow; the inverse (`Undo(Follow)`) is the standard AS mechanism. No design fork.
- **(b) `Undo(Join)` is non-canonical.** Iris models community-membership departure as the standalone
  **`Leave`** activity (the AS2.0 membership primitive), which is *already* covered cross-instance by
  `MembershipFederationIntegrationTests` (`Leave_SignedByActor_DeliveredToCommunity_RemovesMember`). The
  `UndoActivityHandler` has no `Undo(Join)` branch and `RecordUndoLocalAsync` has no `Join` case — but no
  real peer sends `Undo(Join)` where a `Leave` is the standard. Adding a non-canonical inverse would
  exercise a code path with no real federation counterpart, for lower value than locking the canonical
  person un-follow. If a future phase wants full `Undo` symmetry for membership, that is a separate,
  deliberate decision (it would also need a `Join` arm in `RecordUndoLocalAsync`).

## Non-vacuity (proven)

Per the loop's "prove it fails" discipline, B's target-side removal was temporarily disabled in
`UndoActivityHandler.HandleAsync` — the `recipientIri == targetIri` branch's person-target
`RemoveFollowAsync(follower, target)` call was commented out:

- The **un-follow** test **fails** (times out waiting for B to remove the `alice → bob` edge — it never is,
  because B's handler no-ops the removal; assertion: "B should remove the alice → bob follow edge after A's
  server delivered the signed Undo").
- The **forward follow** test still **passes** (it does not depend on the removal path).

This confirms the un-follow test genuinely exercises B's removal path — it is not passing vacuously
(e.g. it would not pass merely because the edge was never recorded, nor because A's local removal
sufficed). Restoring the branch turns the un-follow test green.
