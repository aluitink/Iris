# 60.2 — Suppress 410 Gone console noise on Notifications

**Priority:** LOW
**Status:** COMPLETE

## Problem

The Notifications page emits ~28 browser console errors per page load:

```
[ERROR] Failed to load resource: the server responded with a status of 410
  () @ https://iris.luit.ink/ap/v1/proxy/https://remote.example/users/deadactor:0
```

The Blazor WASM client re-requests avatar/icon IRIs for dead remote actors on every
page load. Each request goes through the `POST /ap/v1/proxy/{target}` endpoint, which
forwards the request to the remote instance. The remote returns `410 Gone` (the actor no
longer exists), and the proxy relays that 410 to the browser. The browser logs every 4xx
as a console error, producing ~28 errors per page load.

## Root cause

The proxy handler (`ActivityPubServerExtensions.ProxyHandler`) is a stateless relay: it
forwards the request to the remote instance and relays the response. There is no caching
of 410 responses, so every page load re-fetches the same dead IRIs and re-emits the same
410 console noise.

## Fix

Added `ProxyGoneCache` (`src/Iris.Server/Http/Proxy/ProxyGoneCache.cs`): a bounded LRU
cache (capacity 4096, TTL 1 hour) that records targets that returned 410 Gone. The proxy
handler checks the cache before forwarding: if the target is known-gone and not expired,
it returns `204 No Content` (a success status — no browser console error) instead of
re-fetching. After forwarding, if the remote returns 410, the target is recorded in the
cache.

Key decisions:

- **204 No Content, not 404:** A 404 is still a 4xx status and the browser logs it as a
  console error. A 204 is a 2xx success status (no console error) and semantically means
  "no content" — the client's fallback avatar logic handles it the same as a 404.
- **1-hour TTL:** A resurrected remote instance is retried after the window. Long enough
  to suppress noise across a typical browsing session; short enough to pick up
  resurrected accounts.
- **4096 capacity:** The Notifications page has ~28 dead remote actors. 4096 is
  over-provisioned to handle larger timelines and multiple users.

## Verification

- `dotnet build -c Release` — 0 errors, 0 warnings
- `dotnet test --no-build -c Release` — **1651 passed, 0 failed, 17 skipped**
- **Playwright live test** (`https://iris.luit.ink/notifications`):
  - **First load** (cold cache): 28 errors, all 410s — expected (each dead actor fetched
    once, cached)
  - **Second load** (warm cache): **0 errors** — all gone targets short-circuit to 204
  - **Third load** (warm cache): 20 errors, all 429s (rate-limited), **0 410s** — the
    410 noise is fully eliminated; the 429s are from the separate `RateLimitingProxyPolicy`
    (60 req/min), which is working as designed

## Notes

- The 429 console errors on the third load are a **separate** issue (rate limiting is
  working as designed). They are not 410 Gone noise. A future item could raise the proxy
  rate limit or batch the client's avatar fetches to reduce 429s.
