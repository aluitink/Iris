# 275 — 31.2: `PagedCollection` initial-load re-render + error-state spinner guard

> 2026-09-05 · Slice 31.2 · Phase 31 (explorer UI & server namespace polish)

## What was built

The `PagedCollection` card is the shared paged-listing component behind the
followed-feed card and every actor-detail collection (outbox, liked, followers,
following, inbox, mutes, blocks, flags). Its first page was never shown after the
initial navigate — the card sat on the "Loading…" spinner until the user clicked
Refresh. Two defects, both fixed:

1. **Initial load never re-rendered the card (the 31.2 report).** `OnParametersSet`
   fires `_ = LoadInitialAsync()` as a **fire-and-forget** task. That method sets
   `Items = null` (the spinner state), awaits the fetch, and populates `Items` on
   completion — but never called `StateHasChanged()`. Because the load is neither
   an `@onclick` handler (which Blazor auto-re-renders) nor awaited by
   `OnParametersSet`, the render pass that committed the spinner was never re-run
   after `Items` was populated. The fix is one `StateHasChanged()` at the end of
   `LoadInitialAsync`, mirroring what Blazor does automatically for the
   `@onclick` handlers `LoadMoreAsync`/`RefreshAsync`. Because every collection
   card is a `PagedCollection`, this one fix repairs all of them at once.
2. **A failed initial fetch rendered the error *and* an eternal spinner.** When
   the fetch threw, `LoadInitialAsync`'s catch set `LoadError` but left `Items`
   null — so the card showed the error line **and** the spinner (the spinner is
   gated on `Items is null` alone). The spinner branch is now guarded on
   `LoadError is null`: a failed initial fetch shows only the error line, which
   is the card's content.

## Tests

4 new bUnit component tests, full fast suite green (1426/1426):

- `InitialLoad_RendersItems_WithoutManualRefresh` — the 31.2 invariant: a
  fire-and-forget initial load re-renders the card once the items arrive
  (spinner gone, both items present, exactly one collection call).
- `InitialLoad_EmptyCollection_RendersEmptyState_WithoutManualRefresh` — an empty
  first page settles into "No items." rather than spinning forever.
- `InitialLoad_Failure_RendersError_WithoutManualRefresh` — a fetch that fails
  *during enumeration* (a mid-request network failure, not a sync throw) settles
  into the error state with **no** spinner — pins the second fix.
- `NewCollectionIri_Reloads_FirstPage` — a new `CollectionIri` (navigating to a
  different actor/community card) triggers a fresh first-page load.

Test-harness notes: bUnit 2.9 uses `BunitContext` + `cut.WaitForAssertionAsync`
(the wait loop observes the fire-and-forget re-render — no manual dispatcher pump
needed). There is no `SetParametersAndRender` in 2.9, so the "new IRI" test
renders a second component instance with the new parameter — the same code path
the parent pages use (a fresh card per collection IRI). The error-state fake must
throw *during enumeration* (`Task.FromException` inside the async iterator); a
synchronous throw before the first `await` escapes the component's `try`/`catch`.

## Design notes

- **Why `StateHasChanged()` (not awaiting the load)?** Awaiting
  `LoadInitialAsync` from `OnParametersSet` is not possible — it is a synchronous
  lifecycle callback. The fire-and-forget + explicit `StateHasChanged()` is the
  idiomatic Blazor pattern for "start background work in a lifecycle callback and
  update the UI when it finishes," and it exactly mirrors the auto-re-render the
  `@onclick` handlers already rely on.
- **Why guard the spinner on `LoadError` (not set `Items = []` on failure)?**
  `Items = []` would make the empty state ("No items.") render *under* the error
  line — a wrong signal (the collection is not empty; the read failed). Keeping
  `Items` null on failure and suppressing the spinner leaves the error line as
  the sole card content, which is the honest state.
- No new NuGet packages (`bunit` was already pinned); no public API changes.
