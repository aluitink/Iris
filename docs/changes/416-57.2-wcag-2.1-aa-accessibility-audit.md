# 57.2 — WCAG 2.1 AA accessibility audit

## Summary

Systematic review of all 35 `.razor` files and `app.css` against WCAG 2.1 AA. Found and fixed: missing ARIA tab patterns on 5 pages, non-keyboard-accessible expand in DirectoryCard, 2 color-contrast failures, and a missing focus style.

## Findings and fixes

### Critical

1. **Missing ARIA tab pattern** (WCAG 4.1.2 — Name, Role, Value)
   - **Files:** `Settings.razor`, `ActorDetail.razor`, `Profile.razor`, `Directory.razor`, `CommunityDetail.razor`
   - **Issue:** Tab bars used plain `<a>` elements with no `role="tab"`, `role="tablist"`, `aria-selected`, or `role="tabpanel"` on the content panels. Screen readers could not identify the tab structure.
   - **Fix:** Added `role="tablist"` with `aria-label` to each tab bar, `role="tab"` + `aria-selected` + `aria-controls` + `id` to each tab link, and `role="tabpanel"` + `aria-labelledby` + `id` to each content panel.

2. **Non-keyboard-accessible expand** (WCAG 2.1.1 — Keyboard)
   - **File:** `DirectoryCard.razor`
   - **Issue:** The card header was a `<div>` with `@onclick` — no keyboard equivalent. The expand indicator was a `<span>` with `aria-label` but no interactive role.
   - **Fix:** Changed the header to a `<button type="button">` with `aria-expanded` and `aria-label`. Made the expand indicator `aria-hidden="true"` (the button's `aria-label` provides the accessible name). Added CSS resets (`background: none; border: none; color: inherit; font: inherit; text-align: left; width: 100%`) so the button renders identically to the old div.

### Major

3. **Color contrast — `.stat-value`** (WCAG 1.4.3)
   - **File:** `app.css`
   - **Issue:** Used `var(--color-accent, #4a6cf7)` — the `--color-accent` token is undefined, so the fallback `#4a6cf7` on `#191d24` gives a contrast ratio of ~4.1:1 (below 4.5:1 for normal text).
   - **Fix:** Changed to `var(--accent, #5b8cff)` — the defined token `#5b8cff` on `#191d24` gives ~4.8:1.

4. **Color contrast — `.stat-label`** (WCAG 1.4.3)
   - **File:** `app.css`
   - **Issue:** Used `var(--color-muted, #6b7280)` — the `--color-muted` token is undefined, so the fallback `#6b7280` on `#191d24` gives a contrast ratio of ~3.9:1.
   - **Fix:** Changed to `var(--muted, #8b93a1)` — the defined token `#8b93a1` on `#191d24` gives ~5.5:1.

5. **Color contrast — `.footer-links a`** (WCAG 1.4.3)
   - **File:** `app.css`
   - **Issue:** `var(--muted)` (`#8b93a1`) at `font-size: 0.8rem` on `#111318` gives ~4.6:1 — technically passing, but the hover state used `--accent-warm` without a matching `:focus-visible` style, so keyboard users got no visual change on hover-equivalent.
   - **Fix:** Added `:focus-visible` to the hover rule so keyboard focus also gets the accent-warm color + underline.

### Assessed (no change)

- **`:focus-visible` styles** (WCAG 2.4.7): Already well-implemented — `a:focus-visible, button:focus-visible, [role="button"]:focus-visible, input:focus-visible, textarea:focus-visible, select:focus-visible, [tabindex]:focus-visible` all get `outline: 3px solid var(--accent-warm); outline-offset: 2px`.
- **Form labels** (WCAG 3.3.2): All inputs have associated `<label>` elements.
- **Error/success announcements** (WCAG 4.1.3): All use `role="alert"` or `role="status"`.
- **Loading spinners**: All have `aria-hidden="true"` + visible text alternative.
- **Heading structure**: All pages have exactly one `<h1>`, no level skips.
