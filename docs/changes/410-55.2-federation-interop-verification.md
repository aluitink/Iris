# 55.2 — Federation Interop Hardening: Live Cross-Instance Verification

## Summary

Stood up a second Iris instance (`iris-dev2.luit.ink`, port 8082) alongside the production
instance (`iris.luit.ink`, port 8088) on the shared Docker network. Verified cross-instance
reachability in both directions. Began live federation testing via the WASM client (carol on
instance 2 searches for + follows alice on instance 1).

**Defect found:** Remote actor search returns the **local** instance's actor IRI instead of
the **remote** one. When carol (iris-dev2) searches for `alice@iris.luit.ink`, the search
correctly resolves alice via WebFinger (through the proxy) and fetches the remote actor doc
(via the proxy — confirmed correct remote IRI `https://iris.luit.ink/ap/v1/u/alice` in the
proxy response). However, the rendered search result links to
`/actor?iri=https://iris-dev2.luit.ink/ap/v1/u/alice` (the **local** IRI), and the actor
profile page shows no posts, 0 followers, and a Follow button that would follow the wrong
actor.

## Defect: Remote Actor IRI Rewritten to Local Base

**Repro:**
1. Log in as carol on `https://iris-dev2.luit.ink`.
2. Search for `alice@iris.luit.ink`.
3. Search finds 1 result: "alice" with "(remote: iris.luit.ink)" annotation.
4. Click the result → `/actor?iri=https://iris-dev2.luit.ink/ap/v1/u/alice` (WRONG IRI).
5. Actor profile shows: name "alice", no posts, 0 followers, Follow button (for wrong actor).

**Network trace (browser):**
```
POST /ap/v1/proxy/https%3A%2F%2Firis.luit.ink%2F.well-known%2Fwebfinger...  → 200 (proxy, correct)
POST /ap/v1/proxy/https://iris-dev2.luit.ink/ap/v1/search?q=...             → 200 (proxy, local search)
POST /ap/v1/proxy/https%3A%2F%2Firis.luit.ink%2Fsearch%3Fq%3D...             → 200 (proxy, remote search)
GET  /ap/v1/u/alice                                                        → 200 (DIRECT, local instance — BUG)
```

The 4th request (actor doc fetch) goes **directly** to the local instance's `/ap/v1/u/alice`
endpoint instead of through the proxy. The local instance serves a local actor doc for `alice`
with the local IRI `https://iris-dev2.luit.ink/ap/v1/u/alice`.

**Root cause hypothesis:** The WASM client's `GetObjectAsync(remoteIri)` is not routing the
remote actor IRI through the `ProxyFallbackHandler`'s cross-instance-read path. Instead, the
`SameOriginApHandler` (or another handler in the pipeline) is rewriting the remote IRI to a
local path before the proxy fallback can engage. The proxy itself works correctly (verified via
direct browser `fetch` to the proxy endpoint — returns the correct remote IRI). The bug is in
the client-side handler pipeline ordering or the cross-instance-read host comparison.

**Impact:** Any remote actor fetched via the WASM client (search, follow, profile view) gets
the wrong IRI. Follows go to the wrong actor. Profiles show no posts. This breaks the core
federation use case (interacting with remote users).

**Status:** DEFECT FOUND — requires fix in the WASM client's handler pipeline. The
`ProxyFallbackHandler`'s cross-instance-read path (lines 151-157) should route the GET through
the proxy, but the network trace shows a direct local GET instead. Investigation needed in the
next slice.
