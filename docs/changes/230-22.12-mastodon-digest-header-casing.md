# 22.12 — Mastodon / draft-10 `Digest` header casing on the inbound server→server path

Phase 23, slice 2. **Type:** test-only (invariant lock — no production code change; the verifier already
handles both casings correctly).

## Problem (and why it is a test, not a fix)

A strict Mastodon peer (draft-10 of the HTTP signatures spec) emits the digest header as
`Digest: SHA-256=<base64>` — **uppercase** algorithm label. Iris's own sender
(`Signatures.ComputeDigest`) emits `sha-256=<base64>` — **lowercase**. The base64 is identical; only the
label case differs.

The question this slice answers: **does an inbound request carrying the draft-10 uppercase `Digest` value
verify?** The answer, traced through the code, is **yes** — and it was already true before this change:

- `HttpSignatureValidator.ToMetadata` (src/Iris.Server/Security/HttpSignatureValidator.cs:178) reads the
  `Digest` header value **verbatim** off the wire (case-insensitive header lookup; the value is not
  canonicalized).
- `Signatures.BuildSignatureBase` (src/Iris.Core/Signing/Signatures.cs:190) embeds that verbatim value into
  the signature base. It does **not** recompute the digest or compare it against a freshly-computed one —
  it trusts the declared wire value.
- Therefore the base the remote sender signed over (embedding its uppercase `SHA-256=…`) byte-matches the
  base Iris reconstructs from the wire, and the signature verifies. Both casings round-trip.

There is no bug to fix: the integrity of the digest value is enforced **by the signature itself** (a
tampered `Digest` header changes the base, which the signature no longer covers → 401), not by Iris
recomputing it. This slice **locks that invariant with tests** so a future change that "helpfully"
recomputes or normalizes the digest label is caught — for **both** casings.

This is the locally-testable proxy for the U-5 "a strict draft-10 sender is accepted" live confirmation:
the `Digest` label casing is the most concrete draft-10 wire difference Iris can exercise in-process (the
rest of U-5 — a real remote account — is deferred to live interop).

## Where (tests only)

- `tests/Iris.Core.Tests/Signing/SignaturesTests.cs` (2 new unit tests):
  1. `BuildSignatureBase_ServerToServer_EmbodiesUppercaseDigestVerbatim` — asserts the signature base
     embeds an uppercase `SHA-256=…` digest value **verbatim** (byte-exact base).
  2. `ServerToServer_UppercaseDigestHeader_SignAndVerifyRoundTrips` — the full round-trip: sign over a base
     embedding the uppercase digest, then `HttpSignatureVerifier.Verify` (which reconstructs the base from
     the wire) accepts. Proves the crypto path is casing-agnostic by verbatim embedding.
- `tests/Iris.Server.Tests/InboundUppercaseDigestIntegrationTests.cs` (3 new integration tests), a
  single-instance `TestServer` topology (alice, signed inbox endpoint) mirroring
  `MastodonPollInboundIntegrationTests`:
  1. `Inbox_AcceptsInboundCreate_WithUppercaseDraft10DigestHeader` — a local-actor `Create` signed with the
     `Digest: SHA-256=<b64>` **uppercase** wire form is accepted (202) **and** processed (the embedded
     `Note` is stored and served by its IRI). This is the draft-10/Mastodon inbound form.
  2. `Inbox_AcceptsInboundCreate_WithLowerCaseDigestHeader` — the complement: the Iris-native lowercase
     `sha-256=<b64>` form is also accepted. Both casings round-trip.
  3. `Inbox_RejectsInboundCreate_WhenDigestValueIsTampered` — a request whose on-the-wire `Digest` header
     carries a value **different** from the one the signature was computed over is rejected (401), proving
     the digest's integrity is enforced by the signature (guard against a future change that stops
     checking it).

## Verification

- Core unit tests: `SignaturesTests` 13 → 15 (+2). The round-trip test passing confirms the uppercase wire
  form verifies at the crypto level.
- Integration tests: `InboundUppercaseDigestIntegrationTests` (3). The uppercase test passing confirms the
  draft-10 wire form is accepted end-to-end through the real signed-inbox middleware; the tamper test
  passing (401) confirms the digest is integrity-checked by signature.
- These are **invariant locks**: the uppercase path was already green before this slice (the verifier
