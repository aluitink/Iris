# 184 — Phase 22.2: instance page — WebFinger handle lookup (US-10)

## Summary

Second 22.2 sub-slice (detail pages on the shared components). The instance page
(`Instance`) gains the second half of US-10 — a **WebFinger handle-lookup** card — so a user can
resolve a `handle@host` address to an actor IRI and jump to that actor's detail page. The page
already showed nodeinfo (name, software, version, open-registration); this adds the handle
resolution.

- **US-10 (WebFinger lookup).** A new "Resolve a handle (WebFinger)" card: the user enters a handle
  (e.g. `alice@iris-dev1.luit.ink`), clicks **Resolve**, and the session's
  `IDiscoveryService.ResolveActorAsync` dials the current instance's base URI to fetch the
  `/.well-known/webfinger` document. A successful resolve renders the actor IRI as a deep-link to
  `/actor?iri=…` (which opens the actor detail page); a failure (unknown handle, no match, or a
  transport error) renders a clear error message.

This is the instance slice of 22.2. Combined with the actor slice (change 183), the actor page
(US-5/15/16/17) and the instance page (US-10) are complete for 22.2. The remaining 22.2 work is the
object page (US-7/12/13/14) and community (US-6/18).

## What changed (code)

- **`samples/SampleBlazorClient/Pages/Instance.razor`**
  - New "Resolve a handle (WebFinger)" card between the nodeinfo card and the recent-instances card:
    a text input (`LookupHandle`), a **Resolve** button, a busy indicator, an error line, and — on
    success — the resolved actor IRI as an `<a href="@LookupHref">` deep-link; on a failed attempt
    with no result, a "Could not resolve that address on this instance." note.
  - New state: `LookupHandle` (bound input), `LookupHandleInput` (the submitted value), `LookupIri`
    (the resolved `Iri?`), `LookupAttempted` (so "could not resolve" only shows after an attempt),
    `LookupBusy`, `LookupError`.
  - New `LookupAsync()`: trims the input, guards empty, and calls
    `Session.Discovery.ResolveActorAsync(handle, Session.DialBaseUri)` (the dial-base overload). A
    `null` result → "did not resolve" error; an exception → its message.
  - New computed `DialBaseLabel` (the dial base for the help text) and `LookupHref` (the
    `/actor?iri=…` URL, or null until a successful resolve).

## Key types / API

- No new `Iris.Core` / `Iris.Client` API. `IDiscoveryService.ResolveActorAsync(string account,
  Uri dialBaseUri, CancellationToken ct = default)` is the existing seam the log-on flow uses
  (`ExplorerSession.LogOnAsync`); the instance page reuses it, dialing the current instance's base
  URI (the host-published port for local instances) so the well-known document is browser-reachable.
  The query resource still carries the handle's host (the account string the user typed), so the
  instance knows which actor to resolve.
- `Session.Discovery` is the `IDiscoveryService?` the session exposes once logged on; `Session.
  DialBaseUri` is the base the client dials.

## Verification

Manual, on the docker compose FQDN stack (the binding test method for the sample UI, per
`docs/reference/TESTING.md`): `docker compose -f docker-compose.yml up --build` → three healthy
services (`iris-a` :8081, `iris-b` :8082, `iris-ui` :8090), instances advertising
`iris-dev1.luit.ink` / `iris-dev2.luit.ink`.

- **Log on** via Home: `alice@iris-dev1.luit.ink`, password `iris-sample`, base
  `http://localhost:8081` → session `https://iris-dev1.luit.ink/ap/v1/u/alice`.
- **Instance page:** the nodeinfo card (instance name, software, protocols, open-registrations) and
  the new "Resolve a handle (WebFinger)" card render (dial base shown as `http://localhost:8081/`).
- **US-10 (success):** enter `bob@iris-dev1.luit.ink` → Resolve. The card shows
  "Resolved bob@iris-dev1.luit.ink → https://iris-dev1.luit.ink/ap/v1/u/bob" as a deep-link
  (`href="/actor?iri=https%3A%2F%2Firis-dev1.luit.ink%2Fap%2Fv1%2Fu%2Fbob"`). Clicking it navigates to
  bob's actor detail page (which renders, including the `Liked` card added in change 183).
- **US-10 (failure):** enter `nonexistent@iris-dev1.luit.ink` → Resolve. The card shows the error
  "The instance did not resolve that address (unknown handle or no WebFinger match)." plus
  "Could not resolve that address on this instance." with no link — a clean failure state (no raw
  dump).
- **Console:** the only errors are the pre-existing `bob/inbox` 403 (private collection, non-admin)
  and the WebFinger **404** for the unknown handle (correctly caught and surfaced as the friendly
  message) — no Blazor render exceptions.

## Decisions

- **The lookup dials the current instance's base, not the handle's own host.** `ResolveActorAsync`
  has two overloads: one dials the address's own host (`dialScheme`), the other dials an explicit
  `dialBaseUri`. The instance page uses the **dial-base** overload with `Session.DialBaseUri` — the
  same authority the session uses to reach the instance. For a local Docker instance the handle's
  advertised host (`iris-dev1.luit.ink`) is not browser-reachable, but the host-published port
  (`http://localhost:8081`) is; dialing the base makes the well-known document fetch succeed. The
  query resource still carries the handle's host, so the instance resolves the right actor. (This is
  exactly the seam the log-on flow relies on.)
- **The resolved IRI is a deep-link, not an auto-navigation.** The card shows the IRI as a link to
  `/actor?iri=…`; the user clicks to open the detail page. This keeps the lookup a deliberate
  "resolve and jump" action (matching the recent-instances "Use" → "Switch" two-step) rather than
  surprising the user with an immediate navigation, and it reuses the actor page's existing
  `?iri=` deep-link (US-22).
- **`LookupHref` / `DialBaseLabel` are properties, not inline interpolation.** A C# string
  interpolation with braces inside Razor markup (e.g. `href="@($/actor?iri={…}")`) is mis-parsed —
  Razor reads the `{…}` as a code-block delimiter, not an interpolation hole. Hoisting the URL (and
  the dial-base label) to `string` properties keeps the markup as plain `@LookupHref` expressions.

## Scope / limits

- This closes **US-10** (the WebFinger lookup half; the nodeinfo half was already present). The
  lookup resolves against the **current** instance's base; to resolve on another host, switch
  instance first (recent-instances card) — the dial base then changes. A "resolve on a specific
  host" control is out of scope for this slice (it would need a per-lookup dial-base override).
- The instance page is now complete for 22.2. Remaining 22.2 work: the **object page** (US-7/12/13/14)
  and the **community page** (US-6/18).
