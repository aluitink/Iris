# 289 — 32.4b: product screens — compose + profile

> 2026-09-06 · Slice 32.4b · Phase 32 (production social platform app) — step 4 (product screens, second sub-slice)

## What was built

Phase 32's **step 4**, second sub-slice, adds the two write/identity screens to the signed-in
product shell built in 32.4a: the **compose** screen (post a note as the signed-in actor) and the
**profile** screen (the actor's own header + their outbox, "your posts"). Together with 32.4a's
`/home` timeline, a signed-in user can now *write* (compose), *read what they wrote* (profile /
outbox), and *read what they follow* (home timeline).

Per the feature-set plan (`docs/plans/production-app-feature-set.md` §1), this remains a
**functionality-first** pass. Compose is a single text note addressed to the ActivityStreams
`as:Public` collection (content warnings, media attachments, and reply threading are later
experience-pass items — F-28 / F-11 / F-12). The profile is the actor's own document + outbox;
browsing *other* actors' profiles (the `/actor/{iri}` detail surface) is the 31.5/31.6 `ActorDetail`
work in the sample client and is not re-landed in `Iris.Web` in this slice.

The compose write path is the one sanctioned path from the UI into ActivityPub state: it calls the
session's `IActivityPubClient.PostNoteAsync(actorId, content, to: [as:Public])`, which builds the
`Note` and publishes a signed `Create` to the actor's own outbox. The profile's "Your posts" card
reads back that same outbox, so the two screens are verified as a **vertical slice** — post in
compose, see the resulting `Create` (and its embedded `Note`) in the profile's outbox.

## Key types & files

### Components — `apps/Iris.Web/Components/`
- `Pages/Compose.razor` — `@page "/compose"`, `[Authorize]`. Reads the signed-in actor's
  `IActivityPubClient` + `ActorId` from `IActorSessionAccessor`. A single textarea composes the note;
  a "Post note" button (disabled while in flight) calls `PostAsync`, which posts a text note addressed
  to the ActivityStreams public collection (`as:Public`) via `Client.PostNoteAsync(actorId, content,
  to: [AsPublic])`. On success it shows the minted `Create` IRI (`DeliveryResult.MintedId`), clears the
  composer, and reveals a "View your posts →" link to `/profile` (the outbox where the note now
  lives). A failure shows the HTTP status; an exception shows its message. The "Posting as" line shows
  the actor IRI so the user can confirm identity.
- `Pages/Profile.razor` — `@page "/profile"`, `[Authorize]`. Loads the signed-in actor's document
  (`Client.GetActorAsync(ActorId)`) in `OnParametersSet` and renders an `<ActorProfile>` header, then a
  **`PagedCollection`** (the 32.4a pager) over `ActorId.OutboxOf()` titled "Your posts" — the actor's
  outbox, newest first, paged with next-link walking. A stable `@key` (`"profile-outbox"`) keys the
  pager.
- `ActorProfile.razor` — a ported profile-header component (from the reference `SampleBlazorClient`'s
  31.5 `ActorProfile`): given an `IObject? Actor` (+ a fallback `string? ActorId`), it pattern-matches
  the actor and renders the avatar (the `icon` IRI, or a colored initial fallback), the handle, the
  name (suppressed when it is redundant with the handle), the summary, and the actor IRI (linked).
  Reusable for the 32.4c/other screens that need an actor header.

### Wiring
- `Layout/MainLayout.razor` — the signed-in nav gains a **"＋ New post"** link to `/compose` (the
  compose entry point), alongside the 32.4a Home / Notifications / Directory / Profile / Search links.
- `wwwroot/css/app.css` — added the compose card (`compose-card` / `compose-content` / `compose-hint` /
  `compose-actions` / `compose-result` / `compose-result-iri`), the profile loading state, the

## Tests

`tests/Iris.Web.Tests/ComposeProfileIntegrationTests.cs` — 5 integration tests that boot the real app
(in-memory, the default) in a `TestServer` and assert the HTTP-observable contract:
- **`/compose` signed-out → 302 to `/login`** and **`/profile` signed-out → 302 to `/login`**: the
  `[Authorize]` attribute + the cookie scheme's `LoginPath` redirect an unauthenticated request to
  `/login` (with a `ReturnUrl` so the user lands back on the page they wanted).
- **`/compose` signed-in → 200 with the composer markup** ("Compose", "Posting as", the content
  textarea, the "Post note" button) and **`/profile` signed-in → 200 with the profile + outbox card**
  markup ("Your profile", "Your posts", the `paged-collection` container). The actor document + outbox
  items themselves are loaded by the interactive circuit, so they are not in the static prerendered
  HTML.
- **compose → outbox round-trip (the vertical contract):** signs in a real local account over the real
  HTTP surface, resolves the session's `IActivityPubClient` from DI exactly the way
  `ActorSessionAccessor` does (the `IActivityPubClientFactory` signs with the shared key store), dials
  the TestServer **in-process**, and calls the same `PostNoteAsync` the compose page makes. It then
  `GET`s the actor's outbox over the ActivityPub HTTP surface and asserts the posted note's content is
  present (the outbox's items are full `Create` activities with the embedded `Note`).

To make the round-trip test pass in-process, the test host overrides the `IActorDocumentFetcher`
(`AddActivityPubServer` registers it with `TryAddSingleton`, so the later test registration wins) with
one whose client dials the TestServer in-process via the TestServer's `CreateHandler()`. Without this,
the inbound signature validator (`RemoteInboundKeyResolver`) would attempt a real TCP connection to
`web.test.local:443` to resolve the local actor's signing key, which does not exist in the test host.
This mirrors the same-origin path production takes when a local actor posts to its own outbox (the
actor's key is resolved by fetching the actor's own document on the same origin).

The interactive circuit's client-side render (the compose button's `@onclick` → `PostNoteAsync` → the
minted-IRI reveal; the profile page's live actor-doc + outbox fetch) is **not** exercisable over
`TestServer` HTTP (it is a circuit action / circuit render) — it is verified live via the MCP
Playwright server, per the feature-set plan. The live click-through confirmed: register
(`e2e-composer`) → `/compose` (composer renders, "Posting as" the new actor) → type + post a note
("Posted (HTTP 202)" + the minted `Create` IRI + "View your posts →") → `/profile` (the profile header
+ the "Your posts" outbox card showing the `Create` for that IRI). The posted `Note`'s content was
also confirmed retrievable over the raw ActivityPub HTTP surface
(`GET /ap/v1/u/e2e-composer/creates/{id}` → `Create` → `Note` with the exact text).

## Decisions

- **Compose posts a single public text note via `PostNoteAsync(actorId, content, to: [as:Public])`.**
  The `as:Public` `to` audience is the conventional public address: the note is stored in the actor's
  outbox *and* fanned out to the actor's followers' feeds (F-14). This is the minimal, honest write
  path — no media, no CW, no reply threading yet (those are the experience-pass items F-28 / F-11 /
  F-12). The `Content.Trim()` guard + the `is not { }` pattern guards (rather than nullable-`Iri`
  arithmetic) keep the `net10.0` / `TreatWarningsAsErrors` build clean.
- **The profile reads the outbox via `ActorId.OutboxOf()`** (the `IriExtensions.OutboxOf` helper) with
  the 32.4a `PagedCollection` pager — the same reusable pager used for the home timeline, so outbox /
  followers / following / community feeds all share one paging component. "Your posts" is the actor's
  own outbox (newest first), not the followed feed.
- **`ActorProfile` is a ported, reusable header component** (avatar/handle/name/summary/IRI with an
  initial fallback), matching the sample client's 31.5 design. It is parameterized on `IObject? Actor`
  so it can render a freshly-fetched actor document (the profile page) or a cached one (later
  actor-detail screens).
- **The compose → outbox test dials in-process and overrides the actor-document fetcher.** A raw
  `HttpClientHandler` (or the default fetcher) would attempt a real TCP connection to
  `web.test.local:443` — the TestServer only intercepts requests that go through its own handler.
  The test therefore (a) builds the session client with `_server.CreateHandler()` and (b) re-registers
  the `IActorDocumentFetcher` so the inbound signature validator resolves the local actor's key by
  fetching the actor's own document in-process. This is the faithful same-origin path production uses
  for a local actor posting to its own outbox — no production code is special-cased.
- **The `/object?iri=…` viewer 404s for now.** The profile's outbox `Create` items link to an
  `/object?iri=…` route that does not yet exist in `Iris.Web` (the object-detail viewer is a later
  slice). This is acceptable for a functionality-first pass and is called out here rather than hiding
  the links; the outbox data itself is complete and retrievable over the raw ActivityPub surface.
