# 196 — 19.6 Docker-only-routable IRI normalization (outbox write path) + regression tests

**Phase 19.6** (C2S invariants), outbox write-path fix + CI-pinned regression tests.

## The bug

On the local compose stack, a signed **Follow** of a *local* actor (e.g. `alice` following `bob` on
the same instance) returned **500** — even though the target is on the same instance. Root cause,
found while driving the actor-detail write buttons through the browser (the 19.6.1 UI half):

- The authoring **client dials** the instance on a host-published base (`http://localhost:8081`) and
  carries **that** base in the activity's object reference (the `Follow`'s `object` →
  `http://localhost:8081/ap/v1/u/bob`).
- The instance **stores** its local actors under the **advertised** base
  (`https://iris-dev1.luit.ink/ap/v1/u/bob`).
- The local-actor check (`DefaultLocalActorResolver.IsLocalActorAsync`) is an **exact-IRI** store
  lookup. The dial-base IRI is not in the store → the lookup misses → the server treats its **own**
  actor as **remote** → it attempts a cross-instance delivery to `localhost:8081` **from inside the
  container** → `Connection refused (localhost:8081)` → 500.

The same class of mismatch affects `Block`/`Flag` (single local targets) and any object reference
carrying the dial base instead of the advertised base.

## The fix

`src/Iris.Server/ActivityPubServerExtensions.cs`:

- **`NormalizeLocalActorObjectIriAsync`** (new private static helper, ~line 2800). When the
  outbox-published activity's `object` is a **local** person (`/ap/v1/u/{handle}`) or community
  (`/ap/v1/c/{name}`) reached via a base that differs from the instance's advertised base, it rewrites
  the reference to the advertised (canonical) IRI before the edge is recorded. It is a **no-op** when
  the object is already on the advertised base, is not a local-actor/community path, or the
  actor/community is not local (confirmed against the stores). Only the first object reference is
  normalized (a person/community `Follow`/`Block`/`Flag` carries exactly one target).
- **Called** from the outbox publish handler right after the acting-actor check (~line 1593), **before**
  the server mints the id (decision 055) and records the edge — so the recorded `Follow`/`Block`/`Flag`
  edge uses the canonical IRI and **no cross-instance hop is attempted**.
- **Diagnostic logging** in the outbox publish handler's catch block (~line 1692): the 500 now logs the
  underlying exception (`ILoggerFactory` resolved from `context.RequestServices`, since
  `ILogger`/`ILogger<T>` are not constructor-injectable into a minimal-API handler) instead of failing
  silently. This is what surfaced the `Connection refused` in the first place.

Verified end-to-end on the compose stack via the browser: a duplicate Follow of `bob` now returns
`202 IsSuccess=True` and the minted activity's `object` is the advertised IRI
(`https://iris-dev1.luit.ink/ap/v1/u/bob`, rewritten from the dial base); the matching **Unfollow**
(Undo) also returns `202` and references the Follow's minted id.

## Regression tests (CI-pinned)

`tests/Iris.Server.Tests/OutboxDialBaseIriNormalizationIntegrationTests.cs` (new) — three
`TestServer` integration tests against a single instance whose **advertised host is
`iris-dev1.luit.ink`** while the signed request is authored against the **dial base
`http://localhost:8081`**:

- **`OutboxPublish_Follow_LocalTargetViaDialBase_RewritesToAdvertisedBase_NoDelivery`** — a Follow whose
  `object` is the local `bob` via the **dial base** is accepted (202), the `alice → bob` edge is
  recorded **under the advertised IRI** (not the dial-base IRI), and **no cross-instance delivery is
  attempted** (a `ThrowingHandler` delivery transport would fail the write if one were). Before the fix
  this test 500'd.
- **`OutboxPublish_Follow_LocalTargetViaAdvertisedBase_Untouched`** — the canonical case: an object
  already on the advertised base is left untouched and the edge is recorded as-is.
- **`OutboxPublish_Follow_RemoteTarget_NotRewritten`** — a Follow of a genuinely **remote** actor (a
  foreign host) is **not** rewritten to the advertised base; the edge is recorded under the remote
  actor's IRI.

The inbound key resolver needs the signing actor's document (to read its `publicKey`), so the host is
given a `Fetcher` (`IrisActorDocumentFetcher`) routed to its own `TestServer` (the shared
`Iris.Testing.LazyHandler` defers the `TestServer` handler until first use, breaking the
construct-before-server chicken-and-egg). The delivery transport is a `ThrowingHandler`: any accidental
cross-instance hop fails the test fast instead of hanging on a real network call.
