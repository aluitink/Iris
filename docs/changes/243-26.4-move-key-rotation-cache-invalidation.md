# 243 — Phase 26.4: `Move` key-rotation cache invalidation (F-25)

**Slice:** 26.4
**Outcome:** **Test-only lock** (no production code change). The `MoveActivityHandler`'s F-25 cache invalidation already exists and is unit-tested, but no **end-to-end** 2-instance test locked the full path (warm cache → `Move` invalidates → old-key delivery rejected, new-key delivery accepted). New `MoveKeyRotationIntegrationTests` (1, 2-instance `TestServer`) closes that gap.

## The slice's claim

> Lock the full `Move` path — alice migrates from an old IRI (A) to a new IRI (B) with a new key; B re-points the follow edge AND clears alice's cached key/actor; a subsequent delivery signed as the new alice (new key) is validated by B by fetching the new actor document (not the stale cached one). Proven non-vacuous (a stale key cache would 401 the new signature).

## What already existed (and why it was not sufficient)

- **`MoveActivityHandler`** (`src/Iris.Server/Inbox/MoveActivityHandler.cs`) already implements F-25: on an inbound `Move` it re-points local person/community follow edges (F-08) **and** clears the moving actor's `RemoteActorCache[oldIri]` + `RemoteKeyCache[oldIri#key-1]` entries (lines 91–99), so the next key resolution fetches fresh rather than serving the stale cached old key.
- **Unit tests** (`tests/Iris.Server.Tests/MoveActivityHandlerTests`) lock the cache invalidation in isolation (the handler is constructed with explicit caches and the test asserts `Invalidate` is called for the right IRIs).
- **`MoveFederationIntegrationTests`** (Phase 12.4) lock the **edge re-pointing** end-to-end (2-instance: a `Move` signed by the moving actor re-points bob's edge + the community's follows set).
- **`KeyRotationFederationIntegrationTests`** (Phase 12, F-21) lock the **same-key-IRI** rotation path (the validator's re-resolve-on-verification-failure), which is a *different* mechanism from F-25.

**The gap:** no integration test proved the F-25 invalidation **end-to-end** through the real signature-validation pipeline — i.e., that after a `Move`, B's *stale* cached old key is actually gone, so a delivery signed with the old key is no longer accepted from the cache (it forces a re-fetch), while a delivery signed with the new key is accepted via a fresh fetch of the new actor document.

## What was built

`tests/Iris.Server.Tests/MoveKeyRotationIntegrationTests.cs` — 1 `[Fact]`, 2-instance `TestServer` (A and B), modeled on `MoveFederationIntegrationTests` + `KeyRotationFederationIntegrationTests` (the F-21 test's pattern of sharing the DI `RemoteActorCache` via `extraServices` + the fetcher, so the handler's invalidation hits the cache the validator reads).

**Topology:** old alice on A (`https://a.domain.local/ap/v1/u/alice`, old key), bob on B (follows old alice), new alice on A (`https://a.domain.local/ap/v1/u/alice-2`, new key — a same-host migration to a new path, so B resolves the new key by a *remote* fetch of A's new-actor doc, not a local lookup).

**The test (`Move_InvalidateOldKey_OldKeyRejectedAfterMove_NewKeyAcceptedAfterMove`) runs three phases:**

1. **Warm.** Old alice (old IRI, old key) delivers a signed `Follow` to bob. B resolves her key by fetching A's actor doc and caches both the actor doc (`RemoteActorCache[oldIri]`) and the key (`RemoteKeyCache[oldIri#key-1]`). Accepted (202). Asserts `RemoteKeyCache.Count == 1` (the stale entry the `Move` must clear).
2. **Move.** Old alice delivers a `Move` (old IRI → new IRI). B validates it (the old key is still valid on A at this point) and the `MoveActivityHandler` re-points bob's edge to the new IRI **and** invalidates the old IRI's cache entries. Asserts: bob no longer follows the old IRI, now follows the new IRI, and `RemoteKeyCache.Count == 0` (the F-25 invalidation ran).
3. **Rotate.** A decommissions the old IRI (`ActorStore.RemoveActorAsync(oldIri)` + invalidate A's `LocalActorDocumentCache` so A's endpoint reflects the removal). Then:
   - **3a:** a delivery signed with the **old** key is **rejected (401)** — B's cache for the old key IRI was cleared by the `Move`, so B re-fetches A's old IRI (now 404) and cannot resolve the key.
   - **3b:** a delivery signed with the **new** key (new IRI) is **accepted (202)** — B resolves the new key by fetching the new actor doc fresh (the new IRI was never cached). Asserts B stored the new-key follow.

## Why it is non-vacuous

The non-vacuous signal is the **Phase 1 → Phase 3a contrast**: the *same* old-key signature that was accepted in Phase 1 (202, from the warm cache) is rejected in Phase 3a (401) *after* the `Move`. The 401 is **only reachable if** the `MoveActivityHandler` cleared `RemoteKeyCache[oldIri#key-1]` — without that invalidation, B would serve the stale cached old key and accept the Phase 3a delivery (202). The `Move`'s edge re-pointing and the old-IIRI decommissioning are *setup*; the invalidation is the *signal*.

**Empirical proof:** temporarily commenting out the `MoveActivityHandler`'s `_remoteKeys?.Invalidate(keyIri)` line (the F-25 key-cache invalidation) makes the test **fail at Phase 2** (`RemoteKeyCache.Count` stays 1 instead of dropping to 0). Restoring the line makes it pass. So the test directly depends on the production F-25 invalidation — it is not vacuous.

**Decision recorded:** the new IRI is modeled on the *same* host (A) as the old IRI (a migration to a new path), rather than on B (the destination instance). Reason: if the new IRI were on B, B would resolve the new key from its **local** key store / local actor doc, not via the remote-fetch path the slice asks to lock ("validated by B by fetching the new actor document"). Keeping the new IRI on A forces B to resolve the new key through the real `IActorDocumentFetcher` → HTTP → A's new-actor-doc path, which is the invariant F-25 protects.
