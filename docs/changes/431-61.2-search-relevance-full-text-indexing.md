# 61.2 — Search relevance + full-text indexing

**Priority:** MEDIUM
**Status:** COMPLETE

## Problem

Search (`GET /ap/v1/search`, `GET /ap/v1/c/{name}/search`) used a case-insensitive
**substring** match (`ILIKE '%q%'`) over the entire `jsonb` `Document` column cast to
`text`. This is an **O(n) sequential scan** with no index support. On a large instance
(100k+ objects), every search query scans the full table.

Two additional issues:
- No **relevance ranking** — results are ordered by IRI (arbitrary), not by match quality.
- The search matches against the **entire** JSON document (including IRIs, keys,
  structural noise), not just the user-visible text fields (`content`, `name`, `summary`).

## Fix

Added a **PostgreSQL `tsvector` column** + **GIN index** to the `Objects` and `Actors`
tables for ranked full-text search.

### Schema changes

| Table | New column | Type | Index |
|---|---|---|---|
| `Objects` | `SearchVector` | `tsvector` | GIN (`IX_Objects_SearchVector`) |
| `Actors` | `SearchVector` | `tsvector` | GIN (`IX_Actors_SearchVector`) |

The `SearchVector` column is populated on write (via raw SQL `UPDATE` after the EF
`INSERT`/`UPDATE`) using PostgreSQL's `to_tsvector('simple', …)` on the user-visible
text fields:

- **Objects:** `content` (weight A) + `name` (weight B) + `summary` (weight C)
- **Actors:** `name` (weight A) + `preferredUsername` (weight B) + `summary` (weight C)

The `'simple'` text search configuration does **no stemming and no stopword removal** —
it matches words literally (case-insensitive), preserving the behavior of the previous
`ILIKE` substring search but with index support and ranking.

### Search query

```sql
SELECT * FROM "Objects"
WHERE NOT "IsTombstoned"
  AND (
    "SearchVector" @@ plainto_tsquery('simple', $query)
    OR ("SearchVector" IS NULL AND "Document"::text ILIKE $pattern ESCAPE '\')
  )
ORDER BY
  ts_rank("SearchVector", plainto_tsquery('simple', $query)) DESC NULLS LAST,
  "Id"
LIMIT $limit OFFSET $offset
```

- **Primary path:** `tsvector @@ plainto_tsquery` — uses the GIN index, O(log n).
- **Fallback path:** `ILIKE` on `Document::text` — for rows where `SearchVector` is
  NULL (pre-migration rows not yet backfilled). This ensures no search results are
  lost during the transition period.
- **Ranking:** `ts_rank` orders by match quality (more matching words = higher rank),
  with ties broken by IRI for stability.

### Migration backfill

The EF Core migration (`20260910000000_AddSearchVector`) adds the columns, creates the
GIN indexes, and backfills existing rows using `to_tsvector` on the jsonb `Document`
column's searchable fields.

### EF Core mapping

`SearchVector` is `[NotMapped]` on both entities — EF Core does not support mapping
`string` to `tsvector`. The column is managed entirely via raw SQL:
- **Write:** `Database.ExecuteSqlRawAsync(UPDATE … SET SearchVector = to_tsvector(…))`
  after the EF `SaveChangesAsync`.
- **Read:** the search query selects via `FromSqlRaw` (the raw SQL includes the
  `tsvector` match + `ts_rank` ordering).

## Design decisions

1. **`'simple'` text search configuration** (no stemming, no stopwords) — preserves
   the `ILIKE` substring behavior for exact word matching. A `english` configuration
   would enable stemming ("running" matches "run") but would also remove stopwords
   ("the", "is") — a behavior change that could surprise users.

2. **`[NotMapped]` + raw SQL** — EF Core's Npgsql provider does not support mapping
   `string` to `tsvector`. The raw SQL approach is clean: the tsvector is only used in
   the search query (not in LINQ), and the write is a single `UPDATE` after the EF
   `SaveChanges`.

3. **ILIKE fallback for NULL tsvector** — during the transition period (before the
   backfill completes, or for rows inserted before the migration), rows with a NULL
   `SearchVector` are still found via the old `ILIKE` path. Once all rows have a
   non-NULL `SearchVector`, the fallback is never triggered.

4. **`TsVectorBuilder` retained** — the C# helper that builds tsvector strings from
   JSON is now unused (we use Postgres' `to_tsvector` in raw SQL instead). It is
   retained for potential future use (e.g., if we move to a different database or
   need to build tsvector in C# for testing).
