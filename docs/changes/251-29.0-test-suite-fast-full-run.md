# 29.0 — Test-suite fast/full run convention (`Category=Slow` trait)

## What was built

A durable, low-risk mechanism to run the suite **fast** (the everyday autonomous-loop green check)
vs. **full** (the source of truth):

- **`Iris.Testing.TestCategories`** (new, `tests/Iris.Testing/TestCategories.cs`) — centralizes the
  xunit trait names: `TestCategories.Category` (the trait key) and `TestCategories.Slow` (the value
  for tests that wait out a real delivery backoff budget). A single source of truth so the literals
  aren't scattered.
- **Two slow tests tagged** with `[Trait(TestCategories.Category, TestCategories.Slow)]`:
  - `DeliveryDeadLetterIntegrationTests` (whole class) — waits out the full default retry budget
    (5 attempts, 1s base → ~15s of real backoff).
  - `DeliveryRetryTests.TransientFailure_WaitsConfiguredBackoff_BetweenRetries` — a real 150ms
    `BaseDelay` (the one test in that class that waits; the rest use `BaseDelay=0`).
- **Documented** in `docs/reference/TESTING.md` (§ "Running the suite: fast vs. full") and
  `PLAN.md` (a new "Test runs" section + Active Slice note):
  - **Fast:** `dotnet test --filter "Category!=Slow"` — excludes the slow tests.
  - **Full:** `dotnet test` — every test including the slow ones.

## The mechanism

xunit v2.9.3 has no `--trait` CLI flag on `dotnet test`; the equivalent is the **vstest `--filter`
expression** with a trait predicate: `--filter "Category!=Slow"`. Verified:

- Full run on `DeliveryRetryTests`: 9 tests, ~725 ms.
- Fast run (`Category!=Slow & FullyQualifiedName~DeliveryRetryTests`): 8 tests, ~265 ms (the 1 slow
  test excluded).
- Fast run across the whole solution: 898 of 900 `Iris.Server.Tests` (the 2 slow tests excluded),
  all green.

## Honest note on the payoff

The `Slow` exclusion is a **correct partition** but a **small time saving** (~1 s of the ~5.5 min
`Iris.Server.Tests` run). Measured: fast full `Server.Tests` = 5 m 37 s vs. full = 5 m 38 s. The
backoff waits are a tiny fraction of total wall-clock.

**Root cause of the real cost:** `Iris.Server.Tests` is ~900 tests across ~130 classes. xunit
creates a **fresh test-class instance per test method**, so each of the ~900 methods builds fresh
in-process `TestServer` hosts and drives real multi-hop federation deliveries. A single
`TestServer` build is cheap (~10 ms, measured via `HarnessSmokeTests`: 4 tests building 2–3
topologies in 51 ms); the aggregate is dominated by the per-method host builds + delivery
round-trips + 50 ms polling granularity, spread across limited cores.

**The structural follow-up (29.3):** reuse hosts across a class's methods (e.g. a
shared-host-per-collection harness) or cut delivery round-trips. That is a larger refactor of the
integration-test harness, not a per-test tag, and is tracked as Up Next item 29.3.

## Key decisions

- **`--filter "Category!=Slow"` over a custom attribute:** xunit v2's `TraitAttribute` is sealed
  and `Xunit.Sdk.ITraitAttribute` is internal, so a user-code `[Slow]` attribute can't be built the
  obvious way. Applying `[Trait(...)]` directly (with centralized name constants) is the
  documented, guaranteed-to-work mechanism.
- **Only wall-clock-waiting tests are tagged:** a short polling `Task.Delay(50)` used to await an
  async hop is cheap and stays in the fast run. Only tests that wait out a real backoff budget are
  excluded — the partition is about *dead-time*, not *integration tests* in general.
- **The fast run is the loop's default; the full run is the source of truth.** Both are documented
  so a future turn knows which to use for which purpose.
