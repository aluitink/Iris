# 285 — 32.1: bare `Iris.Web` Blazor Web App host

> 2026-09-06 · Slice 32.1 · Phase 32 (production social platform app) — step 1 (the bare host)

## What was built

Phase 32's **step 1** stands up the production app as a *bare* host: a new
`apps/Iris.Web` ASP.NET Core **Blazor Web App** (Interactive Server) that boots the
ActivityPub server — `Iris.Server`, **unchanged** — with in-memory persistence and a
single seeded local actor, and serves a minimal landing page. The library's federation
endpoints (WebFinger, actor document, inbox, outbox, NodeInfo) now work inside the new
Blazor Web App process, before production persistence (32.2), local auth (32.3), and the
product screens (32.4) are layered on.

Per [production-app-web-host.md](../plans/production-app-web-host.md) and
[production-app-web-host-structure.md §2](../plans/production-app-web-host-structure.md),
the host binds **`http://localhost:8088`** (the production port — the reverse proxy for
`https://iris.luit.ink` targets host 8088, freed up by [32.0](284-32.0-relocate-sample-compose-stack.md))
and the **advertised** base URI defaults to the same (an operator sets
`Iris:AdvertiseBase` to expose the instance under a public hostname while listening
elsewhere).

The composition order follows the plan: Razor components first, then the ActivityPub
server, then the app pipeline (signature validation + ActivityPub endpoints, then the
Razor component endpoints).

## Key types & files

- `apps/Iris.Web/Iris.Web.csproj` — **new**. `Microsoft.NET.Sdk.Web`, `net10.0`; project
  references to `Iris.Client.Extensions`, `Iris.Server.InMemory`, `Iris.Server`.
- `apps/Iris.Web/Program.cs` — **new**. Thin entry point: creates the builder, reads
  `Iris:AdvertiseBase` from config, calls `WebAppFactory.CreateWebApplication`, runs.
- `apps/Iris.Web/WebAppFactory.cs` — **new**. The **composition root** (a public, testable
  seam). `ConfigureServices` wires: the Blazor Web App (Interactive Server), the
  ActivityPub server (`AddActivityPubServer` with `BaseUri` / `InstanceName` /
  `InstanceActorId` / `NamespaceIri` derived from the advertised base), in-memory
  persistence (`AddInMemoryPersistence`), the single seeded local actor (a `Person` with an
  RSA signing key, `publicKeyPem` in its document), the client-side signer
  (`HttpSignatureSigner` over the seeded key store), and a Basic-auth
  `IActorCredentialValidator` (seed credential `alice`/`alice`) so the seeded actor can
  read its owner-only surfaces. `BuildApp` runs the pipeline (`UseRouting` →
  `UseAntiforgery` → `UseSignatureValidation` → `MapActivityPubEndpoints` →
  `MapRazorComponents<App>`) and registers the seeded key with the server's
  `IKeyProvider`. `CreateWebApplication` is the single end-to-end seam the tests use.
  Actor/community IRIs are built exactly the way the server derives them
  (`BaseUri.Value.TrimEnd('/')` + `/ap/v1/...`) so the seeded actor's IRI is identical to
  the one the handlers resolve (a trailing-slash mismatch would 404 the seeded actor).
- `apps/Iris.Web/Components/` — **new**. `App.razor` (shell, `<base href="/" />`,
  `<ImportMap />`, `blazor.web.js`), `Routes.razor`, `Layout/MainLayout.razor`,
  `Pages/Home.razor` (minimal landing page), `_Imports.razor`.
- `apps/Iris.Web/wwwroot/css/app.css` — **new**. Minimal dark theme.
- `apps/Iris.Web/appsettings.json` / `appsettings.Development.json` — **new**.
  `Iris:AdvertiseBase` defaults to `http://localhost:8088`.
- `tests/Iris.Web.Tests/` — **new** project (`Iris.Web.Tests.csproj`,
  `WebHostIntegrationTests.cs`, `GlobalUsings.cs`). 6 integration tests boot the host in a
  `TestServer` and assert the federation routes + landing page (see *Verification*).
- `src/Iris.Server/ActivityPubServerExtensions.cs` — **changed** (1 method): the NodeInfo
  discovery-root handler (`NodeInfoWellKnownHandler`) now trims the trailing slash off
  `BaseUri.Value` before appending the route prefix, so the `href` is
  `https://host/ap/v1/nodeinfo/2.0` rather than `https://host//ap/v1/nodeinfo/2.0` (a bare
  host's `Iri.Value` ends in `/`). See *Decisions*.
- `Iris.slnx` — **changed**: added the `apps/` folder + `Iris.Web` project and the
  `Iris.Web.Tests` project.

No new NuGet packages (the new projects reference already-centralized ones:
`Microsoft.AspNetCore.TestHost`, `Microsoft.NET.Test.Sdk`, `xunit`,
`xunit.runner.visualstudio` for the test project; the app project is the Web SDK only).

## Decisions

- **`TestServer` hosting seam (tests).** `builder.WebHost` (from `WebApplication`) cannot
  be passed to `new TestServer(IWebHostBuilder)` directly — `TestServer`'s `UseTestServer`
  mutates the service collection, which `WebApplicationBuilder` has already frozen. So the
  test configures the real service graph via `WebAppFactory.ConfigureServices(builder, …)`,
  then hosts it through an independent `new WebHostBuilder().UseTestServer()` that reuses
  the same configured collection and re-runs the same pipeline (`UseRouting` →
  `UseAntiforgery` → `UseSignatureValidation` → `MapActivityPubEndpoints` →
  `MapRazorComponents<App>`). `TestServer(IWebHostBuilder)` is the established in-process
  seam in this repo (`Iris.Server.Tests`, `Iris.Testing`); it is obsolete in .NET 10, so
  `ASPDEPR004`/`ASPDEPR008` are suppressed for the test project only (as the other test
  projects do). `UseAntiforgery` is required (a Blazor endpoint carries anti-forgery
  metadata) and sits between routing and endpoints.
- **The seeded actor is the instance actor** (`ActivityPubServerOptions.InstanceActorId`),
  with a real RSA key (`publicKeyPem` in the document) so a remote resolver could verify
  signatures, and a Basic-auth credential validator (`alice`/`alice`) so its owner-only
  surfaces (inbox, `privateKey`) are reachable in tests. Slice 32.3 (local auth) replaces
  the fixed seed with per-account-provisioned actors.
- **NodeInfo doubled-slash fix (library).** `Iri.Value` is the absolute wire form and ends
  in `/` for a bare host (e.g. `https://host/`), so composing
  `{BaseUri.Value}{RoutePrefix}/nodeinfo/2.0` produced `https://host//ap/v1/nodeinfo/2.0`.
  The fix trims the trailing slash in `NodeInfoWellKnownHandler`. (Actor/community IRIs use
  `BuildActorIri`, which already trims; the `InboxOf`/`AppendSegment` helpers also handle a
  trailing parent path — so the NodeInfo link was the one `{BaseUri.Value}{path}`
  composition that didn't.) The existing server tests only asserted the `href` *contains*
  `nodeinfo/2.0`, so they didn't catch it.
