# 22.10 — Fix the local no-Docker CORS origin gap

**Slice:** Phase 22 closeout item #2 (Up Next) — fix finding **B** from the final manual UI
verification pass (change 226).
**Status:** done. Build clean (0 warnings / 0 errors); **1,365 tests pass** (up from 1,360 — 5 new

## The gap

The documented **local (no-Docker)** log-on path in
[`samples/SampleBlazorClient/README.md`](../../samples/SampleBlazorClient/README.md) runs:

```sh
dotnet run --project samples/SampleServer                       # → http://localhost:5000
dotnet run --project samples/SampleBlazorClient --no-build      # → http://localhost:8080 (Blazor dev server)
```

The browser (origin `http://localhost:8080`) dials the SampleServer cross-origin. But
`SampleServer`'s default `Iris__CorsOrigins` was **only** `http://localhost:8090` — the port the
**Docker** `iris-ui` static host publishes (the compose path). The no-Docker path's origin
(`:8080`) was not in the allow-list, so the browser blocked every cross-origin request (webfinger, the
Basic-auth actor document) with a CORS error, and log-on failed before the app ever reached the
key-import step. (The Docker path worked; only the no-Docker path was broken.)

## The fix

`samples/SampleServer/Program.cs` — the default `Iris__CorsOrigins` now allows **both** documented
local UI origins:

```csharp
var corsOriginsCsv = configuration["Iris:CorsOrigins"]
    ?? "http://localhost:8090,http://localhost:8080";
```

- `http://localhost:8090` — the Docker `iris-ui` static host (the original default; the compose path).
- `http://localhost:8080` — the local no-Docker Blazor dev server (the previously-missing origin).

Either documented local path now works out of the box with no env var. Operators can still override
with `Iris__CorsOrigins` (comma-separated) for a custom deployment. No other code changed.

## Tests (first CORS coverage)

`tests/SampleServer.Tests/SampleServerCorsTests.cs` — 5 new tests. They host the **real**
`SampleServer` in-process (`SampleServer.CreateWebHostBuilder()` + a `TestServer`) and drive the full
CORS middleware with genuine cross-origin requests, so they prove the end-to-end behavior (the
`Access-Control-Allow-Origin` header on the wire), not just the registered policy:

- **`Preflight_Options_CrossOrigin_AllowsTheDocumentedLocalOrigin`** (Theory, `:8090` + `:8080`) — an
  `OPTIONS` preflight from each documented origin gets `Access-Control-Allow-Origin` echoed.
- **`Get_ActorDoc_CrossOrigin_AllowsTheDocumentedLocalOrigin`** (Theory, `:8090` + `:8080`) — a
  cross-origin `GET` to the actor document gets the header echoed.
- **`Get_ActorDoc_UnlistedOrigin_IsNotGrantedAccess`** — a non-allowlisted origin (`http://evil.example`)
  is **not** granted the header. Guards against an accidental "allow any origin" regression that would
  leak the Basic-auth / Bearer credentials to an untrusted browser.

**Proven to catch the regression:** with the old default (`:8090` only), the two `:8080` cases fail —
exactly the documented no-Docker path that was CORS-blocked.

## Decision

- **Widen the default rather than document the env var** (change 226 offered both; the widening was
  preferred). It makes the documented local path work with zero configuration, and the two origins are
  both unprivileged local dev origins — no security concern. The `Iris__CorsOrigins` override is
  preserved for real deployments, so the default change is strictly additive for local dev.
- **Integration test over a policy-resolution unit test.** A `ServiceCollection` + `ICorsPolicyProvider`
  resolution test would be lighter but would not exercise the actual middleware or the wire header.
  Hosting the real server through `TestServer` (the repo's established harness) and asserting the
  response header proves the user-facing behavior and matches the integration-first principle in
  [TESTING.md](../reference/TESTING.md).
