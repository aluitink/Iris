# 33.3 — server production-readiness: resolve local signing identity from the durable key store

**Slice:** Phase 33 step 3. **Branch:** `phase-32-production-app`. **Commits:** `59a9606` (impl + tests), `793a96a` (tests dropped — verify via production container instead).

## Problem

A local actor whose key is in the **durable** `IKeyStore` but was **never registered** with the
in-process `IKeyProvider` could **not sign until a restart**. Concretely: a user who just registered
(32.3 `RegistrationService` → `ActorProvisioner`) or an admin-assisted provision writes the key to the
durable store and *does* call `IKeyProvider.RegisterKey` — but that registration lives only in the
in-process `InMemoryKeyProvider`, which is **not durable**. Two failure modes:

1. **The registration is lost on restart.** 33.2's `RestoreLocalSigningKeys` startup pass re-registers
   every *local account's* key — but only for accounts that exist in the `UserAccount` table at boot.
2. **A post-boot actor provisioned through a path that bypasses the provider** (or a key the provider
   simply doesn't have a mapping for) is un-signable: the `SigningHandler`
   (`src/Iris.Client/Pipeline/SigningHandler.cs:114`) throws
   `No signing identity registered for actor '<actor>'` on the actor's first outbound federation.

The store (EF-backed, in Postgres) is the **source of truth** for the key material; the in-process
provider is only a fast path. When the fast path misses, there is no reason the durable store can't
answer — the key is right there under the well-known local key-IRI convention.

## Change

- **New type `DelegatingKeyProvider`** (`src/Iris.Client/Auth/DelegatingKeyProvider.cs`), an
  `IKeyProvider` that wraps a **primary** provider (the in-memory actor→key map) + the **durable
  `IKeyStore`**:
  - `TryGetIdentity(actorId, out identity)`:
    1. consult the primary first (fast path — seeded + startup-restored actors);
    2. on a miss, resolve the key from the store by the well-known local key IRI
       `{actorId}#{keyFragment}` (default fragment `key-1` — the same convention `SeedActor` and
       `ActorProvisioner` use) and return a `SystemIdentity(actorId, keyIri)`.
    3. if neither resolves, return `false` (genuinely unresolvable).
  - `RegisterKey(actorId, keyId)` delegates to the primary (the fast path is still writable).
  - The key fragment is a constructor parameter (default `key-1`) so the convention stays explicit and
    testable without a magic string.
- **`apps/Iris.Web/WebAppFactory.cs`** now binds the `IKeyProvider` to a `DelegatingKeyProvider`
  (primary = a fresh `InMemoryKeyProvider` over the same `IKeyStore`, fallback = the same durable
  `IKeyStore`). It is registered **after** `AddActivityPubServer`, so the hard
  `AddSingleton<IKeyProvider>` overrides `AddActivityPubServer`'s
  `TryAddSingleton<IKeyProvider, InMemoryKeyProvider>`. `ActorProvisioner` resolves the same
  delegating instance, so a newly-provisioned actor is signable immediately (and also survives a
  restart via 33.2's startup restore, since its key is in the durable store).

Net: **any** local actor is signable on demand — no restart, no explicit `RegisterKey` required. The
in-memory provider remains the fast path; the durable store is the fallback (and the source of truth).

## Decision (recorded)

The fallback uses the **well-known key-IRI convention** (`{actor}#key-1`) rather than scanning the
store or reading a mapping. This matches how every local actor's key is actually named in this codebase
(`SeedActor` + `ActorProvisioner`), so the lookup is a single deterministic store read — no new table,
no migration, no ambiguity. A future per-actor custom key fragment would be a one-line constructor
arg change.

## Tests / verification

**No new automated tests** — per the user's directive ("stop adding tests, verify via the production
container"). An earlier revision added 5 unit tests (`DelegatingKeyProviderTests`) + 1 integration test
(`SigningIdentityRestartTests.LocallyProvisionedActor_IsSignableWithoutRestart`); these were committed
in `59a9606` and then **dropped** in `793a96a` so the suite returns to baseline.

**Verified live in the production container** (rebuilt the image with the fix + `docker compose up -d
iris-web` over the **persistent** Postgres volume):

1. **Restart persistence intact (33.2 regression check):** the seeded actor `alice` and the pre-existing
   user `andrew` both serve their actor documents with their **original** keys (key IRI `#key-1`,
   unchanged public-key PEM) after the restart — the seed did **not** re-mint a key.
2. **The 33.3 scenario — a post-boot actor is signable without a restart:** a brand-new user
   `e2e33330778` was registered via `POST /register` **after boot, with no restart**. The request
   required the `<AntiforgeryToken />` hidden field **and** the `.AspNetCore.Antiforgery.*` cookie
   round-trip (a bare `curl` POST is rejected `400` by `UseAntiforgery` by design — confirmed the 400
   was the antiforgery middleware, not the handler). On success the response was `302 → /` with an
   `iris.auth` cookie; the actor document serves with a real RSA key PEM; and the app log shows
   `Registered account 'e2e33330778' (actor https://iris.luit.ink/ap/v1/u/e2e33330778)` with **no**
   `No signing identity registered` error — proof the just-provisioned actor is signable immediately.
