# 48.3 — Monitoring & alerting

## Summary

Added the monitoring and alerting surface for production Iris.Web deployments:

- **`GET /local/v1/metrics`** endpoint (`WebAppFactory.MapMetricsEndpoint`) — Prometheus
  text-format endpoint exposing the outbound-delivery counters from `IrisDeliveryMetrics`:
  - `iris_delivery_enqueued_total` — total jobs placed on the queue.
  - `iris_delivery_delivered_total` — total successful deliveries (2xx).
  - `iris_delivery_attempt_failed_total` — total failed attempts.
  - `iris_delivery_dead_lettered_total` — total dead-lettered jobs.
  - `iris_delivery_by_type{activity_type=...,direction=...}` — per-activity-type breakdown.
  - `iris_delivery_failure_kind{kind=...}` — per-failure-kind breakdown.
  - No authentication (internal network only; the reverse proxy's rate limit is the gate).
  - Handles the null case (no instance actor → all zeros).

- **`scripts/monitor-iris.sh`** — lightweight monitoring script (cron-able or continuous loop):
  - Polls `/ap/v1/health`, `/ap/v1/ready`, `/local/v1/metrics` every 60s (configurable).
  - Detects transitions to unhealthy/unreachable and sends alerts (Slack webhook, email).
  - Tracks delivery metrics and alerts on dead-letter spikes (>10 new in interval) and
    high failure rate (>50% of attempts failing over 10+ total attempts).
  - Persists state in a temp file (delta detection between checks).

- **`apps/Iris.Web/deploy/MONITORING.md`** — operational documentation:
  - Endpoint reference (health, readiness, metrics) with example bodies.
  - Prometheus scrape config + alert rules (instance down, dead-letter spike, high failure
    rate, queue backlog).
  - Grafana dashboard panel recommendations.
  - systemd service for the monitor script.
  - Log-based alerting patterns (filebeat/fluentd + ELK).
  - External uptime monitoring (Better Stack, UptimeRobot).
  - MTTA target: < 5 minutes.

## Design decisions

- **Prometheus text format over OTel**: the app already has `IrisDeliveryMetrics` with a
  `Snapshot` property (Phase 17.2). The metrics endpoint reads the snapshot and formats it
  as Prometheus text. No new NuGet packages (no `prometheus-net`, no OTel SDK). The endpoint
  is trivial (read counters, format string) and the format is well-understood by all
  monitoring stacks.
- **Endpoint at `/local/v1/metrics`** (not `/ap/v1/metrics`): the `/ap/v1/` prefix is
  reserved for ActivityPub protocol endpoints (WebFinger, actor, inbox, outbox, health,
  ready). The metrics endpoint is an operational endpoint, not a protocol endpoint, so it
  lives under `/local/v1/` alongside the other local (non-federated) endpoints (auth,
  admin, notifications).
- **No authentication on the metrics endpoint**: a Prometheus scraper on the internal network
  reaches it without credentials. For a public instance, the operator should put the endpoint
  behind a network ACL (only the Prometheus server's IP) or add basic auth via the reverse
  proxy. The endpoint exposes no sensitive data (just delivery counters), so the risk of
  leaving it open is low.
- **Monitor script as a fallback**: the recommended path is Prometheus + Grafana (richer
  dashboards, historical data, alerting rules). The script is a lightweight fallback for
  hosts without a Prometheus instance (e.g., a single VPS with no monitoring stack). It
  covers the essential alerting (instance down, dead-letter spike, high failure rate) with
  minimal infrastructure.
