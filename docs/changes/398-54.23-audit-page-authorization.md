# 54.23 — Audit Page Authorization: Lock Down Protected Routes

## Problem

Pages that should require authentication (Settings, Compose, Profile, admin/moderation,
notifications, etc.) were reachable while logged out. The Blazor WASM client used
`RouteView` in `App.razor`, which does not enforce `[Authorize]` attributes on
client-side navigation. Unauthenticated users hitting `/home`, `/settings`, `/compose`,
`/admin/*`, etc. saw pages with null data (or "Sign in to view…" messages) instead of
being redirected to the login page.

Additionally, the admin pages used `[Authorize(Policy = "Admin")]`, but the "Admin"
policy was never defined in `Program.cs` (only `AddAuthorizationCore()` was called with
no policies). The `AdminGuard.AccessDenied()` client-side check provided a secondary
defense, but the policy attribute itself was a no-op.

## Solution

### `App.razor` — `RouteView` → `AuthorizeRouteView`

Replaced `<RouteView>` with `<AuthorizeRouteView>`, which evaluates the `[Authorize]`
attribute on the matched route and, when the user is not authorized, renders the
`NotAuthorized` template. Added a `<RedirectToLogin>` component (navigates to
`/login`) as the `NotAuthorized` template, and an `<Authorizing>` template (shows
"Checking sign-in…" while the auth state is being resolved).

### `RedirectToLogin.razor` (new)

A minimal component that calls `NavigationManager.NavigateTo("/login")` in
`OnInitialized`. Rendered inside the `AuthorizeRouteView`'s `NotAuthorized` template
to redirect unauthenticated users to the login page.

### `Program.cs` — Define the "Admin" policy

Changed `AddAuthorizationCore()` to:
```csharp
AddAuthorizationCore(options =>
{
    options.AddPolicy("Admin", policy => policy.RequireRole("Admin"));
});
```

This makes the `[Authorize(Policy = "Admin")]` attribute on the four admin pages
functionally meaningful: `AuthorizeRouteView` now checks the policy, and non-admin
users (even signed-in ones) are redirected to `/login` when they try to access
admin pages. The existing `AdminGuard.AccessDenied()` client-side check remains as a
defense-in-depth layer (it catches the case where the auth state resolves before the
policy check, or where the user navigates via the footer links).

## Design decisions

- **`AuthorizeRouteView` over `RouteView`**: `AuthorizeRouteView` is the standard
  Blazor WASM mechanism for route-level auth. It evaluates the `[Authorize]`
  attribute on the matched page component and renders the `NotAuthorized` template
  when the user is not authorized. This is the minimal, idiomatic fix — no custom
  middleware or interceptors needed.
- **Redirect to `/login` (not `/`)**: Redirecting to the login page (rather than the
  public home) gives the user a clear next step. The login page shows the sign-in
  form, and after signing in the user lands on `/` (the default post-login redirect).
- **`RedirectToLogin` as a separate component**: Keeps the `AuthorizeRouteView`
  markup clean. The component's `OnInitialized` runs after the `AuthorizeRouteView`
  has determined the user is not authorized, so the navigation is safe.
- **"Admin" policy defined in `Program.cs`**: The policy was referenced by the admin
  pages' `[Authorize(Policy = "Admin")]` attribute but never registered. Adding it
  makes the attribute functional. `RequireRole("Admin")` checks the `ClaimTypes.Role`
  claim, which is set by `CookieAuthenticationStateProvider` from the server's
  session response.
- **Public pages remain public**: `/` (home/landing), `/login`, `/register`,
  `/actor?iri=…`, `/object?iri=…`, `/directory`, `/search`, `/communities`, and
  `/community?iri=…` are intentionally accessible without authentication. The
  `[Authorize]` attribute on these pages is retained for future use (e.g., if the
  instance owner wants to restrict access), but the `AuthorizeRouteView` only
  enforces it when the attribute is present.
