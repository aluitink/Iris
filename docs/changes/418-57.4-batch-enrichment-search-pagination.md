# 57.4 — Batch enrichment and search pagination

## Summary

Fixed the two remaining hot-path N+1 / full-table-scan issues flagged in 57.1:

1. **Batch enrichment** — `EnrichCollectionItemsAsync` previously issued 5 per-item queries (likers, announcers, replies, hasLiked, hasAnnounced) for every collection item. A page of 30 items = 150 round trips. Refactored to 5 batch queries total (one per enrichment kind), using new batch store methods that translate to `WHERE (Kind, Target) IN (...)` on PostgreSQL.

2. **Search pagination** — `GlobalSearchService` previously materialized the full actor + object tables (`ListActorsAsync` / `ListObjectsAsync`) and sliced in memory. A large instance would deserialize every stored object on every search. Added paged store methods (`SearchObjectsAsync` / `SearchActorsAsync` with `limit`/`offset` + `CountSearchMatchesAsync`) so the slice is pushed into the store. The EF implementations use `EF.Functions.Like` (ILIKE) for case-insensitive substring matching.

## Changes

### Store interfaces — batch methods

- `IEdgeStore` (Server.Data): added `InSourcesBatchAsync`, `OutTargetsBatchAsync`, `ContainsBatchAsync` — batch reverse/forward/containment lookups (single `WHERE (Kind, X) IN (...)` query).
- `ILikeStore`: added `GetLikersBatchAsync(IReadOnlyCollection<Iri>)` and `HasLikedBatchAsync(Iri, IReadOnlyCollection<Iri>)`.
- `IAnnounceStore`: added `GetAnnouncersBatchAsync(IReadOnlyCollection<Iri>)` and `HasAnnouncedBatchAsync(Iri, IReadOnlyCollection<Iri>)`.
- `IReplyStore`: added `GetRepliesBatchAsync(IReadOnlyCollection<Iri>)`.
- `IObjectStore`: added `SearchObjectsAsync(query, limit, offset, ct)` and `CountSearchMatchesAsync(query, ct)`.
- `IActorStore`: added `SearchActorsAsync(query, limit, offset, ct)` and `CountSearchMatchesAsync(query, ct)`.

### Store implementations

- **EF** (`EfLikeStore`, `EfAnnounceStore`, `EfReplyStore`): batch methods implemented via `IEdgeStore` batch methods (one `WHERE (Kind, Target) IN (...)` query each).
- **EF** (`EfObjectStore`, `EfActorStore`): `SearchObjectsAsync` / `SearchActorsAsync` use `EF.Functions.Like(e.Document, "%query%", "\\")` (translates to `ILIKE '%query%'` on Npgsql — case-insensitive substring). `CountSearchMatchesAsync` uses the same predicate with `COUNT(*)`.
- **In-memory** (`InMemoryLikeStore`, `InMemoryAnnounceStore`, `InMemoryReplyStore`): batch methods use `lock` + `HashSet` lookups.
- **In-memory** (`InMemoryObjectStore`, `InMemoryActorStore`): `SearchObjectsAsync` / `SearchActorsAsync` use LINQ `Skip(offset).Take(limit)` over the filtered set (Tombstone + Actor exclusion preserved).
- **File-backed** (`FileBackedLikeStore`, `FileBackedAnnounceStore`, `FileBackedReplyStore`): batch methods via `_file.SnapshotAsync`.
- **File-backed** (`FileBackedObjectStore`, `FileBackedActorStore`): same LINQ approach as in-memory.

### `EnrichCollectionItemsAsync` (ActivityPubServerExtensions)

Refactored from a per-item loop (5 queries × M items) to a 3-phase batch:
1. Identify all embedded objects in the page.
2. Issue 5 batch queries (likers, announcers, replies, hasLiked, hasAnnounced) over the full set of object IRIs.
3. Deep-copy each object and annotate with the batch-fetched engagement data.

### `GlobalSearchService` (Services)

- Added `SearchPagedAsync(query, ct, type, limit, offset) → (Items, Total)` — pushes the slice into the stores. The actor pass and content pass are independent: the global offset/limit is split across them (actors first, then content). When a type filter is present and restricts the content pass to a single type, the content slice is taken from the full content match set and filtered (the store count is over the untyped surface, so the total is computed from the filtered set).
- `SearchAsync` now delegates to `SearchPagedAsync(query, ct, type, int.MaxValue, 0)`.

### `GlobalSearchHandler` (ActivityPubServerExtensions)

- Calls `SearchPagedAsync` with the requested `limit`/`offset` and passes the returned `(items, total)` to `BuildSearchPageDocument`.
- `BuildSearchPageDocument` signature changed: now accepts `int total` (the full match count from the paged service) instead of deriving it from `items.Count`. The `total` drives `totalItems` and the next-page link; `items` is the already-sliced page.
- The community search handler (`GET /c/{name}/search`) passes `items.Count` as `total` (it uses the un-paged `SearchAsync`, so items is the full list).

### `IrisDbContext` (Server.Data)

- No schema changes (the GIN trigram index was removed — `gin_trgm_ops` does not support `jsonb` columns; ILIKE on jsonb works without a trigram index and the local surface is small).

### `Iris.Server.Data/Migrations`

- Regenerated single `InitialCreate` migration per the pre-launch squash policy (no model changes in this slice; the migration is byte-identical to the prior one except for the timestamp).

## Test results

Core 296/0, Server 957/0 (17 skipped), Server.Data 10/0, Web 62/0.

## Deferred

- **citext or expression index** for case-insensitive username lookup (low priority pre-launch; ILIKE on the `Handle` column works, and the directory is small).
- **GIN trigram index on `Objects.Document`** for large-instance search (requires a `tsvector`-compatible column or a generated column; the jsonb column does not support `gin_trgm_ops` directly).
