# 25.2 — Cross-instance `Reject` (declined follow) propagation

Phase 25, slice 2. **Type:** code fix + invariant lock (a real code gap in the inbound `Reject` handler,
plus a 2-instance test that locks the cross-instance `Reject` path end-to-end).

## Problem (and why it is a fix, not a test-only lock)

A follow is *provisional* on the follower side until the followed side responds. The existing
cross-instance **`Accept`** path is fully two-sided: the followed side's `Accept` federates back to the
follower's inbox, and `AcceptActivityHandler` finalizes the follower's follow edge — including the G-3
**community-follower** override (a community is a `Group`, not a person in the actor store, so the base
local-actor guard would no-op; the handler widens the local check and records the edge in the
community's follows set).

The **`Reject`** (declined follow) path was **asymmetric**: `RejectActivityHandler` was the bare base
implementation — it only handled a *person* follower (removing the edge from the person follow store) and
had **no G-3 community-follower override**. So a community-initiated follow (published via the community
outbox, gap G-3) would be finalized by an inbound `Accept` but a *declined* follow would **never** be
undone on the community side (the community's follows set would keep listing a follow that the other side
had rejected). The person path worked, but there was also **no 2-instance test** locking the cross-instance
`Reject` hop at all (the single-instance `OutboxFollowDecisionIntegrationTests` collapses both sides into
one store, so it never exercises the B → A federation of the `Reject`).

This slice closes both:

1. **Code fix** — `RejectActivityHandler` now mirrors `AcceptActivityHandler`:
   - `IsLocalRecipientAsync` is overridden to also treat a **local community** as local (the G-3
     override), so the handler no-ops no longer for a community follower.
   - `ApplyAsync` gains a **community branch**: a community's rejected follow is undone by removing the
     edge from the community's follows set (`ICommunityStore.RemoveFollowAsync`) — the inverse of the
     inbound `FollowActivityHandler`'s community branch and the exact mirror of `AcceptActivityHandler`'s
     community arm. A person follower still removes the edge from the person follow store
     (`IFollowStore.RemoveFollowAsync`).

2. **Invariant lock** — a new 2-instance integration test (`CrossInstanceRejectPropagationIntegrationTests`)
   that exercises the real cross-instance `Reject` hop, which the single-instance test cannot.

## The cross-instance `Reject` flow (what the test locks)

Topology: instance A hosts a person follower (`alice`, A's instance actor) and a community follower
(`iris` / C, with its own signing key). Instance B hosts the local person `bob` (B's instance actor, the
follow target, so B's document fetcher is routable). A's and B's outbound delivery workers route to each
other; each instance's fetcher routes by actor-IRI host (so each can validate the other's signatures and
fetch its own local actors).

1. **The follow (A → B):** the follower on A (a person or the community) publishes `Follow(bob)` to its
   outbox on A. A records the follower's local follow edge (person: the follow store's `follower → bob`;
   community: C's follows set `C → bob`) and server-delivers the signed `Follow` to bob's inbox on B. B's
   `FollowActivityHandler` records the remote edge (bob's followers set lists the follower) **and stores
   the original `Follow` in B's activity store** — the copy the `Reject` later resolves against.
2. **The `Reject` (B → A, under test):** bob publishes `Reject(follow)` to his outbox on B. B's
   `RecordFollowDecisionLocalAsync` removes **B's** edge (bob's followers) and returns the *follower's*
   IRI (the remote party). Because the follower is remote, B's outbox-publish handler **server-delivers
   the signed `Reject` to the follower's inbox on A**. A's `RejectActivityHandler` (inbound) resolves the
   original `Follow` from **A's** activity store and removes **A's** follow edge — the person follow edge
   (person path) or C's follows-set edge (community path, the new G-3 override).

The edge is gone on A only if the `Reject` federated B → A **and** A had stored the original `Follow`
(the cross-instance dependency the single-instance test does not exercise).

## Where

- `src/Iris.Server/Inbox/RejectActivityHandler.cs`:
  - New `IsLocalRecipientAsync` override widening the local check to a local community (the G-3 override,
    mirroring `AcceptActivityHandler.IsLocalRecipientAsync`).
  - `ApplyAsync` rewritten from a single `Follows.RemoveFollowAsync` to a two-branch method: a community
    follower removes the edge from the community's follows set (`Communities.RemoveFollowAsync`); a person
    follower removes the edge from the follow store (`Follows.RemoveFollowAsync`).
  - XML docs updated to document the community-follower (G-3) arm.
- `tests/Iris.Server.Tests/CrossInstanceRejectPropagationIntegrationTests.cs` (new, 2 tests, 2-instance
  `TestServer`):
  - `PersonFollowOfRemoteActor_ThenReject_FederatesAndRemovesFollowerEdgeOnOrigin`: alice on A follows
    bob on B; bob publishes `Reject`; B delivers it to A; A removes the `alice → bob` follow edge.
  - `CommunityFollowOfRemoteActor_ThenReject_FederatesAndRemovesCommunityFollowsEdge`: community C on A
    follows bob on B; bob publishes `Reject`; B delivers it to A; A's `RejectActivityHandler` (G-3
    override) removes the `C → bob` edge from C's follows set.

The test harness follows the existing cross-instance propagation tests (`CommunityFollowsCommunityUnfollow…`):
two `TestServer` instances, `SeedPersonWithKey`/`SeedCommunityWithKey`, a host-routed `RoutingFetcher`
per instance, a `CaptureHandler`-based signed-request replay for the outbox writes, and minted-id learning
from the 202 body (decision 055).

## Non-vacuity (proven)

Per the loop's "prove it fails" discipline, the G-3 community-follower override was temporarily disabled
in `RejectActivityHandler.IsLocalRecipientAsync` (returning `false` after the person check, so a community
is no longer seen as local):

- The **community** test **fails** (times out waiting for C's follows edge to be removed — it never is,
  because the handler no-ops for the community).
- The **person** test still **passes** (it does not depend on the community override).

This confirms the community test genuinely exercises the new G-3 code path — it is not passing vacuously.
Restoring the override turns the community test green.
