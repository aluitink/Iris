# 161s — Phase 20.3: sample-UI outbox enumeration + paging (local or remote)

## Summary

Phase 20.3 makes 20.1's "outbox = source of truth" and 20.2's inbox design **visible in the
sample-UI**: a user can now **enumerate a local or remote actor's outbox and page through it** on the
actor detail page. The previous non-paged "Feed (outbox)" card (which loaded the *entire* outbox up
front via `GetCollectionItemsAsync`) is replaced by a **paged "Outbox" surface** that renders each item
as a navigable object view (not raw JSON) and pages with `next`-link walking via a "Load more" button.

This is a **UI-only** enhancement — it reuses the existing paged-collection client
(`IActivityPubClient.GetCollectionAsync`) and object view (`ObjectView.razor`); no server, client, or
persistence changes.

## What changed (code)

- **`samples/SampleBlazorClient/Pages/ActorDetail.razor`** — the "Feed (outbox)" card is replaced by a
  paged **"Outbox"** surface:
  - **First page** loads in `LoadByIriAsync` via `LoadInitialOutboxAsync` → `EnumerateOneOutboxPageAsync`,
    which uses the paged `IActivityPubClient.GetCollectionAsync` against the actor's
    `{actor}/outbox` collection. **No `CollectionQuery.Limit`** — the server pages the outbox at its
    natural page size (the `?limit=` default, 20), and the surface appends one server page per "Load more"
    click. (`CollectionQuery.Limit` caps the *total walk*, not the per-HTTP-page size, so it would not
    have produced the intended per-click page boundary; the server's natural page size is what the user
    actually sees.)
  - **"Load more"** appends the next server page, resuming from `CollectionPage.NextPage` (the
    `next`-linked page IRI) — the same idiom `Feed.razor`'s "Load more" uses. One page per click.
  - Each item renders as `<ObjectView Item="item" />` (a navigable object view).
  - **Local or remote**: the paging contract is host-agnostic — the surface pages whatever outbox it is
    pointed at (the `{actor}/outbox` IRI), whether the actor is on this instance or remote.
  - The **`PendingFollows`** computation (which reads the same outbox to list inbound `Follow`s for
    accept/reject) still reads the full outbox via `GetCollectionItemsAsync` — a separate concern that
    needs *all* `Follow`s, not a paged view.
  - The now-unused `Feed` property and its up-front full-outbox load are removed.

## New tests (4, all passing)

`tests/SampleBlazorClient.Tests/S20OutboxPagingTests.cs` — an integration-first harness (a real
in-process `Iris.Server`, mirroring `S3FollowFeedTests.StartHost`) that seeds an actor's outbox with
enough notes to span more than one server page (page size 20) and asserts the paged enumeration the
surface performs:

1. **`Outbox_PagedEnumeration_WalksNextLinks_AllItemsSurface`** — 25 notes (20 + 5); the paged
   enumeration walks the `next` link and surfaces all 25, no duplicates, all under the actor's own IRI
   prefix (the outbox = source of truth), spanning exactly 2 pages with the final page last.
2. **`Outbox_FirstPage_CarriesNextLinkWhenMoreRemain`** — 25 notes: the first page lists 20 and carries a
   `next` link (the "Load more" mechanism); resuming from `NextPage` serves page 2 (the remaining 5) as
   the last page.
3. **`Outbox_SinglePage_NoNextLink`** — 3 notes: a single-page outbox (fewer than the page size) is the
   last page with no `next` link (the common "Load more"-not-needed case).
4. **`Outbox_PagedEnumeration_SecondLocalActor_AlsoPaged`** — a second actor (26 notes) pages identically
   (20 + 6), confirming the host-agnostic paging contract.
