# 288 — 32.4: product screens — signed-in app shell + home timeline

> 2026-09-06 · Slice 32.4a · Phase 32 (production social platform app) — step 4 (product screens)

## What was built

Phase 32's **step 4** (the first slice of the "product screens" group) adds the **signed-in product
shell** and the **home timeline** to `apps/Iris.Web`. With local auth (32.3) in place, a signed-in
user now has a real app to use: an auth-aware navigation bar, a `/` landing that adapts to their
sign-in state, and a `/home` timeline that renders the union of the actors they follow (the
"followed feed"), paged with next-link walking.

Per the feature-set plan (`docs/plans/production-app-feature-set.md` §1), this is a
**functionality-first** pass: the data flows (the shell's auth-aware nav, the `[Authorize]` gating,
the followed-feed render) are wired and verified live in a real browser (MCP Playwright), not by an
automated UI-test suite. The HTTP-observable contract (the `[Authorize]` 302 gating, the auth-aware
nav shell) is locked by integration tests; the interactive circuit's client-side render is verified
via the live click-through.

The followed feed is rendered by a **`PagedCollection`** (a paged-collection pager ported from the
reference `SampleBlazorClient`) that walks the actor's `/feed` collection (the server's
`GET /ap/v1/u/{handle}/feed` `FollowFeedHandler`, F-14) one page at a time, de-duplicated, newest
first. Each item is rendered by a **`ObjectView`** (a simplified port of the sample's object
renderer).

## Key types & files

### Components — `apps/Iris.Web/Components/`
- `ObjectView.razor` — renders an ActivityStreams object (a note/post, link, or other `IObject`)
  inline: its type, author handle (linked), name, IRI (linked), content, audience, published/updated
  stamps, parent (reply) link, mentions, and media attachments (`<img>` for image attachments,
  same-origin — in `Iris.Web` the instance is the app's own origin, so media IRIs
  `/ap/v1/media/{id}` need no proxy rewrite; Decision 057's cross-origin case is N/A). Sensitive
  content is gated behind a "show" notice. Content is rendered verbatim when it is
  pre-rendered HTML (`IsPreRenderedHtmlContent`), HTML-encoded otherwise (Markdown rendering is a
  later experience-pass item). Pattern-matches `IObject` / `ILink` / unknown.
- `PagedCollection.razor` — a generic paged-collection pager: given an `IActivityPubClient` + a
  collection IRI + a page size, it walks `Client.GetCollectionAsync` (next-link paging), accumulates
  items, and renders them through a default item template (an `ObjectView`). Shows a "Loading…"
  spinner on the first page, an empty-state message when the collection is empty, a "Load more"
  button while more pages remain, a "Refresh" button (re-fetches page 1), and an error message on a
  fetch failure. Re-created (fresh state + fresh fetch) when its `@key` changes.
- `Pages/HomeTimeline.razor` — `@page "/home"`, `[Authorize]`. Reads the signed-in actor's
  `IActivityPubClient` + `ActorId` from `IActorSessionAccessor`, and renders a `PagedCollection`
  over `ActorId.FeedOf()` (page size 5) — the followed feed. A stable `@key` (`"home-feed"`) keys
  the `PagedCollection`.
- `Pages/Home.razor` (reworked) — `@page "/"` is now an **auth-aware landing** (not a redirect):
  signed-out it shows a "Welcome to Iris" card with Sign in / Create an account buttons; signed-in
  it shows "You're signed in" + a "Go to your timeline →" link to `/home` + the product links.
  (An earlier attempt used a `NavigationManager.NavigateTo` dispatcher, but a client-side redirect in
  `OnInitializedAsync` is not observable over HTTP and emitted a self-redirect over `TestServer`;
  the `AuthorizeView` landing is the robust, testable form.)
- `Layout/MainLayout.razor` (reworked) — the app's top bar is now an **`AuthorizeView`-driven nav**:
  signed-in it shows Home / Notifications / Directory / Profile / Search / Log out; signed-out it
  shows Log in / Register. (Notifications / Directory / Profile / Search are nav links for the later
  product screens; they 404 until those slices land, which is acceptable for a functionality-first
  pass — the nav surface is in place.)
- `Routes.razor` (reworked) — wraps the `RouteView` in a **`CascadingAuthenticationState`** so the
  `AuthorizeView` in the layout (and any `AuthorizeView` in a page) can read the `AuthenticationState`.

### Wiring

## Tests

`tests/Iris.Web.Tests/ProductShellIntegrationTests.cs` — 4 integration tests that boot the real app
(in-memory, the default) in a `TestServer` and assert the shell's HTTP-observable contract:
- **`/home` signed-out → 302 to `/login`**: the `[Authorize]` attribute + the cookie scheme's
  `LoginPath` make the authorization middleware redirect an unauthenticated request to `/login`
  (with a `ReturnUrl=%2Fhome` so the user lands back on the page they wanted).
- **`/home` signed-in → 200 with the feed card**: a signed-in request (the `iris.auth` cookie
  captured from the `POST /register` response and re-sent manually) returns 200 with the
  home-timeline card's static markup ("Home timeline", the `paged-collection` container). The feed
  items themselves are loaded by the interactive circuit, so they are not in the static prerendered
  HTML.
- **signed-in nav shows the product links** (Home, Log out, …) and **signed-out nav shows the
  login/register links** (Log in, Register; no "Log out").

The interactive circuit's client-side render (the `PagedCollection` actually fetching + rendering
the followed feed, the auth-aware landing's live state) is **not** exercisable over `TestServer`
HTTP (it is a circuit navigation / circuit render) — it is verified live via the MCP Playwright
server, per the feature-set plan (§1: the app's screens are verified functionally + visually in a
real browser, not by an automated UI test suite). The live click-through confirmed: register →
`/` (signed-in landing) → `/home` (the followed-feed card, with the empty-state "No posts in your
timeline yet. Follow an actor or join a community to populate it." when the user follows no one),
logout → `/login` → `/` (the signed-out "Welcome to Iris" landing).

`dotnet build Iris.slnx` clean (0 warnings, `TreatWarningsAsErrors` on); `Iris.Web.Tests` 40/40
green (36 pre-existing + 4 new).

## Decisions

- **`/` is an `AuthorizeView` landing, not a redirect.** A `NavigationManager.NavigateTo` in
  `OnInitializedAsync` is a client-side navigation that is not observable over HTTP (and emitted a
  self-redirect under `TestServer`). The `AuthorizeView`-driven landing (signed-out prompt /
  signed-in "go to your timeline" link) is the robust, testable form, and matches the feature-set
  doc's "the signed-out user hits `/` and sees a landing-with-sign-in-prompt."
- **The followed feed uses `GetCollectionAsync` over `{actor}/feed`** (the server's
  `FollowFeedHandler`, F-14), not a dedicated `GetFollowFeedAsync` call — the two are the same wire
  path (`GetFollowFeedAsync` is implemented as `GetCollectionItemsAsync({actor}/feed)`), so the
  generic `PagedCollection` pager works unchanged. This keeps the pager reusable for the outbox,
  followers, following, and the community feed in later slices.
- **Media IRIs are rendered as same-origin `<img>`** (no proxy rewrite): in `Iris.Web` the ActivityPub
  instance is the app's own origin, so a note's attachment `url` (`/ap/v1/media/{id}`) is already
  same-origin. Decision 057's cross-origin proxy case applies to the external `SampleBlazorClient`
  (which dials other instances), not to `Iris.Web`.
- **Object content is not yet Markdown-rendered.** `ObjectView` renders pre-rendered-HTML content
  verbatim and HTML-encodes plain content; real Markdown rendering (the sample's `Markdown`
  helper) is a later experience-pass item. Functionality-first: the content is visible and safe.
- **The product nav includes links to not-yet-built screens** (Notifications / Directory / Profile /
  Search). They 404 until their slices land; the nav surface is in place so the shell reads as a
  complete product. This is acceptable for a functionality-first pass and is called out here rather
  than hiding the links.
