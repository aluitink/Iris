### Per-class details

- **OutboxAudienceMatch** (2): A's delivery transport is a `RoutingHandler` that routes by request
  host header (B host → B's server, C host → C's server). A's `RoutingFetcher` routes by actor IRI
  host (A→A, B→B, C→C). B's and C's fetchers reach A (lazily, via `LazyHandler`). The tests verify
  that a public Create/Announce published to alice's outbox is delivered to bob (the follower) but
  NOT to carol (the non-follower). `SeedForFixture` restores all three actors (alice on A, bob on B,
  carol on C) after `Reset()` so B/C's fetchers can resolve actor docs.

### Design decision: `RoutingHandler` vs `LazyHandler`

The `RoutingHandler` (nested in the test class, `internal`) is used for A's delivery transport
because A must route to *either* B or C depending on the request's host header. This is different
from the two-host pattern where a single `LazyHandler` suffices (A always delivers to B). The
`RoutingHandler` clones the request (to avoid HttpClient's single-send constraint) and creates a
fresh `HttpClient` per request.
