# 54.32 — Server-Side Logging: Inbound Activity Types

## Summary

Inbox request logging was previously limited to signature-validation warnings (from the
`HttpSignatureValidator`). There was no visibility into what `type` of ActivityPub activities
were actually arriving, by which actor/instance, or whether they were accepted/processed/rejected
downstream of signature validation. This makes triage of federation issues (e.g. "why isn't
remote X's follow being processed?") guesswork.

## Change

Added structured logging to `HandleInboxPostAsync` (the single choke point through which ALL
inbound inbox deliveries pass — both person inboxes `POST /ap/v1/u/{handle}/inbox` and community
inboxes `POST /ap/v1/c/{name}/inbox`).

### Log lines added (logger category `Iris.Server.Inbox`)

| Scenario | Level | Message |
|----------|-------|---------|
| Invalid signature | Info | `Inbox rejected: invalid signature. Recipient: {Recipient}, KeyId: {KeyId}` |
| Unknown recipient | Info | `Inbox rejected: unknown recipient {Recipient}` |
| Rate-limited | Warn | `Inbox rate-limited: peer {Peer} exceeded budget. Recipient: {Recipient}` |
| Empty body | Warn | `Inbox rejected: empty body. Recipient: {Recipient}, Peer: {Peer}` |
| Unrecognizable payload | Warn | `Inbox rejected: unrecognizable payload. Recipient: {Recipient}, Peer: {Peer}` |
| Processing exception | Error | `Inbox processing failed: {ActivityType} from {Actor} targeting {Target}. Recipient: {Recipient}, Peer: {Peer}` |
| Tombstone accepted | Info | `Inbox accepted: Tombstone. Recipient: {Recipient}, Object: {ObjectIri}, Peer: {Peer}` |
| Activity accepted | Info | `Inbox accepted: {ActivityType} from {Actor} targeting {Target}. Recipient: {Recipient}, Peer: {Peer}` |

The "accepted" line captures the activity `type` (e.g. `Follow`, `Create`, `Like`, `Announce`,
`Undo`, `Mute`), the actor IRI, the target object IRI, the recipient, and the peer host — giving
operators full visibility into federation traffic patterns.

### Helper methods

- `ExtractActorIriFromActivity(Activity)` — returns the `actor` IRI string for logging.
- `ExtractTargetIriFromActivity(Activity)` — returns the `object` (target) IRI string for logging.

Both handle null/missing fields gracefully (return null, rendered as empty in the log).

### Design decisions

- **Info level for accepted deliveries**, not Debug. Operators of a public federated instance need
  this visibility by default (the default log level is Information in Production). An activity
  delivery is a significant federation event; Debug would hide it behind a log-level change.
- **Warn for rejections that indicate peer misbehavior** (rate-limit, empty body, unrecognizable
  payload). **Info for rejections that are expected** (invalid signature, unknown recipient) — these
  are the normal noise of a public instance receiving probes and mis-routed deliveries.
- **Error for processing exceptions** — an activity that passed signature validation but failed
  during processing is a genuine server-side bug worth immediate attention.
- **Guarded the `KeyId` log in the invalid-signature path** — when the signature is absent or
  malformed, `outcome.KeyId` is `default(Iri)` (null `_uri`), and `Iri.ToString()`/`Iri.Value`
  throw `NullReferenceException`. The log now renders `(none)` for a default Iri.

```
  log: Inbox rejected: invalid signature. Recipient: https://iris.luit.ink/ap/v1/u/nonexistent, KeyId: (none)
```

(A fully-signed delivery from a real remote instance would log the "accepted" line with activity
type, actor, target, and peer host — not testable without a second live instance.)
