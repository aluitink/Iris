# 33.4 — server production-readiness: inbound request-body size cap

**Slice:** Phase 33 step 4. **Branch:** `phase-32-production-app`. **Commit:** (impl + tests, this turn).

## Problem

The production app set **no inbound request-body size limit**. Kestrel's default imposes **no**
request-body limit, so an unauthenticated inbound `POST /ap/v1/u/{handle}/inbox` (a federation
endpoint any peer on the fediverse can reach without credentials) could stream an arbitrarily large
body into the app's memory — a denial-of-service vector for a **public** instance
(`https://iris.luit.ink`). A single malicious peer could force the process to buffer gigabytes.

There is already a cheap first line of defense: the inbox handler's **signature gate**
(`SignatureValidationMiddleware`) runs *before* the body is read and rejects an **unsigned** body
with `401` — so an unauthenticated oversized body is rejected without being buffered. But that gate
only stops *unauthenticated* traffic. A **signed** peer (a legitimate federated instance, or a
compromised/buggy one) passes the gate and then reads the body — with no cap, it could still stream
an oversized body and exhaust memory. A server-level request-body limit is the defense-in-depth
backstop that bounds the buffer for *any* body, signed or not.

## Change

- **`apps/Iris.Web/WebAppFactory.cs`**:
  - New `public const long DefaultMaxRequestBodySize = 1024L * 1024L` (1 MiB) — generous for an
    ActivityStreams activity JSON document (legitimate federation payloads are well under a few tens
    of KB), small enough to bound memory.
  - New `public const string MaxRequestBodySizeConfigKey = "Iris:MaxRequestBodySize"`.
  - At the end of `ConfigureServices`, the cap is applied to Kestrel:
    `builder.WebHost.ConfigureKestrel(o => o.Limits.MaxRequestBodySize = <cap>)`, where the cap is
    `Iris:MaxRequestBodySize` when set to a positive integer, else the 1 MiB default. A request whose
    body exceeds the cap is rejected by Kestrel with **413 Payload Too Large** *before* the pipeline
    reads it.
- **`apps/Iris.Web/docker-compose.yml`** + **`.env.example`**: new `IRIS_MAX_REQUEST_BODY_SIZE` env
  var (maps to `Iris:MaxRequestBodySize`, in bytes). Unset → the app's 1 MiB default; set to a larger
  byte count only if a legitimate use case (e.g. very large embedded media on an activity) requires it.

## Decision (recorded)

- **Default is 1 MiB**, not the (effectively unbounded) Kestrel default. A public fediverse instance
  must bound unauthenticated inbound memory by default; an operator who needs more (a legitimate
  large-activity case) raises it explicitly via the env var. A non-numeric or non-positive config value
  falls back to the default (never to 0 / never crashes the boot).
- **The cap is defense-in-depth, not a replacement for the signature gate.** The signature gate still
  rejects *unsigned* oversized bodies with `401` cheaply (before the body is read). The cap is the
  backstop for a *signed* peer that passes the gate and streams an oversized body. Both are needed:
  the gate is cheap and first; the cap is a hard memory bound.

## Tests / verification

**4 new integration tests** (`tests/Iris.Web.Tests/RequestBodyLimitIntegrationTests`) — they assert the
production wiring directly: the Kestrel server options resolved from a `WebAppFactory.ConfigureServices`
+ `Build` host carry the expected `Limits.MaxRequestBodySize`:
- `DefaultCap_IsOneMegabyte` — the default is exactly 1 MiB.
- `ConfiguredCap_IsApplied` — `Iris:MaxRequestBodySize=4194304` flows through to the Kestrel options.
- `InvalidConfig_FallsBackToDefault` — a non-numeric value falls back to the 1 MiB default.
- `NegativeConfig_FallsBackToDefault` — a negative value falls back to the 1 MiB default.

(The tests build the host but do **not** start it, so no port binding / static-assets manifest is
needed and nothing requires disposing. A real-Kestrel 413 round-trip was attempted but the signature
gate rejects an *unsigned* oversized body with 401 before the body is read — which is the correct,
cheaper first-line behavior; the cap is the backstop for *signed* traffic, so the faithful seam is the
resolved Kestrel options, not an unsigned round-trip.)

**Verified live in the production container** (rebuilt the image + `docker compose up -d iris-web` over
the **persistent** Postgres volume):
1. A **small** unsigned `POST /ap/v1/u/alice/inbox` returns **401** (signature gate) — **not** 413: the
   size gate does not interfere with normal traffic.
2. An **oversized (1.5 MiB)** unsigned `POST /ap/v1/u/alice/inbox` returns **401** — the signature gate
   rejects it cheaply *before* the body is buffered (the unauthenticated DoS path is already closed; the
   cap is the backstop for signed peers).
3. `GET /ap/v1/u/alice` still returns **200** (actor document served normally); the app is healthy
   (`GET /ap/v1/health` → 200); **no** 413 / request-body / out-of-memory errors in the container log.

Build clean (`dotnet build`, `TreatWarningsAsErrors` on); `Iris.Web.Tests` 49/49 green (45 prior + 4
new).
