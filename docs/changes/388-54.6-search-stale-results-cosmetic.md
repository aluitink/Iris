# 54.6 — Search stale-results cosmetic

Phase 54 slice (cosmetic). During a re-search, the "Searching…" spinner renders while the
previous result set remains visible below, so the user briefly sees stale results for the
*old* query alongside the spinner (noted in 54.2, deferred).

## Diagnosis

The defect was reported against the Search page's result-rendering
([Search.razor](apps/Iris.Web.Client/Components/Pages/Search.razor)). Investigating the
live behavior (a CDP-throttled re-search with a `MutationObserver` sampling every committed
DOM frame) showed that the current code **already** cleared the stale results in practice:
`RunSearchAsync` sets `Results = null` (alongside `Busy = true`) synchronously *before* its
first `await`, so by the time Blazor re-renders with the spinner up, the old result list is
gone. The observer confirmed the spinner was **never** visible together with any results.

However, the correctness was **incidental** — it depended on the `Results = null` being
reached in the same synchronous chunk as `Busy = true` (before the first `await`), not on
the render guard. The results branch was guarded only by `Results is not null`, so a future
refactor that sets `Results` after `Busy = true` (or leaves a prior `Results` in place) would
silently re-introduce the stale-results flash.

## Change

[Search.razor](apps/Iris.Web.Client/Components/Pages/Search.razor) — made the intent
**structural** rather than timing-dependent. The results-render branch is now gated on
`!Busy` as well:

```razor
else if (Results is not null && !Busy)
```

So while a search is in flight (`Busy` true), the previous result set is never rendered —
the "no stale results during a re-search" behavior no longer depends on `Results` being
nulled in the right order. The in-flight window shows just the spinner (stale results
hidden), matching the slice's requirement ("hide the stale results … while a new search is
in flight"). No CSS change (Razor-only), no API change, no dependencies.

## Verification

Live-verified on the FQDN (`https://iris.luit.ink`), signed in as `alice`, CDP cache
disabled + a 3.5 s network throttle to make the in-flight window observable. Search 1 ("a")
populated 8 stale results; a `MutationObserver` was installed to sample every committed DOM
frame during search 2 ("b"):

- `firstSpinner` state: `spinnerVisible: true, resultCount: 0, h2: null` — when the spinner
  first appeared, the stale results were already cleared.
- `spinnerWithResults`: `null` — the observer **never** saw the spinner visible together
  with any results (stale results hidden throughout the in-flight window).
- `minResultCountDuringSpinner`: `0` — the result count stayed 0 for the entire in-flight
  window.
- After the search completed: spinner gone, 6 "b" results rendered cleanly.

Build clean (0 warnings, `TreatWarningsAsErrors` on); `Iris.Web.Tests` 63/63 (no regression).
0 console errors.
