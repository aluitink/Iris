# 290 — 32.5: Deployment (Docker Compose)

> 2026-09-06 · Slice 32.5 · Phase 32 (production social platform app) — step 5 (deployment)

## What was built

Phase 32's **step 5** (Deployment, `docs/plans/production-app-deployment.md`): the production
`docker-compose.yml` + `Dockerfile` for `Iris.Web` — one deployable Compose stack (app + Postgres +
media volume), `.env`-driven, published on host port **8088** so it takes over the existing
`https://iris.luit.ink` reverse-proxy target with no reconfiguration. Per the Phase 32 pivot
(PLAN.md, 2026-09-06), this slice is accepted by driving the **real stack in a real browser (MCP
Playwright) over the public FQDN**, not by bUnit/UI-automated tests; the in-process `Iris.Web.Tests`
integration suite still gates the code changes.

### New deployment artifacts

- **`apps/Iris.Web/Dockerfile`** — multi-stage: `mcr.microsoft.com/dotnet/sdk:10.0` (restore + publish,
  `/p:UseAppHost=false`) → `mcr.microsoft.com/dotnet/aspnet:10.0` (runtime). `ASPNETCORE_URLS=+:8080`
  (in-container port); `EXPOSE 8080`. Build context is the repo root (the compose file sets
  `context: ../..`).
- **`apps/Iris.Web/docker-compose.yml`** — two services on an internal `iris-web-net` bridge:
  - `db` (`postgres:16`): the `iris-db-data` named volume for `PGDATA`, a `pg_isready` healthcheck,
    and **no host port published** (Postgres is reachable only from `iris-web` on the internal
    network — it is not exposed to the host).
  - `iris-web` (built from the Dockerfile): `iris-media-data` volume (for the future local-disk media
    backend), published `${WEB_PORT:-8088}:8080`, a pure **TCP-connect healthcheck** (the base aspnet
    image has no `curl`), and `depends_on: db: service_healthy`.
- **`apps/Iris.Web/.env.example`** (committed) — documents every variable with its default; the real
  `.env` (git-ignored) holds the DB + admin passwords. Variables map to the app's **actual** config
  surface: `IRIS_ADVERTISE_BASE` → `Iris__AdvertiseBase` (the single advertised base URI — the public
  FQDN), `POSTGRES_*` → the assembled `ConnectionStrings__Iris`, `IRIS_ADMIN_*` → `App__Admin__*`
  (admin bootstrap), `WEB_PORT` → the published host port.
- **`scripts/prod-smoke-test.sh`** — the production-stack smoke test (mirrors
  `scripts/docker-smoke-test.sh`'s style + opt-in gate): `down -v` (clean) → `up --build` → wait for
  `db` + `iris-web` healthy → register a user over HTTP (fetching the antiforgery token from the
  `/register` form first, since `UseAntiforgery` guards the POST) → confirm the actor document +
  outbox resolve → `down` (no `-v`) + `up` → confirm the actor persisted (durability) → `down -v`.
  Generates a throwaway `.env` from `.env.example` if none exists (never overwrites an operator's).

### Code changes

- **`WebAppFactory.ConfigurePipeline`** — added `app.UseForwardedHeaders()` before `UseAuthentication()`
  (`docs/plans/production-app-deployment.md` §5). The app sits behind a TLS-terminating reverse proxy
  (`https://iris.luit.ink` → host 8088); without forwarded headers the app would see plain `http` and
  the auth cookie's `Secure` flag / any scheme-dependent redirect would be wrong. It is in the ASP.NET
  Core shared framework (`Microsoft.AspNetCore.HttpOverrides`) — no new package. No-op when not behind
  a proxy (the headers are absent).
- **`EntityFrameworkPersistenceExtensions` (the deployment's root-cause fix)** — the EF
  `IPersistenceProvider` registration changed from `TryAddSingleton` to a **hard `AddSingleton`**.
  `AddActivityPubServer` registers a *recursive* fallback factory for `IPersistenceProvider`
  (`sp => sp.GetRequiredService<IPersistenceProvider>()`) via `TryAddSingleton`, which becomes the
  first binding. The EF `TryAddSingleton` was therefore a **no-op** (the service was already
  registered by that fallback), leaving the recursive factory as the sole binding — resolving it
  recursed infinitely (an `StackGuard` deadlock) the first time anything resolved
  `IPersistenceProvider` (the startup migration / seed), so the container booted but never reached
  `app.Run()` (no listener, no logs). The hard `AddSingleton` adds a second binding; for singletons the
  **last** registration wins, so the EF factory overrides the fallback and resolves cleanly. (The
  in-memory path was never affected because `WebAppFactory` binds it with a hard `AddSingleton` too.)
  The now-inaccurate comment in `AddActivityPubServer` (which claimed a later `TryAddSingleton` would
  "win") is what let this slip past the in-memory-only integration tests.

## Verification

- **`docker compose up --build` from clean volumes** → `db` + `iris-web` both `healthy`; the app
  serves HTTP 200 on host 8088.
- **MCP Playwright over the public FQDN (`https://iris.luit.ink`)** — the full vertical slice, driven
  in a real browser over the real Compose stack + reverse proxy:
  - `GET /` → the signed-out "Welcome to Iris" landing.
  - `POST /register` (form) → **302** to `/`; the signed-in state renders (nav: Home / ＋ New post /
    Notifications / Directory / Profile / Search / Log out; "You're signed in.").
  - `/compose` → "Posting as `https://iris.luit.ink/ap/v1/u/playwright-e2e`" (the advertised base is
    the public FQDN, confirming `Iris__AdvertiseBase` from the compose env); post → **"Posted (HTTP
    202)."** + the minted `Create` IRI.
  - `/profile` → the actor header (`playwright-e2e` / `Playwright E2E`) + the "Your posts" outbox shows
    the `Create` with the same minted IRI.
  - Raw ActivityPub surface over the FQDN: `GET /ap/v1/u/playwright-e2e` → `Person`; the `Create`'s
    embedded `Note` content reads back exactly. The rows are present in Postgres
    (`UserAccounts`=1, `Actors`=2, `Activities`=1, `Objects`=1).
  - Note: the Blazor circuit's first WebSocket attempt over the proxy logged a transient
    "Unexpected response code: 200" (the external reverse proxy does not upgrade WebSockets — a proxy
    config concern, out of scope for the Compose stack per the deployment plan §5); SignalR retried and
    the circuit booted, so the in-circuit compose post succeeded. This is recorded as a known
    proxy-config consideration for a real public deployment (Caddy upgrades WebSockets by default).
- **Durability** (`production-app-deployment.md` §6): `docker compose down` (no `-v`) + `up -d` →
  `iris-web` healthy; the actor + note persist over the FQDN (the `iris-db-data` volume preserved the
  DB). `docker compose down -v` gives a clean slate (the smoke test starts from it).
- **`scripts/prod-smoke-test.sh`** — **PASSED** end-to-end (clean boot → register → actor/outbox
  resolve → durability across a restart).
- **No regressions** — full fast suite (`dotnet test --filter "Category!=Slow"`) green: 0 failures.
  `Iris.Server.Data.Tests` 8/8 (the EF provider contract + the DI fix), `Iris.Web.Tests` 45/45 (the
  `UseForwardedHeaders` addition), `Iris.Server.Tests` 926 passed / 1 skipped (the known unrelated
  skip), `Iris.Client.Tests` 152, etc.

## Deferred / notes

- **TLS / reverse proxy** is out of scope for the Compose stack itself (deployment plan §5): the MVP
  listens on plain HTTP inside the container, published on 8088, behind the existing
  `https://iris.luit.ink` reverse proxy. The app's `UseForwardedHeaders` handles the `https` scheme on
  the app side; the proxy must upgrade WebSockets (Caddy does by default) for the Blazor circuit.
- The **`iris-media-data`** volume is mounted but unused until the local-disk media backend lands
  (media upload is a later feature; the `Media__*` config section is not yet read by `Iris.Web`, so no
  dead env vars are set).
- 32.4c (notifications + search UI) remains deferred (it was the pre-pivot next slice; see PLAN.md).
