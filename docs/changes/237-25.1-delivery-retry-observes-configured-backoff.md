# 25.1 — Delivery retry observes the configured backoff

Phase 25, slice 1. **Type:** test-only (invariant lock — no production code change; the worker's
exponential-backoff retry policy already works). This is the first locally-actionable Phase 25 slice
(federation hardening & robustness).

## Problem (and why it is a test, not a fix)

The `DeliveryWorker` (F-22 at-least-once delivery) already retries a failed delivery up to
`DeliveryRetryOptions.MaxAttempts` total attempts, waiting an exponentially-growing delay between
attempts (`BaseDelay` doubled each retry, capped at `MaxDelay`), dead-lettering when the budget is
exhausted. The existing `DeliveryRetryTests` suite covers the *outcomes* of that policy thoroughly:

- `TransientFailure_IsRetried_UntilSuccess_NotDeadLettered` (500, 500, 200 → delivered, not dead-lettered)
- `PermanentFailure_ExhaustsBudget_IsDeadLettered`, `TransportError_ExhaustsBudget_IsDeadLettered_AsTransportError`
- `MaxAttemptsOne_IsFailFast_NoRetry_ButDeadLetters`, `WithoutDeadLetterStore_ExhaustedJob_IsDropped_NotCrash`
- `BackoffDelay_GrowsExponentially_AndIsCapped` (reflection check of the private `BackoffDelay(int)` pure function)

But **every outcome test sets `BaseDelay = 0`** so the backoff delays are instant (no real waiting in
the test). That means the suite locks *that* the worker retries and *that* the `BackoffDelay` pure
function has the right exponential shape — but it does **not** lock that the worker *actually observes*
a non-zero delay between retries. A regression that removed the `await Task.Delay(BackoffDelay(attempt), ct)`
call in `DeliverOneAsync` (making retries back-to-back with no spacing, hammering a downed peer) would
keep every existing test green: the retries still happen, the delivery still succeeds, and the
`BackoffDelay` pure function still returns the right value — only the *wait* would be gone.

That is precisely the gap this slice closes. `TransientFailure_WaitsConfiguredBackoff_BetweenRetries`
is the first test in the suite that uses a **real** `BaseDelay` (150ms) and asserts the wall-clock
cost of the wait itself:

1. **Total elapsed** from enqueue to completion is `>= 250ms`. With a 150ms `BaseDelay`, the worker
   observes two backoffs before the third (successful) attempt — `BackoffDelay(1) = 150ms` (before
   attempt 2) and `BackoffDelay(2) = 300ms` (before attempt 3) — so the recovery takes `>= 450ms` of
   pure backoff plus overhead. The 250ms floor is well below that, so the assertion is robust to
   scheduling jitter but well above the ~70ms a no-wait regression would produce.
2. **Per-retry gap** between the first and second handler send is `>= 100ms`, locking that the *first*
   backoff (the 150ms `BaseDelay`) is observed before the retry fires. This catches a regression that
   only dropped the wait on the first retry (or only on later ones) — the total-elapsed assertion
   alone could in principle be masked if a later backoff were the only one removed.

The test extends the existing `FailableHandler` stub (which already scripts a sequence of responses and
counts `CallCount`) to optionally record `Environment.TickCount64` at each send, exposing the
per-attempt gaps. `Environment.TickCount64` is already in milliseconds (no tick conversion needed — a
subtle point that cost one debugging round: the first cut divided by `TimeSpan.TicksPerMillisecond`
and read every gap as 0ms).

## Where (tests only)

- `tests/Iris.Server.Tests/Delivery/DeliveryRetryTests.cs`:
  - New test `TransientFailure_WaitsConfiguredBackoff_BetweenRetries` (a 500, 500, 200 recovery with
    `MaxAttempts = 5`, `BaseDelay = 150ms`, `MaxDelay = 10s`, timestamps tracked): asserts
    `CallCount == 3`, no dead-letter, total elapsed `>= 250ms`, and the gap before the 2nd attempt
    `>= 100ms`.
  - `FailableHandler` gains an optional `trackAttemptTimestamps` flag and two diagnostics views
    (`AttemptTicks`, `AttemptGapsMs`, `MillisecondsBetweenAttempt1And2`) recording the wall-clock time
    of each send.
  - The `BuildWorker` helper gains a `trackAttemptTimestamps = false` parameter (default off, so every
    pre-existing test is byte-for-byte unaffected).
  - The class `<remarks>` notes the one real-delay exception in the otherwise zero-delay suite.

No production code changed. The load-bearing code under test is the pre-existing `await
Task.Delay(BackoffDelay(attempt), ct)` in `DeliveryWorker.DeliverOneAsync`'s retry loop and the
exponential `BackoffDelay(int)` it calls.

## Non-vacuity (proven)

Per the loop's "prove it fails" discipline, the backoff was temporarily disabled in the test by setting
`baseDelayMs: 0` (the worker then waits 0ms between retries):

- With `BaseDelay = 0`, the test **fails** on the total-elapsed assertion: *observed 69ms*, below the
  250ms floor (the 534ms a real 150ms backoff produces). This confirms the test genuinely exercises the
  wait — it is not passing vacuously because the worker happened to be slow.
- Restoring `baseDelayMs: 150` turns it green (observed ~540ms).

A regression that removed the `Task.Delay` from the retry loop would be caught the same way (the
retries would be back-to-back, total elapsed ~70ms, both assertions failing).
