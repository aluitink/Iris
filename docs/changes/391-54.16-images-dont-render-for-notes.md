# 54.16 — Images don't render for notes

Phase 54 slice. Two independent defects combined to make image attachments on notes/posts fail to
display in the home timeline and profile (while the object **detail** page worked):

1. **UI — the feed's rendering path never rendered media.** The home timeline and profile outbox
   render each feed item as the **wrapping activity** (a `Create`), not the embedded `Note`.
   `ObjectView.razor`'s `Item is Create` and `Item is Announce` branches rendered the content +
   engagement bar but had **no media `<img>` loop** — that loop existed only in the direct-object
   branch (`Item is IObject { Id: … }`), which the detail page uses (it fetches the `Note` directly).
   So a note with an image rendered its text in the feed but silently dropped the image; the detail
   page showed the image.

2. **Persistence — uploaded blobs were written to an ephemeral path, not the mounted volume.** The
   EF media store (`EfMediaStore`) persists each uploaded image as one file per media id under a
   blob directory that defaults to `<AppContext.BaseDirectory>/media-blobs` (= `/app/media-blobs` in
   the container) unless `Iris:MediaBlobDir` is set. The Docker compose mounted a **named volume**
   at `/data/media` (intended to hold the blobs) but **never told the app to use it**, so blobs were
   written to the container's ephemeral filesystem. Every `docker compose up --force-recreate` /
   deploy wiped all blobs while their `Media` DB rows (in the durable Postgres volume) survived —
   after any restart, **every** note/avatar image 404'd. (A stale compose comment even claimed the
   media volume was "unused until that feature lands"; the EF media feature had already shipped.)

## Change

1. **Render media in the activity branches** ([ObjectView.razor](apps/Iris.Web.Client/Components/ObjectView.razor),
   [ObjectView.razor.cs](apps/Iris.Web.Client/Components/ObjectView.razor.cs)): added an
   `ActivityMediaAttachments` property that reads the **embedded object's** attachments
   (`ActivityEmbeddedObject?.GetMediaAttachments()`, each rewritten same-origin via the existing
   `RewriteMediaToSameOrigin`), and added the `<div class="object-media"><img …/></div>` loop to both
   the `Item is Create` and `Item is Announce` branches, mirroring the direct-object branch's loop.
   The direct-object branch (detail page) is unchanged and still works.

2. **Point the blob dir at the mounted volume** ([docker-compose.yml](apps/Iris.Web/docker-compose.yml)):
   added `Iris__MediaBlobDir: ${IRIS_MEDIA_BLOB_DIR:-/data/media}` so the EF media store writes blobs
   to the named volume. Removed the stale "unused volume" comment and documented the mapping.

3. **Fix volume ownership for the non-root app user** ([Dockerfile](apps/Iris.Web/Dockerfile)): the
   `/data/media` volume is created root-owned, but the app runs as the `iris` user (uid 1001, the
   50.1 security hardening). The entrypoint already `chown`'d the DP-keys volume; it now also
   `chown -R 1001:1001 /data/media` before dropping privileges, so uploads no longer fail with
   `UnauthorizedAccessException: Permission denied`.

4. **Migrate existing `Media.StorageKey` rows** from the old `/app/media-blobs/<id>` to
   `/data/media/<id>` so the DB convention matches the new blob location going forward. (The old
   blobs were already lost on the last recreate; their images are unrecoverable until re-uploaded,
   but the path is now consistent.)
