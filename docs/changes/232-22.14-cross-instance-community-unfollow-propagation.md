# 22.14 — Cross-instance community un-follow propagation (community → person)

Phase 23, slice 4. **Type:** test-only (invariant lock — no production code change; the remote-side
un-follow handling already works).

## Problem (and why it is a test, not a fix)

The "community/follow hardening" theme of Phase 23: when a **community** C on instance A **follows** a
**person** bob on instance B, the follow federates A → B and B records C in bob's followers set. This
slice locks the **inverse** half end-to-end: when C publishes an `Undo(Follow)`, does B's instance
receive the `Undo` and **remove** C from bob's followers?

The answer, traced through the code, is **yes — it already worked before this change**:

- A's `CommunityOutboxPublishHandler` records C's local follows set and **delivers** the signed
  `Follow` / `Undo(Follow)` to bob's inbox on B (bob is the follow target and a delivery recipient).
- B's `FollowActivityHandler` records the directed edge (C → bob) in B's follow store when the `Follow`
  arrives; B's `UndoActivityHandler` (F-1911-1) resolves the original `Follow` from B's activity store,
  reads the follower/target parties, and — for a **local-actor target** (bob) — calls
  `IFollowStore.RemoveFollowAsync(C, bob)`, removing C from bob's followers set.

The subtle dependency this test locks: **B can only remove the edge if it first received and stored the
original `Follow`** (the `Undo` references the original by its server-minted IRI, and B's handler
resolves the parties from its own activity store — it does not re-fetch the original from A). The test
exercises the real cross-instance flow: the follow federates A → B (B records + stores), then the
`Undo(Follow)` federates A → B (B resolves the stored original and removes).

This is the community-follower, follow-flavored counterpart of 22.13 (person moderation undo) and the
cross-instance un-follow complement of the existing community-follow coverage. Same class of
invariant-lock: the behavior was already correct; the test exists to fail loudly if a future change
regresses the remote-side removal (e.g. an `UndoActivityHandler` refactor that drops the local-actor
target branch, or a delivery-target change that stops delivering the `Undo` to the target's inbox).

## Wiring detail (a decision, recorded)

The `ActivityPubHostFactory` auto-registers a community's key under `https://{host}/ap/v1/c/{Handle}`
(assuming the community's name equals the instance's handle). In this test the community `iris` ≠ the
instance handle `alice`, so the auto-registration would key the community under the wrong IRI and the
outbound `DeliveryWorker` could not sign the federated activity as the community. The test therefore uses
the `IdentityKeys` escape hatch (`BuildIdentityForA`) to register **both** the instance actor and the
community at their correct IRIs, so A's delivery worker signs the `Follow`/`Undo` as the community. (This
is a test-harness wiring choice, not a production behavior change.)

## Where (tests only)

- `tests/Iris.Server.Tests/CommunityFollowsPersonUnfollowPropagationIntegrationTests.cs` (2 new
  integration tests), a 2-instance `TestServer` topology (A = `cf-unfollow-a.domain.local`, instance
  actor `alice` + community `iris`; B = `cf-unfollow-b.domain.local`, person `bob`), wired per the
  established `OutboxPublishServerDeliversIntegrationTests` / `ModerationUndoPropagationIntegrationTests`
  pattern (two `ActivityPubHostFactory.Create` instances; A's `IdentityKeys` registers alice + iris;
  A's `DeliveryTransport` routes to B; A's `RoutingFetcher` routes by actor-IRI host; B's fetcher routes
  to A to fetch the community's document for signature validation):
  1. `CommunityFollowOfRemotePerson_FederatesAndRecordsInRemoteFollowStore` — C publishes a `Follow` of
     bob to `/ap/v1/c/iris/outbox` (202; A records C's local follows set; learns the minted id from the
     2xx body per decision 055); waits for B to record the C → bob edge (proving the Follow federated
     **and** was stored in B's activity store); asserts the community is listed in bob's followers
     (inverse direction) **and** that B stored the original `Follow`.
  2. `CommunityUnfollowOfRemotePerson_FederatesAndRemovesFromRemoteFollowers` — establish the follow (as
     above); C publishes `Undo(Follow)` (202); waits for A to remove its local follows edge; waits for
     **B to remove the C → bob edge**; asserts the community is no longer listed in bob's followers.

  Each test asserts the edge state on **both** A and B, pinning both the local and the cross-instance
  half.

## Non-vacuity (proven)

Per the loop's "prove it fails" discipline, the remote person-target removal was temporarily disabled
(the `IFollowStore.RemoveFollowAsync(followerIri, targetIri)` call in `UndoActivityHandler`'s
local-actor-target branch commented out, then restored):

- With the removal disabled, the **unfollow test fails** (B records the edge but never removes it — it
  times out at 30s) while the **forward follow test still passes** (it does not depend on the removal).
- Restoring the handler turns both green.

This confirms the unfollow test genuinely exercises the cross-instance removal (not passing vacuously
because B never recorded the edge — the follow step asserts B *did* record it).
