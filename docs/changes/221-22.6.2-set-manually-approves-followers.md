# Change 221: `SetManuallyApprovesFollowersAsync` — close the person settings write path (22.6.2)

## Summary

A person can now toggle its `manuallyApprovesFollowers` gate AP-natively through the client, closing the
read/write asymmetry with the community's `SetManuallyApprovesMembersAsync` (change 217). Before this
change the server rendered the gate (`manuallyApprovesFollowers` echoed on the public document, and the
`iris:settings` / `iris:capabilities` advertising from change 220) but there was **no client method to
set or clear it** — the community had `SetManuallyApprovesMembersAsync`, the person did not.

## Problem

- `IActivityPubClient.SetManuallyApprovesMembersAsync(communityIri, enabled, ct)` existed (change 217),
  but there was no person-side counterpart. The only way to change a person's gate was to edit the actor
  store directly.
- The person `OutboxPublishHandler` did not handle an `Add`/`Remove` of the actor's own document (only
  `Create`/`Announce`/`Delete`/`Follow`/`Block`/`Flag`/`Like`/`Undo`/`Accept`/`Reject`), so an AP-native
  settings change to a person's outbox was recorded in the outbox but never applied to the stored actor.
- The public actor document is served through the `LocalActorDocumentCache` (60s TTL). A settings change
  mutated the stored actor but did **not** invalidate the cached render, so the public document kept
  serving the stale (pre-change) copy for up to 60s.

## Solution

### Client (Iris.Client)

1. **`IActivityPubClient.SetManuallyApprovesFollowersAsync(actorIri, enabled, ct)`** + implementation in
   `ActivityPubClient`: builds an `Add` (enable) or `Remove` (disable) of the actor's own document
   carrying the `manuallyApprovesFollowers` extension, and publishes it to the actor's own outbox
   (`actorIri.OutboxOf()`). Mirrors `SetManuallyApprovesMembersAsync` exactly (decision 055: the client
   sends only the activity's shape; the server mints the id and returns it in the 2xx body).

### Server (Iris.Server)

2. **Person outbox `Add`/`Remove` handling**: `OutboxPublishHandler` now handles an `Add`/`Remove` whose
   object is the actor's own document carrying `manuallyApprovesFollowers`:
   - `RecordPersonAddAsync` — sets the stored actor's `manuallyApprovesFollowers` extension when the
     object is the actor's own document and the extension is present.
   - `RecordPersonRemoveAsync` — clears the stored actor's `manuallyApprovesFollowers` extension.
   - `SetManuallyApprovesFollowersAsync` (private helper) — the read-modify-write on the stored actor's
     `ExtensionData`.
   A local-only operation (no delivery), mirroring the community's `RecordCommunityAddAsync` /
   `RecordCommunityRemoveAsync` (change 217).

3. **Actor document cache invalidation (bug fix)**: on a person settings `Add`/`Remove`, the handler now
   calls `LocalActorDocumentCache.Invalidate(actorIri)` so the public document re-renders (reflecting
   `iris:settings` / `iris:capabilities`) on the next read, instead of serving the stale 60s-TTL copy.
   The `LocalActorDocumentCache` is now a dependency of `OutboxPublishHandler`. This is the same class of
   fix as the existing outbox-page invalidation, applied to the actor-document cache.

### Tests

4. **4 new integration tests** (`PersonSettingsIntegrationTests`), modeled on the community
   `CommunityJoinRequestIntegrationTests` signed-request + client-factory harness:
   - `Client_SetManuallyApprovesFollowers_Enabled_SetsStoredFlag` — client `Add` sets the stored flag.
   - `Client_SetManuallyApprovesFollowers_Disabled_ClearsStoredFlag` — client `Remove` clears it.
   - `SetGate_ThenPublicDoc_AdvertisesSettingsExtension_AndClearing_RemovesIt` — enabling the gate makes
     the public document advertise `iris:settings` (outbox IRI) + `"settings"` in `iris:capabilities`;
     clearing removes both (exercises the cache-invalidation fix).
   - `SetGate_ThenInboundFollow_SurfacesInOutbox_WithoutAutoAccept` — a gated inbound `Follow` is
     surfaced in the followed actor's outbox but produces no auto-`Accept` (the gate's effect).

5. **Stub updates**: `StubCollectionClient`, `StubClient`, and `StubActivityPubClient` (test fakes
   implementing `IActivityPubClient`) now implement the new `SetManuallyApprovesFollowersAsync` method.

## Note

The community-side equivalent (change 217) does **not** currently invalidate its document cache on a
settings change; that is a pre-existing, out-of-scope gap (community documents are served through the
collection-page cache, a separate seam). It is noted here for completeness.
