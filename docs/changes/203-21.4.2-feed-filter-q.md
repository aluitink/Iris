# 203 — 21.4.2 Feed filter (`?q`) for the followed feed

**Phase 21** (Sample UI expansion) / **Phase 22** (functional-explorer rebuild), the **21.4.2 "Feed filter
(`?q)`"** — a search box on the Feed page that filters the followed feed to items whose content/name
matches the query (case-insensitive), via the `?q` query on the `{actor}/feed` endpoint. → Phase 22 US-6 /
`PagedCollection` (US-20).

## The change (backend + UI)

### Backend — the followed feed endpoint gains `?q` (mirrors the community feed's F-23 `?q`)

- **`IFollowFeedService.GetFeedAsync`** gains a `string? query = null` parameter. When non-empty/
  whitespace, the feed is **filtered** to the items whose `content` or `name` (either as a single value or
  a value within the multi-valued property, and — for activities — the content/name of each referenced
  object) contains the query as a substring, case-insensitively (the same match as the community feed's
  `?q` filter, F-23). A null/empty/whitespace query returns the feed unfiltered.
- **`FeedService.GetFeedAsync`** is refactored: the unfiltered build is extracted to
  `BuildFeedAsync`, and a non-empty query delegates to a new `FilterFeed` (a static helper mirroring
  `CommunityFeedService.SearchCommunityAsync`'s content/name + nested-object match). The filter is applied
  **after** the merge/dedup/truncate, so the filtered set is a subset of the full feed (order preserved).
- **`FollowFeedHandler`** (`GET /u/{handle}/feed`) reads `?q` from the request and passes it to
  `feedService.GetFeedAsync(actorIri, query, ct)`. An empty/absent `?q` returns the feed unfiltered.

### UI — the Feed page gains a search box

- **`Feed.razor`** adds a search card (input + **Filter** + **Clear** buttons) above the
  `PagedCollection`. When a query is applied:
  - the `FeedIri` is constructed with `?q=…` appended (e.g. `{actor}/feed?q=hello`), so the
    `PagedCollection` fetches the filtered feed;
  - a `@key` on the `PagedCollection` changes (`feed-{query}`), forcing Blazor to re-create the component
    (fresh state + fresh fetch) whenever the filter is applied or cleared;
  - a "Showing items matching **q**." banner + the card title/empty-message update to reflect the filter.

### Test — 4 new integration tests (`FollowFeedIntegrationTests`)

- `Feed_Query_MatchesContent_CaseInsensitive` — `?q=BOB` matches bob's 2 posts (content on the nested
  Note, case-insensitive) but not carol's.
- `Feed_Query_MatchesCarolContent` — `?q=carol` matches carol's 1 post.
- `Feed_Query_NoMatch_ReturnsEmptyCollection` — `?q=zzz` returns `totalItems: 0`.
- `Feed_EmptyQuery_ReturnsUnfilteredFeed` — absent/`?q=` returns all 3 items.

## Method

Phase 22 manual-testing discipline (operator directive, rule 5): UI work is verified with Playwright MCP
(no new framework tests for the UI half). The **backend change** (the `?q` filter on the followed feed)
ships with its 4 integration tests (the directive's exception: "if developing a UI feature requires a
specific backend change, ship that backend change with its normal integration test").

## The pass (compose stack, `iris-a`/`iris-b`/`iris-ui`; logged on as `alice@localhost` dialing `http://localhost:8081`)

- **The search box renders** on the Feed page (input + Filter + Clear). After logging on as alice and
  navigating in-SPA to `/feed`, the search card is present above the `PagedCollection`.
- **The `?q` IRI is constructed correctly:** typing "hello" + clicking **Filter** issues
  `POST /ap/v1/proxy/https://iris-dev1.luit.ink/ap/v1/u/alice/feed?q=hello` (verified in the network
  log). The "Showing items matching **hello**." banner, the "Followed feed — **hello**" card title, and
  the "No followed items match this filter." empty-message all update. **Clear** reverts to the
  unfiltered feed (a new unfiltered request is issued, the banner/title/empty-message revert).
- **The end-to-end "filter returns matching items" step is blocked by the pre-existing external-FQDN
  proxy blocker** (the same documented limitation that affects 19.6.1/19.6.2/21.2.2/21.2.3): the
  followed feed merges alice's **remote** follows' outboxes (fetched via the advertised FQDN
  `iris-dev1.luit.ink`), which 500s in this env (the `FederatedActorDocumentFetcher` cannot resolve the
  FQDN; the proxy returns 500). So the feed 500s **before** the `?q` filter is applied, and the
  `PagedCollection` shows the (filtered) empty state. The `?q` filter logic itself is verified correct by
  (a) the 4 integration tests and (b) the community feed's `?q` (the **same** filter logic) returning
  22 → 1 items for `?q=hello` on the wire. On the public FQDN route (where `iris-dev1.luit.ink`
  resolves) the followed feed populates and the `?q` filter returns the matching items.

### Console / network evidence (reviewed, all by-design / pre-existing)

- **`500` on `POST /ap/v1/proxy/https://iris-dev1.luit.ink/ap/v1/u/alice/feed[?q=hello]`** — the followed
  feed's remote-follow fetch (the documented FQDN proxy blocker, pre-existing).
- **The `?q=hello` is correctly appended** to the feed IRI (request #72 in the network log).
- **The community feed `?q=hello` returns 1 item** (bob's "hello" note) vs. 22 unfiltered — the same
  filter logic works end-to-end on a feed that doesn't hit the FQDN blocker.

No signature failures, no new 500s from the `?q` path itself (the 500 is the pre-existing remote-follow
fetch, which occurs with or without `?q`).

## 21.4.2 status

- **21.4.2 — implemented.** The followed feed endpoint (`GET /u/{handle}/feed`) supports a `?q` content
  filter (case-insensitive content/name match, including nested objects — the same logic as the community
  feed's F-23 `?q`), and the Feed page offers a search box that issues `?q=…` (the `PagedCollection`
  re-creates on filter change via `@key`). 4 integration tests verify the filter. The end-to-end

  blocker (as in 19.6.1/19.6.2/21.2.2/21.2.3); on the public FQDN route the feed populates and the `?q`
  filter returns the matching items.
