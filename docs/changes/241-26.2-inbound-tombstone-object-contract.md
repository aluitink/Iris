# 26.2 — Inbound `Tombstone` object contract (F-10)

Phase 26, slice 2. **Type:** code fix + invariant lock (not test-only — the inbound `Tombstone` path was
genuinely broken in two ways: a standalone `Tombstone` was rejected with `400`, and a `Create`-wrapped
`Tombstone` was mis-processed with a bogus outbox entry + re-federation). This is the **inbound** half of
the F-10 deletion contract: a peer signals that an object was deleted on *its* instance by delivering a
`Tombstone` to a follower's inbox, and the receiving instance must store the tombstone under the object
IRI so a subsequent `GET` serves the tombstone (not the stale federated content, not a `404`).

## Problem

A peer instance (B) deletes an object it authored. The object was already federated to a follower on
another instance (A), so A holds a local copy. B must notify A. The ActivityStreams 2.0 contract (F-10)
supports two inbound shapes for this notification:

1. **A standalone `Tombstone`** — a `IObject` (a subtype of `Object`), **not** an `Activity`, posted
   directly to the follower's inbox.
2. **A `Create` whose embedded `object` is a `Tombstone`** — a `Create` activity (so it rides the normal
   `IDeliveryService` delivery) whose `object` is the tombstone rather than new content.

The **serving** side of F-10 already worked: `ObjectDocumentHandler` / `ServeObjectDocument` serves a
stored `Tombstone` under its IRI correctly (locked by the existing federated-`Delete` tests, where
`DeleteActivityHandler` stores a tombstone and the object endpoint serves it). The gap was entirely on the
**inbound** side — recognizing the peer-delivered `Tombstone` and storing it under the object IRI:

- **Standalone `Tombstone` → `400 Bad Request`.** The inbox endpoint
  (`ActivityPubServerExtensions.HandleInboxPostAsync`) dispatched the payload as: an `Activity`
  (stored + routed to a handler), or the special-cased `Mute` (`Object` with type `Mute`, wrapped into a
  synthetic `Activity`), **else `Results.BadRequest()`**. A `Tombstone` is a `IObject`, not an `Activity`,
  and it is not a `Mute`, so it fell through to the `else` branch → `400`. The tombstone was never stored,
  and A kept the stale federated copy (a `GET` on the object IRI served the old `Note`, not the deletion).

- **`Create`-wrapped `Tombstone` → `202` but mis-processed.** `CreateActivityHandler` treated the
  embedded `Tombstone` as an ordinary new post: it stored the tombstone (so the `GET` *would* serve it),
  **but** it also (a) recorded a `Create` in the author's outbox (a bogus entry — the "new post" was a
  deletion, not content), (b) recorded an object → `Create` index entry (`ICreateIndex.RecordAsync`), and
  (c) re-federated the "new post" to the author's other remote followers (a deletion fanning out as if it
  were a note). The tombstone was stored, but with three incorrect side-effects.

## The fix

A new shared helper, `src/Iris.Server/Inbox/TombstoneInbound.cs`, centralizes the inbound-tombstone
application so both shapes behave identically:

```csharp
internal static class TombstoneInbound
{
    public static async Task ApplyAsync(IPersistenceProvider persistence, Tombstone tombstone, CancellationToken ct)
    {
        var objectIri = new Iri(tombstone.Id!);

        // Capture the prior stored object BEFORE replacing it: the cleanup depends on what was there, and
        // a tombstone for an unknown object stores the tombstone (so a GET serves it, not a 404) but has
        // no local artifacts to clean.
        var hadPriorCopy = await persistence.Objects
            .TryGetObjectAsync(objectIri, out var prior, ct)
            && prior is not null && prior is not Tombstone;

        // F-10: store the tombstone under the object IRI (replacing any prior content) so a GET serves the
        // tombstone, not stale content or a 404.
        await persistence.Objects.PutObjectAsync(tombstone, ct);

        if (!hadPriorCopy) return;

        // F-12: if the deleted object is a reply (it has an inReplyTo), remove the parent → child reply
        // edge so the parent's replies collection no longer lists it.
        var parentIri = prior!.GetParentIri();
        if (parentIri is { } parent)
            await persistence.Replies.RemoveReplyAsync(parent, objectIri, ct);

        // Remove the deleted object's originating Create from the author's outbox + the object → Create
        // index (the inverse of what the Create handler recorded). The author is the prior object's
        // attributedTo (the original content's author owns the outbox entry).
        var authorIri = (prior as Object)?.AttributedTo?.FirstOrDefault()?.ResolveObjectIri();
        if (authorIri is { } author
            && await persistence.Creates.TryGetCreateIriAsync(objectIri, ct) is { } createIri)
        {
            await persistence.Activities.RemoveFromOutboxAsync(author, createIri, ct);
            await persistence.Creates.RemoveAsync(objectIri, ct);
        }
    }
}
```

The cleanup mirrors `DeleteActivityHandler`: the object is not hard-removed but **replaced by a tombstone**
under the same IRI, the reply edge is removed, and the object's originating `Create` is removed from the
author's outbox + the object → `Create` index (decision 055). It is **gated on a prior copy having been
stored** — a tombstone for an object this instance never held stores the tombstone (so a `GET` serves it
rather than a `404`) but has no local artifacts to clean.

The helper is wired into **both** inbound paths:

- **Standalone `Tombstone`** — a new branch in `HandleInboxPostAsync`, placed **after** the `Activity`
  check and **before** the `Object`/`Mute` check (a `Tombstone` is an `Object`, so it must be caught first):

  ```csharp
  if (payload is Tombstone { Id: not null } inboundTombstone)
  {
      var persistence = context.RequestServices.GetRequiredService<IPersistenceProvider>();
      await TombstoneInbound.ApplyAsync(persistence, inboundTombstone, ct);
      return Results.Accepted();
  }
  ```

- **`Create`-wrapped `Tombstone`** — an early check at the top of `CreateActivityHandler.HandleAsync`,
  **before** the outbox/fan-out/index logic, so a wrapped tombstone is stored + cleaned but **not** treated
  as a new post (no outbox entry, no object → `Create` index, no re-federation):

  ```csharp
  if (activity.ExtractEmbeddedObject() is Tombstone embeddedTombstone)
  {
      await TombstoneInbound.ApplyAsync(_persistence, embeddedTombstone, ct);
      return;
  }
  ```

## The test (what it locks)

New `tests/Iris.Server.Tests/Delivery/InboundTombstoneIntegrationTests.cs` (2 tests, 2-instance
`TestServer`, modeled on `ObjectPropagationIntegrationTests` and `CrossInstanceAcceptPropagationIntegrationTests`):

**Topology:** instance B (`tomb-b.domain.local`, author `bob`) and instance A (`tomb-a.domain.local`,
follower `alice`). The follow edge `alice → bob` is recorded on B (bob's home instance owns his follower
set — the propagation target set bob's outbound `Create` federation reads). bob publishes a note (B stores
it + federates the `Create` to alice's inbox on A via a test `DeliveryWorker` signed as bob; A's
`CreateActivityHandler` stores the embedded note — the "remote copy" on A). bob then deletes the note on B
and delivers the deletion to alice's inbox on A.

- **`StandaloneTombstone_ReplacesFederatedCopy_GetServesTombstone_OutboxCleaned`** — bob delivers a
  **standalone `Tombstone`** (a `IObject`, not an `Activity`) to alice's inbox on A. Because a `IObject`
  cannot ride `IDeliveryService` (which only accepts `Activity`), the test sends it as a **direct signed
  `POST`** to alice's inbox through the worker's transport (the same transport the federated `Create`
  used, so A validates bob's signature exactly as for the worker's deliveries). Asserts: A's object store
  now holds a `Tombstone` under the note IRI (not the stale `Note`, not a `404`); bob's outbox on A no
  longer lists the note's `Create`; and A's object → `Create` index no longer maps the note to a `Create`.

- **`CreateWrappedTombstone_StoredAsTombstone_NoBogusOutboxEntry_NoReFederation`** — bob delivers a
  **`Create` whose embedded `object` is a `Tombstone`** to alice's inbox on A (this one rides the worker,
  since a `Create` is an `Activity`). Asserts: A's object store now holds a `Tombstone` under the note IRI;
  bob's outbox on A holds **neither** the original note's `Create` (removed by the tombstone cleanup)
  **nor** a second bogus `Create` for the wrapped tombstone (the pre-fix behavior recorded the wrapped
  `Create` as a new post); and A's object → `Create` index no longer maps the deleted note to a `Create`.

The **non-vacuous signal** is the **stored object on A** (a `Tombstone`, not the stale `Note`) plus the
**cleaned outbox / object → `Create` index**. The follow edge is *not* the signal (it is recorded at
publish and would pass vacuously).

**Non-vacuity proof:** with the fix disabled (the standalone-`Tombstone` branch and the `Create`-wrapped-`Tombstone`
branch removed, restoring the pre-fix behavior):
- the standalone test fails with `expected 2xx … got BadRequest` (the inbox rejects the `Tombstone`
  payload; A keeps the stale note), and
- the `Create`-wrapped test fails because the object → `Create` index still maps the note to a `Create`
  (the bogus entry the pre-fix `CreateActivityHandler` recorded).

With the fix restored, both pass.
