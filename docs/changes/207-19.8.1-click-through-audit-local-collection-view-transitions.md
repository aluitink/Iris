## Key findings

1. **No raw-JSON dead ends** — every collection→view transition renders a proper view with the
   shared components (`ObjectView`, `PagedCollection`, `RawInspector`, `BackLink`).
2. **No CORS failures with no status code** — the 22.4 US-8 proxy fallback (ch.188) is working:
   cross-instance GETs are routed through the same-origin home proxy (`/ap/v1/proxy/{iri}`), not
   direct cross-origin GETs. The console shows CORS errors on the `remote.example` routes, but these
   are because the proxy's error response for an **unresolvable** host lacks CORS headers — the
   browser then reports "TypeError: Failed to fetch", which the UI renders as a clear error state.
   In a real deployment where the remote host IS resolvable, the proxy would succeed and the
   same-origin response would carry CORS headers (no CORS error).
3. **Console errors are all expected/pre-existing:**
   - 429 (Too Many Requests) on the external-FQDN proxy route (rate limiting — the documented
     external-FQDN reverse-proxy blocker).
   - 403 (Forbidden) on the owner-only inbox (by design, decision 056).
   - CORS errors on the unreachable `remote.example` seed host (expected in this env).

## Wire observations

- The log-on used the dial-base resolution from change 205: address `alice@localhost` with an
  **empty** base URL → the map derived `http://localhost:8081`; the actor IRI carried the advertised
  FQDN (`https://iris-dev1.luit.ink/ap/v1/u/alice`); the "Dialing" line confirmed `http://localhost:8081/`.
- The cross-instance read (carla on `remote.example`) went through the home proxy
  (`http://localhost:8081/ap/v1/proxy/http://remote.example/ap/v1/u/carla`), confirming the 22.4 US-8
  fix (ch.188) is in effect (no direct cross-origin GET).
