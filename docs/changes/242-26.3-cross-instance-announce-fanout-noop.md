# 242 — Phase 26.3: cross-instance `Announce` (boost) fan-out to a remote author's local followers — a no-op

**Slice:** 26.3
**Outcome:** **No-op** — no new test, no code change. The slice's scenario is already implemented and already locked end-to-end by Phase 19.3.3's `AnnouncePropagationIntegrationTests`.

## The slice's claim

> Lock that a boost of a remote note reaches the remote author's local followers on the receiving instance (erin on B boosts a federated note by alice on A; B's `AnnounceActivityHandler` propagates the boost to alice's local followers on B, e.g. bob; bob's outbox on B surfaces the boost). Proven non-vacuous.

## Why it is already covered

The cross-instance `Announce` (boost) fan-out to a local follower on the receiving instance is implemented on the **inbound** path, by `AnnounceActivityHandler` (`src/Iris.Server/Inbox/AnnounceActivityHandler.cs`):

1. The boost federates to the receiving instance and is delivered to a **local** actor's inbox (the local recipient — e.g. `bob` on B, who follows the announcer).
2. `AnnounceActivityHandler.HandleAsync` (recipient is local, not blocked) records the boost in the recipient's outbox (`IActivityStore.AddToOutboxAsync`) and the announce edge (`IAnnounceStore.RecordAnnounceAsync`), then propagates to **each** of the recipient's followers:
   - a **local** follower is recorded **directly in their outbox** on this instance (`AddToOutboxAsync(follower, propagated)`) — no cross-instance delivery;
   - a **remote** follower gets a cross-instance delivery (`DeliverToActorAsync` to the follower's home inbox).
   - the propagated copy reuses the server-minted activity id (decision 055).

This is exactly the "boost reaches a local follower's outbox on the receiving instance" behavior the slice asks for.

It is already locked end-to-end by `tests/Iris.Server.Tests/AnnouncePropagationIntegrationTests.cs` (Phase 19.3.3, 2, 2-instance `TestServer`):

- **`Boost_LocalNote_ReachesPeerLocalFollower_Once`** — alice on A boosts a local note → the `Announce` federates to bob on B → B's `AnnounceActivityHandler` propagates it to carol (bob's local follower) → the boost surfaces in **carol's outbox on B exactly once** (no amplification), attributed to alice.
- **`Boost_RemotePeerNote_CarriesObjectLink_NoInfiniteChain`** — alice on A boosts **bob's remote note** (a note authored on B) → the `Announce` federates to B → B's handler propagates it to carol (bob's local follower) → the boost surfaces in carol's outbox, **references the remote note by link** (not an embedded copy), is **attributed to alice** (the announcer, not bob the remote note's author), and does **not** start an infinite announce chain.

The second test is a **1:1 match** for the slice's wording: the "remote author" is bob (the note's author on B), and bob's local follower (carol) on B surfaces the boost. A redundant copy of this scenario would add no new signal.

## A subtlety found while investigating

A first attempt modeled on the slice's literal example — a **local** booster (erin on B) boosting a remote note (alice's on A) via the **outbox-publish** write surface — does **not** exercise the local-follower fan-out:

- The outbox-publish `Announce` branch (`src/Iris.Server/ActivityPubServerExtensions.cs`, `OutboxPublishHandler`) records the announce edge (`RecordAnnounceLocalAsync`) and then fans out to **remote, non-blocked followers only** (`GetRemoteNonBlockedFollowersAsync` → `DeliverToActorAsync`). It does **not** run the `AnnounceActivityHandler`, so it does **not** record a local author's boost in a local follower's outbox.
- The local-follower fan-out (recording a boost directly in a local follower's outbox) lives **exclusively on the inbound path**, in `AnnounceActivityHandler`.

So a boost reaching a **local** follower's outbox necessarily goes through the **inbound** path — which is precisely what the existing `AnnouncePropagationIntegrationTests` lock. The slice's "erin on B boosts … B's `AnnounceActivityHandler` propagates" conflates the outbox-publish write surface with the inbound handler; the handler only runs on federation delivery, and that path is already covered.

## A latent test-suite footgun (noted, not fixed here)

While building a throwaway variant of the test, a spurious `401 Unauthorized` on a signed outbox-publish was traced to a **private `LazyHandler`** defined inside the test file that **shadows** the shared `Iris.Testing.LazyHandler`. The private copy forwarded the request **without cloning**, but the in-process `TestServer` transport + `DeliveryWorker` retry pipeline forbid re-sending the same `HttpRequestMessage` instance, and the signature validator (`HttpSignatureValidator`) issues a **nested** actor-document fetch (via `RemoteInboundKeyResolver` → `IActorDocumentFetcher`) to resolve even a *local* key. That nested fetch reused the same un-cloned request and failed, so key resolution failed → `401`.

The shared `Iris.Testing.LazyHandler` **does** clone the request (and copies content + headers) precisely to survive the retry pipeline. **Recommendation:** future 2-instance tests should reuse the shared `Iris.Testing.LazyHandler` rather than defining a private one; if a private one is unavoidable, it must clone the request (content + headers) exactly as the shared one does. The existing `DuplicateInboundDeliveryIdempotencyIntegrationTests` private `LazyHandler` is functionally correct (it clones) but is a redundant duplicate of the shared class.
