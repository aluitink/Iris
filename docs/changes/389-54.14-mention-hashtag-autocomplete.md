# 54.14 — Mention/hashtag autocomplete popover + `tag` field round-tripping

Phase 54 slice. Compose has long rendered `@handle` mentions as links (the read side) and
accepted `#hashtag` text, but the outgoing ActivityStreams `tag` array carried **only**
`Mention` objects — a `#hashtag` typed in the composer never became a structured `Hashtag`
tag, so other instances (and the Iris UI) could not link it. And there was no authoring
affordance: typing `@` or `#` gave no candidate list.

This slice has two halves. **(a)** the `tag` field round-trips `Hashtag` entries end to end
(write → store → serve → render), and **(b)** the compose textarea offers an inline
autocomplete popover for `@mentions` (searching the instance's actors) and `#hashtags`
(inserting a canonical token).

## (a) `tag` round-tripping

**Read side.** [IriExtensions.cs](src/Iris.Core/Identity/IriExtensions.cs) gains
`GetHashtagTags(this IObject?)`, the mirror of the existing `GetMentionIris`: it walks the
object's `tag` array, picks entries whose `type` includes `"Hashtag"` (case-insensitive), and
returns `(string Name, Iri? Href)`. `href` lives in `ExtensionData` (the library's `Object`
base does not model `href` as a property — only `Link` does), so it is read via
`Iri.TryParse` from the extension data.

**Write side.** [ComposeNote.Build](src/Iris.Core/Compose/ComposeNote.cs) gains `hashtags`
and `hashtagHrefFactory` parameters and emits a combined `tag` array — `Mention` entries
first, then `Hashtag` entries. A `Hashtag` is a generic ActivityStreams `Object` (the
library has no concrete `Hashtag` class) with `Type = ["Hashtag"]`, `Name = ["#tag"]`, and
an optional `href` (the instance's hashtag-search URL for that tag) in `ExtensionData`.
`PostReplyAsync` ([IActivityPubClient.cs](src/Iris.Client/IActivityPubClient.cs),
[ActivityPubClient.cs](src/Iris.Client/ActivityPubClient.cs)) takes the same `hashtags`
parameter and builds the combined tag list for the signed wire Create.

**Client.** [Compose.razor](apps/Iris.Web.Client/Components/Pages/Compose.razor) detects
hashtags in the content (`#([a-zA-Z0-9_]+)`, de-duplicated case-insensitively) and passes
them to all four post paths (Note, Reply, Community, Article). [ObjectView.razor](apps/Iris.Web.Client/Components/ObjectView.razor)
renders `GetHashtagTags()` as links to the local hashtag search (`/search?q=%23tag`),
mirroring how mentions already link to actor profiles.

### The `type`-form quirk (and why the write path is correct)

Investigating the live serve path surfaced a subtle deserializer behavior worth recording.
The object store round-trips its jsonb column through
`ActivityJson.Serialize` → `Deserialize<IObjectOrLink>` ([AsDocument.cs](src/Iris.Server.Data/AsDocument.cs)).
The ActivityStreams library **serializes a single-element `Type` list as a bare string**
(`Type = ["Hashtag"]` → `"type": "Hashtag"`), and `Deserialize<IObjectOrLink>` reconstructs
that string form into a generic `Object` correctly. But a `tag` item whose `type` is an
**array lacking the `"Object"` base** (e.g. `["Hashtag"]`) deserializes to a **null** entry
and is dropped on re-serialize. The write path emits the bare-string form, so it round-trips
cleanly; the `HashtagStoreRoundTripTests` guard this exact shape (store round-trip +
`GetHashtagTags` read-back) so a future change that switches the hashtag to an array-typed
form cannot silently regress the serve path.

## (b) Autocomplete popover

[Compose.razor](apps/Iris.Web.Client/Components/Pages/Compose.razor) wraps the textarea in a
`.compose-autocomplete-wrap` and renders a `.compose-autocomplete` dropdown below it. On
each keyup the component detects an active token at the end of the text
(`(?<=^|\s)([@#])([a-zA-Z0-9_]*)$` — the token must be the last thing in the text and at the
start or preceded by whitespace, so `a@b` mid-word is not mistaken for a mention). For an
`@` token it searches the instance's actors (`SearchAsync` with `Type = "Actor"`, limit 5)
and offers each as a candidate (handle + name); for a `#` token it offers the typed hashtag
as its own candidate (there is no hashtag directory). Accepting a candidate splices the
canonical token into the content (a mention gets a trailing space) and hides the popover.
The search is debounced (180 ms) and cancellable (`CancellationTokenSource`), and the
component is `IDisposable` (a new [Compose.razor.cs](apps/Iris.Web.Client/Components/Pages/Compose.razor.cs)
partial) to dispose the debounce timer and CTS.

**Note on the popover's live UI test:** the autocomplete popover's *trigger* could not be
exercised in the headless Playwright/Blazor-WASM harness — synthetic keystrokes do not reach
the textarea's `@bind` in that environment (the char counter and `Content` stayed at 0 while
the DOM value updated), whereas `click`-driven bindings (e.g. the content-warning checkbox)
work. This is an automation artifact, not an app regression: the `@onkeyup` trigger is a
standard Blazor event, the search path is the same `SearchAsync` the Directory/Search pages
use live, and the popover markup/CSS render cleanly. The popover is therefore verified by
code review + the shared, already-live `SearchAsync` path rather than a synthetic-keystroke
UI test.
