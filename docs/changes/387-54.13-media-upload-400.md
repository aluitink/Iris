# 54.13 — Media upload 400s on a 1.3 MiB image

Phase 54 slice (defect). A compose-post attachment upload of a ~1.3 MiB PNG returned
`400`. The slice originally carried the clue that the error response's headers showed
`Server: nginx/1.29.1`, which pointed (incorrectly) at nginx. The root cause turned out
to be in the app.

## Diagnosis

The request **does** reach the app: an unauthenticated `curl` to the media endpoint gets
a `401` from the app's cookie/Basic auth (nginx would not produce that), and the nginx
access log shows the `POST /local/v1/u/alice/media` reaching the upstream. The `400` is
**size-dependent** — live-verified on the FQDN that 10 KB and 500 KB uploads return `201`
but 1.3 MiB and 2 MB return `400`. The threshold is exactly **1 MiB**, which is
[WebAppFactory.cs](apps/Iris.Web/WebAppFactory.cs)'s `DefaultMaxRequestBodySize`
(1 MiB — a deliberate DoS bound on the unauthenticated federation inbox, but applied
globally to *every* request body by Kestrel).

The chain:

1. Kestrel enforces `Limits.MaxRequestBodySize = 1 MiB` (set in `WebAppFactory`). When a
   media upload's body exceeds 1 MiB, Kestrel aborts the body read with a
   `BadHttpRequestException` (status 413).
2. `LocalMediaUploadHandler` calls `ReadFormAsync`, which surfaces that exception; the
   handler's `catch (BadHttpRequestException)` collapsed it to a blanket `400`.
3. The endpoint's own 10 MiB cap (`MaxMediaUploadBytes`) was never reached, because
   Kestrel rejected the body at 1 MiB first.

So the app was **self-inconsistent**: it advertised a 10 MiB media limit but its own
server cap rejected anything above 1 MiB, and the error was mislabeled `400` instead of
`413`. The nginx `Server` header was a red herring — nginx proxies the (app-generated)
response; nginx's own body-too-large behavior is `413`, not `400`.

## Change

[ActivityPubServerExtensions.cs](src/Iris.Server/ActivityPubServerExtensions.cs),
`LocalMediaUploadHandler`:

- **Exempt the media endpoint from the 1 MiB global cap.** Before `ReadFormAsync`, set
  `IHttpMaxRequestBodySizeFeature.MaxRequestBodySize = MaxMediaUploadBytes` (10 MiB) on the
  request. Kestrel enforces the per-request value over the connection default when the body
  is read, so the authenticated, owner-only media upload can accept up to its intended 10 MiB
  while every other endpoint (notably the unauthenticated federation inbox) keeps the 1 MiB
  DoS bound. The feature is set only when present (the TestServer host doesn't implement it —
  the `is { }` guard makes it a no-op there).
- **Return the correct status for an oversized body.** The `catch (BadHttpRequestException)`
  now propagates the exception's own status code (`413` for a body over the cap, `400` for a
  genuinely malformed/non-multipart body) instead of collapsing both to `400`. This matches
  the handler's documented behavior ("an oversized upload is `413`").

No new dependencies, no API surface change.

(via CDP `Network.setCacheDisabled`) to bypass the stale-WASM-bootstrap artifact:

| Upload size | Before | After |
|-------------|--------|-------|
| 10 KB       | 201    | 201   |
| 1 MiB (exactly the old cap) | 400 | **201** |
| 1.3 MiB (the reported failure) | 400 | **201** |
| 2 MB        | 400    | **201** |
| 9 MiB       | 400    | **201** |
| 11 MiB (over the 10 MiB cap) | 400 | **413** |

Build clean (0 warnings, `TreatWarningsAsErrors` on); `dotnet test --filter
"Category!=Slow"` green — `Iris.Server.Tests` 951/0, `Iris.Web.Tests` 63/63, all other
suites green. 0 unexpected console errors (the single `413` in the console is the
intentional over-cap probe).
