# 188 — Phase 22.4: cross-instance reads via the home proxy (US-8)

## Summary

Closes the **US-8** (browse a remote / cross-instance object and actor) half of **Phase 22.4
(cross-server polish)** on the code side: a browser could not open a remote object or actor. The
explorer's `ObjectPage` / `ActorDetail` fetch a deep-linked or peer item through
`IActivityPubClient.GetObjectAsync` / `GetActorAsync`, which dials the target IRI **directly**. In a
browser a direct cross-origin GET is **CORS-blocked** — it surfaces as a network failure with *no*
status code (a JS `TypeError: Failed to fetch`, an `HttpRequestException` in .NET), so the
`ProxyFallbackHandler`'s 401/403 fallback **never engaged** (it only re-routes on a status-code
rejection) and the read failed. This is the 19.8.1 "remote object reads CORS-fail in the browser" gap.

The fix adds a **cross-instance-read** mode to the `ProxyFallbackHandler`: when the request is a
`GET` whose host differs from the **dial base** (the instance the browser can reach directly), it is
routed **straight through the same-origin home proxy** with no direct attempt. The home proxy
(`POST {home}/ap/v1/proxy/{target}`) relays the GET to the remote instance and returns the document,
so the browser only ever talks to its own origin — the same mechanism Phase 6 built for proxy-fallback
writes, now applied to reads.

## What changed (code)

- **`src/Iris.Client/Pipeline/ProxyFallbackHandler.cs`** — a new constructor overload taking
  `(dialBase, crossInstanceReadsViaProxy)`. When enabled, a `GET` whose host differs from
  `_dialBase` is forwarded to the proxy (`SendViaProxyAsync`) **before** any direct attempt. A
  same-host `GET` (a read of the local instance) dials directly, as before; `POST`/`PUT` writes are
  unaffected (they use the always-proxy mode). The existing 401/403 fallback and the always-proxy
  write path are unchanged.
- **`src/Iris.Client/ActivityPubClientOptions.cs`** — new `DialBaseUri` (the instance the client dials
  directly; `null` → no host comparison, the mode is a no-op) and
  `RouteCrossInstanceReadsViaProxy` (the mode switch).
- **`src/Iris.Client/ActivityPubClientFactory.cs`** — passes the two new options into the
  `ProxyFallbackHandler` when the proxy is configured.
- **`src/Iris.Client.Extensions/IrisClientOptions.cs`** — new `DialBaseUri` (default `null`) and
  `RouteCrossInstanceReadsViaProxy` (default `false`), mirroring the client options.
- **`src/Iris.Client.Extensions/IrisClientFactory.cs`** — maps `IrisClientOptions.DialBaseUri`
  (defaulting to the server base URI) + `RouteCrossInstanceReadsViaProxy` into the
  `ActivityPubClientOptions`.
- **`samples/SampleBlazorClient/SampleBlazorClient.cs`** — `CreateClientService` sets
  `DialBaseUri = serverBaseUri` and `RouteCrossInstanceReadsViaProxy = true`. The home proxy relays
  **both** cross-instance and same-host reads, so every AP read the client makes now goes through the
  home proxy (same-origin in the browser). This is the safe, always-on choice: a same-host read is a
  harmless same-origin relay, and a cross-host read is the fix.

## Tests

- **`tests/Iris.Client.Tests/Pipeline/ProxyFallbackHandlerTests.cs`** (4 new facts): a cross-instance
  `GET` is routed through the proxy with **no** direct attempt (even if the direct attempt would have
  succeeded); a same-host `GET` dials directly (not proxied); a `POST` is not re-routed by the mode;
  a proxy failure is returned as-is (no loop).
- **`tests/Iris.Client.Tests/ClientServerIntegrationTests.cs`** (1 new end-to-end test): the real
  client built by the real factory with `RouteCrossInstanceReadsViaProxy` makes **zero** direct GETs to
  the remote host and **one** Basic-auth `POST` to the home proxy, and the proxied remote actor doc is
  returned to the caller.

Full solution: **1,284 tests, 0 failures**.

## Decision

**Route reads through the home proxy when the target host differs from the dial base (opt-in via
`RouteCrossInstanceReadsViaProxy`), rather than (a) relying on the remote instance to CORS-open its AP
routes, or (b) making the home proxy the default route for every read.**

- *(a)* CORS-opening a third-party instance is not under Iris's control — it depends on every remote
  ActivityPub implementation opting in, and the browser still cannot validate a cross-origin signature.
  The proxy is the only Iris-controlled, always-available path.
- *(b)* Making the proxy the default for *all* reads (ignoring the dial base) would route even local
  reads through an extra hop and would require the proxy's allowlist to cover the local host. Routing
  only cross-host reads keeps local reads on the direct path when the mode is off, and the sample
  opts in (where the home proxy relays both) for a uniform, same-origin read path.
- The mode is **opt-in** at the client level (`RouteCrossInstanceReadsViaProxy`), defaulting to
  `false`, so a non-browser (server-to-server) client — where a direct cross-instance GET works fine
  over the wire — is unaffected. The WASM sample opts in, because it is the browser that needs it.
