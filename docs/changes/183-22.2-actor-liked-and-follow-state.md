# 183 — Phase 22.2: actor page — `liked` collection + follow state (US-5, US-15)

## Summary

First 22.2 sub-slice (detail pages on the shared components). The actor detail page
(`ActorDetail`) gains the two actor-story gaps that the shared components close cleanly:

- **US-5 — the actor's `liked` collection.** A new `Liked` `PagedCollection` card (after the Outbox)
  renders the objects the actor liked, paged with next-link walking, each a navigable `ObjectView`
  (a like is recorded as the liked object).
- **US-15 — the follow state.** The Follow / unfollow card now reflects the *authoritative* follow
  state — whether the logged-on actor's `following` collection contains the viewed actor — instead of
  showing a static "Follow" / "Unfollow" pair. The button label shows the state, a "You follow this
  actor." indicator appears when following, Unfollow is gated on the state, and viewing yourself shows
  a "you can't follow yourself" notice.

This is the actor slice of 22.2. The remaining 22.2 stories (object US-7/12/13/14, actor US-16/17,
community US-6/18, instance US-10) follow in later 22.2 slices.

## What changed (code)

- **`samples/SampleBlazorClient/Pages/ActorDetail.razor`**
  - New `Liked` `<PagedCollection>` card (`CollectionIri="@(ActorIri?.LikedOf())"`) between the Outbox
    and Followers cards. The `liked` collection's items are the liked objects; each renders via the
    page's existing object-view template (navigable). Empty state: "Nothing liked."
  - New `IsFollowing` state (the logged-on actor's follow state toward the viewed actor) and
    `FollowButtonLabel` (`IsFollowing ? "Following" : "Follow"`).
  - `LoadByIriAsync` reads the follow state after the followers/following pages load: when a
    logged-on actor is present, `IsFollowing = await IsInFollowingCollectionAsync(self, actorIri)`.
  - `FollowUnfollowAsync` gains an `affectsFollowState` flag; the Follow / Unfollow wrappers pass
    `affectsFollowState: true` so a successful follow/unfollow **re-reads** the follow state (bypassing
    the collection page cache) and the button reflects the write immediately. Moderation writes
    (mute/block/flag/relay) leave the flag `false`.
  - New `IsInFollowingCollectionAsync(selfIri, targetIri)` — walks the logged-on actor's `following`
    collection (cache-bypassed) and returns whether any item's IRI equals `targetIri`. A read failure
    returns `false` (the Follow button stays available). Mirrors the `liked`-by-actor check on the
    object page.
  - The follow card markup: `@if (IsOwnActor)` → "This is you — you can't follow yourself."; otherwise
    the Follow button (label = `FollowButtonLabel`, disabled while busy) + the Unfollow button
    (disabled when busy, **not** following, or the learned follow id is absent — Decision 055) + a
    "You follow this actor." indicator when `IsFollowing`.

## Decisions

- **Follow state is a read, not a stored flag.** `IsFollowing` is derived from the logged-on actor's
  `following` collection (the same authoritative source the "Following" card lists), not a boolean
  flipped by the page's own Follow click. This makes the state correct even when the follow was made
  elsewhere (another device/session), and it reuses the existing collection read rather than inventing
  a `GET /following/{target}` existence endpoint.
- **Unfollow stays gated on the learned id (Decision 055).** A follow made by *this* page session
  captures `FollowLearnedId`, enabling Unfollow; a follow made elsewhere (no learned id here) leaves
  Unfollow disabled even though the state shows "Following". The state and the *ability to undo from
  this page* are intentionally decoupled — the page never undoes an activity it doesn't have the id of.
- **`FollowButtonLabel` is a property, not an inline ternary.** A Razor ternary with quoted string
  literals inside element content (`@IsFollowing ? "Following" : "Follow"`) is mis-parsed — the `?`
  is read as markup and the expression renders literally. Hoisting it to a `string` property keeps the
  markup declarative and avoids the parsing pitfall.
- **Post-write refresh reuses the cache-bypassed read.** After a follow/unfollow write, the follow
  state is re-read with `BypassCache: true` (the collection page cache would otherwise serve a stale
  page), so the button flips immediately without a full page reload.

## Scope / limits

- This closes the two actor stories that map directly onto the shared components (US-5 liked
  collection, US-15 follow state). Remaining 22.2 work: object (US-7/12/13/14), actor (US-16/17),
  community (US-6/18), instance (US-10). The `liked` collection is read-only here (a like write
  belongs to the object page / authoring surface, US-11/US-12 in 22.3).
- Unfollow from this page only works for a follow made *by this page session* (Decision 055). A
  follow made on another device shows the correct "Following" state but leaves Unfollow disabled
  until the follow's activity id is available — consistent with the existing moderation undo
  behaviour.
