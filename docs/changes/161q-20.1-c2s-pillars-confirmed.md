# 161q — Phase 20.1: confirm the four C2S load-bearing pillars + the outbox-returns-Creates decision

## Summary

Phase 20.1 is a **confirmation + decision** phase (no behavioral overhaul). It verifies, end to end, that
the four client-to-server (C2S) pillars hold in the current architecture, and records the
**outbox-returns-Creates** decision. All four pillars **confirm as-is**; the one place the ROADMAP's
framing needed tightening is pillar (c) — the proxy fallback is a *signature-rejection* fallback (401/403),
not a *network/CORS-failure* fallback. That distinction is now pinned by a test and spelled out below.

## Pillar (a) — C2S via the user's outbox is the single source of truth — **CONFIRMED**

A client-authored activity is a signed POST to the actor's **outbox** and the server records it there.

- **The client never posts an authored activity to an inbox.** Every authoring method in
  `src/Iris.Client/ActivityPubClient.cs` posts to `actorId.OutboxOf()` (or `communityId.OutboxOf()`):
  `FollowAsync` :250, `PostNoteAsync` :693, `PostReplyAsync` :753, `LikeAsync` :336, `AnnounceAsync` :380,
  `AddMemberAsync` :556, `RemoveMemberAsync` :574, `CreateCommunityAsync` :617, and all the inverses
  (Undo/Unlike/Unannounce/Unblock/Unflag/Delete). A grep for `InboxOf`/`/inbox` in the client returns
  **zero** authoring call sites.
- **The server records the authored activity in the actor's outbox.** `OutboxPublishHandler`
  (`src/Iris.Server/ActivityPubServerExtensions.cs:1283`, route `POST /ap/v1/u/{handle}/outbox` :565)
  validates the signature, enforces acting-actor == activity-actor, mints ids (`MintActivityIds` :1338),
  then `persistence.Activities.AddToOutboxAsync(actorIri, activity)` (:1344) and
  `persistence.Activities.PutActivityAsync(activity)` (:1345). The outbox is the write surface for what
  the actor authored.
- **The outbox and the object store agree on the authored object.** For a Create, `RecordCreateLocalAsync`
  (:2070) stores the embedded object via `persistence.Objects.PutObjectAsync(embedded)` (:2084), so the
  Note is addressable/servable by its own (minted) IRI while the outbox lists the Create that references it.
- **The non-author recording paths are server-driven and still land in outboxes (never a bare inbox):**
  inbound `Announce` (boost) → the announcer's + each local follower's outbox
  (`Inbox/AnnounceActivityHandler.cs:121,154`); inbound `Create` → the recipient's outbox
  (`Inbox/CreateActivityHandler.cs:112`); community content → each local member's outbox
  (`Inbox/CommunityContentRecorder.cs:54`). No client can route an authored activity anywhere but its own
  outbox.

## Pillar (b) — Digest / HTTP-signature auth on the browser signed POST — **CONFIRMED**

The browser's signed POST (Basic log-on key, HTTP signature) verifies. This was live-verified in **161o**
(change `161o-browser-signed-post-401-x-signature-date.md`): after the `X-Signature-Date` fix, a direct
outbox POST from the browser returned **202** (not 401), with no proxy fallback. The signer and verifier
share `Signatures.ResolveDateComponent` (the date component can never drift), and the suite's federation
round-trips (`Iris.Server.Tests/Security/FederationSignatureIntegrationTests.cs`) exercise signed
outbox→delivery end to end. Re-confirmed green in this phase (1,111 tests, 0 failed).

## Pillar (c) — Proxy fallback for CORS — **CONFIRMED, with the trigger made explicit**

The client falls back to the same-origin server proxy route when the **direct attempt is rejected with
401/403** — the case where the remote instance cannot validate the browser's WebCrypto signature.

- **Server route:** `POST /ap/v1/proxy/{**target}` (`ActivityPubServerExtensions.cs:746`, handler
  :906–1024). The target is the *absolute* remote IRI in the path; the proxy identifies the acting actor
  from Basic auth, re-signs with the actor's key, relays the `Accept` header + (for writes) the body via
  `X-Iris-Proxy-Method`, and relays the remote response.
- **Client fallback:** `src/Iris.Client/Pipeline/ProxyFallbackHandler.cs` (outermost pipeline stage, wired
  in `ActivityPubClientFactory.cs:69`). `SendAsync` makes the direct signed attempt; **only a 401/403**
  triggers the proxy retry (:93). Any other status (200, 404, 5xx) is returned unchanged; a proxy failure
  is returned as-is (no loop).
- **The CORS nuance (the clarification this phase records):** the fallback is a *signature-rejection*
  fallback, **not** a *network/CORS-failure* fallback. A genuine CORS-blocked **browser** fetch does not
  surface a 401/403 — it throws a JS `TypeError: Failed to fetch` (a .NET `HttpRequestException`, with no
  status code), so the 401/403 branch does not fire on it. A CORS failure is therefore **not** re-routed
  through the proxy (the proxy POST would hit the same partition); it propagates. CORS is instead handled
  by: **(i) writes** — the sample uses **always-proxy mode** when the actor's *advertised* host differs
  from the *dial* host (`samples/SampleBlazorClient/SampleBlazorClient.cs:104`): the write goes straight
  to the home proxy, which is same-origin and cannot CORS-fail; **(ii) reads** — the remote instance
  CORS-opens its AP routes (`IRIS_CORS_ORIGINS`, per the 161o deployment note), so a same-origin-or-
  CORS-allowed read succeeds directly. The proxy fallback covers the orthogonal case: the read/writes are
  *reachable* (not CORS-blocked) but the remote *rejects the browser's signature* (401/403).
- **New test pinning this:** `ProxyFallbackHandlerTests.DirectNetworkFailure_Propagates_NotRoutedThroughProxy`
  — a direct attempt that throws `HttpRequestException` (the CORS-failure mode) propagates as-is and never
  contacts `/ap/v1/proxy/`. This makes the pillar's actual boundary explicit (9 proxy tests total, 0 failed).
  The existing tests already pin 401/403 → proxy, success/404 → direct, always-proxy writes/reads, and
  Accept relay.

## Pillar (d) — Browse external (remote) collections — **CONFIRMED**

The sample UI can open a remote collection and display its items.

- **Client primitives are host-agnostic.** `IActivityPubClient.GetCollectionAsync(collectionId, …)`
  (`ActivityPubClient.cs:764`) and `GetCollectionItemsAsync(…)` (:805) take **any** collection IRI, follow
  the collection's `first` link, and walk `page.NextPage` (paged, with `Limit`). No host check. If the
  direct read 401/403s, the `ProxyFallbackHandler` (pillar c) transparently retries through the home proxy.
- **UI surfaces that accept a remote IRI:**
  - `samples/SampleBlazorClient/Pages/ActorDetail.razor` — renders the actor's **outbox** ("Feed (outbox)")
    via `GetCollectionItemsAsync(actorIri.OutboxOf())` (:336); the `?iri=` deep-link / handle input
    (`LoadByIriAsync` :304) uses the given IRI verbatim (no host restriction) → a **remote actor's outbox
    renders**.
  - `samples/SampleBlazorClient/Pages/ObjectPage.razor` — opens an arbitrary object IRI (text input :24,
    `?iri=` :124) and renders it + its **replies** (`GetRepliesAsync` :173); accepts any absolute URI →
    **remote objects + replies render**.
- **UI surfaces that are local-only (by design — the IRI is dial-base derived):** `Feed.razor` (the
  logged-on actor's followed feed, :134) and `Community.razor` (community feed/members, :141). These have
  no arbitrary-IRI entry point; opening a *remote* feed/members list is a 20.3 (outbox enumeration +
  paging) concern, not a 20.1 gap.
- `Components/ObjectView.razor` is host-agnostic (links to remote actor/object IRIs), so remote items
  render correctly when passed in.

## Decision (e) — outbox-returns-Creates — **CONFIRMED as the operator's expectation**

**The outbox yields `Create` activities** (the post is the Create; the embedded Note is the object), and
the embedded object is a first-class object **addressable by its (originator-minted) id**. Current
behavior already matches the operator's expectation, so no behavioral change is needed.

- **What the outbox yields:** `OutboxPublishHandler` records the **Create** activity in the outbox
  (`AddToOutboxAsync(actorIri, activity)` :1344), not the Note. `GetOutboxAsync` returns the stored Create
  verbatim, and the `GET /{actor}/outbox` collection endpoint
  (`CollectionEndpointHandler` :3068 → `BuildCollectionPageDocument` :3770) serializes the items verbatim
  (no unwrapping, no re-wrapping) → the wire `items` are `Create` objects (each `type:"Create"` with an
  `object` containing the Note).
- **The 2xx body returns the Create** (with the server-minted id; the embedded Note carries its own minted
  id in `object`) — `Results.Text(ActivityJson.Serialize(activity), …, 202)` (:1426). The client learns the
  Create id from `DeliveryResult.MintedId` and the Note id from the returned body's `object`.
- **Inbound federation keeps the shape:** a peer that receives the federated Create stores the Create
  (activity store + the recipient's outbox, `Inbox/CreateActivityHandler.cs:112`) **and** stores the
  embedded Note as a first-class object under the originator's **verbatim** minted id
  (`CreateActivityHandler.cs:188`, decision 055 keeps inbound ids verbatim). The object is served at its
  own IRI by `ObjectDocumentHandler` (:2522).
- **Tests that already pin this:** `OutboxCreateFanOutIntegrationTests.cs:110–130` (outbox contains the
  minted Create; federated copies are `Create`s), `S7ScreenTests.cs:196–207` (outbox lists the post's
  Create under `/creates/`; the Note is separately fetchable by its own IRI), `S3FollowFeedTests.cs:184–188`
  (feed items are `/creates/` activities), `PostNoteSurfacesInOutboxIntegrationTests.cs:93–114`.

**Recorded decision:** outbox = `Create` of objects, with the object addressable by its (originator-)
minted id. This is the current, confirmed behavior; no divergence. (Decision 055 already established the
minted-id model; this confirms its *outbox-collection* consequence.)
