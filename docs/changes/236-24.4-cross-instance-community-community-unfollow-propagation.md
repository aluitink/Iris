# 24.4 — Cross-instance community→community un-follow propagation

Phase 24, slice 4. **Type:** test-only (invariant lock — no production code change; the remote-side
community un-follow handling already works). This is the community→community analogue of 22.14
(community→person un-follow propagation).

## Problem (and why it is a test, not a fix)

When a **community** C on instance A **follows** a **community** D on instance B, the follow federates
A → B and B records C in D's community store (D's follows set — D → C, so C's content reaches D's
members via the federation path — and D's followers set — C → D, so D's `followers` collection lists
C). This slice locks the **inverse** half end-to-end: when C publishes an `Undo(Follow)`, does B's
instance receive the `Undo` and **remove** C from D's follows + followers sets?

The answer, traced through the code, is **yes — it already worked before this change**:

- A's `CommunityOutboxPublishHandler` records C's local follows set (`AddFollowAsync(C, D)`) and
  **delivers** the signed `Follow` / `Undo(Follow)` to D's inbox on B (D is the follow target and the
  delivery recipient, via `RecordCommunityFollowAsync` / `RecordCommunityUnfollowAsync`).
- B's `FollowActivityHandler` (community branch, F-24) records **two** edges in D's community store when
  the `Follow` arrives: `AddFollowAsync(D, C)` (the community's follows set) and `AddFollowerAsync(D, C)`
  (the community's followers set).
- B's `UndoActivityHandler` (community-target branch) resolves the original `Follow` from B's activity
  store, reads the follower/target parties, and — when the target D is a **local community** — calls
  `RemoveFollowerAsync(D, C)` and `RemoveFollowAsync(D, C)`, removing both of D's edges.

The subtle dependency this test locks: **B can only remove the edges if it first received and stored the
original `Follow`** (the `Undo` references the original by its server-minted IRI, and B's handler
resolves the parties from its own activity store — it does not re-fetch the original from A). The test
exercises the real cross-instance flow: the follow federates A → B (B records + stores), then the
`Undo(Follow)` federates A → B (B resolves the stored original and removes).

This is the community-target, community-follower counterpart of 22.14 (community→person) and the
cross-instance community un-follow complement of the existing community-follow coverage. Same class of
invariant-lock: the behavior was already correct; the test exists to fail loudly if a future change
regresses the remote-side community removal (e.g. an `UndoActivityHandler` refactor that drops the
local-community-target branch, or a delivery-target change that stops delivering the `Undo` to D's inbox).

The difference from 22.14 (community→person): the target is a **community**, not a person, so the edge
lives in the **community store** (D's follows + followers sets), not the person follow store. The
`UndoActivityHandler`'s community-target branch (the `TryGetCommunityAsync(targetIri)` arm) is the
load-bearing code under test — it is distinct from the person-target arm (`IsLocalActorAsync(targetIri)`).

## Where (tests only)

- `tests/Iris.Server.Tests/CommunityFollowsCommunityUnfollowPropagationIntegrationTests.cs` (2 new
  integration tests), a 2-instance `TestServer` topology (A = `cc-unfollow-a.domain.local`, instance
  actor `alice` + community `iris` (C, the follower); B = `cc-unfollow-b.domain.local`, instance actor
  `bob` + community `nebula` (D, the follow target)), wired per the 22.14
  `CommunityFollowsPersonUnfollowPropagationIntegrationTests` pattern (two `ActivityPubHostFactory.Create`
  instances; A's `IdentityKeys` registers alice + C; A's `DeliveryTransport` routes to B; A's
  `RoutingFetcher` routes by actor-IRI host (alice/iris → A, bob/nebula → B); B's fetcher routes to A to
  fetch C's document for signature validation):
  1. `CommunityFollowOfRemoteCommunity_FederatesAndRecordsInRemoteCommunityStore` — C publishes a
     `Follow` of D to `/ap/v1/c/iris/outbox` (202; A records C's local follows set; learns the minted id
     from the 2xx body per decision 055); waits for B to record **both** of D's edges (D's follows set
     D → C and D's followers set C → D, proving the Follow federated **and** was stored in B's activity
     store); asserts the community C is listed in D's followers **and** that B stored the original
     `Follow`.
  2. `CommunityUnfollowOfRemoteCommunity_FederatesAndRemovesFromRemoteCommunityFollowers` — establish
     the follow (as above); C publishes `Undo(Follow)` (202); waits for A to remove its local follows
     edge (C → D); waits for **B to remove both of D's edges** (D → C and C → D); asserts the community C
     is no longer listed in D's followers **and** D's follows set no longer contains C.

   Each test asserts the edge state on **both** A and B, pinning both the local and the cross-instance
   half.

## Non-vacuity (proven)

Per the loop's "prove it fails" discipline, the remote community-target removal was temporarily disabled
(the `if (await _persistence.Communities.TryGetCommunityAsync(targetIri.Value, …))` community-target arm
in `UndoActivityHandler`'s target branch short-circuited, then restored):

- With the community-target removal disabled, the **unfollow test fails** (B records D's edges but never
  removes them — it times out at 30s and the "B should no longer list the community C among D's
  followers" assertion fails) while the **forward follow test still passes** (it does not depend on the
  removal).
- Restoring the branch turns both green.

This confirms the unfollow test genuinely exercises the cross-instance community removal (not passing
vacuously because B never recorded the edges — the follow step asserts B *did* record them). It is
distinct from the person-target arm, so a regression that only broke the person path (or only the
community path) would be caught.
