# 54.5 — Responsive regression at tablet/laptop breakpoints

Phase 54 slice. The 54.1 mobile pass covered 375px. This slice extends the
responsive check to the two intermediate breakpoints the app actually renders at:
**768px** (tablet portrait) and **1024px** (laptop), focused on the densest pages
— the Settings cards, the admin users/moderation tables, and the actor-detail tabs —
to confirm no overflow or clipping at those widths.

## Approach

The app defines a **single breakpoint**: `@media (max-width: 768px)` in
[app.css](apps/Iris.Web.Client/wwwroot/css/app.css) (the only `@media` rule besides
`prefers-reduced-motion`). It is inclusive, so:

- **≤ 768px** → the **mobile** layout (nav collapses to a `.nav-toggle` hamburger,
  tighter padding, smaller headings, stacked `page-header-row` / `actor-detail-header` /
  `directory-item`).
- **> 768px** → the **desktop** layout (full horizontal `.main-nav`, roomier padding,
  row-oriented actor header).

So 768px exercises the mobile layout and 1024px exercises the desktop layout — two
distinct render paths, not merely two scales of one.

## Result: no defects found

Live-verified on the FQDN (`https://iris.luit.ink`) with the Playwright browser
signed in as `alice`, viewport set to exactly 768×1024 then 1024×768. Every dense page
was loaded and screenshotted at **both** widths:

| Page                        | 768px (mobile) | 1024px (desktop) |
|-----------------------------|----------------|------------------|
| Settings (6-tab bar, cards) | clean          | clean            |
| Admin · Instance (form)     | clean          | —                |
| Admin · Users (table)       | clean          | clean            |
| Admin · Moderation (table)  | —              | clean            |
| Actor detail (header+tabs)  | clean (stacked)| clean (row)      |
| Home timeline (feed)        | —              | clean            |

- **768px:** the 6-tab Settings bar fits without wrapping; the admin users table
  (HANDLE/ROLE/CREATED/ACTION + "Reset password"/"Delete" buttons) fits inside its card;
  the actor header stacks (avatar/name above the Unfollow/Block/Mute/Report row); tabs
  (Posts/Followers/Following) fit. No horizontal scrollbar, no clipped text.
- **1024px:** the full horizontal nav renders (Home / New post / Notifications /
  Directory / Communities / Profile / Settings / Search / Log out) with room to spare;
  the actor header is row-oriented (avatar/name card left, action buttons right); both
  admin tables and the feed render cleanly. No overflow.

**0 console errors** on every screen after a cache-disabled reload (see the
test-environment note below).

## No code change

No overflow or clipping was found at either breakpoint, so no CSS/razor change was made
this slice. The single 768px breakpoint already covers the tablet/laptop range correctly.

## Test-environment note (not a defect)

On the first visit to `/admin/moderation` after the slice's Docker redeploy, the browser
logged 34 `net::ERR_FAILED` / `download … .wasm failed 0 TypeError: Failed to fetch`
errors. This is the known **WASM immutable-cache artifact**: `_framework/dotnet.js` and
the hashed `.wasm` assets are served `Cache-Control: max-age=31536000, immutable`, so a
stale `dotnet.js` in the browser referenced `.wasm` files that no longer match the fresh
build's hashes. A cache-disabled reload (CDP `Network.setCacheDisabled`) cleared all 34
errors and the page rendered normally — confirming the errors were a stale-bootstrap
test artifact, not an application regression. No app change resulted.
