# 54.31 — `.well-known`/Discovery Endpoint Support

## Summary

Federated software (Friendica, Lemmy, relays) probes standard discovery endpoints. Before this
change, `/.well-known/nodeinfo`, `/.well-known/x-nodeinfo2`, `/.well-known/host-meta`, and any
other unhandled `/.well-known/*` path all returned **200 with the SPA shell** (1729 bytes of
`index.html`) because the Blazor `MapFallbackToFile("index.html")` caught them. This is
confusing to federation software and can cause clients to misinterpret an HTML page as a
discovery document.

## Changes

### New root-level discovery endpoints (`src/Iris.Server/ActivityPubServerExtensions.cs`)

| Endpoint | RFC | Response |
|----------|-----|----------|
| `GET /.well-known/nodeinfo` | 8555 | JSON discovery document linking to `/ap/v1/nodeinfo/2.0` |
| `GET /.well-known/x-nodeinfo2` | (emerging) | JSON discovery document linking to `/ap/v1/nodeinfo/2.0` |
| `GET /.well-known/host-meta` | 6415 | XML XRD document with `<Link>` to the WebFinger endpoint |

The NodeInfo 2.0 resource (`/ap/v1/nodeinfo/2.0`) and WebFinger (`/.well-known/webfinger`)
already existed; this adds the standard root-level discovery paths that federation software
actually probes.

New handler methods: `NodeInfoXNodeInfo2Handler`, `HostMetaHandler`.

### 404 catch-all for unknown `/.well-known/*` paths (`apps/Iris.Web/WebAppFactory.cs`)

Added `app.MapGet("/.well-known/{**rest}", () => Results.NotFound())` mapped BEFORE
`MapActivityPubEndpoints`. Exact routes (webfinger, nodeinfo, x-nodeinfo2, host-meta) registered
by `MapActivityPubEndpoints` take precedence over this parameterized catch-all in ASP.NET Core
routing. Unknown `/.well-known/*` paths now return **404** instead of the SPA shell.

### Decision: `/api/v1/instance` left as SPA fallback

`/api/v1/instance` is a Mastodon-specific API endpoint. Iris does not implement the Mastodon
API (its API is under `/local/v1/*` and `/ap/v1/*`). The path still returns 200 with the SPA
shell via the fallback. This is acceptable: Mastodon software probing `/api/v1/instance` will
receive an HTML page (not a JSON error), which it will treat as "not a Mastodon instance" — the
correct outcome. Adding a 404 for this specific path is a minor nicety that doesn't justify the
complexity of a broader `/api/*` catch-all (which could interfere with the `/api` Swagger
landing page).
