# 28.2 — Outbox-publish relay fan-out for `Update` / `Delete`

## What was built

A code fix + 3 integration tests to make the **outbox-publish** `Update` and
`Delete` paths fan out to the author's subscribed **relays** (F-06, ActivityPub
§5.1.3), complementing the `Create`/`Announce` relay fan-out added in 28.1.

### Code fix: `DeletePropagationService` relay fan-out

**File:** `src/Iris.Server/Delivery/DeletePropagationService.cs`

The outbox-publish `Update` and `Delete` branches route to
`UpdateActivityHandler` / `DeleteActivityHandler`, which call
`IDeletePropagationService` (`DeletePropagationService`). That service computed
the remote-propagation target set (the author's remote followers, plus the
remote parent-owner for a deleted reply) and delivered to each via
`IDeliveryService.DeliverToActorAsync` — but it never delivered to the author's
subscribed **relays**. So a local author's content edits and deletions never
reached their relays; the relays kept serving stale (or non-tombstoned) copies
of the object.

Added a `DeliverToRelaysAsync` helper (reads the author's relay subscriptions
from `IRelayStore.GetRelaysAsync`, enqueues one delivery job per relay via
`IDeliveryService.DeliverToActorAsync` signed as the author; a per-relay failure
does not suppress the others) and called it from `PropagateUpdateAsync` and
`PropagateDeleteAsync` (after the follower fan-out).

This is only reached for a **local** author (the home instance): the handlers
guard the propagation call with `actorIsLocal`, so a remote instance that
receives an `Update`/`Delete` does not re-fan it to relays (avoiding a double
fan-out).

This mirrors the `DeliverToRelaysAsync` helper added in 28.1 on the
outbox-publish path (`ActivityPubServerExtensions`) — the two now behave
consistently across all four content-producing activity types (`Create`,
`Announce`, `Update`, `Delete`).

## Tests

**File:** `tests/Iris.Server.Tests/UpdateDeleteRelayFanOutIntegrationTests.cs`
(3 tests, 2-instance `TestServer` topology: author instance B + relay instance R)

Topology: instance B (update-delete-relay-b.domain.local) hosts the local author
`bob`, who has subscribed to a relay (the `relay` actor on instance R,
update-delete-relay-r.example.com). B's outbound delivery transport routes to
R's `TestServer` (so the fanned-out activity reaches the relay's inbox), and B's
fetcher resolves the relay's document from R and bob's document from B.

1. **`OutboxPublish_Update_IsFannedOutToRelay`** — bob publishes a `Create` (a
   Note) to his outbox; the 28.1 fan-out delivers it to the relay and R stores
   the Note (attributedTo bob). bob then publishes an `Update` (the same Note
   with new content) to his outbox. B's outbox-publish routes to
   `UpdateActivityHandler` → `PropagateUpdateAsync`, which now also fans out to
   the relay (F-06). R's `UpdateActivityHandler` accepts it (remote actor bob,
   attributed copy) and refreshes R's stored Note with the updated content.

2. **`OutboxPublish_Delete_IsFannedOutToRelay`** — same setup, but bob publishes
   a `Delete` (the Note) to his outbox. B's outbox-publish routes to
   `DeleteActivityHandler` → `PropagateDeleteAsync`, which now also fans out to
   the relay (F-06). R's `DeleteActivityHandler` tombstones R's stored Note.

3. **`OutboxPublish_Update_WithNoSubscribedRelays_IsNotFannedOut`** — a fresh
   author (carol) on B with **no** subscribed relays publishes a `Create` then
   an `Update`. The relay store (for carol) is empty, so no relay fan-out
   occurs; R's object store has no trace of carol's note. (Negative control —
   confirms the fan-out is subscription-driven.)

## Non-vacuity

- **`Update` branch:** Removing the `DeliverToRelaysAsync` call from
  `PropagateUpdateAsync` → test 1 fails (R keeps the original content; the
  assertion that R's stored Note has the updated content fails).
- **`Delete` branch:** Removing the call from `PropagateDeleteAsync` → test 2
  fails (R keeps the original Note content, not tombstoned).
- **Negative control:** test 3 passes regardless (no relays → no fan-out),
  confirming the behavior is subscription-driven.

## Key decisions

- The fix lives in `DeletePropagationService` (the shared propagation service
  for `Update`/`Delete`) rather than in the outbox-publish handler, because that
  service is the single code path both handlers use and it already has access to
  `IPersistenceProvider` (for `IRelayStore`) and `IDeliveryService` (for
  `DeliverToActorAsync`). This keeps the relay fan-out co-located with the
  follower fan-out and avoids duplicating the logic across the two handlers.
- The fan-out is only reached for a local author (the handlers guard the
  propagation call with `actorIsLocal`), so a remote instance that receives an
  `Update`/`Delete` does not re-fan it to relays — avoiding a double fan-out and
  matching the existing follower-propagation guard.
- This is the `Update`/`Delete` complement of 28.1's `Create`/`Announce` relay
  fan-out; together the four content-producing activity types now all fan out to
  subscribed relays on the outbox-publish path.
