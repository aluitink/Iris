# 172 — Phase 19.8.1 minor UX: Actor-detail #handle field accepts a full IRI

## Summary

The `ActorDetail` page's `#handle` input previously **always** resolved its text to
`{dial-base}/ap/v1/u/{input}`. Pasting a full actor IRI (e.g. `http://remote.example/ap/v1/u/bob`)
produced a double-path IRI (`.../ap/v1/u/http://remote.example/...`) and a confusing **"Not an actor"**
error. Now a pasted absolute `http(s)` IRI is used **directly** (it names the actor on its own
instance), and anything else is treated as a **preferred username** on the current instance. This
closes the **19.8.1 minor-UX gap** noted in the 161m click-through audit.

## What changed (code)

- **`samples/SampleBlazorClient/Pages/ActorDetail.razor`**
  - New **`public static Iri ResolveActorIri(string input, Uri dialBase)`** helper — the resolution
    logic, extracted for isolated testability:
    - trims the input; throws `InvalidOperationException("Enter a username or an actor IRI.")` when
      empty/whitespace.
    - a `http://` / `https://` prefix is used directly (validated via `Uri.TryCreate`; a malformed
      URL throws `"Not a valid IRI: {input}"`).
    - otherwise: `{dialBase authority}/ap/v1/u/{input}` (the preferred-username path).
  - `LoadAsync` now calls `ResolveActorIri(Handle, baseUri)` and catches the `InvalidOperationException`
    to surface the message in the page's `Error` field (no more silent double-path failure).
  - The `#handle` label/placeholder updated to hint at the new capability:
    `"Actor (username on this instance, or a full IRI)"`.
- **`tests/SampleBlazorClient.Tests/S19ActorDetailCompletenessTests.cs`**
  - Added `using Iris.Samples.SampleBlazorClient.Pages;`.
  - Six new unit tests on `ResolveActorIri`:
    - `PlainUsername_ResolvesToUserIriOnDialBase` — `alice` → `http://localhost/ap/v1/u/alice`.
    - `WhitespaceUsername_Trimmed` — `"  alice  "` → same.
    - `FullHttpIri_UsedDirectly` — a pasted `http://remote.example/ap/v1/u/bob` is used as-is.
    - `FullHttpsIri_UsedDirectly` — a pasted `https://remote.example/@bob` is used as-is.
    - `MalformedIri_Throws` — `"http://"` (malformed) throws `InvalidOperationException`.
    - `EmptyInput_Throws` — whitespace-only input throws `InvalidOperationException`.

## Key types / API

- `ActorDetail.ResolveActorIri(string input, Uri dialBase)` — the `#handle` → actor-IRI resolution (a
  `public static` helper, tested in isolation).
- The page's existing `Error` field — now carries the resolution failure message (empty/malformed
  input) instead of a downstream "Not an actor".

## Why this is a UX fix (not a behavior change for the happy path)

The preferred-username path is unchanged: a plain `alice` still resolves to
`{dial-base}/ap/v1/u/alice`. The only new behavior is that an absolute IRI is honored directly. The
label now tells the user both forms are accepted. This removes the "confusing double-path 'Not an
actor' error" called out in the 161m audit.

## Scope / limits

- A pasted IRI for a **remote** actor loads via the client's proxy-fallback handler (S8) — the remote
  actor document is fetched (direct or via the home proxy) and rendered. The *browser CORS* gap (19.8.1
  gap (a)) — where a remote object read CORS-fails in the browser because the client dials the remote
  IRI directly with no same-origin proxy route — is a separate, larger 19.1.x item and is **not**
  addressed by this UX fix (it concerns the *transport* of a remote read, not the *resolution* of the
  `#handle` input).
- Live/UI verification (a real browser click-through of the `#handle` field with a pasted IRI) is a
  19.8.x live item, not a code gate.
