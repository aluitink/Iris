## Finding A (hard regression — blocks the browser login path)

> **Fixed in 22.9 (change 227).** The root cause was a `CancellationToken` passed as a JSON
> interop argument in the `Iris.WebCrypto` bootstrap (the `$.WaitHandle.Handle` path is
> `CancellationToken.WaitHandle.Handle`, not a `Task`). See
> [change 227](227-22.9-fix-wasm-webcrypto-login-serialization.md).

**Symptom.** Logging on to `alice@localhost` from the WASM explorer fails with:

```
SerializeTypeInstanceNotSupported, System.IntPtr  Path: $.WaitHandle.Handle.
```

**What succeeds first.** The network trace shows the two login requests both succeed:

```
GET http://localhost:5000/.well-known/webfinger?resource=acct:alice@localhost   200
GET http://localhost:5000/ap/v1/u/alice                                         200   (Basic auth → privateKey + keyAlgorithm)
```

So WebFinger resolution and the owner-only actor-document fetch are fine; the crash happens **after**
the document is fetched, while the browser WebCrypto path imports the private key
(`WebCryptoSigningKeyFactory.CreateAsync` → `WebCryptoSigningKey.CreateAsync` → the `IJSRuntime`
interop in `Iris.WebCrypto`).

**Why it is a regression.** The in-process explorer / client tests use the **default BCL /
BouncyCastle** key loader (no `IJSRuntime` in a test host), so they never exercise the **WebCrypto**
key-import path that a real browser uses. That path is therefore untested, and it currently throws a
`System.Text.Json` "cannot serialize this type" error on a member shaped like a `Task`
(`$.WaitHandle.Handle` is `System.Threading.WaitHandle.Handle`, the property `Task` exposes) — i.e.
something reachable through the JS-interop / key-load object graph is being handed to the JSON
serializer and it has a `Task` property.

**Impact.** The documented primary browser path (log on by WebFinger address in the WASM explorer) is
**broken** against a local instance. The console smoke path and the in-process tests are unaffected
(different key loader). This must be fixed before the explorer is usable in a browser.

**Next step (next turn).** Root-cause the serialization in the `Iris.WebCrypto` key-import path:
identify which object graph (most likely an `IJSRuntime` / interop wrapper, or a `Task`-holding field
reached while the key is registered with the session key store / key provider) is being serialized,
add a `[JsonIgnore]`/ignore the offending member (or restructure so a `Task`/JS-runtime object is never
in a serialized graph), and — critically — add a **browser-path test** (or a test that forces the
`IJSRuntime`-based factory with a stubbed `IJSRuntime`) so this path is covered and the regression
cannot recur silently.

## Finding B (documented local path — CORS origin gap)

> **Fixed in 22.10 (change 228).** `SampleServer`'s default `Iris__CorsOrigins` now includes
> `http://localhost:8080` (alongside the Docker `:8090` origin), so the documented local no-Docker
> path works out of the box. See [change 228](228-22.10-fix-local-cors-origin-gap.md).

**Symptom.** The first login attempt failed with a **CORS** error before the serialization error
surfaced: the explorer (origin `http://localhost:8080`) was blocked from reading
`http://localhost:5000/.well-known/webfinger` because the server's default CORS policy only allows
`http://localhost:8090`.

**Cause.** `SampleServer` defaults `Iris__CorsOrigins` to `http://localhost:8090` (the Docker
`iris-ui` compose port). The **local no-Docker** path in the `SampleBlazorClient` README runs the WASM
dev server on `http://localhost:8080`, but the README's local instructions tell the user to set the
**endpoint override** to `http://localhost:5000` — they do **not** mention that the server must also be
started with `Iris__CorsOrigins=http://localhost:8080`, otherwise every cross-origin request the browser
makes is CORS-blocked. (For verification it was restarted with
`Iris__CorsOrigins=http://localhost:8080,http://localhost:8090`, after which the webfinger + actor
document fetched fine and the error moved to finding A.)

**Impact.** A user following the README's local (no-Docker) instructions will hit a CORS wall on log on.

**Next step (next turn, small).** Either (a) have `SampleServer` add the local WASM dev-server origin
(`http://localhost:8080`) to the default CORS allow-list, or (b) document the required
`Iris__CorsOrigins` env var in the README's local section. (a) is preferred — it makes the documented
local path work out of the box.
