# 27.1 — Cross-instance `Update` (object edit) propagation

## What was built

Two code fixes + 3 integration tests to make cross-instance `Update` (object edit) propagation work end-to-end.

### Code fix 1: Outbox-publish `Update` branch

**File:** `src/Iris.Server/ActivityPubServerExtensions.cs`

The `OutboxPublishHandler` had explicit branches for `Create`, `Announce`, `Delete`, `Add`, `Remove`, and a catch-all for other activity types. An `Update` published to the outbox fell into the catch-all, where `recipientIri` resolved to `null` (no case for `Update` in the recipient switch), so **no delivery occurred** — the remote followers never received the update, and the local object store was never refreshed either.

Added an `else if (activity is Update update)` branch (between the `Delete` branch and the `else` catch-all) that routes the `Update` to `UpdateActivityHandler` via `handlers.OfType<UpdateActivityHandler>().FirstOrDefault()`, mirroring the existing `Delete` branch pattern. The handler then:
1. Refreshes the local object store (if the actor owns the stored object)
2. Calls `PropagateUpdateAsync` to deliver the `Update` to the author's remote followers (only when the actor is local — the home instance re-propagates; a remote instance that received the `Update` does not re-propagate)

### Code fix 2: Tightened owner guard

**File:** `src/Iris.Server/Inbox/UpdateActivityHandler.cs`

The owner guard was:
```csharp
if (!actorIsLocal && (stored is null || !IsAttributedTo(stored, actorIri)))
```

This only checked `attributedTo` when the actor was **remote**. When the actor was **local** (`actorIsLocal == true`), the guard was bypassed entirely — any local actor on the instance could overwrite any object in the object store, including federated copies of remote actors' objects.

Tightened to:
```csharp
if (stored is null || !IsAttributedTo(stored, actorIri))
```

Now **both** local and remote actors must be the `attributedTo` of the stored object. A local actor who created the object on this instance is attributed to it (the `CreateActivityHandler` / outbox-publish path stores the embedded object with `attributedTo` set to the author). A remote actor who is the owner of a federated copy is likewise attributed. An actor updating an object they do not own is rejected.

## Tests

**File:** `tests/Iris.Server.Tests/UpdatePropagationIntegrationTests.cs` (3 tests, 2-instance `TestServer`)

1. **`OutboxPublish_UpdateFederatesToFollower_RefreshesStoredCopy`** — Bob (B) creates a Note → federates to alice (A) → A stores the copy. Bob updates the Note (new content) → B's outbox-publish invokes `UpdateActivityHandler` → local refresh + `PropagateUpdateAsync` delivers to alice on A → A's `UpdateActivityHandler` accepts it (remote actor bob, attributed copy) → refreshes A's stored copy. Asserts A's stored Note has the updated content.

2. **`OutboxPublish_UpdateWithNoRemoteFollowers_RefreshesLocalCopyOnly`** — Dave (on A, no followers) creates a Note, then updates it. The Update refreshes A's stored copy locally. Nothing is federated (no remote followers).

3. **`OutboxPublish_UpdateByNonOwnerOfRemoteObject_IsNoOp`** — Bob (B) creates a Note → federates to alice (A). Alice (local on A) publishes an `Update` to bob's note IRI with her own `attributedTo`. The owner guard rejects it (the stored object is attributed to bob, not alice). The stored copy on A is unchanged.

## Non-vacuity

- **Fix 1 (outbox-publish branch):** Disabling the `Update` branch (`else if (false && activity is Update update)`) → test 1 fails (A keeps the original content after 30s timeout; the `Update` is never delivered).
- **Fix 2 (owner guard):** Reverting to the old `!actorIsLocal &&` guard → test 3 fails (alice's forged update succeeds; the stored note content changes to "alice's forged update").

## Key decisions

- The slice was originally worded as "profile change propagation" (actor doc update). Investigation revealed that `UpdateActivityHandler` handles updates to **objects** in the `IObjectStore` (posts/notes), not actor documents. Actor docs are resolved via `IActorDocumentFetcher` (remote fetch) and are not stored in the `IObjectStore`. The test was reframed to cross-instance `Update` of a **note** (the canonical `Update` use case), which exercises the same handler code path.
