# 52.1 — Change password (self-service)

**Slice:** 52.1
**Status:** Complete
**Date:** 2026-09-08

## Summary

Implemented the self-service change-password flow: the Settings → Password tab now has a
working form (current password, new password, confirm) that calls a new server endpoint
to verify the current password and persist the new hash.

## What changed

### Backend

- `ChangePasswordService` (`apps/Iris.Web/Accounts/ChangePasswordService.cs`) — verifies
  the current password via `PasswordHasher.Verify`, validates the new password's length
  (≥ 8, reusing `RegistrationService.MinPasswordLength`), hashes it, and persists via
  `IUserAccountStore.UpdatePasswordHashAsync`. Returns a `ChangePasswordResult`.
- `POST /local/v1/account/password` endpoint in `WebAppFactory.MapAccountEndpoints` —
  `[Authorize]`-gated, resolves the account via the `sub` claim, accepts a JSON body
  (`ChangePasswordRequest { CurrentPassword, NewPassword }`), returns 200 or 400.
- `ChangePasswordService` registered as a singleton in DI.

### Frontend (WASM)

- `Settings.razor` — the "Password" tab now renders three password fields (current, new,
  confirm) + a "Change password" button. Calls `POST /local/v1/account/password` via the
  named "iris" HttpClient. Shows success/error messages. Client-side validation for
  new-password == confirm.
- `IHttpClientFactory` injected; `_http` initialized in `OnInitialized`.

## Design decisions

- The endpoint uses cookie auth (`[Authorize]`) + the `sub` claim to resolve the account,
  consistent with the notifications endpoints. No Basic auth (the user is already signed in).
- The new password is sent over the same-origin HTTPS connection (cookie-auth session);
  no additional transport-layer protection beyond TLS.
- Minimum length 8 is enforced server-side (reusing the registration constant).
