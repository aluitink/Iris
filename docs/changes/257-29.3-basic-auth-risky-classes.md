## Summary

This is the **third partial** of the 29.3 follow-up. It converts two RISKY single-instance classes
that use **Basic auth** (not signature validation) for their local-moderation endpoints, and require
**client rebuild** in `InitializeAsync` (since their `BuildLocalClient`/`BuildLocalModerationClient`
depend on seed-time keys):

- `MutesCollectionIntegrationTests` (8 methods) — mute/unmute via Basic auth
- `RelaysCollectionIntegrationTests` (8 methods) — relay subscribe/unsubscribe via Basic auth

Combined with the previous partials, **nine RISKY single-instance classes** are now converted.

## What changed

### Client rebuild in `InitializeAsync`

The pattern for Basic-auth classes with `BuildLocalClient`/`BuildLocalModerationClient`:

1. The **fixture** builds the host once (with the initial seed's key for the self-fetcher + the
   `CredentialValidator` closure, both deterministic).
2. The **test class** constructor takes the fixture, creates an `HttpClient`, and sets the client
   fields to `null!` (they'll be built in `InitializeAsync`).
3. `InitializeAsync` calls `_fixture.Reset()` + `SeedForFixture(_persistence)`, then **rebuilds**
   the `_client` and `_local` fields using the **reseeded** keys (fetched from the fixture's
   persistence, which is intact after `Reset()`).

The client fields are **non-readonly** (they're rebuilt per-method). `DisposeAsync` disposes the
current client + the `HttpClient`.

### Why the key-replacement issue doesn't apply

These classes use **Basic auth** (`LocalCredentials`), not signature validation. The `BuildSelfFetcher`
is only used for actor document resolution (to validate the `CredentialValidator`'s IRI check), not
for validating signed requests. So the self-fetcher's `InMemoryKeyStore` (which holds the initial
key) is never used to validate a signature — the key-replacement issue (where `SeedPersonWithKey`
generates a new key on reseed, causing a signature mismatch) doesn't apply.

## What did NOT work this turn

`BlocksCollectionIntegrationTests` (8 methods) was attempted but **reverted**. It uses
`BuildDeliveryClient` to **sign** a `Block` activity, and the server validates the signature by
fetching bob's actor document (via the self-fetcher) and comparing the public key. After reseed
(`SeedPersonWithKey` generates a new key), the self-fetcher's `InMemoryKeyStore` still has the
**initial** key, but the test signs with the **reseeded** key — a mismatch, causing 401s. The fix
would require either (a) not reseed the key (use `SeedPerson` + manual `publicKey` setup), or
(b) updating the self-fetcher's `InMemoryKeyStore` with the reseeded key after each `Reset()`. Both
are more involved; deferred to a future turn.
