# 185 — Phase 22.2: community page — create a community (US-18)

## Summary

Third 22.2 sub-slice (detail pages on the shared components). The community page (`Community`) gains
the missing half of **US-18** — a **create-community** surface — so a user can establish a community
from the UI and then manage it. The page already reviews and manages an *existing* community in full
(US-6: rendered fields, members, feed, following/followers, moderation collections, inbound-follows
accept/reject, membership add/remove, peer follow/unfollow, follow/unfollow, search, raw inspector);
this adds the *create* path.

- **US-18 (create a community).** A new "Create a community" card: the user enters a **name** (the
  community's handle on this instance — the path segment, e.g. `mycommunity`) and a **display name**
  (the human-readable Group name, optional — defaults to the name), clicks **Create**, and the
  session's `IActivityPubClient.CreateCommunityAsync` publishes a `Create` of a Group to the
  logged-on actor's outbox. The server materializes the community (minting its id + collections) and
  federates it. On success the card reports the created name; the user then sets the "Community" name
  above to it and clicks **Load** to review and manage the new community.

This is the community slice of 22.2. Combined with the actor slice (change 183) and the instance
slice (change 184), the actor page (US-5/15/16/17), the instance page (US-10), and community **create**
(US-18) are complete for 22.2. The object page's review (US-7), like/boost (US-13), and delete (US-14)
are already present, and the community review surface (US-6) is already present — the only remaining
22.2 item is the object-page **reply form (US-12)**, which is tracked under 22.3 (authoring).

## What changed (code)

- **`samples/SampleBlazorClient/Pages/Community.razor`**
  - New "Create a community" card between the load card and the load-result cards: two text inputs
    (`CreateName` — the handle, `CreateDisplayName` — the Group name), a **Create** button, a busy
    indicator, a success line (`Status: created community '<name>' (status 202)`), and an error line.
  - New state: `CreateName`, `CreateDisplayName`, `CreateBusy`, `CreateResult`, `CreateError`.
  - New `CreateCommunityAsync()`: trims both inputs, guards an empty name, defaults the display name
    to the name when blank, and calls `Session.GetClient().CreateCommunityAsync(actorIri, name,
    displayName)` with `Session.ActorIri`. A success → the `Status: …` line; a failure → `failed
    (status …)`; an exception → its message.

## Key types / API

- No new `Iris.Core` / `Iris.Client` API. `IActivityPubClient.CreateCommunityAsync(Iri actorId,
  string name, string displayName, CancellationToken ct = default)` is the pre-existing seam (the
  client authors a `Create` of a Group to the actor's outbox; the server materializes the community).
  `Session.ActorIri` is the logged-on actor's IRI (the creating actor); `Session.GetClient()` is the
  logged-on `IActivityPubClient`.

## Decisions

- **Create, then Load (two-step), not auto-load.** Creating a community returns a 202 (the `Create`
  delivery); the server materializes the Group and its collections asynchronously. Rather than
  auto-navigate or auto-reload (which could race the materialization), the card reports the created
  name and the operator re-uses the existing Load control (set the name, click Load) to review the new
  community — reusing the page's established load path and keeping the create action deliberate. This
  matches the page's existing "enter name → Load" idiom.
- **`CreateName` is the handle (path segment), not a full IRI.** The community IRI on an instance is
  derived as `{base}/ap/v1/c/{name}` (exactly what `LoadAsync` computes). So the create card takes the
  name segment (`mycommunity`) and lets `CreateCommunityAsync` (via the outbox) mint the community —
  the operator then types the same name into the Load control, which re-derives the IRI. No separate
  IRI input is needed.
- **The display name defaults to the handle.** A community's human-readable Group name is optional for
  the create action; when the operator leaves it blank the name is used, so a single input is enough
  for the minimal case.

## Scope / limits

- This closes **US-18** (create a community). The community review surface (US-6) was already present
  before this slice; US-18 was the only missing community piece for 22.2.
- The new community is created on the **current** instance (the logged-on base). To create on another
  host, switch instance first (recent-instances card on Home).
- Remaining 22.2 work: the object-page **reply form (US-12)** (object review US-7 + like/boost US-13 +
  delete US-14 are already present); US-12 is tracked under 22.3 (authoring).
