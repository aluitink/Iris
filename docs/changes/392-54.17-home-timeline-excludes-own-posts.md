# 54.17 — Home timeline excludes the user's own posts

Phase 54 slice. The home timeline (the followed feed) only showed the posts of the actors the
signed-in user **follows** — the user's **own** posts were never included, so after posting, the new
post did not appear in the user's own home feed.

## Root cause

`FeedService.BuildFeedAsync` (the server-side feed composer behind `GET /u/{handle}/feed`, F-14) read
the actor's follows (`GetFollowingAsync`) and merged **only the followed actors' outboxes** — the
local follows' outboxes (read from the local activity store) and the remote follows' outboxes (fetched
over the wire). The actor's **own** outbox was never read or merged, so the actor's own posts were
absent from the feed. Additionally, when the actor followed no one, the method returned an empty list
immediately (an early `return []` before any outbox was read), so a user with zero follows saw an
empty home timeline even if they had their own posts.

## Change

1. **Include the actor's own outbox in the feed**
   ([FeedService.cs](../../src/Iris.Server/Services/FeedService.cs)): `BuildFeedAsync` now reads the
   actor's own outbox (`_persistence.Activities.GetOutboxAsync(actorIri, ct)`) and adds those items to
   the feed **before** the followed-actors loop, so the actor's own posts are part of the union. The
   early `return []` when the actor follows no one was removed (the method now always reads the actor's
   own outbox first, then the follows' outboxes). The de-duplication (by item IRI) and capping
   (`FeedOptions.MaxFeedSize`) are unchanged and apply to the combined set.

2. **Update the service XML docs**
   ([IFollowFeedService.cs](../../src/Iris.Server/Services/IFollowFeedService.cs),
   [FeedService.cs](../../src/Iris.Server/Services/FeedService.cs)): the class and method summaries
   previously described the feed as "the union of the actor's local and remote follows' outboxes";
   they now describe it as "the actor's own outbox + local follows + remote follows," and the
   `GetFeedAsync` return doc no longer claims the feed is "empty when the actor follows no one" (it is
   now empty only when the actor has no posts of their own **and** no followed actor has content, or
   nothing matches the filters).

3. **Fix three `FeedNoteIrisAsync` test helpers** that crashed when the feed started including the
   actor's own non-`Create` activities:
   - [BlocksCollectionIntegrationTests.cs](../../tests/Iris.Server.Tests/BlocksCollectionIntegrationTests.cs)
   - [FlagsCollectionIntegrationTests.cs](../../tests/Iris.Server.Tests/FlagsCollectionIntegrationTests.cs)
   - [MutesCollectionIntegrationTests.cs](../../tests/Iris.Server.Tests/MutesCollectionIntegrationTests.cs)

   Each helper read the feed and extracted content-object IRIs from every item with an `object`
   property, assuming `object` was always a content object (a `Note`, or an array of one). With the
   actor's own outbox now in the feed, the helper could encounter the actor's own `Block`/`Undo`/
   `Flag` activities, whose `object` property is a **link** (an actor IRI string), not a content
   object. The helper's `o.GetProperty("id")` then threw
   `InvalidOperationException: The requested operation requires an element of type 'Object', but the
   target element has type 'String'`. Each helper's filter now skips items whose `object` is a link
   (a `String`, or an array whose first element is a `String`), so only content-object items
   contribute IRIs. The test assertions (`Assert.Contains`/`Assert.DoesNotContain(noteIri, …)`) are
   unchanged and still verify the block/flag/mute semantics correctly.
