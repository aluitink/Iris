## What changed

### Per-class details

- **AnnouncePropagation** (2): The tests sign an `Announce` request as alice and POST it to A's outbox
  (`/ap/v1/u/alice/outbox`); A's server records the boost, routes it to `AnnounceActivityHandler`
  (which fans out to bob's inbox), and delivers to B. B validates the signature against alice's actor
  document (fetched from A) and propagates the boost to carol (bob's local follower). The loop-safety
  assertion checks that B's outbound delivery count (to A) is bounded (≤ 4) — if B re-announced the
  boost back to A, A would re-deliver it to B and the chain would grow unboundedly (the classic
  boost-loop failure).

### DeliveryCounter design decision

The `DeliveryCounter` is a top-level `public sealed class` in the test file (not nested in the test
class) because the fixture class (a separate top-level class) needs to create and expose it. The
fixture holds `Lazy<DeliveryCounter>` statics (`ToBRef`, `ToARef`) that are resolved once and shared
between the `DeliveryTransport` lambdas (which capture the `Lazy<T>`) and the public `ToB`/`ToA`
properties (which the test reads). The test calls `_toB.Reset()` / `_toA.Reset()` in `InitializeAsync`
for per-method isolation.

### Test breakdown

1. `Boost_LocalNote_ReachesPeerLocalFollower_Once` — alice boosts her own note; carol (bob's local
   follower) sees it exactly once; B's outbound delivery count is bounded
2. `Boost_RemotePeerNote_CarriesObjectLink_NoInfiniteChain` — alice boosts bob's note (remote
   content); the stored boost references the remote object by link; attributed to alice; no
   infinite announce chain

### Notes

- The `CountingHandler` (nested in the test class) is `internal` so the fixture class can instantiate
  it.
- The `RoutingFetcher` (nested in the test class) is `internal` so the fixture class can instantiate
  it.
- The `DeliveryCounter` is a top-level class (not nested) so the fixture can reference its type.
