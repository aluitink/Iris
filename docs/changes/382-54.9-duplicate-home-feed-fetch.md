# 54.9 — Duplicate home-feed fetch

Phase 54 slice. A Playwright session observed two calls to the feed endpoint
(`GET /ap/v1/u/{actor}/feed`) on first `/home` load.

## Investigation

`Iris.Web.Client` is a **pure Blazor WebAssembly** app (`WebAssemblyHostBuilder`,
no server-side prerendering), so the "prerender + circuit double-mount" hypothesis
in the slice description is **ruled out** — the entire UI renders client-side after
the WASM boots, and `/home` is not SSR'd.

The slice initially hypothesized a `PagedCollection` re-fire (a transient null-
`Client` re-render resetting the `_loadedFor` tracker and re-dispatching the
fire-and-forget initial load). That was **not** the cause. A live diagnostic
(`Console.WriteLine` in `PagedCollection.OnParametersSet`, run against the
deployed WASM via the FQDN `https://iris.luit.ink`) showed the tracker behaved
correctly — `OnParametersSet` fired exactly once with a non-null `Client`,
dispatching the load exactly once. The two `GET /feed` requests both came from a
**single** `LoadInitialAsync` invocation.

The real cause is in the ActivityPub **client's collection walker**,
`ActivityPubClient.GetCollectionAsync` (`src/Iris.Client/ActivityPubClient.cs`):

1. It resolves the first page by fetching the collection document
   (`GetObjectAsync(collectionId)` → `GET /feed`), then reading its `first` link.
2. It then fetches the first page via `FetchCollectionPageAsync(pageIri)`.

For Iris, a feed/outbox collection is an `OrderedCollection` served as its own
first page, carrying a **self** `first` link (`first` == the collection's own IRI —
verified: `id: https://iris.luit.ink/ap/v1/u/alice/feed`,
`first: https://iris.luit.ink/ap/v1/u/alice/feed`). So step 1 fetches `/feed` to
get `first`, and step 2 fetches `/feed` **again** for the first page — two
identical requests for the same document.

## Fix

`src/Iris.Client/ActivityPubClient.cs` — `GetCollectionAsync`:

- Extracted the fetched-object → `CollectionPage` conversion (previously inlined in
  `FetchCollectionPageAsync`) into a reusable static helper
  `ConvertToCollectionPage(IObject?)`. `FetchCollectionPageAsync` now delegates to it.
- **Fast path in `GetCollectionAsync`:** after fetching the collection and resolving
  the first-page IRI, if `pageIri.Equals(collectionId)` (the self-`first` case), the
  already-fetched collection document **is** the first page — it is converted via
  `ConvertToCollectionPage(first)` and reused, so no second `GET` is issued. The
  subsequent `while` loop yields it without a fetch (the `page ??= FetchCollectionPageAsync(...)`
  only fetches when the fast path did not apply).
- The loop resets `page = null` after each yield, so **page 2+ are always fetched
  normally** (the fast path applies only to the first page). A genuinely external
  `first` link (non-self) still takes the slow path and fetches the real first page.

`PagedCollection.razor` is **reverted** to its pre-54.9 state: the earlier
`_loadingInitial` in-flight guard (committed in `97f0e2d`) addressed the wrong
root cause and is removed. The original `_loadedFor` tracker already fires the
initial load exactly once per distinct collection and is unchanged.

Net effect: exactly one `GET /feed` for the first page of a self-`first`
collection (was two), with pagination (page 2+) and external-`first` collections
unaffected.

## Notes

- The FQDN is the correct live-test origin: the signing-key load (`LoadKeyAsync`)
  performs an owner-only actor-document read that must be same-origin, and the
  `AdvertiseBase` is `https://iris.luit.ink`. Accessing the app via the LAN IP
  (`192.168.1.225:8088`) makes that read cross-origin, the key load fails,
  `Session.Client` stays null, and no feed fetch fires at all — a test-environment
  artifact, not an app regression.
- This is Phase 45+ (WASM manual-test phase): no new coded tests; verification is
  the live Playwright pass plus the existing client/server test suites.
