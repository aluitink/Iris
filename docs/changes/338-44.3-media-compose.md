# 44.3 — Media attachment (image) on compose

**Status:** COMPLETE
**Commit:** (pending — part of the 44.3 working set)
**Tests:** 5 new unit tests + 4 new integration tests (full suite: 0 failures)

## What

A user can attach an image to a post they compose. The compose page gains an **Attachment**
file picker (top-level Note/Article posts only — not replies, not community posts). On post,
the chosen image is uploaded first to the local media endpoint to mint a same-origin media IRI,
and the post then carries a single `Image` attachment whose `url` (and `id`) is that IRI. The
feed's existing media rendering (`ObjectView` → `IriExtensions.GetMediaAttachments`) already
knows how to show such an attachment, so no feed change was needed.

This is the F-27 "media attachment" feature. The read half (feed rendering) and the upload
surface (the `IMediaClient` + the server's `LocalMediaUploadHandler`, Phase 20.4 (a)) already
existed from earlier slices; this slice adds the **compose-time upload** and the **attachment
wiring** into `ComposeNote.Build` / the Article path.

## Changes

### `src/Iris.Core/Compose/ComposeNote.cs`

- `ComposeNote.Build` gains three optional params — `mediaIri`, `mediaType`, `mediaName`. When
  `mediaIri` is present it builds a single `Image` attachment and sets `note.Attachment`:
  `Url = [Link { Href = mediaIri }]`, `Id = mediaIri`, `MediaType = mediaType`, and `Name` set
  **only** when `mediaName` is non-blank (a `null`/whitespace file name leaves `Name` at its
  default). The `id` mirrors the `url` so a reader can resolve the media without the `url`. A
  blank `mediaName` is a no-op (the `Image.Name` property is left untouched) — a `{ Length: > 0 }`
  pattern alone would not catch a whitespace-only name, so the guard is
  `mediaName is { } raw && !string.IsNullOrWhiteSpace(raw)`.

### `apps/Iris.Web/Accounts/IActorSessionAccessor.cs`

- The session now exposes `IMediaClient? MediaClient` (the interface) and the lazy `ActorSession`
  implementation creates it on first access via
  `_clientFactory.CreateMediaClient(new ActivityPubClientOptions { ActorId = actorId }, new HttpClientHandler())`
  — the same pattern as the existing `LocalModeration` client.

### `apps/Iris.Web/Components/Pages/Compose.razor`

- **Attachment picker** (rendered only when `ReplyToIri is null`, i.e. not a reply): an
  `<InputFile id="compose-attachment" accept="image/*">` with `OnAttachmentChosen` /
  `OnAttachmentRemoved`; when a file is chosen its name + a remove (✕) button are shown.
- `Attachment` (an `IBrowserFile?`) + a 10 MiB `MaxAttachmentBytes` cap (the server 413s anything
  larger).
- `PostAsync` uploads the attachment **before** posting: when `Attachment is { Size: > 0 }`, it
  calls `UploadAttachmentAsync` (which reads the bytes via `file.OpenReadStream(MaxAttachmentBytes)`
  and POSTs via `Session.MediaClient.UploadAsync`) to get a `MediaUploadResult`. The result's
  `MediaIri` / `ContentType` / `FileName` are then threaded into the post:
  - **Note** → `ComposeNote.Build(..., mediaIri, mediaType, mediaName)` then `PostNoteAsync`.
  - **Article** → `PostArticleAsync(client, actorId, media)`, which builds the `Image` attachment
    inline (same url/id/mediaType/name rules as `ComposeNote.Build`).
  - **Reply / community** → no attachment (the picker is hidden and `media` stays `null`).
- On a successful post the `Attachment` is cleared (alongside the content/sensitive reset).
- `UploadAttachmentAsync` throws a friendly `InvalidOperationException` when the session has no
  media client (upload unavailable).

### `apps/Iris.Web/wwwroot/css/app.css`

- `.compose-attach-label`, `.compose-attach` (flex row, wrap), `.compose-attach input`,
  `.compose-attach-name`, and `.compose-attach-remove` (the ✕ button) styles.

### `tests/Iris.Core.Tests/Compose/ComposeNoteTests.cs`

5 new unit tests:

1. `Build_NoAttachment_WhenNoMedia` — a note with no media params has `Attachment` null.
2. `Build_MediaAttachment_CarriesImage` — a note with media params carries a single `Image` whose
   `Url` resolves to the media IRI, with `MediaType` + `Name` set.
3. `Build_OmitsAttachmentName_WhenMediaNameBlank` — a whitespace-only file name yields a note with
   `Name` left null (the image still has url + mediaType).
4. `Build_MediaAttachment_RoundTripsThroughWire` — the attachment survives an
   `ActivityJson.Serialize`/`Deserialize` round-trip.
5. `Build_MediaAndSensitiveAreIndependent` — a sensitive note with a media attachment carries both
   the `sensitive` extension term and the image attachment.

### `tests/Iris.Web.Tests/MediaComposeIntegrationTests.cs` (new)

4 integration tests booting the real app in-process via `WebAppFactory` + `TestServer`:

1. `MediaUpload_ReturnsSameOriginIri_StoresBytes` — a media upload returns a same-origin
   `/ap/v1/media/{id}` IRI and the stored bytes match what was sent.
2. `NoteWithMedia_RoundTripsImageAttachment` — post a note carrying a media attachment; the stored
   object's `Attachment` is a single `Image` whose `Url` resolves to the uploaded media IRI.
3. `TextOnlyNote_HasNoAttachment` — a note with no attachment has a null `Attachment`.
4. `MediaAttachment_AppearsInPublicObjectDocument` — the media attachment is present in the public
   object document served for the note (the path the feed's `GetMediaAttachments` reads).

## Design notes

- The upload is a **local, Basic-authenticated multipart POST** to
  `POST /local/v1/u/{handle}/media` (the Phase 20.4 (a) surface) — **not** a signed inbox delivery.
  It returns a **same-origin** media IRI (`/ap/v1/media/{id}`), so the browser loads the image
  same-origin (Decision 056 (b): never a cross-origin media host). The post then references that IRI
  in the `Image` attachment's `url`/`id`.
- The attachment is single (one `Image`), matching the one-file picker and the F-27 scope.
- Only top-level Note/Article posts carry an attachment; replies and community posts do not (the
  picker is hidden for replies, and the post paths pass no media).
- The `Image.Name` property is set only for a non-blank file name because a `null` assignment to it
  is a no-op (the property has a non-null default); a `{ Length: > 0 }` pattern is insufficient for a
  whitespace-only name, hence the explicit `IsNullOrWhiteSpace` check.
- No server change: the `LocalMediaUploadHandler`, the `IMediaClient`/`MediaClient`, and the feed's
  `GetMediaAttachments` rendering all predate this slice.
