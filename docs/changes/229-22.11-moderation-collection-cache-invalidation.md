# 22.11 — Moderation collection page-cache invalidation on a local moderation write

Phase 23, slice 1. **Type:** fix (server→client cache-consistency / C2S invariant).

## Problem

An actor's moderation collections — `blocks`, `flags`, and `mutes` — are served through the same
`LocalCollectionPageCache` (a 60s-TTL server→client response cache) as the outbox collection. But, unlike
the outbox, **none of the moderation write paths invalidated the cached page-1 after recording (or
removing) an edge.** The outbox write path invalidates its page (`InvalidateLocalOutboxPage`, change
19.6.2), which is why an outbox publish surfaces immediately on a plain read — but the moderation writes
had no equivalent, so the owner's card would not reflect the edge it just recorded (a `Block` / a `Flag` /
a mute) or removed (an `Undo` of one / an un-mute) until the 60s TTL lapsed or a manual `?refresh=true`
bypass was issued.

This is the same class of C2S invariant gap as the already-fixed outbox case (change 19.6.2 / 056): a write
that is not paired with an invalidation of the cached read leaves the primary (plain, non-`?refresh`) read
stale.

## Where

The page-1 key shape for every local collection is `{owner}/{collection}` (the bare collection IRI), so one
generalized invalidation covers all moderation collections:

- `src/Iris.Server/ActivityPubServerExtensions.cs`
  - `InvalidateLocalOutboxPage` is now a thin alias for the new general helper
    `InvalidateLocalCollectionPage(collectionCache, ownerIri, collectionName)`.
  - `OutboxPublishHandler` — the `Block` / `Flag` branches now invalidate the `blocks` / `flags` page; the
    `Undo` branch resolves the undone sub-activity from the activity store and invalidates `blocks` /
    `flags` **only** when the undone activity is a `Block` / `Flag` (an `Undo` of a `Follow` / `Like` /
    `Announce` touches no moderation collection, so it is left alone).
  - `LocalMuteHandler` (the person `POST /local/v1/u/{handle}/mutes/{target}`) and `CommunityMuteHandler`
    (the community `POST /local/v1/c/{name}/mutes/{target}`) now invalidate the `mutes` page after a
    record **or** removal. Both take a new `LocalCollectionPageCache collectionCache` parameter (the cache
    is a registered singleton, so the minimal-API DI binding is unchanged).

The invalidation is pure-additive: no delivery, ordering, or semantic change — only the cached page is
dropped so the next non-`?refresh` read re-renders from the live store.

## Verification

New integration suite `tests/Iris.Server.Tests/ModerationCollectionCacheInvalidationIntegrationTests.cs`
(5 tests), a single-instance `TestServer` topology (alice = moderator, bob = target / muter) mirroring the
prime → write → plain-read pattern of `OutboxPublishCacheInvalidationIntegrationTests`:

1. `Block_IsVisibleOnPlainBlocksRead_WithoutRefreshBypass` — prime `blocks` empty; signed `Block` to the
   outbox publish endpoint; plain `blocks` read now lists the target.
2. `UndoBlock_IsGoneFromPlainBlocksRead_WithoutRefreshBypass` — seed a block edge, prime `blocks`; publish
   the original `Block` (minted + stored); re-prime; signed `Undo(Block)`; plain `blocks` read is empty
   again.
3. `Flag_IsVisibleOnPlainFlagsRead_WithoutRefreshBypass` — prime `flags` empty; signed `Flag`; plain
   `flags` read now lists the target.
4. `Mute_IsVisibleOnPlainMutesRead_WithoutRefreshBypass` — prime `mutes` empty; Basic-auth `MuteAsync`;
   plain `mutes` read now lists the target.
5. `Unmute_IsGoneFromPlainMutesRead_WithoutRefreshBypass` — seed a mute edge, prime `mutes`; Basic-auth
   `UnmuteAsync`; plain `mutes` read is empty again.

**Proven to fail on the old code:** with the moderation invalidation stashed out, all 5 tests fail (the
plain read serves the stale cached page). Restoring the fix turns them green.
