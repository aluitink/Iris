# 35.5 — Delete own posts from object detail

**Phase 35 — Timeline actions & content completeness**

## What was built

A "Delete" button on the object detail page, visible only when the signed-in user owns the object (i.e., the object's `attributedTo` includes the session actor's IRI).

### Flow

1. User clicks **Delete** (red button, `.button--danger`)
2. Confirmation appears inline: "Delete this post?" with **Confirm** (red) and **Cancel** (secondary) buttons
3. **Confirm** → calls `IActivityPubClient.DeleteAsync(actorId, objectId)`
4. On success → navigates to `/home`
5. On failure → shows an error message inline
6. **Cancel** → returns to the single Delete button

### Ownership check

`IsOwnPost` property: checks if any entry in the object's `attributedTo` collection resolves to the same IRI as `Session.ActorId`. Uses `ResolveObjectIri()` (handles both `IObject` and `ILink` entries) and string comparison via `ToString()`.

### Key changes

- `ObjectDetail.razor`: added `NavigationManager` injection, `ConfirmingDelete`/`Deleting`/`DeleteError` state, `IsOwnPost` property, `DeleteAsync` method, and the Delete/confirm UI in the actions row
- `app.css`: `.button--danger` (red background, white text) + `.delete-confirm` (inline flex layout)

## Design decisions

- **Inline confirmation, not a modal.** Simpler, no overlay/z-index management. The confirmation replaces the Delete button in the same actions row, keeping the layout stable.
- **Ownership via `attributedTo`, not IRI path prefix.** The IRI path convention (`/ap/v1/u/{handle}/notes/...`) could work but is fragile (communities, migrated actors). `attributedTo` is the ActivityStreams-authoritative field.
- **Redirect to `/home` after delete, not back to the previous page.** The object no longer exists; there's nothing to return to. Home is the natural landing point.
