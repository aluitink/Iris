# 33.5 — server production-readiness: CORS same-origin default + opt-in allow-list

**Slice:** Phase 33 step 5. **Branch:** `phase-32-production-app`. **Commit:** (impl + tests, this turn).

## Problem

The production app implemented **no** CORS middleware at all. The Blazor Web App UI is
**same-origin** (served by the same host as its API), so it needs no CORS — but that left the
cross-origin behavior **implicit**. Two consequences:

1. **The safe default was accidental, not enforced.** "No cross-origin access" was simply "no CORS
   middleware configured." A future developer adding a third-party API consumer could easily reach
   for `AllowAnyOrigin()` and silently open the instance's API to any origin — with no guardrail or
   documentation that the default should be same-origin-only.
2. **No opt-in path.** A legitimate non-UI consumer (a third-party app that wants to call this
   instance's API from a different origin) had no way to be granted access — there was no
   configuration knob at all.

## Change

- **`apps/Iris.Web/WebAppFactory.cs`**:
  - New `public const string CorsPolicyName = "iris-api"` — the name of the CORS policy registered
    when cross-origin access is opted into.
  - New `public const string CorsOriginsConfigKey = "Iris:Cors:Origins"`.
  - At the end of `ConfigureServices`, **only when** `Iris:Cors:Origins` (env `IRIS_CORS_ORIGINS`) is
    set to a non-empty comma-separated allow-list, a named policy (`CorsPolicyName`) is registered:
    `WithOrigins(<the listed origins>)` + `AllowCredentials()` + `WithMethods("GET","POST","PUT",
    "DELETE","OPTIONS")` + `WithHeaders("Content-Type","Authorization","Signature","Host")`. **Never**
    `AllowAnyOrigin`. When the allow-list is empty/unset, **no** policy is registered.
  - In `ConfigurePipeline`, `app.UseCors(CorsPolicyName)` is applied **only when** the policy is
    registered (checked via the resolved `IOptions<CorsOptions>.GetPolicy(CorsPolicyName) is not null`).
    It runs **after** `UseRouting` and **before** `UseAuthentication`, so a cross-origin **preflight**
    (`OPTIONS`) is answered before the signature/cookie gate.
- **`apps/Iris.Web/docker-compose.yml`** + **`.env.example`**: new `IRIS_CORS_ORIGINS` env var (maps to
  `Iris:Cors:Origins`, comma-separated origins). Blank → same-origin-only.

## Decision (recorded)

- **Same-origin-only is the default, achieved by *not* adding a permissive policy.** ASP.NET Core's
  default (no CORS middleware) already blocks cross-origin access in browsers; the slice makes that
  explicit + documented and adds the opt-in knob, rather than adding an explicit "deny" policy. This
  keeps the default path free of any CORS middleware (zero overhead for the common same-origin case)
  while making the intent clear and the opt-in path a strict allow-list.
- **The allow-list never uses `AllowAnyOrigin`.** A public instance's API must not be open to any
  origin by a one-line config; an operator grants access to specific, known origins only. Credentials
  are allowed (`AllowCredentials`) because a cookie-authenticated cross-origin consumer is the
  realistic third-party case (and `AllowCredentials` is only honored for a specific origin, never `*`).
- **The `UseCors` guard (`GetPolicy(...) is not null`)** mirrors exactly the condition under which the
  policy is registered, so the middleware is applied if-and-only-if the operator opted in. `GetPolicy`
  returns `null` for an unregistered policy (no throw), so the check is safe.

## Tests / verification

**4 new integration tests** (`tests/Iris.Web.Tests/CorsIntegrationTests`) — they boot the **real**
service graph (via `WebAppFactory.ConfigureServices`, which registers the policy only when
`Iris:Cors:Origins` is set) on a `TestServer`, mirroring `ConfigurePipeline`'s CORS wiring verbatim
(`UseCors` applied only when the policy is registered), and assert the `Access-Control-Allow-Origin`
header behavior for a cross-origin request to `GET /ap/v1/u/alice`:
- `Default_NoCrossOriginAccess_AllowOriginHeaderAbsent` — no origins configured → the header is
  **absent** (same-origin-only default).
- `OptedIn_RegisteredOrigin_AllowOriginHeaderPresent` — origins set + request from a registered origin
  → the header **echoes that origin**.
- `OptedIn_UnregisteredOrigin_AllowOriginHeaderAbsent` — origins set + request from an origin **not** in
  the list → the header is **absent** (strict allow-list, never `AllowAnyOrigin`).
- `OptedIn_RegisteredOrigin_Preflight_AllowsTheMethod` — a preflight (`OPTIONS` + `Origin` +
  `Access-Control-Request-Method: POST`) from a registered origin → **204** with `allow-origin` +
  `allow-methods` containing `POST` (the preflight short-circuits before the signature/cookie gate).

**Verified live in the production container** (rebuilt the image + `docker compose up -d iris-web` over
the **persistent** Postgres volume):
1. **Default** (no `IRIS_CORS_ORIGINS`): a cross-origin `GET /ap/v1/u/alice` (with an `Origin` header)
   returns **200** with **no** `Access-Control-Allow-Origin` header — same-origin-only default confirmed.
2. **Opted-in** (`IRIS_CORS_ORIGINS=https://app.example.org`): a cross-origin GET from that origin
   returns **200** + `Access-Control-Allow-Origin: https://app.example.org` (echoed); a cross-origin
   GET from `https://evil.example.com` returns **200** with **no** CORS header (denied — not in the
   allow-list); a preflight `OPTIONS` from the registered origin returns **204** +
   `Access-Control-Allow-Origin` + `Access-Control-Allow-Methods: GET,POST,PUT,DELETE,OPTIONS`.
3. Restored to the default (env removed): cross-origin GET again gets no CORS header.

Build clean (`dotnet build`, `TreatWarningsAsErrors` on); `Iris.Web.Tests` 53/53 (49 prior + 4 new).
