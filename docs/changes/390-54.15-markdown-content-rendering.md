# 54.15 — Markdown content rendering

Phase 54 slice. Federated servers send `content` in two flavors: **pre-rendered HTML** (the
client already converted Markdown → HTML before posting) and **Markdown/plain text source** (the
client posted the raw Markdown, or the text simply isn't HTML). The production WASM app's
`ObjectView` handled the first correctly (emitted verbatim) but treated the second as inert
plain text — `WebUtility.HtmlEncode(content)` — so a note whose `content` was Markdown displayed
its literal source (`**bold**`, `# heading`, `- item`, `` `code` ``, …) instead of the formatted
result.

## Change

The fix reuses the app's existing, dependency-free Markdown renderer. That renderer already lived
in the **sample** client ([samples/SampleBlazorClient/Markdown.cs](samples/SampleBlazorClient/Markdown.cs))
and was already used by the sample's `ObjectView` and `Compose` — but the **production**
`Iris.Web.Client` did not use it (it had no reference to it; the sample's local copy was in a
namespace the production client didn't import).

1. **Moved the renderer to a shared home:** `Iris.Core.Rendering.Markdown`
   ([src/Iris.Core/Rendering/Markdown.cs](src/Iris.Core/Rendering/Markdown.cs)). `Iris.Core` is a
   pure-logic library (no UI deps) that both the sample (`SampleBlazorClient` → `Iris.Client.Extensions`
   → `Iris.Client` → `Iris.Core`) and the production client (`Iris.Web.Client` → `Iris.Core`)
   already reference, so both now share one implementation. The sample's local `Markdown.cs` was
   deleted (`git rm`); the sample's `ObjectView.razor` and `Compose.razor` now `@using
   Iris.Core.Rendering`. No behavior change for the sample.

2. **Production now renders Markdown:** the two content-rendering properties in
   [ObjectView.razor.cs](apps/Iris.Web.Client/Components/ObjectView.razor.cs) (`RenderedContent`
   and `ActivityContent`) and the helper in
   [ObjectViewActivityRenderer.cs](apps/Iris.Web.Client/Components/ObjectViewActivityRenderer.cs)
   (`SafeContent`) all previously did `IsPreRenderedHtmlContent() ? content : HtmlEncode(content)`.
   They now do `IsPreRenderedHtmlContent() ? content : Markdown.ToHtml(content)`. Pre-rendered HTML
   is still emitted verbatim (unchanged); Markdown/plain text is run through the safe renderer.

**Security (unchanged, now applied in production):** `Markdown.ToHtml` HTML-escapes the entire
input *first* (so any raw HTML in the content is inert), then applies the Markdown transforms, and
sanitizes link targets to `http`/`https`/`mailto` only (a `javascript:` or any other scheme is
rendered as plain text, never a live link). The output is safe to emit as a Blazor `MarkupString`.

**Note on a pre-existing cosmetic quirk:** when a Markdown link's URL is *rejected* (e.g. a
`javascript:` scheme), the renderer renders the link's text but a trailing `)` remains (it shows
`click me)` rather than `click me`), because the shared link regex's rejection path returns only the
`text` group while the `)` was outside the matched group. This is a pre-existing behavior of the
shared renderer (also present in the sample), not a security issue, and out of scope for this
slice — noted here so it isn't mistaken for a regression.
