# Change 224: Centralize the settings-gate extension term names in `Iris.Core` (22.6.2)

## Summary

The wire names of the two AP-native settings-gate extension terms — `manuallyApprovesFollowers`
(person) and `manuallyApprovesMembers` (community) — are now defined **once** in
`Iris.Core.ActivityPubExtensionNames`. The client (which builds and reads the terms) and the server
(which renders and updates them) both reference the shared Core constants, so the term strings can no
longer drift apart silently.

## Problem

The two settings-gate terms ride in a document's `ExtensionData` (the library does not model them), and
their exact string value is the wire contract between:

- the **client write path** — `ActivityPubClient.SetManuallyApprovesMembersAsync` /
  `SetManuallyApprovesFollowersAsync` build the settings `Add`/`Remove` object with the term string; and
- the **client read path** — `IrisDocumentExtensions.GetManuallyApprovesMembers()` /
  `GetManuallyApprovesFollowers()` read the term back; and
- the **server render/update path** — `ActivityPubServerConstants.ManuallyApproves{Followers,Members}ExtensionName`
  drives the public-document echo and the `Record*Add/RemoveAsync` persistence updates.

Before this change the term strings were **duplicated**: `ActivityPubServerConstants` defined them, while
the client **hardcoded the same two strings** in four places (`ActivityPubClient.cs` ×2,
`IrisDocumentExtensions.cs` ×2). That is a dependency-direction violation of the "no magic strings" coding
rule (`Iris.Client` must not know about `Iris.Server`), and more importantly a **silent-drift risk**: a
typo on either side would make the client store/read the gate under a different term than the server
expects — settings would stop propagating on the wire with no error, no failed test, and no log line.

## Solution

### New: `Iris.Core.ActivityPubExtensionNames`

A static class in `Iris.Core` (the lowest shared dependency, reachable from both `Iris.Client` and
`Iris.Server`) with two `const string` members:

- `ActivityPubExtensionNames.ManuallyApprovesFollowers` = `"manuallyApprovesFollowers"`
- `ActivityPubExtensionNames.ManuallyApprovesMembers` = `"manuallyApprovesMembers"`

These are the **single source of truth** for the two terms.

### `Iris.Server.ActivityPubServerConstants` (aliased)

`ManuallyApprovesFollowersExtensionName` and `ManuallyApprovesMembersExtensionName` now **alias** the
Core constants:

```csharp
public const string ManuallyApprovesFollowersExtensionName =
    Iris.Core.ActivityPubExtensionNames.ManuallyApprovesFollowers;
public const string ManuallyApprovesMembersExtensionName =
    Iris.Core.ActivityPubExtensionNames.ManuallyApprovesMembers;
```

The constant **values** are unchanged (so all server call sites and existing wire behavior are untouched);
only the *definition* now flows from `Iris.Core`.

### `Iris.Client` (de-hardcoded)

- `ActivityPubClient.SetManuallyApprovesMembersAsync` / `SetManuallyApprovesFollowersAsync`: the
  `ExtensionData` key is now `ActivityPubExtensionNames.ManuallyApprovesMembers` /
  `ActivityPubExtensionNames.ManuallyApprovesFollowers` instead of a literal string.
- `IrisDocumentExtensions.GetManuallyApprovesMembers()` / `GetManuallyApprovesFollowers()`: the term passed
  to the shared `GetManuallyApprovesGate` helper is now the Core constant instead of a literal string.

The client no longer contains any raw `manuallyApproves*` string.

## What is NOT changed

- No wire format, endpoint, or behavior change. The term values are byte-for-byte identical.
- No change to the `iris:settings` / `iris:capabilities` discovery seam (change 220) or the
  collection-endpoint readers (change 222).
- The `search` term (change 222) was already covered by `iris:capabilities` and is intentionally not a
  dedicated reader; it is also not part of this centralization (only the two gate terms had duplicated
  client literals).

## Tests

- **Unit** (`Iris.Core.Tests.ActivityPubExtensionNamesTests`, 2 tests): pin the exact wire strings
  (`"manuallyApprovesFollowers"` / `"manuallyApprovesMembers"`) so a typo in the canonical constant is
  caught.
- **Integration** (`Iris.Server.Tests.SettingsGateReaderTests`, +2 tests):
  `PersonGate_ClientWriteAndReader_ShareTheCoreConstant` and
  `CommunityGate_ClientWriteAndReader_ShareTheCoreConstant` drive the full round-trip — the client's
  `SetManuallyApproves*Async` writes the gate, the stored actor/community `ExtensionData` key is asserted
  to be exactly the **Core constant's** term, and the reader (which reads the same Core term) observes
  `true`. This proves the write side and the read side share one term; a typo on either side would break
  the round-trip.

Suite total: **1,341 → 1,347** (2 Core + 2 Server).
