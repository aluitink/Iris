# 54.3 — Accessibility & keyboard-navigation regression

Phase 54 slice. A manual Playwright a11y/keyboard regression pass over the
post-1.0 UI: verify the 47.3 ARIA pass held across the 54.1/54.2 changes and
sweep Tab order, visible focus, heading hierarchy, and screen-reader
announcement of action feedback.

## 47.3 items re-verified (held)

- Icon-only controls keep their accessible names: `button "Like"`,
  `button "Boost"`, `link "Reply"`, `button "More options"` (EngagementBar).
- Decorative SVGs are still `aria-hidden="true"` (brand icon, hamburger,
  loading spinners, notification-row icons).
- Navigation links are real `<a>`/`<nav>` with proper `aria-label` /
  `aria-expanded` on the menu toggle.
- Tab order is logical (brand → menu → nav links → page controls → content).
- 0 client-side console errors on the swept pages.

## Defects found & fixed

### 1. Heading hierarchy — 14 pages had no `<h1>` (HIGH)

Every page should have exactly one top-level `<h1>` (the page title); a
screen-reader user navigating by heading gets no "you are on page X"
announcement otherwise. Only `/` (landing, not-signed-in branch) and
`/login`/`/register` had an `<h1>`; all other content pages started at
`<h2>`.

**Fix:** promoted the page-title `<h2>` → `<h1>` on 15 pages, and promoted the
direct sub-section headings one level up so no level is skipped:

| Page | Page title → `<h1>` | Sub-sections |
|---|---|---|
| HomeTimeline | `Home timeline` | — |
| Directory | `Directory` | — |
| Communities | `Communities` | `Create a community` → `<h2>` |
| Notifications | `Notifications` | — |
| Search | `Search` | `Results for…`/`All content` → `<h2>` |
| Settings | `Settings` | 7 tab headings → `<h2>`; 5 sub-sub (`Notification types`, `Muted actors`, `Blocked`, `Muted`, `Reported`) → `<h3>` |
| Profile | `Your profile` | — |
| Compose | `@PageTitle` | `Formatting tips` → `<h2>` |
| ActorDetail | `@PageHeading` | — |
| CommunityDetail | `@PageHeading` | `Edit community` → `<h2>` |
| ObjectDetail | `@PageHeading` | `Replies` → `<h2>` |
| AdminDashboard | `Instance dashboard` | `Recent registrations` → `<h2>` |
| AdminUsers | `Instance users` | — |
| AdminModeration | `Moderation queue` | — |
| AdminInstance | `Instance settings` | — |

Shared components also corrected: `EditProfileForm` `Edit profile` → `<h2>`;
`PagedCollection` card `Title` `<h3>` → `<h2>` (feed cards are peer
sub-sections of the page).

Result: every page now has exactly one `<h1>`; sub-sections are `<h2>`,
sub-sub-sections `<h3>` — no level skips.

### 2. No visible keyboard-focus indicator (MEDIUM)

The only `outline` rule in the whole stylesheet was `outline: none` on form
inputs. Buttons/links relied on the thin (1px) UA default outline, which is
low-contrast on the dark theme; form inputs lost the outline entirely and
relied on a border-color change alone.

**Fix (`app.css`):** added a high-contrast, offset focus ring that applies on
keyboard focus (`:focus-visible`) to every focusable element (links, buttons,
`role="button"`, inputs, textareas, selects, `[tabindex]`):

```css
a:focus-visible,
button:focus-visible,
[role="button"]:focus-visible,
input:focus-visible,
textarea:focus-visible,
select:focus-visible,
[tabindex]:focus-visible {
    outline: 3px solid var(--accent-warm);
    outline-offset: 2px;
    border-radius: 2px;
}
```

and removed the `outline: none` from `.form-group input:focus` /
`textarea:focus` (keeping the `border-color` accent) so the global
`:focus-visible` ring shows on keyboard-focused inputs too.

Live-verified: the focused element reports `outline: 3px solid
rgb(124,159,255)`, `outline-offset: 2px`, and the ring is clearly visible in a
screenshot (bright blue rounded outline on the dark theme).

### 3. Action error/success not announced to screen readers (MEDIUM)

The action error/success messages (the friendly copy from 54.2) were rendered
in plain `<div class="error">` / `<div class="success">` with no live region,
so a screen reader never announced them when they appeared after a user
action. (Login/Register already had `role="alert"`.)

**Fix:** added `role="alert"` (assertive — for errors) and `role="status"`
(polite — for successes) to every action-feedback and load-error element across
the pages and shared components: Compose, Settings (7 tab errors + 2
successes), Communities (create error/success + load), ActorDetail,
CommunityDetail (save + join-request + member-remove + load), ObjectDetail
(edit + delete + load), Profile, Directory, Search, AdminUsers (reset/delete
+ load), AdminInstance (save + load), AdminDashboard, AdminModeration,
`EditProfileForm`, and the central `PagedCollection` load error (covers all
feed cards).

Live-verified via the Settings → Change password flow:
- wrong current password → `alert` node "Current password is incorrect."
- correct change → `status` node "Password changed successfully."
Both appear in the accessibility tree with the correct role, so a screen
reader announces them.
