# 161m — 19.8.1 click-through audit (live UI navigability)

## Summary

Phase 19.8.1 (the **click-through audit**): from *every* collection surface, selecting an item must
navigate to a **rendered view** (ObjectPage / ActorDetail / Community) — never a raw-JSON dead end. This
slice is the **live-verification half** of the Phase 19 UI work: it drives the Blazor "server explorer"
against the running Docker env (iris-a `iris-dev1.luit.ink`, dial base `http://localhost:8081`) with
Playwright, logs on as `alice`, and clicks through every collection surface, recording each
collection→view transition that works and each that does not.

**No code change** resulted — the audit is an evaluation record. It confirms the 19.8.x UI surfaces
render properly for all *local* content and surfaces the remaining live-interop gap (remote reads) that
19.1.x must close. ROADMAP 19.8.1 stays **unchecked** until the two open gaps below are resolved.

## Method

- **Env:** `docker compose up -d` (iris-a / iris-b / iris-ui). The UI is a **Blazor WebAssembly** static
  site (published `SampleBlazorClient`) served by `IrisStaticHost` on `:8090` (host-published `:8088`).
  The browser dials the servers on their host-published ports (`:8081` for iris-a).
- **Log on:** `alice@localhost` + password `iris-sample` + base `http://localhost:8081` (Basic-auth
  WebFinger dial). Logged-on actor: `https://iris-dev1.luit.ink/ap/v1/u/alice`.
- **Navigation:** in-app SPA links (not `page.goto`) so the in-memory session survives; each surface is
  captured via `browser_evaluate` (headings / links / buttons / `.error` / item previews).

## Open gaps (keep 19.8.1 unchecked)

1. **Remote (cross-instance) object reads CORS-fail in the browser.** A remote item in a feed (e.g. the
   `mastodon.world/…` Follow, or a remote note) links to `/object?iri=https://mastodon.world/…`. The
   ObjectPage then has the **browser** fetch that IRI **directly**, and the request is **CORS-blocked**
   (no `Access-Control-Allow-Origin` on `mastodon.world`). Nothing renders. The client has no
   **same-origin proxy route** for reads — only the *server* has a proxy fallback (for server-side
   fetches). This is a live-interop gap for 19.1.x: either the UI must route remote reads through a
   same-origin (server) proxy, or remote items in the UI should be rendered as non-interactive links to
   the canonical public URL rather than attempted in-app loads.
2. **Instance page has no recent-instances list.** The 19.8.1 audit lists "recent-instances" as a
   surface; the Instance overview shows only the single current instance (software / protocols /
   NodeInfo) with no list of recently-seen/peer instances.

## Minor UX findings (non-blocking)

- **Actor-detail `#handle` field rejects a full IRI** with a confusing double-path error:
  `Not an actor: http://localhost:8081/ap/v1/u/https://iris-dev1.luit.ink/ap/v1/u/alice`. The field
  expects a **handle** (e.g. `alice`); passing a full actor IRI is mis-joined. Consider accepting both
  or showing a clearer validation message.
- **Instance name renders with an `iris-` prefix** (`Instance iris-iris-dev1.luit.ink`) — a cosmetic
  label quirk in the instance overview.

## Harness note (not a code bug) — stale WASM cache

The Blazor WebAssembly app is **aggressively cached by the browser**. After rebuilding the `iris-ui`
image, the browser kept serving a **stale** cached `SampleBlazorClient.*.wasm` (a bundle from before
19.8.6), which made the **Boost button appear missing** from the ObjectPage (the DOM showed Like /
Delete with the surrounding `@if` comment markers but no Boost `<button>`). The server was serving the
correct new bundle; the browser's HTTP cache was not.

- **Diagnosis:** the browser's actual network request was for
  `SampleBlazorClient.gdzi1y7s4x.wasm` (a **404** from the server — a cached-only hash), while the
  server served `SampleBlazorClient.vray4uuml4.wasm` (the fresh no-cache build).
- **Fix for the check:** `Network.clearBrowserCache` (CDP) + a fresh boot loaded the current bundle and
  the Boost button rendered in the correct position (Like / **Boost** / Delete).

**Operational rule:** after any `iris-ui` rebuild, **clear the browser cache (or use a fresh browser
context)** before asserting on UI markup — otherwise a stale WASM bundle produces false "missing
element" results.
