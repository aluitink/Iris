# 279 — 31.6: communities — profile-style header + tabs

> 2026-09-05 · Slice 31.6 · Phase 31 (explorer UI & server namespace polish)

## What was built

The `/community` page was **one long page**: the community document, the feed,
members, followers, following, inbound follows, pending join requests,
moderation, follow/unfollow, membership management, peer management, settings,
search, and a raw inspector — all stacked top to bottom. The 31.6 report asked
for **the same treatment as the 31.5 actor-detail page**: a profile-style
header plus tabbed sections (a community is the `Group`-actor analogue of an
actor).

Two changes, both pure client-side reorganization (no data flow, wire, or
server behavior changed):

1. **The profile-style header.** The old "Community" card (a raw `<ObjectView>`
   of the Group document + an IRI line) is replaced by the shared
   `<ActorProfile>` component introduced in 31.5. A community is a `Group`, and
   a `Group` is an `Actor` — so the 31.5 component (avatar + handle + name +
   summary + IRI, with a name-initial fallback and a non-actor placeholder) is
   **reused verbatim** with no changes. This is the "make the top look like a
   profile, not just the raw object view" the report asked for, and it confirms
   the 31.5 component generalizes beyond `Person`.

2. **Tabbed sections.** The page's sections are organized into tabs:

   | Tab | Contents |
   | --- | --- |
   | **Feed** | the community's unified feed (its `feed` collection) |
   | **Members** | the member actors (its `members` collection) + per-member remove |
   | **Followers** | its `followers` collection (paged) |
   | **Following** | its `following` collection (paged) |
   | **Manage** | follow/unfollow + manage membership + peer management + settings + search |
   | **Requests** | inbound follows + pending join requests (accept/reject) |
   | **Moderation** | the community's mutes/blocks/flags collections + the mute/block/flag writes |
   | **Raw** | the raw inspector (the Group document) |

   The header and the tab bar are always visible; only the active tab's section
   renders. All data is loaded up front in `LoadAsync`, so switching tabs is
   instant and does not lose state. `ActiveTab` defaults to **Feed** and resets
   to **Feed** on a new community load.

## Key types & files

- `samples/SampleBlazorClient/Pages/Community.razor`
  - The "Community" card is replaced by
    `<ActorProfile Actor="CommunityDoc" ActorId="communityIri.Value" />` + a
    `<nav class="tabs">` (mirroring 31.5's markup).
  - Each section is wrapped in `@if (ActiveTab is "<key>")` — the 8 tabs above.
  - New state: `string ActiveTab = "feed"`, a `record Tab(Key, Title, Badge)`,
    a `Tabs` collection expression (the 8 tabs in display order), and
    `SetActiveTab`. `LoadAsync` resets `ActiveTab = "feed"`.
  - `CommunityDoc` is now typed `IObject` (it is the Group **actor** document);
    the `@code` methods that used it (`IsGated`) still pattern-match it, and
    `LoadAsync`/`SetGatingAsync` already assign an `IObject` (the `GetActorAsync`
    result), so no method body changed.
  - The tab markup is nested one level deeper than the original flat cards, so
    the `else if (CommunityIri is { } communityIri)` outer variable is no longer
    in scope inside each `@if (ActiveTab …)` block — the few places that read
    `CommunityIri.Value` in the descriptive text use the null-conditional form
    (`@(CommunityIri?.Value ?? string.Empty)`).
- `samples/SampleBlazorClient/Components/ActorProfile.razor` — **unchanged**
  (reused from 31.5).
- `samples/SampleBlazorClient/wwwroot/css/app.css` — **unchanged** (the
  `.actor-profile*` and `.tabs`/`.tab`/`.tab-badge` styles from 31.5 apply).

## Design notes

- **Reuse, not duplication.** The whole point of 31.5 extracting `ActorProfile`
  was that 31.6 would drop it in unchanged. This slice adds zero new component
  or CSS code — it is purely the `Community.razor` markup reorganization plus
  the tab state.
- **Tab grouping is a community-appropriate split.** Unlike the actor page
  (whose tabs are outbox/liked/followers/following/raw/moderation), the community
  page has no outbox/liked of its own; its distinctive sections (feed, members,
  membership management, join requests) drive the tab split. "Manage" groups the
  operator's write surfaces (follow, membership, peer, settings, search) so the
  frequently-viewed read sections (feed, members, followers, following) stay
  prominent.
- **The raw inspector is a tab, not a header replacement.** As in 31.5, the raw
  `<ObjectView>` of the Group document remains available (the "Raw" tab); the
  `ActorProfile` header is an added human-facing layer on top.
- **`ActiveTab` defaults to Feed** (not Outbox, as on the actor page) because the
  community's primary content is its feed — the first thing an operator loads a
  community to see.
- No new NuGet packages; no server or client-library changes; no CSS changes.
