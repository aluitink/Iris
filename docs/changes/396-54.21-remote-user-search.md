# 54.21 — No search for external/remote users

**Status:** COMPLETE (live-verified on the FQDN)
**Phase:** 54 — Post-1.0 polish & hardening

## Problem

Search only found local actors and stored content objects. A user typing a remote handle (e.g. `admin@mastodon.social`) got no results, even though the instance could already resolve remote actors via WebFinger and fetch remote objects through the cross-instance proxy fallback (54.7/54.20).

## Solution

### `IActorSessionAccessor.ProxyGetAsync` (new)

Added `Task<string?> ProxyGetAsync(string target, string? accept, CancellationToken ct)` to `IActorSessionAccessor` / `ActorSessionAccessor`. Routes a `GET` request to a remote instance through the home instance's proxy endpoint (`POST /ap/v1/proxy/{target}`), authenticating by the site cookie (the WASM client has no Basic credentials). The proxy signs the forwarded request with the acting actor's key and relays the remote response. Returns null when signed out, the proxy rejects the request, or the remote returns a non-success status.

### `Search.razor` — remote search support

The search page now detects when the query looks like a remote handle and runs a remote lookup in parallel with the local search:

**Handle detection** (`ParseRemoteHandle`): accepts `user@host`, `@user@host`, or a full IRI (`https://host/@user`). Validates that the host part contains a dot (or is `localhost`) and the user part has no slashes. Returns null for non-remote queries (local searches are unchanged).

**Remote lookup** (`TryRunRemoteSearchAsync`): three steps, all best-effort:
1. **WebFinger** — `GET https://{host}/.well-known/webfinger?resource=acct:{user}@{host}` through the home proxy. Parses the `application/jrd+json` response, extracts the `self` link's `href` as the actor IRI.
2. **Federated search** — `GET https://{host}/search?q={query}&limit=20&type=any` through the home proxy. Handles two response shapes: ActivityPub `OrderedCollection`/`OrderedCollectionPage` (Iris, or AP-native endpoints — reads `items`/`orderedItems` and deserializes each entry) and Mastodon's JSON array of `{type, account, status, hashtag}` (extracts account URLs, fetches the first 5 actor documents via the proxy). A 406/404/any failure is swallowed (the remote search is a bonus, not a requirement).
3. **Actor doc fallback** — if WebFinger resolved the actor but federated search returned nothing (or was skipped by "Actors only"), fetches the actor document via `IActivityPubClient.GetObjectAsync` (which already handles cross-origin proxy fallback from 54.7).

**Result merging**: local results are added first; remote results are deduplicated by IRI (case-insensitive) against the local set. A `(remote: {host})` annotation is shown in the results header when remote results contributed.

## Live verification (FQDN `iris.luit.ink`)

- `admin@mastodon.social` → 1 result (remote: mastodon.social), actor "admin" with link to `/actor?iri=https://mastodon.social/users/admin`. Clicking through renders 2 posts from the outbox (54.20's orderedItems fix working).
- `@Gargron@mastodon.social` → 1 result (remote: mastodon.social), actor "Gargron" (Eugen Rochko) with display name + bio.
- `bob` (local) → 6 results, no remote annotation. Local search unchanged.
- One expected console 406: Mastodon's `/search` rejects the ActivityPub `Accept` header (Mastodon uses its own REST API, not AP). Handled gracefully — the WebFinger + actor-doc-fallback path still returns the actor.
