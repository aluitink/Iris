## Context

The slice asked: "verify that undoing a like of a remote object (object IRI on a different instance)
federates correctly — the 24.1 fix covered `Like`/`Announce` of remote objects (resolving the
object's author for the delivery target); lock that the `Undo(Like)` path also resolves the author
correctly."

## Finding

The scenario is already fully locked end-to-end by Phase 24.1's
`LikeAnnounceUndoPropagationIntegrationTests.UndoLike_ServerDeliversToRemote_StoredOnRemoteInstance`
(2-instance `TestServer`):

1. **Step 1a:** alice (A) publishes a `Like` of bob's remote Note (B) to A's own outbox. A's
   outbox-publish handler calls `RecordLikeLocalAsync`, which records the local like edge and resolves
   the Note's author (bob) via `ResolveObjectOwnerForDeliveryAsync` — the 24.1 fix that fetches the
   remote object's document and reads its `attributedTo`. A then delivers the signed `Like` to bob's
   inbox on B.
2. **Step 1b:** B stores the `Like` activity (proving the delivery reached B — the 24.1 delivery-target
   invariant).
3. **Step 2a:** alice (A) publishes an `Undo` (of the `Like`) to A's own outbox. A's handler calls
   `RecordUndoLocalAsync` → `RemoveLikeLocalAsync`, which removes the local like edge and again
   resolves the Note's author (bob) via the same 24.1 path. A delivers the signed `Undo` to bob's
   inbox on B.
4. **Step 2b:** A's local like edge is removed.
5. **Step 2c:** B stores the `Undo` activity (proving the undo federated to B — the receiving
   `UndoActivityHandler` resolved the original `Like` from B's activity store).

The under-test invariant (the 24.1 delivery-target resolution for `Undo(Like)`) is the same as for
`Like`: `ResolveObjectOwnerForDeliveryAsync` must resolve the remote object's author so the delivery
targets the author's inbox (not the object IRI's non-existent `/inbox`). Without it, B would never
receive the `Undo` and the activity would not be stored.

No new test or code was added. Both tests in the class pass (verified: 2/2 green).
