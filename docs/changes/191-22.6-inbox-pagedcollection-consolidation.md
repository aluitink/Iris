# 191 — 22.6 Implementation sweep: consolidate the Actor-detail Inbox onto `PagedCollection`

**Phase 22.6** (implementation sweep + manual test pass), first slice.

## What changed

The **Actor detail** page's read-only **Inbox** card (US-21 "view the actor's inbox") was hand-rolling
the load / empty / error / "Load more" / next-link-walking logic that the shared
[`PagedCollection`](../../samples/SampleBlazorClient/Components/PagedCollection.razor) component
already implements. This slice consolidates it onto that component, removing the duplication.

- `samples/SampleBlazorClient/Pages/ActorDetail.razor`
  - The Inbox `<div class="card">` (its `InboxItems` / `InboxHasMore` / `InboxLoadingMore` /
    `InboxError` state, its `Loading…` / empty / error markup, its `Load more` button) is replaced by a
    single `<PagedCollection Client="…" CollectionIri="@actorIri.InboxOf()" Title="Inbox" …
    ItemTemplate="@InboxItemTemplate" />`.
  - The now-dead fields `InboxItems` / `InboxHasMore` / `InboxLoadingMore` / `InboxError` /
    `_inboxResumeFrom` and the methods `LoadMoreInboxAsync` / `EnumerateOneInboxPageAsync` are removed;
    the initial inbox load in `LoadAsync` is dropped (`PagedCollection` loads on demand).
  - A new `private static RenderFragment<IObjectOrLink> InboxItemTemplate` field renders each delivered
    activity: its ActivityStreams `type` (muted `<span>`) and `id` (`<code>`), or the relay IRI
    (`<code>`) when the entry is a bare link.
  - The `ActorIri is not null` guard becomes `ActorIri is { } actorIri` (a non-null local) so the
    `CollectionIri` attribute can call `actorIri.InboxOf()`.

## The Razor `ItemTemplate` limitation discovered (and the robust pattern)

`PagedCollection.ItemTemplate` is a `RenderFragment<T>`. Passing it as an **inline lambda attribute**
(`ItemTemplate="@(item => { … })"`) is **not reliable** in this project's net10.0 Razor toolchain:

- A multi-statement lambda body inside the attribute (with `@if` blocks / a `RenderFragment`
  declaration) breaks parsing — the compiler reports cascading `CS9348: A compilation unit cannot
  directly contain members` (the `@code` block detaches into global code). A minimal one-statement
  lambda compiles, but anything non-trivial does not.
- The `Description` parameter is a plain `string` attribute: it **cannot** contain markup tags (e.g.
  `<c>`) or a C# interpolation mixed with text — either yields `RZ9986: Component attributes do not
  support complex content`.

The **robust pattern** (used here and recommended for any `PagedCollection` custom renderer): assign the
`RenderFragment<T>` to a **`@code` field** (built with `RenderTreeBuilder`, which *can* contain
multiple statements / `if`s) and pass that field's name: `ItemTemplate="@InboxItemTemplate"`. This
compiles cleanly and keeps the item markup out of the attribute.

## Behavior parity

The Inbox card's states (loading spinner, empty "No activities delivered.", error, Load more) now come
from `PagedCollection`, identical to the Outbox / Liked cards on the same page. The read of one's own
inbox over a plain (non-owner) session returns **no pages** — the client's
`FetchAuthenticatedCollectionPageAsync` deliberately treats a 403/404 as "no readable inbox" and yields
nothing — so the card shows the coherent empty state. This is the **same** behavior the original
hand-rolled card had (it used the same `GetCollectionAsync`), so there is no regression.

## 22.6 remaining

The Community `following` / `followers` cards and the Actor-detail **mutes / blocks / flags** cards still
hand-roll paged reads. They can be consolidated the same way **once** their item markup uses only member
access or a field-based `RenderFragment<T>`; the `following`/`followers` cards render via the
`HandleOf` / `RelayIriOf` helper methods, which must move into a field-based `InboxItemTemplate`-style
`RenderFragment<T>` (the inline-attribute form will not compile). The full Phase 22.6 manual test pass
(including the external-FQDN reverse-proxy route) still stands.
