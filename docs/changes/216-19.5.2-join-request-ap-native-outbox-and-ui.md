# 216 — Join-request flow: AP-native outbox surfacing + UI

> 2026-09-03 · 19.5.2 remainder · Phase 19.5 (Community)

## What was built

The remote-actor join-request → accept flow (change 215) was complete server-side but **not
AP-native**: the Join activity was stored only in a separate join-requests store (actor IRI only),
not in the community's outbox. This meant the join activity IRI was unavailable for an AP-native
`Accept(joinIri)`/`Reject(joinIri)`, and there was no standard outbox read to discover pending join
requests.

This change makes the flow AP-native by mirroring the inbound-follow pattern:

1. **`MembershipActivityHandler`** now stores the `Join` activity in the community's outbox (when
   `manuallyApprovesMembers` is set), exactly as `FollowActivityHandler` stores inbound `Follow`
   activities. The join-requests store still tracks membership state (pending/accepted), but the
   **outbox is the AP-native source** for the activity IRI needed for Accept/Reject.
2. **`Community.razor`** gains a "Pending join requests" card (reads the community's outbox for
   `Join`-type activities, Accept/Reject via `AcceptJoinAsync`/`RejectJoinAsync`) and a "Join (as
   me)" button (publishes a `Join` to the community's inbox via `RequestJoinAsync`).

## Decisions

**Lightweight decision: the outbox is the AP-native source for pending join requests (not a
separate "join-requests" collection).**

The community's outbox already surfaces inbound follows (the `FollowActivityHandler` stores them
there). Making Join follow the same pattern keeps the community's protocol surface consistent:
inbound activities of interest (Follow, Join) are stored in the outbox, and the client reads the
outbox to discover them. No new `GET /c/{name}/join-requests` endpoint is needed. The join-requests
store (`ICommunityStore.AddJoinRequestAsync`/`GetJoinRequestsAsync`) still tracks membership state
(pending vs. accepted) so that `RecordJoinDecisionLocalAsync` can remove the pending request on
Accept/Reject — but the activity IRI for the Accept/Reject reference comes from the outbox, not the
store.

This is the same trade-off as inbound follows: the outbox is not a "pending" collection (it also
contains the community's authored activities), so the client filters for `Join`-type activities.
The filter is reliable because the community's outbox only receives `Join` activities from the
inbound path (the community never authors `Join` activities to its own outbox).
