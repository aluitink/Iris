      - **33.4 — inbound request-body size cap (Phase 33 step 4):** the production app set **no** inbound request-body limit (Kestrel's default is unbounded), so an unauthenticated inbound `POST /ap/v1/u/{handle}/inbox` (reachable by any fediverse peer) could stream an arbitrarily large body into the app's memory — a **denial-of-service vector for a public instance**. `WebAppFactory.ConfigureServices` now caps Kestrel's `Limits.MaxRequestBodySize` at **1 MiB** by default (new `WebAppFactory.DefaultMaxRequestBodySize`), overridable via `Iris:MaxRequestBodySize` (new `MaxRequestBodySizeConfigKey`; env `IRIS_MAX_REQUEST_BODY_SIZE` in `docker-compose.yml` + `.env.example`, in bytes); a non-numeric/non-positive value falls back to the default. An over-limit body is rejected by Kestrel with **413** before the pipeline reads it. **Defense-in-depth:** the inbox signature gate already rejects an *unsigned* oversized body with **401** cheaply (before the body is read — the unauthenticated DoS path is already closed); the cap is the backstop for a *signed* peer that passes the gate and streams an oversized body. **4 new integration tests** (`RequestBodyLimitIntegrationTests`) assert the resolved Kestrel options carry the expected cap (default = 1 MiB / configured 4 MiB / invalid→default / negative→default). **Verified live** in the production container (rebuilt image + redeployed `iris-web` over the persistent Postgres volume): a small unsigned inbox POST → **401** (not 413); an oversized (1.5 MiB) unsigned inbox POST → **401** (rejected before the body is buffered); `GET /ap/v1/u/alice` → **200**; `/ap/v1/health` → **200**; no 413/OOM errors in the log. `dotnet build` clean (0/0); `Iris.Web.Tests` 49/49 (45 prior + 4 new).
