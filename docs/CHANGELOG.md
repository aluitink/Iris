## Phase 1 — Core: Identity, Keys, Signatures & Caching

- `Iri` (record struct) + `Iri.Public` + `TryParse`; `IriExtensions` (`InboxOf`/`OutboxOf`/`FollowersOf`/`FollowingOf` + library `string?`/`Uri?` ↔ `Iri` boundary conversions). Unit-tested incl. relative-vs-absolute handling.
- Identity/key foundation: `KeyAlgorithm` (Rsa/EcP256), `KeyPair` (Sign/Verify SHA-256, `ExportPrivateKeyPem`, `GetPublicJwk`, RFC 7638 thumbprint, `FromPem`), `KeyPairGenerator` (RSA-2048 / EC P-256), `IIdentity` + `SystemIdentity` record.
- `IKeyStore` (put/try-get/remove) + `InMemoryKeyStore` (ephemeral, disposes evicted keys).
- `HttpRequestMetadata` (HTTP-agnostic snapshot; value-based equality; case-insensitive header lookup; `With()` for partial copies).
- HTTP-signature layer: `Signatures` (shared base/digest/algorithm-label/`Signature`-header constants), `SignatureHeader` (parse/format), `HttpSignatureSigner` / `HttpSignatureVerifier` (RSA + ECDSA). Keys are **borrowed** from the `IKeyStore` (store owns lifetime).
- `SigningProfile` enum: `ClientToServer` = `(request-target) host date`; `ServerToServer` = `+ digest content-type`. Verifier reconstructs the base from the declared `headers` list, so it accepts both.
- `ActivityJson` static helpers: single `JsonSerializerOptions` (registers the library's `ObjectOrLinkConverter`, `WhenWritingDefault`, no naming policy); content-type constants; `Serialize`/`Deserialize` overloads. Unit-tested against the wire format.
- Caching layer: `CachePolicy` (record struct + validated defaults: Actor 5m, CollectionPage 30s, Key 1h, WebFinger 15m), `CacheState` (Fresh/Stale/Expired), `CacheEntry<TValue>` (value + createdAt + captured policy; `GetState(now)`), `ICache<TValue>` (Get/TryGetEntry/Put/Invalidate/Count, keyed by `Iri`, clock injected), `MemoryCache<TValue>` (thread-safe LRU, bounded capacity, opportunistic expired-eviction, stale-while-revalidate), `CachedValue<TValue>` (lookup result), `CacheExtensions` (`Lookup`/`GetOrAdd`).
- `KeyPem.Load`/`KeyPem.Save` over `KeyPair.FromPem`/`ExportPrivateKeyPem` (PKCS#8 PEM for the `privateKey` actor-doc property). Round-trip tested for both algorithms.
- Unit tests: key generation, key sign/verify round-trip + tamper (both algos), PEM round-trip, IRI helpers, full HTTP-signature sign/verify per `SigningProfile` (both algos × both profiles, signature-base spec examples, digest, tamper detection, unknown-key/malformed-header), cache TTL/stale-while-revalidate/LRU eviction/invalidation (incl. exact-boundary behavior and expired-eviction on write).

## Phase 2 — Client Library

- `IActivityPubClient` (`GetObjectAsync` → `IObject`, `GetActorAsync` → `Actor` via pattern-match cast, `DeliverAsync` → status) implemented by `ActivityPubClient`; `IActivityPubClientFactory`/`ActivityPubClientFactory` wire a `SigningHandler` (signer + key provider over the caller's transport) into an owned `HttpClient`. `IActivityPubClient` extends `IDisposable`.
- `SigningHandler` (`DelegatingHandler`) adds `Date` + `Signature`; `ClientToServer` for bodyless GETs, `ServerToServer` (digest+content-type) for body POSTs; derives host from the request URI when no `Host` header is set. Round-trip verified against `HttpSignatureVerifier`.
- `JsonLdHandler` (content negotiation per Decision #4): bodyless requests get `Accept: application/activity+json, application/ld+json`; body requests get `application/activity+json` as `Content-Type` when unset.
- `RetryHandler`: retries only idempotent requests (GET/HEAD/OPTIONS), never POST/PUT/DELETE (avoids double-delivery); retries on 429/5xx + transient `HttpRequestException`; honors `Retry-After` (delta-seconds); exponential backoff (base 250ms, doubling) with up to 100% jitter; injectable delay + jitter source for deterministic tests; default budget 3 attempts. Factory pipeline order: `RetryHandler` → `JsonLdHandler` → `SigningHandler` → transport (retry outermost so it replays the signed request; JsonLd sets headers before signing). `ActivityPubClientOptions.EnableRetry` (default true) + `MaxRetryAttempts` (default 3). 12 handler tests. (Decision #23.)
- `IClientAuthenticator` + `BasicAuthClientAuthenticator` (Basic-auth → owner actor doc + loaded `KeyPair`; reads owner-only `privateKey` PKCS#8 PEM extension via `KeyPem`; keyId from `publicKey.id` extension else actor IRI; algorithm from the `keyAlgorithm` doc extension — Decision #20); `AuthenticatedActor` record.
- `IKeyProvider` (resolve signing `IIdentity` from an actor IRI) + `InMemoryKeyProvider` (actor→key map over `IKeyStore`; keys borrowed, never disposed).
- `WebFingerClient` (RFC 8410 lookup on the account's own host — Decision #18, `self`-link resolution, `acct:` normalization, graceful null on 404/parse failure) + `IDiscoveryService`/`WebFingerDiscoveryService`.
- Client caching: `CachingClientCache<TValue>` (generic async read-through engine over `ICache<TValue>`: `bypassCache` skips the read but writes back; stale-while-revalidate serves a stale entry immediately and refreshes in the foreground; an absent/null result is never cached so 404s retry). Four concrete caches: `ActorCache` (`IObject`, 5m), `CollectionPageCache` (`IObject`, 30s), `WebFingerCache` (`Iri` via `WebFingerHit`, 15m), `KeyCache` (`JwkKey`, 1h — Decision #21). `JwkKey` (JWK JSON + algorithm label) and `WebFingerHit` (account + actor IRI) records. **Wired into the call paths:** `ClientCaches` (record: `Actors`/`CollectionPages`/`WebFinger`) threaded through `ActivityPubClientOptions.Caches` + the factory; `GetObjectAsync`/`GetActorAsync` read through `ActorCache`, `GetCollectionAsync` reads each page through `CollectionPageCache` (honoring `CollectionQuery.BypassCache`); `WebFingerClient.ResolveActorAsync` reads through `WebFingerCache` (keyed by the normalized `acct:` subject). A null cache = no caching (straight to network). 15 cache unit tests + 8 cache-wiring unit tests.
- Rich paged collections: `CollectionPage` (Iris wrapper — contains `OrderedCollectionPage`, flattened `IReadOnlyList<IObjectOrLink> Items`, `Iri? NextPage`/`Iri? PrevPage`, `int? TotalItems`, `Iri? PageId`, `IsLastPage`); `CollectionQuery` (record: `Limit`, `BypassCache`); `GetCollectionAsync` (follow the collection's `first` link — or use the fetched object directly if it is itself a page — then follow `next` links, yielding `CollectionPage` in order; stops at `Limit` or the last page; yields nothing on 404 / non-page) and `GetCollectionItemsAsync` (flattens per-page `Items` across pages in order, respecting `Limit` *within* a page). Items deserialize from the `items` JSON key (Decision #22). 8 unit tests.
- Integration tests (client ↔ live `TestServer`): `FakeActivityPubServer` (in-process `TestServer`-backed, Decision #24) serves the actor document, WebFinger, and a two-page outbox collection, and records every request; a flaky mode returns 503 on the first hit per path. 7 integration tests drive the **real** `ActivityPubClient` (real factory, full `Retry → JsonLd → Signing` pipeline) over a genuine HTTP stack: real `Signature`/`Accept`/`Content-Type` headers, WebFinger resolution, multi-page follow, actor + page cache hit/bypass, retry on a transient 503.
- 69 client unit tests total at phase close.

## Phase 3 — Server Foundation

- Persistence interfaces: `IActorStore`, `IActivityStore`, `IFollowStore`, `IObjectStore`, `ICommunityStore`; `IPersistenceProvider` aggregates the five stores + the `IKeyStore` (the key store is the local actor's signing keys, shared with the signing infra). `IKeyStore` already lives in `Iris.Core`.
- `Iris.Server.InMemory`: `InMemoryActorStore`, `InMemoryActivityStore` (with `AddToOutboxAsync`), `InMemoryFollowStore`, `InMemoryObjectStore`, `InMemoryCommunityStore`, `InMemoryPersistenceProvider` aggregate. `AddInMemoryPersistence()` registers the seam (keeping `Iris.Server` free of a concrete persistence dep).
- `AddActivityPubServer()` + `MapActivityPubEndpoints()` — versioned route prefix (`/ap/v1`, Decision #10) + `Iris-Version` meta header on every response (group endpoint filter). `AddActivityPubServer` registers `ActivityPubServerOptions` (config), `IActorCredentialValidator` (safe no-op default), and `IKeyProvider` → `InMemoryKeyProvider`; `IPersistenceProvider` is a seam registered by the persistence package or host.
- Actor document endpoint with conditional `privateKey` inclusion (Decisions #1/#2): public by default; when authenticated (Basic auth → `IActorCredentialValidator`), the owner-only `privateKey` (PEM) + `keyAlgorithm` extensions are added. `BasicAuthCredentialValidator` parses the `Authorization: Basic` header and delegates credential validation to a host-supplied delegate (constant-time comparison). The key IRI is resolved from the actor's `publicKey.id` (carried in `ExtensionData`) or a `#key-1` fragment fallback.
- WebFinger (`acct:{handle}@{host}` → actor IRI; the instance host is derived from `BaseUri`, not the request host), NodeInfo (`/ap/v1/nodeinfo/2.0`) + NodeInfo discovery root (`/ap/v1/.well-known/nodeinfo`).
- Server caching: `CachingServerCache<TValue>` (async read-through engine: `forceRefresh` = the `?refresh=true` bypass skips the read but writes back; stale-while-revalidate serves a stale entry immediately and refreshes before returning; an absent/null result is never cached so 404s retry). Four remote object caches: `RemoteActorCache` (`IObject`, server 1h), `RemoteKeyCache` (`JwkKey`, 1h), `CollectionPageCache` (`CollectionPage`, 30s), `WebFingerCache` (`WebFingerHit`, 15m) + `ServerCaches` aggregate record. `LocalActorDocumentCache` (rendered local actor docs, 60s fresh / 300s stale — Decision #26) backs the server → client response cache. Registered in `AddActivityPubServer`; TTLs wired from `ActivityPubServerOptions.CachePolicies` (`ServerCachePolicies`; a null policy falls back to the `CachePolicy` default). The four **remote** caches are populated by the server's outbound federation paths in Phase 4; they are registered + unit-tested now so the seam is in place.
- Response `Cache-Control` on the actor document endpoint: public docs `max-age=60, stale-while-revalidate=300` (served through the local cache); owner-only (authenticated) docs `no-store` (never cached); `?refresh=true` bypass → `no-cache`.
- Integration tests (live `TestServer`, host topology per Decision #25): public actor doc, authenticated actor doc (with PEM `privateKey`), wrong-password → public doc, WebFinger resolution + unknown-handle 404, NodeInfo + discovery root, the `Iris-Version` meta header, and cache behavior (populate with `Cache-Control`, second request served from cache, `?refresh=true` bypass with `no-cache`, authenticated request `no-store` and never cached, unknown handle with `?refresh=true` still 404s). 15 live-`TestServer` tests + 12 cache unit tests = 27 Server tests.

## Phase 4 — Inbox & Delivery

### Slice log

- **Inbound signature validation.** `ISignatureValidator` + `HttpSignatureValidator` (reconstructs the signature base from the `headers` list declared in the `Signature` header, so it accepts **both** signing profiles) + `SignatureValidationMiddleware` (validates **POST** requests only — GETs are skipped to avoid recursive key-resolution bootstrap; stores the outcome in `HttpContext.Items`; unsigned/invalid → the endpoint returns 401) + `UseSignatureValidation()`. **Inbound key resolution:** `IInboundKeyResolver` + `RemoteInboundKeyResolver` resolves a remote signing key by its `keyId` → derives the actor IRI → fetches the actor document over the wire (`IActorDocumentFetcher` + `IrisActorDocumentFetcher`, signed as `InstanceActorId`; `NoopActorDocumentFetcher` degrades to no resolution when no instance actor is configured — Decision #27) → reads the `publicKey` JWK/PEM → `KeyPair.FromJwk` (public-only, verify-only) → cached in `RemoteKeyCache`. The validator verifies with the resolved key **directly** (`ISignatureVerifier.Verify(metadata, key, header)` — a new overload, since remote keys are not in the local `IKeyStore`). **Inbox endpoint:** `POST /u/{handle}/inbox` enforces a valid signature (401), 404 on unknown handle, deserializes the body (`IObjectOrLink`→`Activity` with a non-null `Id`), stores it via `PutActivityAsync`, returns 202. **Signing fix:** `SigningHandler` now sends the `Digest` header and restores `Content-Type` on the signed content so a receiver can reconstruct the `ServerToServer` base. DI registers the stack + a standalone `RemoteKeyCache`. 5 resolver unit tests + the first two-instance federation integration test (alice follows bob over live `TestServers`; B fetches A's actor doc over the wire to resolve alice's key, validates the signature, stores the activity (202); unsigned→401; tampered body (digest mismatch)→401).
- **Inbox processor pipeline + activity handler registration.** `IInboxProcessor` (stores the delivered activity, then dispatches it to the registered handler for its type) + `InboxProcessor` (default impl). **Dispatch:** prefers an *exact* `HandledActivityType` match, else walks the activity's type hierarchy to the closest base-type handler; unknown activity types are still stored (preserved, not dropped). **Handler contract:** `IActivityHandler` (non-generic surface: `HandledActivityType` + `DispatchAsync(delivery, activity, ct)` — threads the `CancellationToken`, no reflection) + `IActivityHandler<TActivity>` (the strongly-typed `HandleAsync(delivery, TActivity, ct)`) + `ActivityHandlerBase<TActivity>` (wires a typed `HandleAsync` into the non-generic dispatch; handlers only ever see their activity type). **`InboxDelivery`** record (`RecipientIri` + `Activity`): the recipient is the inbox the activity was delivered to — authoritative for a follow's target. **`FollowActivityHandler`:** records the directed follow edge (follower from the activity's `actor`; target = `RecipientIri`) in the `IFollowStore`. The inbox endpoint now hands the validated activity to the processor (a handler failure → 500). DI registers the default handlers + `IInboxProcessor` in `AddActivityPubServer`. 8 `InboxProcessor` unit tests + a federation integration test proving a signed Follow over the wire records the edge in B's `IFollowStore`.
- **Outbound delivery queue + worker.** `DeliveryJob` (a `record (Iri InboxIri, Activity Activity)`) + `IDeliveryQueue` / `InMemoryDeliveryQueue` (bounded `Channel<T>` — `EnqueueAsync`, `TryDequeueAsync`→`DeliveryJob?`, `CompleteAsync`, `Count`; `BoundedChannelFullMode.Wait`; default capacity 1000; zero-capacity = unbounded). `IDeliveryService` / `DeliveryService` — activity handlers call `DeliverAsync(inboxIri, activity)` to **schedule** a delivery (enqueues and returns immediately) or `DeliverToActorAsync(actorIri, activity)` which derives the recipient's inbox via `InboxOf()`; guards relative IRI + null activity. `DeliveryWorker` (`BackgroundService`, registered as a hosted service in `AddActivityPubServer`) pumps jobs off the queue and POSTs each to the recipient's inbox, **signed as `InstanceActorId`** via a one-off `ActivityPubClient` (built from an `IActivityPubClientFactory` + a `Func<HttpMessageHandler>` transport seam — the default is a real `HttpClientHandler`; a host/test overrides it to route deliveries, e.g. to an in-process `TestServer`). A non-2xx or transient failure is **logged and dropped** (the worker never crashes on a single bad delivery); if `InstanceActorId` is unset the worker logs a warning and idles. 12 unit tests + 3 integration tests (worker POSTs an enqueued job to a **remote** `TestServer` inbox **over the wire**; the receiving instance validates the HTTP signature by fetching the sender's actor document and stores the activity — the full outbound→inbound federation loop; `DeliverToActor` resolves the inbox; an unknown-inbox 404 is dropped without crashing the worker).
- **Delivery signs with the acting actor's key** (Decision #29). `DeliveryJob` now carries an optional `ActorIri` (the local actor performing the automated event; null = the instance actor). `IDeliveryService`/`DeliveryService` gain `DeliverAsync`/`DeliverToActorAsync` overloads that thread the acting actor through. The `DeliveryWorker` signs each job as its acting actor by sending the request with an `X-Iris-Actor` header (a per-request override the `SigningHandler` already honors — it resolves the named actor's key from the `IKeyProvider`, overriding the client's default `InstanceActorId` identity) via the new `IActivityPubClient.SendAsync` raw-request seam; a job with no acting actor omits the header and signs as the instance actor (the "system key for automated events"). `FollowActivityHandler` signs the `Accept` it schedules as the local actor being followed (`delivery.RecipientIri`), not the instance actor. 3 unit tests + `InboxProcessorTests` asserts the queued Accept's `ActorIri` is the followed local actor + a **two-actor federation integration test** (`Follow_TwoActors_AcceptIsSignedWithActingActorsKey_NotInstanceActor`): B hosts two local actors (bob = instance actor, carol = a second local actor); alice follows carol → B's `FollowActivityHandler` records the edge + schedules an Accept signed as carol → B's `DeliveryWorker` delivers it to alice's inbox over the wire → A validates the signature by fetching B's actor doc for carol (resolving carol's key) and stores the Accept. A bob-signed Accept would resolve bob's key (which does not match carol's signature) and be rejected (401), never stored — so storing it proves the delivery was signed with carol's (the acting actor's) key.
- **Follow/Accept/Reject flow end-to-end** (Decision #28). `FollowActivityHandler` (followed side) records the follow edge **and** constructs + delivers an `Accept` back to the *follower's* inbox (via `IDeliveryService.DeliverToActorAsync(followerIri, accept)`). The `Accept`/`Reject` IRIs are deterministic (`{localActorIri}/accepts/{followId}` / `{localActorIri}/rejects/{followId}`) so re-delivery is idempotent. **Two-sided follow lifecycle:** the follow edge is recorded on the *followed* side when the recipient is a **local** actor (gated by the new `ILocalActorResolver` / `DefaultLocalActorResolver`, which resolves locality from the persistence actor store); on the *follower* side the follow is **provisional** until the followed side responds — `AcceptActivityHandler` finalizes the local follow edge (records `follower → target`, the target resolved from the stored `Follow` that the `Accept`'s object references by IRI) and `RejectActivityHandler` undoes it. A remote follower's `Accept`/`Reject` is a no-op (the remote instance owns that follow). `FollowIris` centralizes the deterministic IRIs, the `Accept`/`Reject` builders, and `ResolveActorIri` (`Link`→`Href`, embedded `Object`→`Id`). **Full-loop federation integration test** (`Follow_ThenAccept_FullFederationLoop_AcceptIsDeliveredBackToAliceInbox`): alice follows bob over the wire → B's `FollowActivityHandler` records the edge + schedules an Accept → B's `DeliveryWorker` delivers the Accept to alice's inbox over the wire (signed as bob) → A validates bob's signature (fetching B's actor doc, via a `LazyHandler` that breaks the A↔B wiring chicken-and-egg) and stores the Accept (202). `IKeyProvider.RegisterKey(actorId, keyId)` is on the interface. Unit tests cover the Accept/Reject handlers (local finalizes/removes the edge; remote is a no-op; an unresolvable target is a no-op) and the `FollowActivityHandler` local-recipient guard.
- **Remote actor-doc fetch through the cache** (Decision #30). The outbound key-resolution path now reads the remote actor's **document** through the Phase 3 `RemoteActorCache` (by actor IRI, the 1h `CachePolicy.Actor` policy) instead of going straight to the network. `IrisActorDocumentFetcher` takes the `RemoteActorCache` and reads/writes it; the `IActivityPubClient` is the factory on a miss. An absent result (the client returned null) is not cached, so a later lookup retries. The `RemoteKeyCache` (key level) already sat above this in `RemoteInboundKeyResolver`, so a remote actor's document is now fetched once and reused across key resolutions and deliveries within the TTL. `RemoteActorCache` is registered standalone in DI (mirroring `RemoteKeyCache`) and reused in `ServerCaches` so the fetcher and the aggregate share one instance. 4 new `IrisActorDocumentFetcher` unit tests (miss fetches + caches; fresh hit is cached — same instance, no re-fetch; absent not cached — retried; distinct actors each fetch) + the two federation test fetcher constructions updated to pass a cache.
- **Outbound WebFinger account resolution through the cache** (Decision #31). A new `IAccountResolver` (default `WebFingerAccountResolver`) resolves a remote **account** (`bob@host`) to its **actor IRI** via WebFinger, reading through the Phase 3 server-side `WebFingerCache` (keyed by the normalized `acct:` subject IRI, 15m policy) so the account is resolved once and reused within the TTL. `forceRefresh` bypasses the read (mirrors `?refresh=true`) but writes back; an absent resolution (unknown account → 404) is not cached, so a later lookup retries. The resolver depends on a new `IWebFingerResolver` abstraction (implemented by the client's sealed `WebFingerClient`) so the server can use the client's RFC 8410 lookup without subclassing it. **WebFinger endpoint fix (federation-correctness):** the server now also serves WebFinger at the RFC 8410 standard **root** path (`/.well-known/webfinger`) — the versioned route (`/ap/v1/.well-known/webfinger`) alone was unreachable by a standard client, so an Iris instance could not resolve another Iris instance's accounts. **DI:** a standalone `WebFingerCache` is registered and reused by `ServerCaches`; `WebFingerClient` is registered (plain unsigned `HttpClient`, no `JsonLdHandler` — WebFinger is not ActivityPub) via the existing `Func<HttpMessageHandler>` transport seam; `IWebFingerResolver` → `WebFingerClient`; `IAccountResolver` → `WebFingerAccountResolver`. 5 `WebFingerAccountResolver` unit tests + 3 integration tests over a live `TestServer` (resolve a remote account over the wire + caches; `forceRefresh` re-fetches; unknown account → null).
 - **Paged local collection endpoints (outbox/followers/following)** (Decision #32). `GET /ap/v1/u/{handle}/{collection}` (`outbox`|`followers`|`following`, bound by a regex route) serves an actor's collection as a paged ActivityStreams document. **Page 1** is the `OrderedCollection` (the collection IRI `{actor}/{collection}`, with a `first` link to page 1 + `totalItems`); **page N>1** is an `OrderedCollectionPage` at `{collection}/?page=N` (with `partOf` the collection IRI, `startIndex` (1-based), `totalItems`, and `prev`/`next` — `next` omitted on the last page). (As of Phase 11 Slice 11.1, page 1 also carries a `next` link to page 2 when more pages remain — see that slice; this closed the carried-forward page-1 client/server interop gap.) Pagination via `?page` (1-based, clamped to the last page) and `?limit` (default `20`, capped at `100`, invalid → default); `?refresh=true` bypasses the read. Reads are served through the new **`LocalCollectionPageCache`** — a `CachingServerCache<string>` keyed by the **page IRI** (the rendered document string; 60s fresh / 300s stale, mirroring the local actor-document cache) — registered in DI and reused by `ServerCaches`. The response carries `Cache-Control: max-age=60, stale-while-revalidate=300`. Outbox items come from `IActivityStore.GetOutboxAsync` (newest first); followers/following are `Link`s from `IFollowStore`. `ActivityJson.Serialize` is used throughout (the library's `ObjectOrLink`/one-or-multiple converters render a single `Link` as a bare IRI and a single activity as an object; the `Link`-typed `first`/`partOf`/`prev`/`next` as IRI strings). 6 `LocalCollectionPageCache` unit tests + 7 integration tests over a live `TestServer` (page 1 ordering + `first`/`totalItems`; page 2 `prev`/`next`; last page has no `next`; out-of-range clamps to last; followers + following served as `Link` IRIs; `?refresh=true` bypasses; unknown handle → 404).
- **Remote collection fetch through the cache** (Decision #33). The server's outbound path can now fetch a single page of a **remote** actor's collection (e.g. a remote actor's `outbox`/`followers`) over the wire, reading through the Phase 3 server-side `CollectionPageCache` (keyed by the **page IRI**, the 30s `CachePolicy.CollectionPage` policy) so a page is fetched once and reused within the TTL. New `IRemoteCollectionFetcher` / `IrisRemoteCollectionFetcher`: `GetCollectionPageAsync(pageIri, forceRefresh, ct)` reads through the cache; on a miss it issues a **signed** GET (the `IActivityPubClient`'s `SendAsync` raw-request seam, signed as `ActivityPubServerOptions.InstanceActorId`), deserializes the body via `ActivityJson.Deserialize<IObjectOrLink>` (Rule 1), and flattens an `OrderedCollectionPage` into the client's `CollectionPage` (items + `next`/`prev` IRIs + `totalItems` + `PageId`). A `forceRefresh` bypasses the read (mirroring the local endpoints' `?refresh=true`) but writes the page back. An **absent** result (a non-2xx, an empty body, or a fetched object that is **not** an `OrderedCollectionPage` — e.g. the plain collection IRI, which returns the `OrderedCollection` whose `first` is the first page) is **not cached**, so a later lookup retries. **DI:** `CollectionPageCache` is registered standalone (reused by `ServerCaches`); `IRemoteCollectionFetcher` is registered as `TryAddSingleton` and **throws** when `InstanceActorId` is null (outbound fetches must be signed) — mirroring the `IrisActorDocumentFetcher` pattern. 6 unit tests (stub `IActivityPubClient` + real `CollectionPageCache` — miss fetches + caches; fresh hit cached — same instance, no re-fetch; absent not cached — retried; non-page not cached; `forceRefresh` bypasses + writes back; next/prev/total) + 3 integration tests over a live `TestServer` (signed fetch over the wire + cache; `forceRefresh` re-fetch; plain collection IRI not a page → null).
- **Announce activity handler + propagation to local followers** (Decision #34). A local actor's `Announce` (boost/repost) is now interpreted and propagated. **`AnnounceIris`** centralizes the deterministic IRI (`{announcer}/announces/{objectIri}`), the propagated-`Announce` builder (`actor`/`attributedTo` = the announcer, `object` = the announced object, `to` = the follower, `cc` = the announcer, reusing the original announce's IRI for idempotency), and `ResolveObjectIri` (Link→Href, embedded Object→Id). **`AnnounceActivityHandler`** (an `ActivityHandlerBase<Announce>`): when the recipient (the delivery's `RecipientIri`) is a **local** actor, it (1) records the announce in the recipient's outbox via the new **`IActivityStore.AddToOutboxAsync`** (newest first; the in-memory impl already had this method — it is now on the interface), and (2) propagates the announce to each of the recipient's **local** followers — for every local follower it schedules the propagated `Announce` to the follower's inbox via `IDeliveryService.DeliverToActorAsync(follower, propagated, announcer, ct)`, signed as the **announcer** (the recipient) so the follower's instance verifies it against the announcer's key (the per-actor `X-Iris-Actor` path, Decision #29). Remote recipients and remote followers are no-ops (a remote follower is the remote instance's concern); a malformed announce (no resolvable actor or object) is stored but interpreted as a no-op. **DI bug fix (Decision #34):** the activity handlers were registered with `TryAddSingleton<IActivityHandler, X>` — since `TryAddSingleton<TService, TImpl>` treats all registrations as the *same* service type, only the **first** (`FollowActivityHandler`) was registered and `AcceptActivityHandler`/`RejectActivityHandler` (and this `AnnounceActivityHandler`) were **silently dropped** from the pipeline. They are now registered with `AddSingleton<IActivityHandler, X>` (an open list; a host may add more, e.g. `Create`). 4 unit tests + 1 two-instance federation integration test (carol signs an `Announce` → B validates carol's signature via a self-loop fetch + stores it in carol's outbox → B's handler propagates it to bob's inbox over the wire signed as carol → B re-validates + stores the propagated form, to=bob/cc=carol).
- **Integration tests (cross-instance):** two in-process `TestServer` instances (distinct hostnames, `a.domain.local`/`b.domain.local`) exchanging activities with full signature validation — true instance-to-instance federation. (1) alice (A) follows bob (B): a client signed as alice POSTs to B's inbox; B validates the HTTP signature by fetching A's actor doc over the wire to resolve alice's key and checking it cryptographically, then stores the activity (202). **The inbox processor then interprets the Follow: the `FollowActivityHandler` records the edge in B's `IFollowStore`, so `bob`'s followers now include `alice` and `alice`'s following now includes `bob`** (asserted in `Follow_SignedByAlice_RecordsFollowEdgeInBobFollowStore`). Negative paths: an unsigned POST → 401; a tampered body (digest mismatch) → 401. B's `IInboundKeyResolver` resolves alice's key by fetching A's actor doc (unit-verified). (2) **Full Follow/Accept loop** (`Follow_ThenAccept_FullFederationLoop_AcceptIsDeliveredBackToAliceInbox`): a self-contained two-instance topology (fresh persistence per instance) where the Follow is delivered, B's handler records the edge + schedules an Accept, B's `DeliveryWorker` delivers the Accept to alice's inbox over the wire (signed as bob), and A validates bob's signature (fetching B's actor doc — wired via a `LazyHandler` that breaks the A↔B handler chicken-and-egg) and stores the Accept (202).

- **`Reject`-driven full-loop federation test** (Decision #35) — the last Phase 4 follow-up: the `RejectActivityHandler` was unit-tested but had no end-to-end federation test, so the `AddSingleton` DI fix (Decision #34) was not yet proven to dispatch a `Reject` through the live pipeline. New two-instance federation integration test (`Follow_ThenReject_FullFederationLoop_RejectIsDeliveredBackAndRemovesFollowEdge`): alice follows bob — A records the follow it sent (the activity, so the `RejectActivityHandler` can later resolve the follow's target, and alice's own provisional `alice → bob` edge); bob rejects it — B builds the `Reject` (deterministic IRI `{bob}/rejects/{followId}`, the local actor's explicit decision via `FollowIris.BuildReject`, not auto-generated) and delivers it to alice's inbox over the wire **signed as bob**; A validates bob's signature (fetching B's actor doc) and its `RejectActivityHandler` resolves the follow's target from A's store and removes the `alice → bob` edge from A's follow store (and, visibly, from alice's public `following` collection — the page-1 cache is invalidated before the read). This proves the full inbound `Reject` pipeline end-to-end: signature validation → store → dispatch → remove the provisional edge, and that the `RejectActivityHandler` is actually registered (a dropped handler would store the `Reject` but leave the edge in place). **Decision #35:** a `Reject` is the followed side's explicit decision and **supersedes the auto-Accept** the `FollowActivityHandler` schedules — so the test does not wire B's outbound delivery transport (the `Reject` is delivered directly, signed as bob), keeping the auto-Accept from racing the `Reject` back into alice's inbox and re-adding the edge.

## Phase 5 — Community / Group Support

- **`ICommunityStore` + in-memory implementation (+ membership):** the Phase 5 foundation. `ICommunityStore` reads/writes the community (the library's `Group` actor) by IRI and now also carries the community's **membership set**: `AddMemberAsync` (idempotent), `RemoveMemberAsync`, `IsMemberAsync` (false for an unknown community), and `GetMembersAsync` (member actor IRIs; empty for an unknown community). `InMemoryCommunityStore` is a `ConcurrentDictionary<community Iri, ConcurrentDictionary<actor Iri, byte>>` — thread-safe for concurrent membership adds, with membership **isolated per community**. This underpins the community feed and the `/c/{name}/members` endpoint. 13 unit tests (group store/retrieve + guards, membership add/remove/contains/list, per-community isolation, 50-concurrent-add thread-safety).
- **Community endpoints (document, members, inbox):** `GET /ap/v1/c/{name}` (the community = the library's `Group` actor document, addressed by its `{name}` handle — carries the standard collection links + a `members` extension), `GET /ap/v1/c/{name}/members` (member actor IRIs as a paged `OrderedCollection`/`OrderedCollectionPage`, `?page`/`?limit`, reusing the shared page renderer + the collection `Cache-Control`), and `POST /ap/v1/c/{name}/inbox` (signed federation activities addressed to the community — 401 unsigned/invalid, 404 unknown community, 400 malformed, else store + dispatch via the `IInboxProcessor`). `BuildCommunityIri` derives the community IRI from the `{name}` route segment. 7 integration tests (document shape + links + `members` extension, unknown community 404, members page 1/page 2, members unknown 404, unsigned inbox 401, unknown-community inbox 401).
- **`ICommunityFeedService` — local member posts half of the unified feed:** `CommunityFeedService` resolves the community's membership set, concatenates each member's outbox (newest first), de-duplicates by activity IRI (keep first), and sorts members ascending by IRI so the feed is deterministic/reproducible. `GET /c/{name}/feed` serves the feed as a paged `OrderedCollection`/`OrderedCollectionPage` (the shared renderer, the collection `Cache-Control`; 404 for an unknown community; an empty feed renders `items: []` + a self `first`). The community document now advertises a `feed` extension link. The **followed community content** half arrives with the community-following slice (local-only v1, per Decision #7). 6 integration tests (feed = union of member outboxes in member order; a member with an empty outbox contributes nothing; page 1 `OrderedCollection`; page 2 `OrderedCollectionPage` w/ prev/next; last page has no `next`; unknown community 404; member-less community → empty feed).
- **`CommunityInboxActivityHandler`:** the handler that records content activities (`Create`/`Like`/`Announce`) delivered to a community's inbox in each of the community's **local** members' outboxes (via `IActivityStore.AddToOutboxAsync`, newest first), so the `ICommunityFeedService` (which merges member outboxes) surfaces the followed content alongside member posts. Local-members-only (a remote member's instance receives the content via its own federation path); a non-community recipient is a no-op. Registered in DI with the other `IActivityHandler`s. 9 unit tests (records to one + multiple local members, Like/Announce, newest-first, remote-member skipped, unknown-community no-op, no-members no-op, null guards).
- **Community following:** a `Group` actor (community) follows a remote actor (Decision #36). **`ICommunityStore`** gains the community's **follows set** (`GetFollowsAsync`/`AddFollowAsync`/`RemoveFollowAsync`; the in-memory impl is a `ConcurrentDictionary<community Iri, HashSet<actor Iri>>`). **`FollowActivityHandler`** now handles a community recipient: when the follow's `RecipientIri` is a **local community** (a `Group`, which is *not* in the `IActorStore`), it records the follow in the community's follows set (`AddFollowAsync` — the community follows the follower, Decision #36) instead of a person-follow edge, and delivers the `Accept` to the follower's inbox in either case. The local-recipient guard checks the community store **first**, then falls through to `ILocalActorResolver` (a `Group` would otherwise be misclassified as remote). **`CommunityIris`** centralizes the community's deterministic `Accept` IRI + builder. 7 follows-set unit tests, 1 follow-handler community test, and 3 **two-instance federation integration tests** (a follow of a community is recorded in B's follows set + an `Accept` is delivered back; content delivered to the community inbox is recorded in the local member's outbox and surfaced in the community feed; content to an unknown community inbox is not propagated).
 - **Client: `GetCommunityFeedAsync(Iri communityId, FeedFilter?)`** — works identically to personal feeds. `IriExtensions.FeedOf` derives the feed IRI (`{community}/feed`); the method is a thin wrapper over `GetCollectionItemsAsync(communityId.FeedOf(), …)`, so the same paged-collection enumeration + `CollectionPageCache` semantics apply. 2 unit tests (derives the `/feed` IRI and flattens items across pages; unknown community 404 → yields nothing). *Note (historical):* at this slice the client's `FetchCollectionPageAsync` accepted only an `OrderedCollectionPage` first page, so the test modeled the wire format the client consumes; the Iris server serves page 1 as an `OrderedCollection`. The resulting client/server page-1 interop gap was **closed in Phase 11 Slice 11.1** (server page-1 `OrderedCollection` now emits a `next` link; the client reads it to walk past page 1).
- **Specialized collections — `/c/{name}/search` + `iris:capabilities`:** `/c/{name}/search`, a **case-insensitive search** over the community's content (the feed surface: the union of the local members' outbox activities, newest first, de-duplicated by activity IRI). The search matches an activity's own `content`/`name` and, for activities, the `content`/`name` of each referenced object (e.g. a `Create`'s `Note`); an **empty/whitespace `?q`** matches all items (the feed, unfiltered). Paging uses the **shared `limit`/`offset` shape** (Decision #6): `?offset` (0-based, default 0, negative clamped) + `?limit` (bounded); page 1 (offset 0) is an `OrderedCollection` (self `first` + a `next` extension when more pages remain), page N>1 an `OrderedCollectionPage` (`partOf`/`prev`/`next`, `next` omitted on the last page), `totalItems` the full match count. A non-empty query records the query under an **`iris:searchQuery`** extension (in the configurable namespace). **`ICommunityFeedService`** gains `SearchCommunityAsync(communityIri, query, ct)`. **`iris:capabilities`** (Decision #11) now appears on the community document as a capability array `[feed, members, search]` under the **configurable `NamespaceIri`** (Decision #9) — the canonical default `https://iris.example/ns#` when unset (Decision #1); the community document also carries a `search` extension link alongside `members`/`feed`. **`ActivityPubServerConstants`** gains `DefaultCapabilitiesNamespaceIri`, `CapabilityFeed`/`CapabilityMembers`/`CapabilitySearch`, `CapabilitiesTerm`, `OffsetQueryParameterName`. 9 integration tests (`CommunitySearchIntegrationTests` — case-insensitive content match, empty query = all, no-match = empty, page 1 `next`, page 2 `OrderedCollectionPage` w/ prev/next, last page no `next`, offset-beyond-end empty page, unknown community 404, `iris:capabilities` array + `search` link).
- **Integration tests (cross-instance):** `CommunityFollowingIntegrationTests` — a two-instance federation topology (alice on A, bob + community `iris` on B). (1) `Community_FollowOfRemoteActor_RecordsCommunityFollow`: alice (A) follows the community (B) → B validates alice's signature and stores the follow → B's `FollowActivityHandler` records the follow in the community's follows set (the community follows alice) + delivers an `Accept` back to alice's inbox over the wire (asserted on the follow edge, the effect of the delivery). (2) `RemoteContent_ToCommunityInbox_PropagatesToMemberAndAppearsInFeed`: a `Create` from alice is delivered to B's community inbox → B's `CommunityInboxActivityHandler` records it in the local member bob's outbox → the note appears in the community feed (`GET /c/iris/feed`). (3) `Content_ToUnknownCommunityInbox_IsNotPropagated` (404 guard).
- **Community `following`/`followers` collections + community-follows-community:** `GET /ap/v1/c/{name}/{collection}` (`following`|`followers`, bound by a regex route) — a community (a `Group`) is followed (and follows) actors and other communities the same way a person is, so it carries the same `following`/`followers` collections, mirroring the actor collection endpoint (`/u/{handle}/{collection}`). **`following`** is backed by the community's follows set (`ICommunityStore.GetFollowsAsync` — the community follows the follower, Decision #36); the items are the followed actors'/communities' IRIs as `Link`s. **`followers`** serves the empty collection (a follow of a community records an edge in the community's *follows* set, not a followers set, so there is no followers set for a community to serve). Paged via the shared `?page`/`?limit` shape (page 1 = `OrderedCollection` with self `first`; page N>1 = `OrderedCollectionPage` with `partOf`/`prev`/`next`); unknown community → 404; the response carries the collection `Cache-Control`. **Community-follows-community** is end-to-end over the wire with **no new production code beyond the collection endpoint**: a `Group` is an `Actor`, so the inbound `IActorDocumentFetcher`/`RemoteInboundKeyResolver`/`IActivityPubClient.GetActorAsync` already resolve a community-as-follower's key by fetching its document (the `publicKey` JWK is read from the `Group` doc) and validate its signed `Follow`/`Create` uniformly; the outbound `Follow` is signed by the local community's key (registered in the `IKeyStore`+`IKeyProvider`) via the existing per-actor delivery path. 4 **two-instance federation integration tests** (`CommunityFollowsCommunityIntegrationTests` — a community `Follow` of a remote community is recorded in the local community's follows set (not membership); the `following` collection is queryable — A's shows the edge, B's is empty (one-sided, no Accept worker on A) — and `followers` is empty both sides).

## Phase 6 — Proxy Fallback

- **Server `POST /ap/v1/proxy/{target}` endpoint** (Basic auth → identify actor → sign with actor's key → forward). The catch-all route is `/proxy/{**target}` (route value key `target` — Decision #37); the proxy relays the client's `Accept`, signs the forwarded `GET` as the authenticated actor via the per-actor `X-Iris-Actor` override (the `SigningHandler` resolves the actor's key), and relays the remote response's status/body. The outbound transport is the `Func<HttpMessageHandler>` seam (a test routes it to another in-process `TestServer`).
- **Client `ProxyFallbackHandler`** (outermost pipeline stage; a 401/403 on the direct attempt is retried via `POST {proxyBase}/ap/v1/proxy/{target}` with Basic auth). A successful direct response (or any non-401/403 outcome) is returned unchanged; a proxy failure is returned as-is (no loop). Wired via `ActivityPubClientOptions.ProxyBaseUrl` + `ProxyCredentials`.
- **Rate limiting + target allowlist.** `IProxyTargetPolicy` (allowlist: exact hostname, empty = allow all; rejects non-http(s)) + `RateLimitingProxyPolicy` (per-actor fixed-window, 1 minute) composed by `CompositeProxyTargetPolicy` (first rejection wins). A rate-limit rejection → 429; an allowlist rejection → 403. Configured via `ActivityPubServerOptions.ProxySettings`.
- **Integration tests:** `ProxyFallbackIntegrationTests` (two-instance `TestServer` harness; the happy-path signed-forward, allowlist 403, rate-limit 429, and unknown-actor 401 — the proxy's signed `GET` is validated by the remote `TestServer`'s `SignatureValidationMiddleware` exactly as a direct federation request). `ProxyFallbackHandlerTests` (unit: 401/403 fallback, no-fallback on success/404, proxy-failure no-loop, `Accept` relay).

## Phase 7 — Blazor Client Extensions & Samples

## Resolved Decisions

1. **Private key format in actor doc**: **PEM**. The `privateKey` property on the authenticated actor document carries a PEM-encoded private key (PKCS#8 for RSA, SEC1/PKCS#8 for EC). PEM loads directly into `RSA`/`ECDsa` via `ImportPkcs8PrivateKey`/`ImportFromPem`-style helpers — no JWK→parameter loader needed. The public key remains JWK in the standard `publicKey` field (ActivityPub convention).
2. **`privateKey` property name**: **`privateKey`** confirmed. Non-standard extension of the actor document, served only to authenticated owners with `Cache-Control: no-store`.
3. **Pagination**: `OrderedCollectionPage` with `next`/`prev`, **default page size 20**.
4. **Content types**: **flexible** — produce `application/activity+json`; accept `application/activity+json` and `application/ld+json` on inbound. Content negotiation is lenient, not locked to a single type.
5. **Client key lifetime**: **in-memory for v1** (lost on page refresh; user re-authenticates — acceptable for Basic auth). Revisit with OAuth2.
6. **Collection & feed format**: **all collections share one `limit`/`offset`-style pagination shape** (backed by `OrderedCollectionPage` `next`/`prev`). Rather than invent a custom feed format, we **extend the ActivityStreams schema** to support search/sort parameters, and/or expose **specialized collections** off actors/communities (e.g. `/c/{name}/feed`, `/c/{name}/search`) that implement specialized searching/sorting. Our own namespace (e.g. `iris:` terms) acts as the **capability indicator** — a client that sees an `iris:`-namespaced collection link knows the server supports the extended search/sort semantics. Standard `OrderedCollectionPage` remains the wire format for federation compatibility.
7. **Community propagation model**: **(b) local-only** for v1 — the community feed is a local aggregation; federation happens at the community-follow level, not per-post.
8. **Cache TTLs**: **configurable per-deployment** via `CachePolicy`/options. Defaults as listed (actors 5min client / 1hr server, pages 30s, keys 1hr) are the starting point.
9. **Configurable namespace base**: the `iris:` namespace IRI is **configurable per-deployment** (an option, e.g. `options.NamespaceIri`). Forks may extend the namespace with additional terms/capabilities later without breaking the base. The default is a canonical Iris IRI; a fork overrides it.
10. **API versioning via route prefix**: versioning is an **early, first-class design decision** using a **route prefix** (e.g. `/ap/v1/...`) rather than a post-hoc change. A version header (e.g. `Iris-Version`) is also emitted as **meta information** for observability/interop, but the route prefix is the authoritative versioning mechanism. New major versions add a new prefix; existing prefixes stay stable.
11. **`iris:capabilities` on collections**: a custom **`iris:capabilities`** property (in the configurable namespace) on a collection/actor/community document **declares what is available** on that collection (e.g. `search`, `sort`, `filter`, `feed`). This is the discovery mechanism for specialized collections — a client reads `iris:capabilities` to know which extended query params / sub-collections the server supports.
12. **Mastodon live test — deferred**: the live Mastodon compatibility suite is **saved for far later**, after instance-to-instance viability is first confirmed with our own in-process servers. When we get there, it runs against a **Dockerized Mastodon** in a **fully isolated, routable Docker-composed test environment** (our server instance + Mastodon + any relay on an internal network with routable hostnames).
13. **Multi-instance test topology**: **start with 2 servers** for basic federation, using simple hostnames **`a.domain.local`** and **`b.domain.local`**. **Plan for N servers** to support relay/fan-out scenarios (the harness must scale to N instances with distinct `*.domain.local` hostnames).
14. **Key lifetime in signing**: a `KeyPair` wraps a non-clonable `AsymmetricAlgorithm`, so it **cannot be safely shared by reference across independent owners**. The `IKeyStore` is the single owner; `HttpSignatureSigner`/`HttpSignatureVerifier` **borrow** the key (never dispose it). A `KeyPair` created outside a store (e.g. by `KeyPairGenerator`) must be disposed by its creator.
15. **Algorithm label placement**: the `algorithm` value (`rsa-sha256` / `ecdsa-p256-sha256`) is carried in the `Signature` header, **not** folded into the signature base (which is built only from the declared `headers` list, per draft-cavage-03). Verification is by the key's actual algorithm; the label is informational and must match the key type.
16. **Cache clock injection**: `ICache<TValue>`/`MemoryCache<TValue>` take an explicit `nowUtc` on read/write (and an injectable `clock` on the constructor) rather than calling `DateTime.UtcNow` internally. This makes TTL / stale-while-revalidate / LRU-eviction **deterministic in unit tests** (no sleeps). The default `clock` is `DateTime.UtcNow`, so production callers get real time.
17. **Cache eviction policy**: `MemoryCache<TValue>` is a **bounded LRU** (capacity default 1024). Expired entries are evicted **opportunistically on write** (best-effort pass from the LRU end); stale entries are never evicted by time alone — they are served (stale-while-revalidate) until they cross the `StaleFor` window, at which point the next read returns a miss and evicts them.
18. **WebFinger base URL**: the WebFinger query is issued against the **account's own host** (derived from the `acct:` URI, e.g. `https://b.domain.local/.well-known/webfinger?resource=acct:bob@b.domain.local`), *not* the `HttpClient`'s `BaseAddress`. This matches the RFC 8410 / ActivityPub §3 rule that WebFinger is resolved on the domain that owns the account, and keeps the client correct for multi-domain federation without requiring a pre-set base address.
19. **Signing host derivation**: when an outgoing `HttpRequestMessage` has no explicit `Host` header, the `SigningHandler` derives the `host` signature component from the request URI's authority. An explicit `Host` header (virtual hosts / SNI) always takes precedence.
20. **Key algorithm round-trip**: both RSA and EC private keys are exported as identical PKCS#8 `-----BEGIN PRIVATE KEY-----` PEM (`.ExportPkcs8PrivateKeyPem()`), so the algorithm **cannot be inferred from the PEM header**. The actor document therefore carries a `keyAlgorithm` extension field (values `rsa` / `ecdsa-p256`) alongside `privateKey`; `BasicAuthClientAuthenticator` reads it to load the key with the correct `KeyAlgorithm`, defaulting to RSA when absent. (A deployment that exports EC as SEC1 `-----BEGIN EC PRIVATE KEY-----` would still be mis-detected — Iris standardizes on PKCS#8 + the explicit `keyAlgorithm` field.)
21. **Client `KeyCache` value type**: the **client** `KeyCache` maps `Iri (keyId) → JwkKey` (JWK JSON + algorithm label), *not* a `KeyPair`. A client only ever holds the **public** key material it fetched from a remote actor's `publicKey` link (needed to verify inbound signatures); it never has the private half, so caching a full `KeyPair` would be wrong. (The **server** key cache, Phase 3, caches over `IKeyStore`/`KeyPair` for its own actors.) `JwkKey` is a small record carrying the raw JWK JSON plus the `Signature`-header algorithm label, with `ToElement()` for parsing.
22. **`OrderedCollectionPage` items JSON key**: the `KristofferStrube.ActivityStreams` library deserializes `OrderedCollectionPage.Items` from the **`items`** JSON key (not `orderedItems`). The library's `Items` property carries a `[JsonPropertyName("items")]` mapping. Iris collection documents therefore emit/expect **`items`** on pages (the library's wire form). The ActivityStreams spec's `orderedItems` is *not* what this library reads — using it yields an empty `Items`. (If a remote federated server emits `orderedItems` instead, the client will see zero items; this is a known interop gap to revisit if it bites in live federation testing.)
23. **Client retry policy & pipeline order**: the client retries **only idempotent** requests (GET/HEAD/OPTIONS) — never POST/PUT/DELETE — because replaying an activity `DeliverAsync`/`Follow`/`Accept` would double-post. Retriable conditions: HTTP 429/500/502/503/504 and transient `HttpRequestException` (connection reset / timeout). `Retry-After` (delta-seconds) is honored when present; otherwise exponential backoff (base 250ms, doubling) with up to 100% additive jitter. Default budget is 3 total attempts, configurable via `ActivityPubClientOptions.MaxRetryAttempts`; `EnableRetry` (default true) toggles the handler. **Pipeline order** is `RetryHandler` → `JsonLdHandler` → `SigningHandler` → transport: retry is outermost so it replays the *fully signed* request (a fresh signature is produced each attempt); `JsonLdHandler` sets `Accept`/`Content-Type` *before* `SigningHandler` reads the content type into the signature base.
24. **Client integration-test topology (pre-Phase-3)**: because the real `Iris.Server` has no endpoints until Phase 3, the Phase 2 client integration tests use a **`FakeActivityPubServer`** — a minimal in-process `TestServer` that serves only the endpoints the client reads (actor doc, WebFinger, a two-page outbox collection) and records every request. It is a *fake* (no signature validation, no persistence): its job is to serve well-formed ActivityPub documents so the **real** `ActivityPubClient` (built by the real `ActivityPubClientFactory`, full `Retry → JsonLd → Signing` pipeline) can be proven end-to-end over a genuine HTTP stack — real `Signature`/`Accept`/`Content-Type` headers, WebFinger resolution, multi-page follow, cache hit/bypass, and retry on a transient 503 (via a flaky mode that 503s the first hit per path). True **inbound signature validation** and the **Basic-auth → owner-only `privateKey` (PEM)`** flow require a full-fidelity server and are deferred to Phase 3/4.
25. **Server integration-test host topology**: `WebApplication` does not implement `IWebHost`, and `new TestServer(webApplication)` is not a supported overload, so the Phase 3 server integration tests build the host with **`WebHostBuilder`** and pass the *builder* to `new TestServer(IWebHostBuilder)` (the `IWebHost`/`IServiceProvider` overloads are not usable here). Because the `IApplicationBuilder` handed to `Configure` does **not** implement `IEndpointRouteBuilder` (verified on .NET 10 — `typeof(IEndpointRouteBuilder).IsAssignableFrom(typeof(IApplicationBuilder)) == false`), `MapActivityPubEndpoints(IEndpointRouteBuilder)` cannot be called directly on it. The tests therefore call `webApp.UseRouting();` + `webApp.UseEndpoints(endpoints => endpoints.MapActivityPubEndpoints());`, which requires `services.AddRouting()` in `ConfigureServices`. (The `ASPDEPR004`/`ASPDEPR008` obsolete-API warnings from the `WebHostBuilder` path are suppressed in the test project via `<NoWarn>`.) The `Iris-Version` meta header is added by a `RouteGroupBuilder` endpoint filter on the `/ap/v1` group, so it applies to every mapped endpoint automatically.
26. **`CachePolicy.StaleFor` semantics — total usable window, not an additional window**: `CacheEntry.UsableUntilUtc = CreatedAtUtc + StaleFor` (and `FreshUntilUtc = CreatedAtUtc + Ttl`), so an entry is *fresh* for `Ttl` and *usable-but-stale* until `StaleFor` **measured from creation** — the stale window is the interval `(Ttl, StaleFor]`. This means `StaleFor` must be **≥ `Ttl`** for a non-empty stale window; a policy with `StaleFor == Ttl` (e.g. the default `CachePolicy.Actor` = 5m/5m) has **no stale window** (an entry goes fresh → expired at the same instant). The `CachePolicy` doc comments ("5 minutes fresh, *then* stale for 5 minutes") describe `StaleFor` as an *additional* window and are **misleading** relative to the implementation — the implementation (and the Core `CacheEntryTests`) are the source of truth. Consequence for the server: `LocalActorDocumentCache` uses `CachePolicy.Create(60s, 300s)` (not 60s/60s) so the HTTP `stale-while-revalidate=300` has a real 240s stale window; the four remote caches use the `CachePolicy` defaults (no stale window), which is fine — their primary value is the fresh-window cache + the `?refresh=true` bypass, and Phase 4 can switch them to a `StaleFor > Ttl` policy if background revalidation is wanted. (The Core doc comments will be corrected in a follow-up; not blocking Phase 3.)
27. **Inbound key reconstruction + outbound federation identity**: (a) A server validating an **inbound** federation request resolves the remote signing key by fetching the sender's actor document and reading its `publicKey` **JWK**, then reconstructing a **public-only** `KeyPair` via the new `KeyPair.FromJwk(jwkJson, algorithm, keyId)` (verify-only — it has no private half, so `Sign` throws `CryptographicException`). This is the inbound counterpart to `GetPublicJwk`. (b) The validator verifies with the resolved key **directly** via the new `ISignatureVerifier.Verify(metadata, key, signatureHeader)` overload — it does **not** route the remote key through the local `IKeyStore` (a remote actor's key is not in the local store; an earlier `SingleKeyStore` adapter was tried but the DI-registered verifier used its *own* store, so the remote key was never found — the direct-key overload is the correct seam). (c) The server's **outbound** federation fetches (e.g. fetching a remote actor's document to resolve their key) are signed as the instance's **`ActivityPubServerOptions.InstanceActorId`** (an "instance actor" identity); when no instance actor is configured, the default `IActorDocumentFetcher` degrades to a no-op (`NoopActorDocumentFetcher`) and remote signatures fail validation (the instance can still serve its own endpoints, but cannot validate remote-signed requests). A host that sets `InstanceActorId` gets full inbound key resolution.
28. **Two-sided follow lifecycle — the follow edge is provisional on the follower until accepted**: an inbound `Follow` is interpreted by the **followed** side's `FollowActivityHandler`, which records the `follower → recipient` edge only when the recipient (the delivery's `RecipientIri`) is a **local** actor (resolved by `ILocalActorResolver` / `DefaultLocalActorResolver`, which consults the persistence `IActorStore`). The handler then schedules an `Accept` (deterministic IRI `{recipient}/accepts/{followId}`) to the follower's inbox. On the **follower** side the follow is *provisional*: the inbound `Accept` is handled by `AcceptActivityHandler`, which finalizes the edge (records `follower → target`, the target read from the stored `Follow` that the `Accept`'s object references by IRI), and the inbound `Reject` is handled by `RejectActivityHandler`, which removes it. In both follower-side handlers the *follower* is the delivery's `RecipientIri` (the inbox the response was delivered to) — **not** the response's `Actor` (which is the followed side). A `Accept`/`Reject` whose follower is a **remote** actor is a no-op (the remote instance owns that follow's state). Rationale: this mirrors the ActivityPub two-sided handshake (follow → accept/reject) and keeps each instance authoritative for its own actor's following set, while still recording the edge immediately on the followed side so followers are visible even before the follower's instance processes the Accept.
29. **Per-actor delivery signing via the `X-Iris-Actor` request header (not a per-request client):** outbound federation deliveries are signed as the **acting actor** — the local actor performing the automated event (e.g. the local actor being followed in a `Follow` → `Accept`) — rather than always as the instance actor. Mechanism: the `DeliveryJob` carries an optional `ActorIri`; the `DeliveryWorker` sends the delivery with an `X-Iris-Actor` header set to that actor, which the client's `SigningHandler` already honors as a per-request override of its default `InstanceActorId` identity (it resolves the named actor's key from the `IKeyProvider`). When the job has no acting actor (`ActorIri` is null) the header is omitted and the delivery is signed as the instance actor — the "system key for automated events" (e.g. an `Announce` by a system actor). This reuses the existing `SigningHandler` override + `IKeyProvider` seam rather than constructing a per-request `ActivityPubClient` (which would rebuild the whole `RetryHandler`→`JsonLdHandler`→`SigningHandler` pipeline per delivery — wasteful, and would need a `keyId` that only the key provider knows). The worker needs a raw request seam for this, so `IActivityPubClient` gained `SendAsync(HttpRequestMessage, ct)` (the pipeline still signs the request; the worker just controls the acting-actor header). Rationale: a remote receiver validates an inbound activity's signature by the activity's **actor** (it fetches that actor's document and checks the `keyId` against it), so a delivery must be signed with the acting actor's key to pass validation — a delivery signed as the instance actor for an event performed by a different local actor would be rejected.
30. **Two-level remote-object caching: the actor document and the key are cached separately.** The outbound key-resolution path caches at **two levels**: the remote actor's **document** (the `Actor`/`IObject` fetched over the wire) in `RemoteActorCache` (by actor IRI), and the derived **key** (a `JwkKey`) in `RemoteKeyCache` (by key IRI). The key cache sits *above* the document cache: `RemoteInboundKeyResolver` reads the key from `RemoteKeyCache`, and on a miss its factory fetches the actor document — which `IrisActorDocumentFetcher` itself serves from `RemoteActorCache`. Both are populated by the same outbound fetch, so a remote actor's document is fetched once and reused: the document feeds the key extraction, and the key (once cached) lets subsequent resolutions skip the document read entirely. The two caches are keyed differently (actor IRI vs key IRI) and have independent TTLs (`CachePolicy.Actor` 1h vs `CachePolicy.Key` 1h), so a key rotation invalidates the key entry while the (stale-able) document entry remains. Caching the document — not just the key — means a later path that needs the full document (e.g. reading an actor's `inbox`/`outbox` endpoints for delivery) reuses the same fetch rather than re-hitting the wire. (The `CollectionPageCache` and `WebFingerCache` follow the same read-through pattern in their respective future slices.)
31. **WebFinger is served at the RFC 8410 root path, not (only) under the versioned prefix.** RFC 8410 defines the WebFinger well-known URI at the host root — `https://{host}/.well-known/webfinger?resource=acct:…` — which is the path every ActivityPub client queries to resolve an account. Iris's versioned route (`/ap/v1/.well-known/webfinger`) was unreachable by that standard client path, so an Iris instance could not resolve *another* Iris instance's accounts (the integration test returned 404). The fix is to **also** map `/.well-known/webfinger` at the endpoint root (the versioned route is retained for symmetry). This is a federation-correctness requirement, not a preference: without the root path, outbound account resolution — the entry point for every cross-instance interaction (follow, fetch a remote actor, deliver to a discovered inbox) — fails against any conformant server.
32. **Local collection pages are cached by *page* IRI, and page 1 is the collection itself.** An actor's `outbox`/`followers`/`following` is served paged: page 1 is the `OrderedCollection` document at the collection IRI (`{actor}/{collection}`) and carries the `first` link; page N>1 is an `OrderedCollectionPage` at the *query-string* page IRI `{collection}/?page=N`. Because each page has a distinct, stable IRI, the server→client `LocalCollectionPageCache` (a `CachingServerCache<string>` of the rendered document) is keyed by that **page IRI** — so each page is rendered and cached independently, and a client re-reading a page within the TTL (60s fresh / 300s stale) is served from the cache with `Cache-Control: max-age=60, stale-while-revalidate=300`. `?refresh=true` bypasses the read (mirroring the actor-document cache) and `?page` is clamped to the last page. Caching by page IRI (not collection IRI + page number as a composite key) keeps the cache key a single `Iri` — the same shape as every other Iris cache — and matches how a client actually addresses pages.
33. **The remote-collection fetch reads through the same `CollectionPageCache` the client uses, keyed by page IRI.** The server's outbound remote-collection fetch (`IrisRemoteCollectionFetcher`) does **not** keep its own page cache — it reads through the Phase 3 server-side `CollectionPageCache` (a `CachingServerCache<Iris.Client.CollectionPage>` keyed by the page IRI, the 30s `CachePolicy.CollectionPage` policy), the same cache the client's `GetCollectionAsync` would populate. Rationale: (a) a remote page is fetched **once** regardless of which outbound path needs it (the key-resolution path, a future feed path, a manual fetch) — the cache is the single source of truth for "have we seen this page in the last 30s?"; (b) the cache value is the client's flattened `CollectionPage` (items + next/prev IRIs), not the raw `IObject`, so any caller can follow the page's `NextPage` link without re-deserializing; (c) an **absent** result — a non-2xx, an empty body, or a fetched object that is not an `OrderedCollectionPage` (notably the plain collection IRI, which returns the `OrderedCollection` whose `first` is the first page) — is never cached, so a 404 or a not-yet-a-page result retries on the next lookup (mirroring the actor-document and WebFinger caches). Because the cache is shared, the `CollectionPageCache` is registered **standalone** in DI (not just inside `ServerCaches`) so both the `ServerCaches` aggregate and the `IrisRemoteCollectionFetcher` resolve the **same instance** — the same pattern used for `RemoteActorCache`/`RemoteKeyCache`/`WebFingerCache`.
34. **Activity handlers are registered with `AddSingleton` (not `TryAddSingleton`), and an `Announce` is propagated to the announcer's local followers.** (a) **DI bug:** `services.TryAddSingleton<IActivityHandler, FollowActivityHandler>()` + `…AcceptActivityHandler()` + `…RejectActivityHandler()` registered only the **first** handler — `TryAddSingleton<TService, TImpl>` keys the registration on the *service* type (`IActivityHandler`), so the 2nd and 3rd registrations were treated as duplicates and **skipped**. The `InboxProcessor` (which injects `IEnumerable<IActivityHandler>`) therefore never saw `Accept`/`Reject`, so the follower-side finalize/undo was silently dead (only the followed-side `Follow` edge was recorded). The fix is `AddSingleton<IActivityHandler, X>` for each distinct handler — an **open list** a host may extend (e.g. register a `Create` handler). (b) **`Announce` propagation model:** an inbound `Announce` addressed to a **local** actor is (1) recorded in that actor's outbox (`IActivityStore.AddToOutboxAsync`, newest first) and (2) propagated to each of that actor's **local** followers' inboxes, signed as the **announcer** (the recipient — the per-actor `X-Iris-Actor` path, Resolved #29), so the follower's instance verifies it against the announcer's key. The propagated copy **reuses the original announce's IRI** (`{announcer}/announces/{object}`) — idempotent: the same boost delivered to N followers, or redelivered on retry, is the same activity, so a follower that stores by IRI does not accumulate duplicates. Propagation is **local-follower-only**: a local follower's inbox is delivered by this instance's `DeliveryWorker`, whereas the ActivityStreams `Announce` type (and this library) exposes no resolvable `sharedInbox`, so a remote follower is skipped (the remote instance receives the boost via its own federation path). This is the in-scope, verifiable behavior; a future phase can extend to shared-inbox fan-out for remote followers (see Phase 9+).
35. **A `Reject` supersedes the auto-Accept the `FollowActivityHandler` schedules.** The `FollowActivityHandler` (followed side) records a follow and *always* schedules an `Accept` back to the follower — there is no separate "reject" code path on the followed side. A `Reject` is therefore the followed side's **explicit, operator-driven** decision (built with `FollowIris.BuildReject`, deterministic IRI `{follower}/rejects/{followId}`) that **supersedes** the auto-Accept: when both an `Accept` and a `Reject` for the same follow reach the follower's inbox, the `Reject` (the later, deliberate signal) is authoritative — it removes the provisional `follower → target` edge. Consequence for the full-loop federation test: wiring the followed instance's outbound delivery transport would let its auto-Accept race the `Reject` back into the follower's inbox (via the `DeliveryWorker`), and the `AcceptActivityHandler` would re-add the edge the `Reject` just removed — a non-deterministic outcome. The test therefore delivers the `Reject` directly (signed as the followed actor) and does not wire the followed instance's delivery transport, so the `Reject` is the only response that reaches the follower's inbox. (A future phase with an explicit follow-approval model could drop the auto-Accept in favor of a manual approve/reject, removing the collision entirely.)
36. **A follow of a community records an edge in the community's *follows* set (not the person-follow store), and the community's followed content is recorded in the local members' outboxes.** A `Group` (community) is a local actor per the `ICommunityStore`, *not* the `IActorStore`, so the `FollowActivityHandler`'s local-recipient guard must check the community store **first** (a `Group` IRI would otherwise be misclassified as remote by `ILocalActorResolver` and the follow dropped). When the follow's `RecipientIri` is a local community, the directed edge `community → follower` is recorded in the community's **follows set** (`ICommunityStore.AddFollowAsync`), *not* the `IFollowStore` person-follow edge — a community "follows" the follower (it subscribes to the follower's content), which is the reverse of a person being followed. The two cases are disjoint (an IRI is either a community or a person), so the `Accept` is delivered to the follower's inbox in either case. Following a community is **not** a membership grant (membership is a separate, locally-administered set). The followed content reaches the community's members via the **`CommunityInboxActivityHandler`**: content activities (`Create`/`Like`/`Announce`) delivered to the community's inbox are recorded directly in each **local** member's outbox (`IActivityStore.AddToOutboxAsync`, newest first), so the `ICommunityFeedService` (which merges member outboxes) surfaces it alongside member posts. This is done *directly* (recorded in the outbox) rather than by scheduling a delivery to the member's inbox — the members are local (their outboxes *are* the local store, and the feed reads the outbox), and scheduling a delivery to a local member's own inbox would be circular and would require pumping the local delivery queue. Remote members are skipped (their instance receives the content via its own federation path).
37. **The proxy catch-all route value is keyed by the parameter name (`target`), and the route template must be `/proxy/{**target}`.** Two ASP.NET Core routing gotchas surfaced while building the Phase 6 proxy endpoint. (a) The **catch-all** route parameter is named by the template segment: `group.MapPost("/proxy/{**target}", …)` binds the entire remaining path (the absolute target IRI, slash-containing) to the route value key **`target`** — *not* the route segment name `proxy`. A handler that reads `context.Request.RouteValues["proxy"]` gets `null` and 404s; it must read `RouteValues["target"]`. (b) The catch-all name in the template must be **`{**target}`** (explicit braces around the catch-all name). A bare `**target` (no braces) is not a valid catch-all in a .NET 10 route template and matches nothing (every request 404s). Note the related, distinct trap: registering the *same* template on a group and directly on the endpoints builder is a route **ambiguity** (500 `DefaultEndpointSelector.ReportAmbiguity`), not a 404 — so the proxy route is mapped once, on the `/ap/v1` group.
 39. **Sample Docker topology (Phase 8): two same-image `SampleServer` instances on a routable bridge network; the Blazor client stays a console composition root (no WASM container) for now.** The Phase 8 composition is **two `SampleServer` instances** (`iris-a`, `iris-b`) that share one image and differ only in the `Iris__HostName`/`Iris__Port`/`Iris__Actor` environment. Each container's `Iris__HostName` is its **service name** and `Iris__Port` the real in-network port (`8080`), so each **advertises its own routable base URI** (`http://iris-a:8080` / `http://iris-b:8080`) and the two resolve each other via Docker's built-in DNS on the `iris-net` bridge network. A relay is **not** included (two instances is enough to prove cross-container federation over genuine network I/O; a relay is a Phase 14+ concern). The Blazor client is **not** a third container: the `SampleBlazorClient` is a **console composition root** (the Blazor `Program.cs` equivalent), and a WASM host + its static-host container is deferred — a WASM runtime is heavy/flaky for in-loop work, and the client path is fully covered by the in-process two-instance integration tests. Rationale: the deployment guarantee Phase 8 needs is "two real servers boot, advertise routable base URIs, and reach each other over the network," and two same-image instances give that with the least moving parts; the client's job (auth → sign → feed → proxy fallback) is already proven in-process, so containerizing it adds risk without new coverage. (Open Question #2, resolved.)
 40. **Public-instance FQDN & TLS provisioning (Phase 9): the operator provides a public FQDN + a TLS-terminating reverse proxy; Iris binds an internal HTTP address and advertises the public base URI via `ActivityPubServerOptions.BaseUri`.** The two addresses are kept **distinct**: the **bind address** (Kestrel's internal URL, e.g. `http://127.0.0.1:8080`) is what the reverse proxy points at, and the **advertised base URI** (`ActivityPubServerOptions.BaseUri`, e.g. `https://iris.example.org`) is what goes on the wire (actor IRIs, WebFinger subjects, NodeInfo links) and what *other* instances dial. The operator must provide: (a) a public FQDN with A/AAAA record(s), (b) a TLS certificate for it (Let's Encrypt or operator-managed — Iris does not provision certs; the proxy does), and (c) a reverse proxy (Caddy/nginx/cloud LB) that terminates TLS on `:443` and forwards to the internal bind address. `BaseUri` **must** be set to the public FQDN (not the internal bind address) or federation breaks — a remote instance fetches the advertised IRI, and if it does not round-trip to the instance holding the actor, key resolution + delivery fail. This is the public analogue of the Phase 8 rule (each container's advertised base URI must be routable on the network). The full plan + bootstrap runbook live in [DEPLOYMENT_PREP.md](DEPLOYMENT_PREP.md). (Open Question #3, resolved — the *specific* FQDN/cert values remain operator-provided at deployment time, which Phase 13 consumes.)
   41. **Live-interop suite is a separate, runtime-gated test project (`Iris.LiveInterop.Tests`), not a trait in `Iris.Server.Tests`.** The Phase 9 test-harness-extension design (ROADMAP bullet 5) requires the live-interop suite to be "not part of the default `dotnet test` run" (TESTING.md:37) so a misconfigured local run can never contact a third-party instance or fail the default build on a missing FQDN. The two candidate shapes: (a) a folder + `[Trait("live")]` inside `Iris.Server.Tests` — rejected, because xUnit has **no built-in "skip unless env var set"** mechanism (no skip pattern exists in any C# test project today — all plain `[Fact]`), so the tests would be compiled and *attempted* by the default `dotnet test`, and every test would need a per-test constructor guard; (b) a **separate project** `tests/Iris.LiveInterop.Tests` registered in `Iris.slnx` with a shared `LiveGuard.Requires()` runtime skip (an xUnit early-return, the C# analogue of `docker-smoke-test.sh`'s `exit 0` when Docker is unavailable) — chosen. The project's tests **skip** (not fail) when `IRIS_LIVE_INTEROP=1` + the FQDN/target config are absent, and CI excludes the project from the default job (a dedicated opt-in job runs it, mirroring the Phase 8 Docker smoke script's deferred CI job). Rationale: a separate project is the cleanest structural guarantee of the "not in the default run" requirement — the default `dotnet test Iris.slnx` neither compiles-into-the-run nor fails on it, and the in-process self-tests that *do* run by default (proving the hoisted harness works) live alongside the live-gated scenario tests in the same project, clearly separated by the `LiveGuard`. (No new NuGet package — the project references only existing solution projects + `xunit` + `Microsoft.AspNetCore.TestHost`, both already in the dependency set.)     42. **The client's `PostNoteAsync` delivers the `Create` to the author's *own inbox* (the "local post" path), not to followers' inboxes.** A client cannot enumerate the author's follower set (that is server-side state the client does not hold), and ActivityPub has **no "post to my outbox" endpoint** — outboxes are read collections, not POST targets. The author's own instance is therefore the correct recipient for a client-originated post: it is the only party that (a) is authoritative for the author's outbox and (b) can federate the post to the author's (local and remote) followers. `PostNoteAsync` builds a `Create` carrying an **embedded** `Note` (content, `attributedTo` = author, optional audience `to`) with **deterministic, content-hash-derived** ids (`{actor}/notes/{hash16}` / `{actor}/creates/{hash16}`) so a retried post dedupes on the receiver and distinct posts get distinct ids, then delivers it to `actorId.InboxOf()` through the signed pipeline. The embedded note (a full object, not a link) means the receiver stores the content without a second fetch. **Scope note:** this closes only the *client* half of J-6. The server now records an inbound `Create` in the author's outbox (J-8, Slice 11.6 / Resolved #43) but does not yet deliver it to followers (J-18); that outbound half is the remaining "post and have it federate" work (Phase 12).
 43. **Surface a local post with a dedicated `Create`-typed handler that owns the recipient decision (closes J-8 / J-6's "recorded" server half).** The `InboxProcessor.FindHandler` returns exactly **one** handler per activity, preferring the **most specific** registered type. The existing `CommunityInboxActivityHandler` is `ActivityHandlerBase<Activity>` (a catch-all that records any content activity in a community's members' outboxes). To surface a local post in the **author's own outbox** (J-8) without dropping the community `Create` path, the options were: (a) widen `CommunityInboxActivityHandler` to also record in a person's outbox — rejected, because it conflates two distinct recipient semantics (a person's own post vs. a community's followed content) in one handler and would make the handler's "is the recipient a community" guard misleading; (b) register a dedicated `CreateActivityHandler : ActivityHandlerBase<Create>` — chosen. Because the processor prefers the specific type, the `Create` handler intercepts **every** inbound `Create` before the `Activity` catch-all, so it must handle **both** recipient cases or community `Create`s would be silently dropped. It therefore owns the recipient decision: local **person** → record in the person's outbox (the author's own post); local **community** → record in the members' outboxes (delegating to the shared `CommunityContentRecorder`); neither → no-op. The person and community stores are disjoint (a community is in the community store, not the actor store), so `IsLocalActorAsync` (actor store) and `TryGetCommunityAsync` (community store) cleanly partition the recipient. To keep the two community content paths from diverging, the member-recording loop was **extracted** into a shared `CommunityContentRecorder.RecordToMembersAsync` used by both `CreateActivityHandler` (community `Create`) and `CommunityInboxActivityHandler` (community `Like`/`Announce`). `CommunityInboxActivityHandler` still records a `Create` if invoked directly (its unit tests are unchanged), but the inbox dispatch never routes a `Create` to it. **Scope note:** this closes J-8 (the "recorded" server half). The outbound federation of the post to the author's **remote** followers (J-18) is a separate, later concern — a host may add a delivery step (a delivery to each remote follower's inbox, signed as the original author) once the J-6 client half + this handler are in place.
  38. **`Iris.Client.Extensions` is a BCL-only composition root — no `Microsoft.Extensions.DependencyInjection` dependency.** The package's job (per PROJECTS.md §5) is to give a Blazor (WASM) host a pre-configured pipeline: authenticate (Basic auth → owner-only doc + PEM key) → hold the key in memory for the session lifetime (Resolved #5) → build signed clients. Two constraints shape it: (a) it must be **WASM-safe** and not pull in a new centrally-managed NuGet package (`Microsoft.Extensions.DependencyInjection.Abstractions`) without a ROADMAP note + justification; and (b) the *composition* (session + key store + key provider + client factory) is a small, fixed graph. The resolution is to express the composition as a **plain BCL builder** — `IrisClientBuilder.Create(options).WithAuthenticator(…).WithKeyStore(…).Build()` → an `IrisClientBundle` exposing `Session`, `ClientFactory`, `KeyStore`, `KeyProvider`, and `CreateClient(actorId, transport?)` — rather than `IServiceCollection` extension methods. A Blazor host creates one `IrisClientBundle` (a singleton), logs in via `bundle.Session.LoginAsync(…)`, and builds clients with `bundle.CreateClient(…)`. The `IKeyStoreProvider`/`SessionKeyStoreProvider` seam lets the session and the client factory share one in-memory `IKeyStore` without a hard reference between them. A Microsoft-DI host that wants `AddIrisClient(services, …)` sugar can wrap the builder in its own DI registration (the builder is the single composition point); that sugar is intentionally **not** in the package so the package stays dependency-free. Rationale: the builder is testable without a DI container, is WASM-safe, and avoids a new package dependency for a surface that is a handful of constructor calls.
 44. **The default generated actor key is RSA-2048, and the public key is served as PEM (`publicKeyPem`), with PKCS#1 public-key PEM import for real-world interop.** (Slice 11.8.) Three coupled choices: (a) **RSA-2048 is the default** generated key (`KeyPairGenerator.Generate` / `GenerateRsa`), signed with `RSA-SHA256` — the draft-cavage ActivityPub signature scheme's default and the algorithm real-world servers (Mastodon, Pleroma, Rayven) overwhelmingly use. EC P-256 remains fully supported (`GenerateEcP256`) for deployments that prefer it. (b) **The actor document serves the public key as PEM**, not JWK: the `publicKey` extension carries `publicKeyPem` (a PKIX `-----BEGIN PUBLIC KEY-----` document from `KeyPair.ExportPublicKeyPem()`) alongside `id`/`owner`, replacing the former JWK member shape (`kty`/`crv`/`x`/`y`). PEM is the format a remote instance's key-import path already consumes for the *private* half (the Basic-auth `privateKey`), so serving the *public* half in the same format removes the need for a JWK parser on the receiving side and matches what the interop targets publish. The `keyAlgorithm` extension field (Resolved #20) is unchanged — it still disambiguates `rsa` vs `ecdsa-p256` for the private-PEM path, and now also matches the public PEM's actual algorithm. (c) **`KeyPair.FromPem` accepts a PKCS#1 RSA public-key PEM** (`-----BEGIN RSA PUBLIC KEY-----`), in addition to the existing PKCS#8 private and PKIX public forms. The PKCS#1 body is the raw `RsaPublicKey` DER (`SEQUENCE { modulus, publicExponent }`), which .NET 10's BCL has no direct importer for (there is no `RSA.ImportPkcs1PublicKey`), so `ImportPkcs1` wraps the body in a minimal **SubjectPublicKeyInfo** envelope by hand (the `rsaEncryption` OID `1.2.840.113549.1.1.1`, `NULL` parameters, and an `OCTET STRING` carrying the `RsaPublicKey` bytes — small DER-encoding helpers) and calls `RSA.ImportSubjectPublicKeyInfo`. The result is a **verify-only** key (no private half, `Sign` throws `CryptographicException`), identical in behaviour to the existing PKIX public-key import. `FromPem` dispatches on the PEM label; an unrecognized label (including EC) still falls back to `ImportFromPem`. `RemoteInboundKeyResolver.AlgorithmFromPem` short-circuits to `KeyAlgorithm.Rsa` on the `RSA PUBLIC KEY` label so the PKCS#1 path is reached without a failed EC import attempt first. Rationale: a server that publishes its public key only as a PKCS#1 PEM (a common OpenSSL default) is otherwise unresolvable by Iris's inbound key-resolution path — this makes such a server a valid federation peer. No new NuGet package; the DER helpers are ~40 lines of BCL-only code in `Iris.Core`.
  45. **An un-follow is an `Undo` of the `Follow`, handled by a dedicated `UndoActivityHandler` that removes the local follow edge (the follow inverse).** (Slice 11.9.) The ActivityStreams **`Undo`** is the inverse primitive: it undoes the activity referenced by its `object`. A follow is undone by the party that **made** it, so the `Undo` is delivered to the **follower's** inbox and `InboxDelivery.RecipientIri` is the follower — the same convention `AcceptActivityHandler`/`RejectActivityHandler` use for follow responses. The handler resolves the follow's **target** from the original `Follow` (referenced by IRI in the `Undo`'s `object`, fetched from the local activity store) and, when the recipient is a **local** actor, removes the `follower → target` edge: a local **person** → `IFollowStore.RemoveFollowAsync`; a local **community** → `ICommunityStore.RemoveFollowAsync` (the inverse of `FollowActivityHandler`'s community branch). A missing / unknown / non-`Follow` referenced object is a **no-op** (no edge to remove); a **remote** recipient is not this instance's concern. `FollowIris` gains `UndoIri` (`{actor}/undoes/{followId}`) + `BuildUndo` so a future client `UnfollowAsync` can reference the **same deterministic `Follow` IRI** `FollowAsync` builds. **Scope note:** this handles the **local** un-follow (the recipient is a local actor whose follow edge this instance owns); the follow's *outbox* entry is **not** removed (outbox removal is an open design question — Phase 12 gap register). The inverse of the follow's *edge* is what `Undo` semantically requires, and the edge (not the outbox record) is what gates whether the un-followed actor's content still reaches the follower. No new NuGet package.
  46. **A local actor's `manuallyApprovesFollowers` gates auto-accept: the follow edge is recorded but the `Accept` is suppressed, and the operator responds with an explicit `Accept`/`Reject`.** (Slice 11.10.) The ActivityPub `manuallyApprovesFollowers` actor property is **library-untyped** (the `Actor` type does not model it), so it rides in the actor's `ExtensionData` (seeded by the host) under the named constant `ActivityPubServerConstants.ManuallyApprovesFollowersExtensionName` (no magic string). `FollowActivityHandler` reads it (`IsManuallyApprovingAsync`): when a **local person** has it set, the inbound follow's **edge is still recorded** (so the follower's content reaches the local followers' outboxes via the federation path) but the `Accept` is **not** scheduled — the operator delivers an explicit `Accept` or `Reject` instead. The flag is **person-only**: a **community** recipient always auto-accepts, and a missing/`false` value is the default (auto-accept). `BuildActorDocument` echoes the flag onto the **public** actor document only when it is `true` (a `false` value is omitted — the default need not be spelled out), so a remote follower can tell the follow will not be auto-accepted. **`FollowIris.BuildReject`** (previously unused) now has a live path: the operator signs a `Reject` (actor = the followed actor) and delivers it to the follower's inbox; the existing `RejectActivityHandler` removes the follow edge. **Scope note:** the flag is a *data* property surfaced on the actor doc — there is no dedicated moderation endpoint in this slice (an operator sets it at seed time and responds to a pending follow by delivering a signed `Accept`/`Reject`, exactly as a remote instance would). A dedicated moderation UI/API (list pending follows, one-click approve/reject) is a Phase 12 item. No new NuGet package.
   47. **`sharedInbox` (F-01) is honored in both directions: an instance advertises `endpoints.sharedInbox` when configured, and outbound delivery to a remote recipient resolves the recipient's advertised `sharedInbox` from its document (falling back to the per-actor inbox).** (Slice 12.2.) Two halves. **Serve side:** `ActivityPubServerOptions.SharedInboxIri` configures the instance's shared inbox; when set, the public actor and community documents carry `endpoints.sharedInbox` (the library's `Actor.Endpoints` → `Endpoints.SharedInbox`, a typed `Uri` — *not* a library-untyped `ExtensionData` property, correcting the earlier "no `sharedInbox` property in this library" premise). The per-actor `Inbox` is still advertised, so a sender that ignores `endpoints.sharedInbox` still lands on the right collection. **Consume side:** `DeliveryService.DeliverToActorAsync` resolves the recipient's delivery target by fetching the recipient's document via `IActorDocumentFetcher` (which reads through the `RemoteActorCache`, so a repeated delivery to the same recipient reuses the cached document rather than re-fetching): an advertised `endpoints.sharedInbox` is honored; a fetch failure (null) or an absent `sharedInbox` **falls back** to `recipientIri.InboxOf()` (the ActivityPub convention). `DeliveryService` takes an optional `IActorDocumentFetcher?` (the 2-arg ctor is retained for the unit tests; a null fetcher means always-fallback), and DI wires it to the same `IActorDocumentFetcher` registration the inbound signature path uses — a `NoopActorDocumentFetcher` (no instance actor configured) yields the fallback. **Why the fetch lives in the delivery service (not the caller):** the inbox is resolved once per delivery at enqueue time, against the *remote* recipient's document, which is exactly the data the inbound-signature path already caches; keeping it in `DeliverToActorAsync` means every actor-targeted delivery (follow responses, post federation, boosts) honors the remote shared inbox without each handler re-implementing the resolution. No new NuGet package.
   48. **Content-object write path: `Update` refreshes a stored object in place, `Delete` tombstones it (the IRI still resolves), and the object is served by IRI at `GET /ap/v1/o/{**path}`.** (Slice 12.3.) The `CreateActivityHandler` now stores the `Create`'s **embedded** object in the `IObjectStore` under the object's own IRI (both the person and community branches; a bare-link `Create` stores nothing), via the shared `IriExtensions.ExtractEmbeddedObject` boundary helper (the library's `object` is `IEnumerable<IObjectOrLink>` — a typed `IObject` with an `Id`, or a bare `Link`). **`UpdateActivityHandler`:** an inbound `Update` from a **local** actor whose embedded object's IRI matches a stored object re-stores the updated object in place (so a later `GET` serves the edited content); a reference-only `Update` (no embedded content) and a non-local actor are no-ops (nothing to apply / not this instance's to rewrite). **`DeleteActivityHandler`:** an inbound `Delete` from a **local** actor for a stored object **replaces** it with an AS2.0 `Tombstone` (`IriExtensions.BuildTombstone` — `{"type":"Tombstone","id":…,"formerType":[…]}`) so the IRI still resolves and serves the "deleted" marker (F-10) rather than a `404`; the `formerType` is the deleted object's AS2.0 `type`. **Owner guard (both handlers):** the activity's `actor` must be a **local** actor *and* the referenced object must be one this instance stores; otherwise a no-op — this prevents a remote actor from rewriting or tombstoning content it does not own. **Object-document endpoint:** `GET /ap/v1/o/{**path}` — the `{**path}` catch-all is the object IRI's path relative to the route prefix (the `/o/` segment is only the serving prefix, **not** part of the object IRI), combined with the base URL to reconstruct the absolute IRI; a stored object is served as itself, a deleted object as its `Tombstone`, an unknown IRI `404`s (Cache-Control mirrors the actor document). `IObjectStore.TryDeleteObjectAsync` (a hard delete) is added for the rare remove-outright case — the preferred delete path is `PutObjectAsync(tombstone)`. **Scope note:** this is the **local** write path (a local actor's own object); the `Update`/`Delete` are not yet *federated* to remote followers (that outbound half pairs with the J-18 post-federation path — Phase 12 gap register), and the object store is in-memory (`IObjectStore`), so a server restart drops stored objects (persistence is a Phase 13+ concern). No new NuGet package.
    49. **Ed25519 signing/verification via BouncyCastle + a common `ISigningKey` interface (F-05).** (Slice 12.4.) Two coupled choices. **(a) BouncyCastle for Ed25519:** no BCL `Ed25519` type exists on this runtime (.NET 10.0.10), and `MLDsa.IsSupported` is `False` on Linux. Ed25519 is therefore backed by **BouncyCastle.Cryptography 2.4.0** (a new NuGet dependency — the only one introduced by Phase 12 so far). `Ed25519Key` wraps BouncyCastle's `Ed25519Signer`/`Ed25519PublicKeyParameters`/`Ed25519PrivateKeyParameters`, supporting `Sign`/`Verify`, PEM round-trip (PKCS#8 private / PKIX public via BouncyCastle's `PemWriter`/`PemReader`), JWK (`Ed25519Key.FromJwk`/`GetPublicJwk` — `kty: OKP`, `crv: Ed25519`, `x` base64url), and RFC 7638 thumbprint. **(b) `ISigningKey` unification:** rather than threading `Ed25519Key` through every call site that previously accepted `KeyPair` (which would require a parallel `IEd25519KeyStore`, a parallel `ISignatureVerifier.VerifyEd25519`, etc.), a common **`ISigningKey`** interface was introduced in `Iris.Core` with members `Algorithm`, `KeyId`, `Sign(byte[])`, `Verify(byte[], byte[])`, `GetPublicJwk()`, `ExportPublicKeyPem()`, `ExportPrivateKeyPem()`, and `GetThumbprint()`. Both `KeyPair` and `Ed25519Key` implement it. The entire pipeline — `IKeyStore`/`InMemoryKeyStore`, `Signatures`, `ISignatureVerifier`/`HttpSignatureVerifier`, `IInboundKeyResolver`/`RemoteInboundKeyResolver`, `HttpSignatureValidator`, `KeyPem`, `AuthenticatedActor`, `BasicAuthClientAuthenticator` — was updated to use `ISigningKey`. `InMemoryKeyStore` and `HttpSignatureValidator` use a `DisposeIfDisposable` pattern (checking `key is IDisposable`) because `KeyPair` implements `IDisposable` (wrapping a BCL `RSA`/`ECDsa`) but `Ed25519Key` does not (BouncyCastle parameters are not disposable). `KeyPem.Load` returns `ISigningKey` and dispatches on `KeyAlgorithm` (Ed25519 → `Ed25519Key.FromPem`, else `KeyPair.FromPem`). `RemoteInboundKeyResolver.ResolveAsync` returns `ISigningKey?`, dispatching on the resolved algorithm (Ed25519 → `Ed25519Key.FromJwk`/`FromPem`, else `KeyPair.FromJwk`/`FromPem`). Rationale: the `ISigningKey` seam is the minimal surface that lets a new algorithm be added without touching every call site — a future algorithm (e.g. MLDsa) implements the same 8-member interface and is dispatched on in `KeyPem.Load` + `RemoteInboundKeyResolver` without any pipeline changes.
    50. **`Move` (F-08) re-points local follow edges by target and does not gate on the recipient — and the handler invalidates the moving actor's outbound key/doc caches (F-25).** (Slice 12.5.) An inbound `Move` (ActivityPub §5.2.1.6) carries the moving actor in its `actor` (the **old** IRI) and the new location in its `object` (the **new** IRI). **Why the handler re-points by target rather than gating on the recipient:** a `Move` is delivered to the moving actor's **followers**, so the recipient (the follower) is *not* the actor moving — gating on `IsLocalActor(recipient)` (the pattern `Follow`/`Undo` use, where the *recipient* is the acted-upon actor) would reject every `Move` (the recipient is a follower, not the mover). Instead the handler enumerates **local** follow edges that target the old IRI and re-points them at the new one: person followers via `IFollowStore.GetFollowersAsync(oldIri)` (each follower that is itself a local actor → `RemoveFollowAsync(follower, oldIri)` + `RecordFollowAsync(follower, newIri)`) and local-community follows via the `ICommunityStore` follows set. A **remote** follower's edge is left to that follower's own instance (the `Move` reaches it the same way). **F-25 cross-ref (key re-resolution):** the handler invalidates the moving actor's outbound `RemoteKeyCache` entry (keyed by the `publicKey.id` IRI — `oldIri#key-1`) and `RemoteActorCache` entry (keyed by the actor IRI) so the next key/actor-document resolution fetches the new key rather than a stale one. This is the *invalidation* half of F-25; the full move-driven re-fetch for reads (re-fetching the new document when serving the old IRI) is the remaining F-25 half (still open, Wave 3). **`ICommunityStore.GetAllCommunityIrisAsync`** was added because the follows set is not indexed by target (the handler must enumerate local communities and check each follows set). **DI registration:** `MoveActivityHandler` is registered via a factory (it needs the local community IRIs + the two outbound caches resolved at construction; both caches are optional — a no-cache instance still re-points the follow edges). No new NuGet package.
    51. **The WebFinger response is served as `application/jrd+json`, and the conformance suite regression-protects the spec-required wire/header/status surface (the C-03 outbound signature base included).** (Slice 12.6.) **Content-type:** RFC 8615 §4.1 mandates that a WebFinger response be a JRD document with the `application/jrd+json` content type; the server was serving `application/json`. The fix is safe because the client's `WebFingerClient` already declares `WebFingerContentType = "application/jrd+json"` and parses the JSON body regardless of the media type — only the served media type was non-conformant. **Why the suite is endpoint-shape + signature-base tests (not re-testing behavior):** the functional integration tests (follow/federation, post, move, delete) already prove the *behavior*; what was missing was a regression net over the *spec surface* — the exact content types, the JRD `subject`/`self`-link shape, the NodeInfo 2.0 fields, the actor document's `@context`/`endpoints`, and the C-03 outbound `ServerToServer` signature base (which must cover `digest` + `content-type` for a body-carrying delivery — the inbound verifier is lenient by design (Decision #4), but a strict peer's signature only verifies if the outbound base is complete). The outbound tests capture the `DeliveryWorker`'s real signed request over a capturing `HttpMessageHandler` (the same transport seam the federation integration tests use) so they assert the *actual* on-the-wire signature, then round-trip it through `HttpSignatureVerifier`. No new NuGet package.
